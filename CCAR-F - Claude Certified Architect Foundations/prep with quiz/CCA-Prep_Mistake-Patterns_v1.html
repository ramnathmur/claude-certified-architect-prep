Two of these four patterns fail by reaching for something heavier than the situation calls for. Two fail by reaching for something lighter than it calls for. Topic 1 of 4 · D4 §4.6 · status: partly open

The tool_choice guarantee ladder

By the endYou can pick auto / any / a forced-specific tool by matching the setting's guarantee strength to what the step actually requires — not by which one sounds safest.
The concept

tool_choice has three settings, and they form a ladder of increasing strength. Each rung guarantees more than the one below it, and each guarantee costs something.

The trap

Exam questions test both directions on this ladder. One trap under-specifies: a step genuinely needs a guarantee, and auto or a prompt instruction is offered as a tempting-but-probabilistic alternative. The other trap over-specifies: a step has a real "no tool needed" case built into it, and any or a forced tool is offered as a tempting-but-too-strong alternative that removes that case.

What you actually did
Exams 7 → 8 → 10

The same §4.6 shape — a step needs one specific tool to run, any is offered as the tempting weaker alternative — missed on three straight scored papers, three different concrete situations. Confirmed as a stubborn misconception, not attempt noise.

Exams 12 → 13

The identical question shape, the identical wrong pick, ~14 hours apart — including after reading the full rationale the first time. This was the single most valuable diagnostic across ten scored papers at the time it happened.

Exam 17

Closed. Four items tested the ladder in four directions; three landed, including the repeat trap in a completely fresh frame — 138 seconds of visible, deliberate work, the longest question on the paper.

Exam 19 · Q23

A new, opposite-direction trap opened the same week Exam 17 closed the old one. A triage step where roughly half the requests need no tool call at all — auto was correct. any was picked instead, forcing a call on every request including the ones that didn't need one. First test of over-specification. Missed.

The pattern underneath both directions

Under-guarantee and over-guarantee look like opposite errors, but they're the same skill gap from two sides: picking a rung by habit or vibe instead of by reading the requirement stated in the scenario. "This needs to be reliable" pulled toward any even when which tool mattered (Exams 7/8/10/12/13). "This needs structured output" pulled toward any even when roughly half the cases had nothing to structure (Exam 19).

The right way to answer these
Ask this question first, every time — before looking at the options.
What does the step actually require?Setting
Nothing — a normal conversational turn, sometimes no tool is appropriate{"type":"auto"}
Structured output is mandatory, but any of several tools may fit (e.g. document type is unknown){"type":"any"}
One named tool must run — order matters, or only that tool produces the needed data{"type":"tool","name":"..."}

If an option reads "force a tool call to be safe" and the scenario explicitly describes a real no-tool-needed case, that's the over-specification trap. If an option reads "the model will handle it" or leans on a prompt instruction, and the scenario explicitly needs one exact tool or ordering, that's the under-specification trap. Both traps are recognizable from the same tell: does the stated requirement match the strength of the setting being offered, exactly — not more, not less.

Self-check

A pipeline step must always end with a signed attestation record. Exactly one tool (sign_attestation) produces that record; a second tool (draft_attestation) exists only for previewing wording during development, and is sometimes called by mistake in production. Which tool_choice setting is correct?

Reveal answer

Forced, specific: {"type":"tool","name":"sign_attestation"}. The requirement isn't "some tool runs" — it's that exactly one tool, by name, produces the record the downstream gate reads. any would still let draft_attestation satisfy the guarantee, which doesn't fix the actual problem. This is the same shape as Exam 20's Structured Data Extraction block — match the setting to which specific requirement is stated, not to "sounds reliable."

Topic 2 of 4 · D2 §2.8 · status: open — oldest unresolved trap in the corpus

Composite tools vs. prompt bundling

By the endYou default to prompting the agent to bundle two paired tool calls into one turn, and only reach for a new composite tool when the corpus gives you an explicit reason bundling can't cover.
The concept

When an agent habitually calls two tools together — get_customer then lookup_order, say — there are two ways to remove the extra round-trip. The corpus states its preference in about four lines: prompt the agent to bundle both requests into one turn. Building a new composite tool that hard-codes the pairing is explicitly the not-preferred option, because it hides the composition — the two steps stop being visible or independently reusable.

The trap

Building a purpose-made tool sounds like the more professional engineering answer — a dedicated tool, a cleaner interface. That instinct is exactly what the trap is built from. The exam consistently rewards the lighter fix here, not the more architected-looking one.

What you actually did
Exams 5, 8, 10, 11, 14

Five separate sittings. This is the single most persistent individual trap across the whole project — more than the tool_choice ladder, more than any other single misconception.

Exam 14 · Q26

This question was deliberately built "from the opposite end" — starting from a team that already has a composite tool and is weighing its cost — specifically to test whether the underlying belief was wrong, not just the memorized stem. It was. The picked wrong answer, close to verbatim: "composite tools are always preferable to prompt-level bundling once a pairing is established." That's a held general rule, not a one-off misread.

Why this one is hard to shake

A slogan ("composites reduce round-trips") is easier to recall under time pressure than a conditional rule ("composites reduce round-trips when the pairing is universal enough that hiding it costs nothing"). Exam 14 proved the slogan is what's actually stored — reskinning the stem didn't help, because the stem was never the problem.

The right way to answer these
SituationAnswer
Two tools get called together often, but not on every single casePrompt-bundle — keep both calls visible
The pairing is universal and the corpus states a specific reason bundling can't cover (e.g. a guarantee a bundle instruction can't provide)Composite may be justified — check for that stated reason first
No stated reason is given, the option just "sounds more efficient" or "more architecturally clean"Still prompt-bundle — that feeling is the trap, not a justification

Default to prompt-bundling. Only move to a composite tool when the question hands you a concrete, stated reason a bundle instruction genuinely cannot satisfy — never because building the dedicated tool feels like the more senior answer.

Self-check

Telemetry shows a research coordinator calls web_search then extract_citations together in roughly 20% of turns — the other 80% of the time only one or the other is needed. A teammate proposes a single search_and_cite composite tool. What's the correct call?

Reveal answer

Prompt-bundle for the 20%, don't build the composite. This is an occasional pairing, not a habitual one — a composite here would force the 80% of single-purpose calls through a tool built for two, which is over-fetching for the common case. This is exactly the "opposite polarity" version of the trap: the tempting answer this time is building the tool, not avoiding it.

Topic 3 of 4 · D2 §2.7 + D4 §4.5 · status: confirmed, 2 different surfaces

Prevention at the source vs. cleaning up after

By the endYou recognize one principle wearing two different technical outfits — hooks and schema design — instead of only recognizing it when the question literally says "hook."
The concept

The same idea shows up in two places in the corpus. In tool design: a PreToolUse hook can block or modify a call before it executes — deterministic prevention. A PostToolUse hook only ever sees the result after the call already happened. In schema design: typing a field so an invalid value literally cannot be emitted prevents the bad value at the point of creation; a downstream pass that finds and rewrites bad values is repairing something that was already allowed to exist. Different mechanisms, same shape: constrain the source, don't just catch the output.

The trap

This distinction doesn't travel well when the surface changes. A question can name hooks directly (PostToolUse vs. PreToolUse) or it can dress the exact same choice up as tool scoping or schema design, with no hook vocabulary anywhere in the stem.

What you actually did
Exam 17 · Q2

Asked directly, as PostToolUse vs. PreToolUse. Correct.

Exam 17 · Q19

The identical distinction, dressed as tool design: an over-broad fetch_url tool had already reached an internal endpoint. Picked a PostToolUse hook to discard the response after retrieval, instead of a tool scoped so it couldn't reach that endpoint at all. Wrong — same paper, minutes apart from getting the "same" question right.

Exam 19 · Q58

Same shape again, now as schema design: award dates arrived in four different formats. Picked a post-extraction rewrite pass to normalize them, instead of typing the extraction schema so only one format could ever be emitted. Wrong, on a completely different technical surface than either Exam 17 instance.

What this confirms

The rule is known — Q2 proves that. It just doesn't fire unless the question says "hook." The moment the same choice is framed as tool design or schema design, the "clean it up afterward" option stops reading as a trap and starts reading as a reasonable answer.

The right way to answer these

Whenever an option is some version of "catch it and fix it after it happens" — a hook that cleans up a response, a validation pass that rewrites bad values, a review step that reverts a bad action — stop and ask one question first, regardless of what the surface vocabulary is: could the bad state have been made impossible earlier in the pipeline instead? A tool that structurally can't reach the wrong endpoint. A schema field that can't hold the wrong shape. A precondition that blocks before execution. If an earlier constraint point exists and the question doesn't rule it out, that's very likely the intended answer — no matter whether the stem calls it a hook, a schema, or a tool's scope.

Self-check

An extraction tool's schema declares a currency field as free text. Amounts arrive as "$1,240.00", "1240", and "USD 1240" — a downstream reconciliation script normalizes all three formats before comparison. What's the correct fix?

Reveal answer

Type the field in the schema (e.g. a numeric type, or a structured amount+currency object) so only one shape can be emitted — not a smarter normalization script. No hook is mentioned anywhere in this stem. That's deliberate: the surface is schema design, but the choice is the identical prevention-vs-repair decision as Exam 17 Q19 and Exam 19 Q58.

Topic 4 of 4 · D3 §3.1 / §3.2 · status: recovering — confirm, don't assume closed

The .claude/rules/ reflex

By the endYou place configuration by matching it to a decision table — scope and universality — instead of reaching for whichever mechanism sounds most specific and impressive.
The concept

Three places project guidance can live, and the corpus gives an exact table for which one fits which case.

CCA-Prep_Domain-3_v2.md §3.2 — where guidance belongs
Use caseBest location
A convention that applies always, everywhere in the projectRoot CLAUDE.md
A convention scoped to a specific file type or directory.claude/rules/ with glob patterns
Workflow-specific guidance you invoke (PR review, deploy)A Skill in .claude/skills/

The trap

.claude/rules/ is the newest, most surgical-sounding mechanism of the three, and "where should this live" questions tempt toward it by default — regardless of whether the actual guidance in the scenario is scoped to specific files, or is meant to apply everywhere.

What you actually did
Exam 12 · Q1

The question needed a diagnostic step (/memory, to check what's actually loaded) before any placement decision. Reached straight for a rules file instead of diagnosing first.

Exam 12 · Q56, Exam 13 · Q41, Exam 17 · Q41

Three more instances, each time the default reach whenever a question smells like "where should this live?"

Exam 14 · Q18 & Q38

Fired twice in the same paper — Q18 repeats the diagnose-first miss; Q38 is a new surface entirely, reaching for a rules file to supply missing run context to a CI step, not a "where does this belong" framing at all. Six instances total, across four separate papers.

Exam 19

Recovered. This domain scored 12/12 on a paper that wasn't even built to target it. That's a real signal — but one clean, untargeted paper is a start, not proof the reflex is gone for good.

Why the recovery counts

Exam 19's Professor's Note was written before this pattern had been correctly cross-referenced against the right prior exam — it never asked for this section to be covered. A clean score on a paper that wasn't targeting the weak spot is stronger evidence than a clean score on one that was.

The right way to answer these

Two separate checks, run in order:

First askThen
Is the question actually about diagnosing why something isn't applying consistently?That's a /memory check — a load-verification step, not a placement decision at all. Don't skip straight to "create a file."
Does the guidance apply always, everywhere?Root CLAUDE.md — not a rules file.

Self-check

A review step must always close its comments with a single risk rating, regardless of which files changed. A developer proposes a glob-scoped .claude/rules/review-format.md "to make it reliably load." What's the correct fix?

Reveal answer

Root CLAUDE.md. The requirement has no path dimension at all — it applies to every review, everywhere. A rules file's glob-scoping solves a problem this scenario doesn't have; reaching for it because it "sounds more reliable" is the exact trap.

Recap

Before Tuesday

Four decision rules, one habit to check for every time.

1 · tool_choice guarantee ladder

Match the setting's strength to the stated requirement — auto when nothing's mandatory, any when some tool must run, forced-name when it must be that exact tool. Watch for both too-weak and too-strong options.

2 · Composite tools vs. prompt bundling

Default to prompt-bundling. Only build a composite tool when the scenario states a concrete reason bundling can't cover it — not because the tool sounds more professional.

3 · Prevention vs. after-the-fact repair

Ask if the bad state could've been made impossible earlier — a scoped tool, a typed schema field, a blocking precondition — before accepting an option that catches and fixes it afterward. Applies whether the stem says "hook" or not.

4 · The .claude/rules/ reflex

Diagnose before you place. If the question is about inconsistent behavior, check /memory first. If it's about placement: always-everywhere → CLAUDE.md; scoped → rules/; a workflow → a Skill.

The one thing underneath all four

Every one of these fails the same way at the meta level: an option is chosen because of how it sounds — safer, more architected, more specific, more thorough — rather than because it matches what the scenario actually, specifically states is required. Before picking an answer, name the requirement in one sentence first. Then check which option matches that sentence exactly, not which one sounds best.
