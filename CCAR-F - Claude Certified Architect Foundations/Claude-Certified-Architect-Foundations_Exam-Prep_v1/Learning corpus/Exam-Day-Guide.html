4How the exam reasons

The 12 official sample questions come with the examiners' own explanations. Read together, they show a small set of judgements the exam rewards again and again. Every concept card later in this file points back to one or more of these.

The examiner's habitWhat it looks like in the samples
Fix the root cause, not the symptom.Q7: reports miss music, writing and film → the coordinator's decomposition was too narrow; the downstream agents "are working correctly within their assigned scope". Q2: tool misrouting → the descriptions are minimal; that is "the root cause".

Reading the stem

Stems carry a qualifier that decides the answer: most effective first step, most likely root cause, most maintainable, best enables recovery. Two options are often both true; the qualifier picks between them. Read it twice.

TS 1.1Design and implement agentic loops for autonomous task execution

Three cards. The loop, its stopping rule, and who decides the next step.

1.01The agentic loop and stop_reason

TS 1.1

What it is. One iteration: send the request to Claude → inspect stop_reason → if it is "tool_use", execute the requested tool(s), append the results to the conversation, and call again; if it is "end_turn", the task is complete and the loop terminates. The tool results go into the conversation history so the model can reason about them on the next iteration.

How the exam asks it

"Which control flow correctly implements the loop?" or "Your loop sometimes stops early / never stops — what is wrong?" The right answer is the one whose continue/terminate decision is driven by stop_reason and nothing else.

Traps

  • Terminating when the assistant's text "sounds finished" (parsing natural-language signals). Named anti-pattern.
  • Using an iteration cap as the primary stopping mechanism. Named anti-pattern — a cap can be a safety net, but the loop's decision is stop_reason.
  • Checking whether the response contains text content as the completion indicator. Named anti-pattern. (Author's gloss, not from the guide: a tool_use response can carry text as well.)
  • Forgetting to append tool results between iterations, so the model repeats the same call.

1.02Tool results in the conversation history

TS 1.1

What it is. After executing a tool, its result is appended to the message history and sent back with the next request. That is how "new information" reaches the model. Later in D5 (card 5.01) the same fact returns as a cost: those results accumulate and consume tokens, so you trim them to relevant fields.

How the exam asks it

"The model keeps calling the same tool with the same arguments" or "the agent doesn't act on what the tool returned". Root cause: the result was not added to context between iterations.

Traps

  • Passing only the latest tool result and dropping prior turns — the guide's D5 wording is "the importance of passing complete conversation history in subsequent API requests".
  • Treating "the tool ran" as equivalent to "the model saw the result".

1.03Model-driven decisions vs pre-configured decision trees

TS 1.1

What it is. In an agentic system Claude reasons about which tool to call next from the context it has. The alternative — a fixed decision tree or scripted tool sequence, or a routing layer that parses the user's words and pre-selects the tool — removes that reasoning. The exam treats model-driven selection as the default. Where a step must be guaranteed, the guide's instrument is enforcement — a hook or prerequisite gate that constrains a call (cards 1.13, 1.17) — not a routing layer that picks the tool; both routing-layer options in the samples (Q1, Q2) are rejected.

How the exam asks it

Tool misrouting or ordering problems, with one option proposing "a routing layer that parses user input before each turn and pre-selects the tool". Sample Q2 rejects it as over-engineered and as bypassing the model's language understanding.

Traps

  • Keyword-based routing offered as a reliability fix — it fixes tool availability, not selection quality, and adds a brittle layer.
  • Confusing this with programmatic enforcement (a prerequisite gate that blocks a call). Enforcement constrains; it does not choose the tool for the model.
Official sample: Q2 (routing layer distractor), Q1 (routing classifier distractor).

TS 1.2Orchestrate multi-agent systems with coordinator–subagent patterns

Four cards. Who talks to whom, what each agent knows, and what the coordinator is for.

1.04Hub-and-spoke: everything through the coordinator

TS 1.2

What it is. The coordinator manages all inter-subagent communication, error handling and information routing. Subagents do not talk to each other. The guide's stated benefits: observability, consistent error handling, controlled information flow.

How the exam asks it

"Subagent A needs output from subagent B — how should that flow?" Through the coordinator. Or a design where agents message each other directly is presented as "reducing latency" and you are asked what it costs (observability, error handling).

Traps

  • Direct subagent-to-subagent channels "to save round trips".
  • Q9's nuance: reducing round trips is legitimate, but the sanctioned way is a scoped tool for the common case, keeping complex cases on the coordinator path — not opening a side channel.
Official sample: Q9.

1.05Subagents have isolated context

TS 1.2 · 1.3

What it is. A subagent does not inherit the coordinator's conversation history and does not share memory with other invocations. Whatever it needs must be in the prompt it is given. This is stated twice in the guide (1.2 and 1.3) — it is load-bearing.

How the exam asks it

"The synthesis agent produces a report that ignores the search results" / "the subagent asks for information the coordinator already has". Root cause: the coordinator assumed inheritance. Fix: include the complete findings from prior agents directly in the subagent's prompt.

Traps

  • "The subagent can see the parent's context because it runs in the same session." It cannot.
  • Passing a one-line summary where the guide says complete findings (e.g., the web results and the document analysis outputs go to synthesis).
  • Relying on a shared memory between invocations of the same subagent type. There is none.

1.06What the coordinator does — and dynamic subagent selection

TS 1.2

What it is. The coordinator decomposes the task, delegates, aggregates results, and decides which subagents to invoke based on query complexity. It should analyse the query and select dynamically rather than always running the full pipeline. It also partitions scope so subagents do not duplicate work (distinct subtopics or source types per agent).

How the exam asks it

"Simple queries take as long as complex ones" or "two subagents return overlapping findings". Answers: dynamic selection of subagents per query; explicit partitioning of subtopics/source types.

Traps

  • "Always run every subagent for consistency."
  • Fixing duplication by post-hoc deduplication in synthesis instead of partitioning the assignment.

1.07Narrow decomposition → coverage gaps; the iterative refinement loop

TS 1.2

What it is. If the coordinator decomposes a broad topic too narrowly, subagents execute perfectly and the report still misses whole areas. The remedy the guide names is an iterative refinement loop: the coordinator evaluates the synthesis output for gaps, re-delegates to search and analysis subagents with targeted queries, and re-invokes synthesis until coverage is sufficient.

How the exam asks it

Sample Q7 exactly: every subagent "completes successfully" yet the report covers only visual arts; the coordinator's log shows three visual-arts subtasks. Root cause: the coordinator's decomposition. Follow-up form: "how do you make the system self-correct?" → the refinement loop above.

Traps

  • Blaming synthesis for not "identifying gaps", blaming search for narrow queries, blaming analysis for filtering — all downstream of the real cause.
  • Answering "add more subagents" when the assignment, not the headcount, is the problem.
Official sample: Q7.

TS 1.3Configure subagent invocation, context passing, and spawning

Five cards. The mechanics: how a subagent is started, what it is given, how several run at once, and how they are defined. (This task statement's fourth knowledge item, fork-based session management, is carried by card 1.19.)

1.08The Task tool and allowedTools must include "Task"

TS 1.3

What it is. In the Agent SDK, subagents are spawned via the Task tool. A coordinator can only invoke subagents if its allowedTools includes "Task".

How the exam asks it

"The coordinator never delegates; it tries to do everything itself" or "delegation fails silently". Check allowedTools for "Task" first.

Traps

  • Looking for the fault in the subagent definitions or the prompt when the coordinator simply lacks the tool.
  • Options that name a different mechanism for spawning (there is one in the guide: the Task tool).

1.09Explicit context passing, and separating content from metadata

TS 1.3

What it is. Because context is not inherited (card 1.05), the coordinator includes the complete findings from prior agents in each subagent's prompt. When it does, it uses structured data that keeps content separate from metadata — source URLs, document names, page numbers — so attribution survives the handoff. This is the D1 root of the D5 provenance cards (5.13, 5.14).

How the exam asks it

"The final report has claims but no sources — where was attribution lost?" Answer: in an unstructured handoff. "How should findings be passed to synthesis?" Answer: structured records (claim, evidence excerpt, source URL/document name, date), not prose blobs.

Traps

  • Passing a prose summary "to save tokens" and expecting sources to reappear later.
  • Asking synthesis to "re-find" the sources instead of preserving them in the payload.

1.10Parallel subagents: multiple Task calls in one response

TS 1.3

What it is. To run subagents in parallel, the coordinator emits multiple Task tool calls in a single response — not one per turn. Exercise 4 in the guide has you measure the latency gain against sequential execution.

How the exam asks it

"Research takes four times longer than expected; logs show search, analysis and verification each waited for the previous one" → the coordinator is issuing one Task call per turn. Fix: emit them together in one response.

Traps

  • "Increase concurrency settings" or a queue — the mechanism is how the coordinator emits the calls.
  • Parallelising steps that genuinely depend on each other (synthesis needs search output).

1.11AgentDefinition: description, system prompt, tool restrictions

TS 1.3

What it is. Each subagent type is configured with an AgentDefinition: a description, a system prompt, and tool restrictions. The tool restrictions are how you give a subagent only the tools of its role (D2 card 2.06 explains why that matters).

How the exam asks it

"Where do you constrain what the document-analysis agent may do?" → its AgentDefinition (tool restrictions), not the coordinator's prompt.

Traps

  • Restricting tools by asking nicely in the prompt when the definition can restrict them structurally.

1.12Goal-oriented coordinator prompts

TS 1.3

What it is. Coordinator prompts should specify research goals and quality criteria rather than step-by-step procedural instructions, so subagents can adapt to what they find.

How the exam asks it

"Subagents follow the script and miss obviously relevant material" → the prompt was procedural. Rewrite around goals and quality bars.

Traps

  • Adding more steps to the procedure to cover the missed case.
  • Do not confuse this with enforcement: where a rule must always hold, that is a hook or gate (1.13), not a longer prompt.

TS 1.4Implement multi-step workflows with enforcement and handoff patterns

Three cards. This is the sample-Q1 territory: guaranteed ordering, escalation handoffs, and multi-issue requests.

1.13Programmatic enforcement vs prompt guidance

TS 1.4

What it is. Two ways to order a workflow: programmatic enforcement (hooks, prerequisite gates) and prompt-based guidance. Prompt instructions alone have a non-zero failure rate. When deterministic compliance is required — the guide's example is identity verification before financial operations — use a programmatic prerequisite that blocks downstream tool calls until the prerequisite step has completed (block process_refund until get_customer has returned a verified customer ID).

How the exam asks it

Sample Q1: "in 12% of cases the agent skips get_customer and calls lookup_order from the stated name → misidentified accounts, incorrect refunds." Answer: the programmatic prerequisite. Variants swap the tools but keep the shape: a required order + a costly failure.

Traps

  • "State in the system prompt that verification is mandatory" — probabilistic.
  • "Few-shot examples showing get_customer first" — still probabilistic.
  • "A routing classifier that enables only the right subset of tools" — addresses availability, not ordering.
  • The reverse trap: reaching for a hook when nothing costly is at stake and the question asks for the proportionate first step (then criteria/few-shot is right, as in Q3).
Official sample: Q1.

1.14Structured handoff summaries for escalation

TS 1.4

What it is. When escalating mid-process to a human who cannot see the transcript, the agent compiles a structured handoff: customer ID, root-cause analysis, refund amount, recommended action. The guide's phrasing: customer details, root cause, recommended actions.

How the exam asks it

"Human agents report they have to re-ask everything after an escalation — what should the agent pass?" → the structured summary, not the raw transcript, not a one-line "customer is unhappy".

Traps

  • Forwarding the whole conversation and calling it a handoff.
  • Omitting the recommended action — the guide lists it explicitly.

1.15Multi-concern requests: decompose, investigate in parallel, synthesise one resolution

TS 1.4

What it is. A customer message that raises several issues at once is decomposed into distinct items, each investigated in parallel using shared context, then synthesised into a unified resolution.

How the exam asks it

"The customer asks about a late order, a duplicate charge, and a password reset in one message; the agent answers only the first." Answer pattern: decompose → parallel investigation with shared context → one combined reply.

Traps

  • Handling issues strictly one at a time and asking the customer to re-raise the rest.
  • Investigating each in isolation without the shared context (e.g., the same verified customer ID).

TS 1.5Apply Agent SDK hooks for tool call interception and data normalization

Two cards. Hooks are the deterministic instrument; know the two directions.

1.16PostToolUse hooks: normalise tool results before the model sees them

TS 1.5

What it is. A PostToolUse hook intercepts a tool's result and transforms it before the model processes it. The guide's use case: heterogeneous formats from different MCP tools — Unix timestamps vs ISO 8601, numeric status codes — normalised so the agent reasons over one consistent shape.

How the exam asks it

"Three backend tools return dates in three formats and the agent miscompares them — where do you fix it?" → PostToolUse hook, not "tell the model to convert" and not rewriting every backend.

Traps

  • Prompt instructions to normalise (probabilistic).
  • Modifying the MCP servers you may not own, when a hook does it in one place.

1.17Tool-call interception hooks: block and redirect policy violations

TS 1.5

What it is. A hook that intercepts an outgoing tool call can enforce a compliance rule deterministically — the guide's example is blocking refunds above $500 and redirecting to an alternative workflow such as human escalation. The distinction to hold: hooks give deterministic guarantees; prompt instructions give probabilistic compliance. (The guide names PostToolUse explicitly and describes this second kind as "tool call interception" without naming it.)

How the exam asks it

"Refunds over the limit must never go through" → interception hook that blocks and redirects to escalation. Any option that lives in the prompt is the wrong tier of guarantee.

Traps

  • "Add the $500 rule to the system prompt and log violations." Non-zero failure rate.
  • Blocking without redirecting — the guide's pattern blocks and routes to the alternative workflow.

TS 1.6Design task decomposition strategies for complex workflows

One card, two patterns.

1.18Prompt chaining (fixed) vs dynamic adaptive decomposition

TS 1.6

What it is. Prompt chaining is a fixed sequential pipeline of focused passes — right for predictable multi-aspect work such as a code review (analyse each file individually, then run a cross-file integration pass; this avoids attention dilution). Dynamic decomposition generates subtasks from what is discovered at each step — right for open-ended investigation ("add comprehensive tests to a legacy codebase": map structure → identify high-impact areas → prioritised plan that adapts as dependencies appear).

How the exam asks it

Sample Q12 for the review shape: a 14-file single-pass review gives uneven depth and contradictory findings → per-file passes plus an integration pass. For the open-ended shape: "how should the agent approach adding tests to an unfamiliar legacy system?" → map, prioritise, adapt.

Traps

  • Fixing attention dilution with a bigger context window (Q12: it "doesn't solve attention quality").
  • Fixed pipeline for open-ended work (misses discovered dependencies) or ad-hoc exploration for a predictable review (uneven coverage).
Official sample: Q12. Same pattern in D4 card 4.13.

TS 1.7Manage session state, resumption, and forking

One card, four decisions.

1.19--resume, fork_session, stale results, and telling the agent what changed

TS 1.7

What it is. Four facts. (1) --resume <session-name> continues a specific named prior conversation. (2) fork_session creates independent branches from a shared analysis baseline to explore divergent approaches — two testing strategies, two refactoring approaches — without redoing the analysis. (3) If code changed since the session was analysed, tell the resumed session which files changed so it re-analyses those, rather than forcing a full re-exploration. (4) When prior tool results are stale, starting a new session with a structured summary injected is more reliable than resuming.

How the exam asks it

"Compare two migration approaches from one codebase analysis without repeating it" → fork. "Continue yesterday's named investigation" → --resume with the name. "The team refactored heavily overnight; the resumed agent gives answers based on the old code" → either inform it of the specific changes, or (if most results are stale) start fresh with a summary.

Traps

  • Resuming with stale tool results and expecting the model to notice they are stale.
  • Forking when there is no shared baseline worth preserving (just start two sessions), or resuming when you actually want independent branches.
  • Full re-exploration when a targeted "these files changed" note would do.

TS 2.1Design effective tool interfaces with clear descriptions and boundaries

Three cards. Descriptions decide selection; overlap causes misrouting; the system prompt can quietly override both.

2.01Tool descriptions are the primary selection mechanism

TS 2.1

What it is. The model chooses among tools by reading their descriptions. Minimal descriptions ("Retrieves customer information" / "Retrieves order details") give it nothing to separate similar tools. A good description states purpose, expected inputs and their formats, outputs, example queries, edge cases, and when to use this tool versus similar alternatives. Trigger for this card: the tools have distinct purposes but thin descriptions, and the stem asks for the first step → enrich the descriptions. When the tools' purposes genuinely overlap, see 2.02.

How the exam asks it

Sample Q2: the agent calls get_customer for "check my order #12345"; both tools have minimal descriptions and accept similar identifiers. "Most effective first step?" → expand each description with input formats, example queries, edge cases and boundaries.

Traps

  • Few-shot examples of correct routing (5–8 of them) — adds tokens, does not fix the cause.
  • A routing layer that parses input and pre-selects the tool — over-engineered, bypasses the model.
  • Merging both into one lookup_entity — "a valid architectural choice" but more than a first step.
Official sample: Q2.

2.02Overlap causes misrouting: rename, differentiate, or split

TS 2.1

What it is. Two tools with near-identical descriptions (analyze_content vs analyze_document) get confused. Trigger for this card: the tools' names or purposes genuinely overlap, or one generic tool does several jobs — a richer description alone would still leave them ambiguous. Fixes the guide names: rename to something purpose-revealing and rewrite the description (analyze_content → extract_web_results with a web-specific description); split a generic tool into purpose-specific tools with defined input/output contracts (analyze_document → extract_data_points, summarize_content, verify_claim_against_source).

How the exam asks it

"The document agent sometimes calls the web-analysis tool on PDFs — what change fixes selection?" → rename + web-specific description. "One generic analysis tool produces inconsistent output shapes" → split by purpose with contracts.

Traps

  • Consolidating further ("one analyze tool for everything") when the problem is ambiguity.
  • Leaving the overlap and adding prompt text telling the model which to prefer.

2.03System-prompt wording can override good tool descriptions

TS 2.1

What it is. Keyword-sensitive instructions in the system prompt ("always search when the user mentions…") can create unintended tool associations that beat well-written descriptions. Reviewing the system prompt for such instructions is a listed skill.

How the exam asks it

"Descriptions were rewritten and are now clear, yet the agent still routes X to the wrong tool" → look for a system-prompt instruction that keys on a word in the user's request.

Traps

  • Rewriting descriptions a third time when the descriptions are no longer the problem.

TS 2.2Implement structured error responses for MCP tools

Two cards. The error shape and the error path.

2.04isError, error categories, and retryable metadata

TS 2.2

What it is. MCP tools signal failure with the isError flag. A useful error carries structured metadata: an errorCategory (transient / validation / permission — and the guide also lists business errors, i.e. policy violations), an isRetryable boolean, and a human-readable description. Business-rule violations carry retriable: false plus a customer-friendly explanation so the agent can communicate rather than retry. (The guide spells the same flag both ways — isRetryable and retriable; either form in an option means the retryability flag.) A uniform "Operation failed" gives the agent nothing to decide with, and unlabelled retryability wastes retry attempts.

How the exam asks it

"The agent retries a refund three times that policy will never allow" / "the agent gives up on a timeout that would have succeeded" → the tool's errors don't distinguish transient from business/permission, or lack a retryable flag. Answer: structured error metadata.

Traps

  • "Return an HTTP status code" or a generic message — not enough for a recovery decision.
  • Retry logic in the prompt ("try again if it fails") — the decision needs the category.
  • Treating validation errors (bad input — fix the call) like transient ones (wait and retry).

2.05Recover locally; propagate only what you cannot fix — and empty ≠ error

TS 2.2 · 5.3

What it is. Subagents handle transient failures themselves and propagate to the coordinator only errors they cannot resolve locally — together with partial results and what was attempted. Separately: an access failure (timeout, needs a retry decision) is not the same as a valid empty result (the query succeeded and matched nothing); the report to the coordinator must say which. The full propagation pattern is D5 card 5.07.

How the exam asks it

"How should a subagent handle a transient timeout?" → retry locally; if still failing, propagate structured context with partial results. "The coordinator treats 'no results' as a failed search and retries endlessly" → distinguish empty-success from access-failure in the response.

Traps

  • Propagating every hiccup upward (noise) or swallowing everything (silent loss).
  • Marking an empty result as an error, or a timeout as an empty result.

Two cards. How many tools, which ones, and how to force or require a call.

2.06Fewer, scoped, constrained: tool distribution across agents

TS 2.3

What it is. Four linked facts. (1) Too many tools (the guide's figure: 18 instead of 4–5) degrades selection reliability. (2) Agents holding tools outside their specialisation misuse them (a synthesis agent attempting web searches). (3) Give each agent only its role's tools, plus limited cross-role tools for specific high-frequency needs — the sample-Q9 verify_fact for the synthesis agent — while complex cases still route through the coordinator. (4) Replace generic tools with constrained alternatives (fetch_url → load_document that validates document URLs).

How the exam asks it

Sample Q9: 85% of synthesis verifications are simple fact checks costing 2–3 coordinator round trips → scoped verify_fact; complex ones stay on the coordinator path. Also: "the agent has 18 tools and picks wrong ones" → reduce and scope.

Traps

  • Giving synthesis all web-search tools (over-provisioned, breaks separation of concerns).
  • Batching all verifications to the end (creates blocking dependencies).
  • Speculative caching of "extra context" by the search agent (cannot predict what synthesis will need).
Official sample: Q9.

2.07tool_choice: auto, any, forced

TS 2.3 · 4.3

What it is. "auto" — the model may call a tool or answer in text. "any" — the model must call a tool, its choice which. Forced — {"type": "tool", "name": "extract_metadata"} — the model must call that specific tool. Forcing is used to guarantee a first step (e.g., extract_metadata before enrichment tools), with subsequent steps handled in follow-up turns. "any" guarantees a tool call rather than conversational text — used in D4 when several extraction schemas exist and the document type is unknown.

How the exam asks it

"Sometimes the model replies in prose instead of producing the structured record" → any (or forced if there is exactly one tool that must run). "Metadata extraction must always run before enrichment" → forced on the first turn.

Traps

  • Believing auto guarantees a tool call. It does not.
  • Forcing one tool when the document type is unknown and several schemas apply — that is what any is for.
  • Expecting a forced tool_choice to sequence a whole multi-step pipeline in one turn; it forces one call, then you continue.

TS 2.5Select and apply built-in tools (Read, Write, Edit, Bash, Grep, Glob) effectively

TS 3.1Configure CLAUDE.md files with appropriate hierarchy, scoping, and modular organization

Two cards. Which CLAUDE.md applies to whom, and how to keep it from becoming a monolith.

3.01The CLAUDE.md hierarchy: user, project, directory

TS 3.1

What it is. Three levels: user-level ~/.claude/CLAUDE.md (applies only to that user; not shared through version control), project-level (.claude/CLAUDE.md or a root CLAUDE.md; shared with the repo), and directory-level (a CLAUDE.md inside a subdirectory). How the exam asks it

"Conventions work on your machine but a new hire's Claude ignores them" → the instructions are in ~/.claude/CLAUDE.md; move them to the project CLAUDE.md. "Where do universal team standards live?" → project level.

Traps

  • Putting team standards in the user file "because it always loads".
  • Blaming the new hire's installation when the file simply isn't in the repo.

3.02@import, .claude/rules/, and /memory

TS 3.1

What it is. @import pulls an external file into a CLAUDE.md so it stays modular — each package's CLAUDE.md imports only the standards files relevant to it, chosen by the maintainers who know that package. .claude/rules/ holds topic-specific rule files (testing.md, api-conventions.md, deployment.md) as an alternative to one monolithic CLAUDE.md. /memory shows which memory files are loaded — the tool for diagnosing inconsistent behaviour across sessions.

How the exam asks it

Traps

  • Duplicating the same standards text into every package's CLAUDE.md instead of importing.

  • Rules in .claude/rules/ without paths: frontmatter are topic files, not path-conditional — the conditional variant is card 3.05.

TS 3.4

What it is. TS 3.5Apply iterative refinement techniques for progressive improvement

  • A fourth, longer prose description instead of examples.
  • Fixing interacting issues one at a time (each fix undoes the last).
  • Skipping the interview and implementing from assumptions in an unfamiliar domain.

TS 4.1Design prompts with explicit criteria to improve precision and reduce false positives

Two cards. The CI-review scenario lives here.

4.01Specific categorical criteria beat "be conservative"

TS 4.1

What it is. Precision comes from explicit criteria that define what to report and what to skip — "flag comments only when claimed behaviour contradicts actual code behaviour" rather than "check that comments are accurate"; report bugs and security issues, skip minor style and local patterns. General instructions such as "be conservative" or "only report high-confidence findings" do not improve precision the way specific categorical criteria do.

How the exam asks it

"The reviewer flags too many non-issues; the team wants fewer false positives" → write specific criteria for what counts (and what does not), not a confidence threshold or a tone instruction.

Traps

  • "Only report findings you are >90% confident about." Confidence filtering is the named non-fix.
  • "Be more conservative." Same problem.
  • Reaching for a bigger model instead of defining the criteria.

4.02False positives erode trust: disable the noisy category, define severity with examples

TS 4.1

What it is. A category with a high false-positive rate undermines developers' confidence in the accurate categories too. Two listed skills: temporarily disable the high-false-positive category while you improve its prompt, and define explicit severity criteria with concrete code examples for each severity level so classification is consistent.

How the exam asks it

"Developers have started ignoring all review comments because the 'naming' category is mostly wrong" → disable that category now, fix it separately. "Severity labels are inconsistent across similar findings" → per-level criteria with code examples.

Traps

  • Keeping the noisy category live "for coverage" while trust drains.
  • Defining severity in adjectives ("serious", "minor") without examples.

TS 4.2Apply few-shot prompting to improve output consistency and quality

Two cards. Few-shot is the exam's favourite proportionate fix — know exactly what it fixes.

4.03Few-shot: 2–4 targeted examples that show the reasoning

TS 4.2

What it is. When detailed instructions still give inconsistent results, few-shot examples are the most effective technique for consistently formatted, actionable output. The guide's recipe: 2–4 targeted examples for the ambiguous cases, each showing why one action was chosen over plausible alternatives; examples that demonstrate the exact output format (location, issue, severity, suggested fix); and examples that distinguish acceptable code patterns from genuine issues, which reduces false positives while letting the model generalise judgement to novel patterns rather than matching only the listed cases.

How the exam asks it

"Instructions are detailed but the format still varies" → few-shot with the format. "The agent escalates simple cases and handles complex ones" (sample Q3) → explicit criteria plus few-shot showing escalate-vs-resolve. "Ambiguous tool selection" → few-shot showing the reasoning for the choice.

Traps

  • Piling on 5–8 examples of the easy case (sample Q2's distractor) — target ambiguity, not volume.
  • Examples that show only the answer, not why it beat the alternative.
  • Using few-shot where a guarantee is required (Q1) — few-shot is still probabilistic.
Official samples: Q3 (few-shot is right), Q1 and Q2 (few-shot is the distractor).

4.04Few-shot for extraction: varied document structures, empty required fields

TS 4.2

What it is. In extraction, few-shot examples reduce hallucination by demonstrating correct handling of varied formats — informal measurements, inline citations vs bibliographies, methodology sections vs embedded details, narrative vs tables. Adding examples of correct extraction from varied formats is the listed fix for required fields coming back empty or null.

How the exam asks it

"Publication dates extract correctly from bibliographies but come back null when cited inline" → few-shot showing extraction from both structures.

Traps

  • Making the field required and retrying (see 4.08: retries cannot conjure absent data; and 4.07: required fields invite fabrication).
  • Rewriting the schema when the problem is format variety in the source.

TS 4.3Enforce structured output using tool use and JSON schemas

Three cards. The mechanism, the tool_choice setting, and the schema design decisions.

4.05Tool use + JSON schema: guaranteed structure — syntax yes, semantics no

TS 4.3

What it is. Define an extraction tool whose input parameters are the JSON schema you want; the structured data comes back in the tool_use response. This is the most reliable route to schema-compliant output and it eliminates JSON syntax errors. It does not prevent semantic errors: line items that don't sum to the total, values placed in the wrong field. Those need validation (TS 4.4).

How the exam asks it

"Output is sometimes malformed JSON / has extra prose around it" → tool use with a schema. "Schema validation passes but totals don't add up" → semantic error; add validation logic and self-correction fields, not a stricter schema.

Traps

  • "Ask for JSON in the prompt and parse it" as the reliable option — it is the less reliable one.
  • Believing a strict schema guarantees correct values.

4.06tool_choice for structured output

TS 4.3 · 2.3

What it is. Same three settings as D2 card 2.07, applied to extraction. "auto" may return text instead of calling a tool. "any" guarantees a tool call when several extraction schemas exist and the document type is unknown — the model picks the matching one. Forced {"type": "tool", "name": "extract_metadata"} ensures a particular extraction runs before enrichment steps.

How the exam asks it

"Invoices, receipts and contracts arrive mixed; the model sometimes answers in prose" → any. "Metadata must be extracted first every time" → forced.

Traps

  • Forcing extract_invoice on a mixed stream (wrong schema for non-invoices).
  • Leaving auto and blaming the model for prose replies.

4.07Schema design: nullable fields, "unclear", "other" + detail, normalisation rules

TS 4.3

What it is. Make a field optional/nullable when the source may not contain it — a required field pushes the model to fabricate a value to satisfy the schema. For enums, add "unclear" for ambiguous cases and an "other" value with a detail string for extensible categories. Put format-normalisation rules in the prompt alongside the strict schema to handle inconsistent source formatting.

How the exam asks it

"The model invents a tax ID when the document has none" → make it nullable. "New categories keep appearing that aren't in the enum" → "other" + detail. "Dates arrive as 03/04/2026 and 4 March 2026" → normalisation rules in the prompt.

Traps

  • Marking everything required "so nothing is missed" — this is the fabrication trap.
  • Ever-growing enums instead of the extensible pattern.
  • Trying to encode normalisation in the schema type alone.

TS 4.4Implement validation, retry, and feedback loops for extraction quality

Two cards. What retry can fix, and how to design for semantic checks.

4.08Retry with error feedback — and its limit

TS 4.4

What it is. On a validation failure (Pydantic or JSON-schema), send a follow-up that includes the original document, the failed extraction, and the specific validation errors, so the model can self-correct. Retries fix format mismatches and structural output errors. They cannot fix information that is absent from the source (or exists only in a document you did not provide) — retrying that is wasted work.

How the exam asks it

"Which failures should the retry loop attempt?" → format/structure errors. "The field is still null after five retries" → the value isn't in the document; stop retrying, mark it and route (see 5.12).

Traps

  • Retrying with the same prompt and no error feedback.
  • Retrying absent-information failures until a value appears — that value is fabricated.
  • Retrying without re-including the document.

4.09Semantic checks by design: calculated_total, conflict_detected, detected_pattern

TS 4.4

What it is. Semantic validation errors (values don't sum; wrong field placement) are the class the schema cannot catch. Design for them: extract calculated_total alongside stated_total so discrepancies are flagged; add a conflict_detected boolean for inconsistent source data. For review pipelines, add a detected_pattern field to each finding so that when developers dismiss findings you can analyse which code constructs cause false positives.

How the exam asks it

"Invoice totals sometimes disagree with the line items and nobody notices" → calculated vs stated total. "We can't tell which kinds of findings developers keep dismissing" → detected_pattern.

Traps

  • Tightening the schema to catch a semantic error.
  • Logging dismissals without a field that names the triggering construct.

TS 4.5Design efficient batch processing strategies

Two cards. The facts, then the operations.

4.10Message Batches API: 50% cheaper, up to 24 h, no latency SLA, no mid-request tool loop

TS 4.5

What it is. Batches cost 50% less, may take up to 24 hours, and carry no guaranteed latency. Fit: non-blocking, latency-tolerant work — overnight reports, weekly audits, nightly test generation. Unfit: anything someone waits on, such as a pre-merge check. A batch request cannot execute tools mid-request and return results — no multi-turn tool calling inside one request. Results are correlated by custom_id; completion is found by polling.

How the exam asks it

Sample Q11: manager wants both the blocking pre-merge check and the overnight debt report on batch → batch the report only. "Can our agentic loop run in a batch?" → not if it needs tool results mid-request.

Traps

  • "Batch is usually faster than 24 h, so it's fine for pre-merge" — no SLA.
  • "Keep both real-time to avoid ordering issues" — custom_id handles correlation.
  • "Batch with a timeout fallback to real-time" — unnecessary complexity when matching each workflow to the right API is simpler.
Official sample: Q11.

4.11Batch operations: SLA arithmetic, resubmit by custom_id, refine on a sample first

TS 4.5

What it is. (1) Submission frequency follows from the SLA: with 24-hour processing, submit in 4-hour windows to guarantee a 30-hour SLA (the guide's example). (2) On failures, resubmit only the failed documents, identified by custom_id, with modifications — e.g., chunk documents that exceeded context limits. (3) Refine the prompt on a sample set before batching a large volume, to maximise first-pass success and avoid iterative resubmission cost.

How the exam asks it

"30-hour SLA, 24-hour batch window — how often do you submit?" → every 4 hours. "12 of 1,000 documents failed for context length" → resubmit those 12, chunked. "First batch of 5,000 had a 40% failure rate" → should have refined on a sample first.

Traps

  • Resubmitting the whole batch.
  • Resubmitting failed items unchanged.
  • Batching the full volume before validating the prompt on a sample.

TS 4.6Design multi-instance and multi-pass review architectures

4.12Self-review is weak; use an independent instance

TS 4.6

What it is. A model that generated code retains its reasoning context and is less likely to question its own decisions in the same session. An independent review instance — without the generator's reasoning context — catches subtle issues more effectively than self-review instructions or extended thinking.

How the exam asks it

"The session that wrote the code reviews it and finds nothing; QA finds three bugs" → second, independent Claude instance for review.

Traps

  • "Add 'review your work critically' to the prompt."
  • "Enable extended thinking for the review step" — same reasoning context, same blind spots.

4.13Multi-pass review: per-file, then integration; confidence per finding for routing

TS 4.6

What it is. Large reviews split into per-file passes for local issues plus a separate cross-file integration pass for data flow — this avoids attention dilution and contradictory findings. Verification passes can have the model self-report a confidence alongside each finding to enable calibrated routing of review attention.

How the exam asks it

Sample Q12: 14-file PR, single-pass review is uneven and self-contradictory → per-file passes plus an integration pass.

Traps

  • Bigger context window (does not fix attention), forcing developers to split PRs (shifts burden), consensus voting across three runs (suppresses intermittently caught real bugs).
  • Nuance to hold: per-finding confidence for routing reviewer attention is a listed skill here; self-reported confidence as an escalation trigger is an unreliable proxy in D5 (card 5.06). Same number, different job.

TS 5.1Manage conversation context to preserve critical information across long interactions

Four cards. Four different ways context loses facts, each with its own fix.

5.01Tool results bloat context: trim to relevant fields; keep full history

TS 5.1

What it is. Tool results accumulate and consume tokens out of proportion to their relevance — an order lookup returning 40+ fields when 5 matter. Trim verbose tool outputs to the relevant fields before they accumulate. Separately, subsequent API requests must carry the complete conversation history for coherence — trimming means fewer fields per result, not dropping turns.

How the exam asks it

"Long support sessions hit the context limit after a dozen lookups" → keep only return-relevant fields from each lookup. "The agent forgets what was agreed three turns ago" → history is not being passed in full.

Traps

  • Summarising history to save space (see 5.02 for what that loses) when trimming tool payloads is the proportionate fix.
  • Sending only the last message and expecting continuity.

5.02Progressive summarisation loses numbers — keep a persistent case-facts block

TS 5.1

What it is. Summaries condense numerical values, percentages, dates and customer-stated expectations into vague prose. Fix: extract transactional facts (amounts, dates, order numbers, statuses) into a persistent "case facts" block that is included in each prompt outside the summarised history; for multi-issue sessions, persist structured issue data (order IDs, amounts, statuses) as a separate context layer.

How the exam asks it

"After summarisation the agent quotes the wrong refund amount / forgets the promised delivery date" → case-facts block. "Three issues in one session and the agent conflates their order numbers" → structured per-issue layer.

Traps

  • "Summarise more carefully" — the fix is structural, not a better summariser.
  • Keeping the facts only inside the summary that is being compressed.

5.03Lost in the middle: put key findings first, use explicit section headers

TS 5.1

What it is. Models reliably process the beginning and end of long inputs and may omit findings from the middle. Mitigate by placing a key-findings summary at the beginning of aggregated inputs and organising the detailed results under explicit section headers.

How the exam asks it

"The synthesis reliably covers the first and last subagent's findings and drops the ones in between" → position-aware ordering with a summary up front and headed sections.

Traps

  • Shortening every finding until the input is "small enough" — the position effect is not only about length.
  • Concatenating findings in arrival order with no structure.

5.04Upstream agents return structured data when downstream budgets are tight

TS 5.1

What it is. Require subagents to include metadata (dates, source locations, methodological context) in structured outputs so downstream synthesis is accurate; and when downstream agents have limited context budgets, modify upstream agents to return structured data — key facts, citations, relevance scores — instead of verbose content and reasoning chains.

How the exam asks it

"The synthesis agent runs out of context ingesting three subagents' full reasoning" → change what upstream returns: key facts + citations + relevance scores.

Traps

  • Truncating the upstream output at N tokens (loses arbitrary content) instead of restructuring it.
  • Giving synthesis a bigger budget as the only fix.

TS 5.2Design effective escalation and ambiguity resolution patterns

Two cards. This is sample Q3 and the 80% first-contact-resolution target.

5.05Escalation triggers — and honouring an explicit request immediately

TS 5.2

What it is. Escalate when: the customer explicitly asks for a human (honour it immediately, without first attempting investigation); policy is ambiguous or silent on the request (the guide's example: competitor price-matching when policy covers only own-site adjustments) — a policy gap, not merely a complex case; or the agent cannot make meaningful progress. When the customer is frustrated but the issue is within capability, acknowledge the frustration and offer to resolve; escalate only if they reiterate. Put explicit escalation criteria in the system prompt with few-shot examples of escalate-vs-resolve.

How the exam asks it

Sample Q3: 55% resolution; escalating standard damage replacements while handling policy exceptions itself → explicit criteria + few-shot. "Customer says 'get me a person'" → escalate now. "Customer is angry about a simple late delivery" → acknowledge, offer resolution, escalate if they insist.

Traps

  • Investigating first "to try to help" when a human was explicitly requested.
  • Escalating every frustrated customer (see 5.06: sentiment ≠ complexity).
  • Treating "complex" as the trigger; the trigger is a policy gap or no progress.
Official sample: Q3.

5.06Unreliable proxies (sentiment, self-reported confidence) and multiple matches

TS 5.2

What it is. Sentiment-based escalation and self-reported confidence scores are unreliable proxies for case complexity — the agent that mis-escalates is already mis-calibrated about its own confidence. When a lookup returns multiple customer matches, ask for additional identifiers; never pick one by heuristic.

How the exam asks it

Q3's distractors: "self-report a 1–10 confidence and route below threshold", "sentiment analysis to escalate on frustration", "a classifier trained on historical tickets" (over-engineered before prompt fixes). "Two customers named J. Patel match" → request another identifier.

Traps

  • Any escalation rule built on a number the model reports about itself.
  • "Pick the most recent account" or similar heuristic on multiple matches.
  • Do not over-generalise: per-finding confidence for routing reviewer attention (D4 card 4.13, D5 card 5.12) is a listed skill; it is the use as an escalation trigger that the guide calls unreliable.

TS 5.3Implement error propagation strategies across multi-agent systems

One card. This is sample Q8.

5.07Structured error context to the coordinator; two anti-patterns; coverage annotations

TS 5.3

What it is. A failing subagent returns structured error context — failure type, the attempted query, partial results, potential alternative approaches — so the coordinator can decide: retry with a modified query, try an alternative, or proceed with partial results. Distinguish access failures (timeout → retry decision) from valid empty results (success, no matches). Two named anti-patterns: silently suppressing errors (returning empty results as success) and terminating the whole workflow on one failure. Generic statuses ("search unavailable") hide the context the coordinator needs. Downstream, synthesis output carries coverage annotations: which findings are well-supported and which topic areas have gaps because sources were unavailable.

How the exam asks it

Sample Q8: the web-search subagent times out; "which propagation approach best enables intelligent recovery?" → structured error context. Follow-on: "how should the final report reflect the failed search?" → coverage-gap annotations.

Traps

  • Retry with backoff inside the subagent, then a generic "search unavailable" — the retry is fine, the generic status is the fault.
  • Return an empty result marked successful.
  • Propagate the exception to a top-level handler that kills the run.
Official sample: Q8. Local-recovery half of this is D2 card 2.05.

TS 5.4Manage context effectively in large codebase exploration

Three cards. Symptoms, three mitigations, and crash recovery.

5.08Context degradation and scratchpad files

TS 5.4

What it is. In extended sessions the model starts giving inconsistent answers and referencing "typical patterns" instead of the specific classes it discovered earlier. Have agents maintain scratchpad files that record key findings and refer back to them for later questions.

How the exam asks it

"Two hours in, the agent describes how a repository layer 'usually' works rather than the one it read earlier" → context degradation; scratchpad of findings.

Traps

  • Asking the agent to "remember" harder.
  • Restarting the session and losing everything, when a scratchpad would carry the findings.

5.09Delegate verbose exploration; summarise between phases; /compact

TS 5.4

What it is. Spawn subagents for specific questions ("find all test files", "trace refund-flow dependencies") while the main agent keeps high-level coordination. Summarise key findings from one exploration phase before spawning subagents for the next, injecting the summary into their initial context. Use /compact to reduce context usage when an extended session fills with verbose discovery output.

How the exam asks it

"The main agent's context is full of grep output" → delegate discovery to subagents (or the Explore subagent, D3 card 3.07). "Phase-2 subagents repeat phase-1 discovery" → inject a phase summary. "Mid-session, context is nearly full" → /compact.

Traps

  • Passing the entire phase-1 transcript to phase-2 agents instead of a summary.
  • Starting from scratch instead of compacting.

5.10Crash recovery: state exports and a manifest the coordinator reloads

TS 5.4

What it is. Each agent exports its state to a known location; on resume, the coordinator loads a manifest and injects the state into agent prompts. This is structured state persistence for crash recovery.

How the exam asks it

"The 6-hour analysis crashed at hour five and had to restart from zero" → structured state exports + manifest reload.

Traps

  • Relying on session resumption alone (card 1.19: stale tool results; and a crashed run may not have a clean session to resume).
  • Persisting logs rather than structured state the coordinator can inject.

TS 5.5Design human review workflows and confidence calibration

Two cards. Measuring accuracy honestly, and routing scarce reviewer time.

5.11Aggregate accuracy hides segment failures; stratified random sampling

TS 5.5

What it is. A 97% overall accuracy can mask poor performance on a specific document type or field. Before reducing human review, analyse accuracy by document type and by field to verify consistent performance across segments. Keep measuring after automation with stratified random sampling of high-confidence extractions — it measures the ongoing error rate and detects novel error patterns.

How the exam asks it

"Accuracy is 97%; can we stop reviewing high-confidence extractions?" → first segment by document type and field; then automate with stratified sampling still running.

Traps

  • Automating on the aggregate number.
  • Reviewing only low-confidence items forever and never sampling the high-confidence ones (novel errors hide there).

5.12Field-level confidence, calibrated on labelled data, routes review

TS 5.5

What it is. Have the model output a confidence per field; calibrate the review thresholds using labelled validation sets; route low-confidence extractions and those from ambiguous or contradictory source documents to human review, so limited reviewer capacity goes where it matters.

How the exam asks it

"Reviewers can check 5% of extractions — which 5%?" → low field-level confidence and ambiguous/contradictory sources, with thresholds set from a labelled set.

Traps

  • Using the raw confidence number without calibrating it against labelled data.
  • One document-level score when errors are field-specific.

TS 5.6Preserve information provenance and handle uncertainty in multi-source synthesis

Two cards. Where sources get lost, and how conflicts, dates and formats are handled.

5.13Claim–source mappings survive synthesis; conflicts are annotated, not resolved by fiat

TS 5.6

What it is. Attribution is lost when findings are compressed without their claim–source mapping. Require subagents to output structured claim–source mappings (source URLs, document names, relevant excerpts) that downstream agents preserve and merge. When credible sources give conflicting statistics, keep both values with attribution and annotate the conflict — the analysis agent completes with the conflict included and explicitly marked, and the coordinator decides how to reconcile before synthesis. Reports separate well-established findings from contested ones, preserving the sources' own characterisations and methodological context.

How the exam asks it

"Two credible sources give different market sizes — what should the analysis agent do?" → include both, annotate with sources, let the coordinator reconcile. "The final report cites nothing" → the mapping was dropped in a summarisation step.

Traps

  • Picking the "more credible" value silently, or averaging them.
  • Asking synthesis to add citations after the fact.

5.14Dates prevent false contradictions; render each content type in its natural form

TS 5.6

What it is. Require publication or data-collection dates in structured outputs so that a 2023 figure and a 2025 figure are read as a time series, not a contradiction. In synthesis, render content types appropriately — financial data as tables, news as prose, technical findings as structured lists — instead of flattening everything into one format.

How the exam asks it

"The report flags two revenue figures as conflicting; they are from different years" → dates were not carried in the structured output. "Every section reads as the same undifferentiated prose" → per-content-type rendering.

Traps

  • Treating temporal differences as source conflicts.
  • A uniform output format "for consistency".

  • Batch both with timeout fallback: "unnecessary complexity when the simpler solution is matching each API to its appropriate use case".

Q1214-file PR; single-pass review is uneven and contradictory

→ cards 4.13, 1.18

Answer: split into focused passes — each file individually for local issues, then a separate integration-focused pass on cross-file data flow — "directly addresses the root cause: attention dilution".

Why the others fail

  • Require developers to split PRs: "shifts burden to developers without improving the system".
  • Higher-tier model with bigger context: "larger context windows don't solve attention quality issues".
  • Three passes, flag only consensus: "would actually suppress detection of real bugs by requiring consensus on issues that may only be caught intermittently".
