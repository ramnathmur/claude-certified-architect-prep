The exam-day rules, in brief

  • Valid, unexpired, government-issued photo ID; the name must match your registration exactly.
  • Clear desk. No phones, watches, headphones, notes, or second monitors. Stay in webcam view.
  • You accept a confidentiality agreement before the first question. Decline it and the session ends with no refund.
  • Reschedule or cancel more than 24 hours out; inside 24 hours you forfeit the fee.
  • Retakes: 14 days after a first fail, 30 after a second, 90 after a third; four attempts per rolling year.
  • Renewal is a free, non-proctored assessment before the 12 months elapse. Let it lapse and you sit the whole thing again at full price.

The six scenarios — four of which you will see

Every question sits inside one of these. Recognising the room tells you which domains the examiner is most likely probing, which narrows your options before you have read them.

Scenario 1 · Customer Support Resolution Agent

An Agent SDK agent handling returns, billing disputes, account issues. Backend reached through custom MCP tools: get_customer, lookup_order, process_refund, escalate_to_human. Target: 80%+ first-contact resolution, while knowing when to escalate.

Probes: orchestration, tool design, context & reliability.

Scenario 2 · Code Generation with Claude Code

A team using Claude Code for generation, refactoring, debugging, documentation. Custom slash commands, CLAUDE.md configuration, plan mode versus direct execution.

Probes: Claude Code configuration, context & reliability.

Scenario 3 · Multi-Agent Research System

A coordinator delegating to specialised subagents — web search, document analysis, synthesis, report generation — producing comprehensive cited reports.

Probes: orchestration, tool design, context & reliability.

Scenario 4 · Developer Productivity with Claude

An agent that explores unfamiliar codebases, reads legacy systems, generates boilerplate. Leans on the built-in tools (Read, Write, Bash, Grep, Glob) and MCP servers.

Probes: tool design, Claude Code configuration, orchestration.

Scenario 5 · Claude Code for Continuous Integration

Claude Code in the CI/CD pipeline: automated review, test generation, pull-request feedback. Prompts must be actionable and must not drown developers in false positives.

Probes: Claude Code configuration, prompt engineering.

Scenario 6 · Structured Data Extraction

Extraction from unstructured documents, validated against JSON schemas, high accuracy, graceful edge-case handling, feeding downstream systems.

Probes: prompt engineering, context & reliability.

How to read an option list

  • An option naming a flag or parameter that does not exist is wrong. The examiner plants these deliberately — CLAUDE_HEADLESS=true, --batch, a .claude/config.json with a commands array, a session_id API parameter. None are real.
  • An option that adds a model, a classifier, or a training pipeline when a prompt or description change is untried is over-engineering. It is almost never the answer to a "first step" question.
  • An option that fixes a downstream agent when the stem tells you the upstream one misassigned the work is solving the wrong problem.
  • An option relying on the model's own confidence or on sentiment as a routing signal is wrong unless the stem is specifically about calibrating confidence against a labelled validation set.
  • Read the verb in the question. "Most likely root cause", "most effective first step", and "how should you evaluate this proposal" want three different kinds of answer.

What I cannot ask you

Published as out of scope. If an option leans on one of these as its main idea, that is a signal — and if a topic below is eating your revision time, stop.

  • Fine-tuning or training custom models
  • API authentication, billing, account management
  • Deep language- or framework-specific implementation beyond tool and schema configuration
  • Deploying or hosting MCP servers — infrastructure, networking, containers
  • Claude's internal architecture, training process, or weights
  • Constitutional AI, RLHF, safety-training methodology
  • Embedding models or vector-database implementation detail
  • Computer use — browser automation, desktop interaction
  • Vision and image analysis
  • Streaming APIs and server-sent events
  • Rate limits, quotas, pricing calculations
  • OAuth, key rotation, authentication protocols
  • Cloud provider configuration — AWS, GCP, Azure
  • Benchmarking or model comparison metrics
  • Prompt caching implementation detail — beyond knowing it exists
  • Token counting algorithms and tokenisation

Agentic Architecture & Orchestration

27% — roughly 16 questions. The largest domain, and the one where the wrong answers are most seductive. Almost every item here reduces to one of three judgements: is the loop driven by structure or by guesswork; does information flow through the hub; and is this rule enforced or merely requested.

The agentic loop

Send a request. Inspect stop_reason. If it is "tool_use", execute the requested tool, append the result to the conversation, and send again. If it is "end_turn", stop and return the response.

Tool results are appended to conversation history so the model can reason about the next action with the new information in hand. That accumulation is the mechanism.

The trap — three termination anti-patterns: parsing the natural-language text for something like "I'm done"; using an arbitrary iteration cap as the primary stopping mechanism; and treating the presence of assistant text as a completion signal. The structured field is the signal.
see also tool_use and tool_choice the stateless API

Model-driven decisions versus a decision tree

Claude reasons about which tool to call next from the context it has. That is different in kind from a pre-configured sequence or decision tree you wrote in advance.

Know when each is right. Model-driven adaptability is the point of an agent. But where a step is safety-critical or financially consequential, you constrain it with code — see preconditions and gates — rather than abandoning the agentic design entirely.

Hub and spoke

One coordinator manages all inter-subagent communication, all error handling, and all information routing. Subagents do not talk to each other.

The reasons are observability, uniform error handling, and controlled information flow. Direct agent-to-agent exchange leaves the coordinator blind to what was said and duplicates error handling in every spoke.

The coordinator's job: decompose the task, delegate, decide which subagents to invoke for this particular query, aggregate the results.

Subagents start empty

A subagent does not inherit the coordinator's conversation history, and does not share memory between invocations. Whatever it needs must be written into its prompt.

So when the synthesis subagent needs the web search results and the document analysis output, you pass those findings in the prompt. Use a structured format that separates content from metadata — source URLs, document names, page numbers — so attribution survives the handoff.

see also provenance and claim–source mapping

Spawning: the Task tool

  • Subagents are spawned via the Task tool.
  • A coordinator's allowedTools must include "Task" or it cannot delegate at all.
  • AgentDefinition configures each subagent type: description, system prompt, tool restrictions.
  • Parallel execution means emitting multiple Task calls in a single coordinator response — not one per turn across successive turns.
The trap — an option describing sequential turns and calling it parallelism. The distinction is one response containing several calls.

Coordinator prompts: goals, not procedures

Write coordinator prompts that state the research goal and the quality criteria. Step-by-step procedural instructions remove exactly the adaptability you delegated for.

Least privilege across subagents

Give each subagent the tools its role needs and no more. Agents holding tools outside their specialisation misuse them — the synthesis agent starts running web searches. Around 4–5 well-chosen tools; 18 degrades selection reliability badly.

Where one cross-role need is genuinely high-frequency, provide a scoped tool for it — a verify_fact for the synthesis agent handling the 85% of simple lookups — while complex cases still route through the coordinator.

see also tool distribution

Decomposition is the coordinator's most consequential act

When every subagent reports success but the final output has gaps, look at what they were asked, not at how they performed.

The canonical case: a report on "AI in creative industries" covers only visual arts, because the coordinator split the topic into digital art, graphic design, and photography. Music, writing, and film were never assigned to anyone. The subagents did their jobs perfectly.

Partition scope to minimise duplication — distinct subtopics or distinct source types per agent.

The trap — options blaming the synthesis agent's gap-detection, the search agent's query breadth, or the analysis agent's relevance filter. All are downstream of the real fault.

Fixed pipeline or adaptive decomposition

Prompt chaining — fixed sequence Predictable, multi-aspect work where the steps are known in advance. Review each file individually, then run a cross-file integration pass.
Dynamic adaptive decomposition Open-ended investigation where subtasks depend on what earlier steps discover. "Add comprehensive tests to a legacy codebase": map the structure, find high-impact areas, build a prioritised plan that adapts as dependencies surface.

Splitting a large review into per-file local passes plus an integration pass exists to defeat attention dilution — the reason a single pass over 14 files gives deep feedback on some and superficial feedback on others, and sometimes contradicts itself.

see also multi-pass review architecture

Iterative refinement loops

The coordinator evaluates the synthesis output for gaps, re-delegates to the search and analysis subagents with targeted queries, and re-invokes synthesis. It repeats until coverage is sufficient. One pass through the pipeline is not the ceiling.

Coverage annotations — degrading gracefully

When a source was unavailable or a subagent failed, the synthesis output says so: which findings are well-supported, which topic areas have gaps and why. Proceeding with partial results is correct; proceeding silently is not.

Enforcement versus guidance

Prompt instructions have a non-zero failure rate. Where compliance must be deterministic, enforce it in code.

Block lookup_order and process_refund until get_customer has returned a verified customer ID. That is a programmatic prerequisite, and it is what an item about "the agent skips verification in 12% of cases" is asking for.

The trap — "strengthen the system prompt to say verification is mandatory" and "add few-shot examples showing correct ordering" both look reasonable and both remain probabilistic. When the consequence is financial, probabilistic is the wrong category of answer.

Hooks

PostToolUse — normalise what comes back Intercept tool results before the model sees them. Canonical use: reconciling heterogeneous formats from different MCP tools — Unix timestamps, ISO 8601, numeric status codes — into one shape.
Tool-call interception — police what goes out Intercept outgoing calls to enforce policy. Block a refund above $500 and redirect to human escalation.

Choose a hook over prompt wording whenever the business rule requires a guarantee.

Structured handoff on escalation

The human receiving the escalation cannot see the conversation transcript. The handoff payload therefore carries: customer ID, root-cause analysis, the refund amount or equivalent figures, and a recommended action.

see also when to escalate

Multi-concern requests

Decompose a message raising several issues into distinct items, investigate each in parallel against shared context, then synthesise one unified resolution. Not one issue per turn.

Sessions: resume, fork, or start fresh

MechanismWhat it doesReach for it when
--resume <session-name>Continues a specific named prior conversation The prior context is still mostly valid
fork_sessionIndependent branches from one shared baseline Exploring divergent approaches — two testing strategies, two refactorings — from the same codebase analysis
Fresh session + injected summaryNew context seeded with a structured summary The prior tool results are stale

Starting fresh with a structured summary is more reliable than resuming onto stale tool results. Resuming carries the old observations forward as though they were still true.

When you do resume after code has changed, tell the agent which files changed so it re-analyses those specifically, rather than forcing a full re-exploration.

Independent review instances

A model that just generated code retains its own reasoning context and is correspondingly unlikely to question its own decisions. A second, independent instance — without that context — catches subtle issues that self-review instructions and extended thinking do not.

Tool Design & MCP Integration

18% — roughly 11 questions. The unifying idea of this domain: the description is the interface. Tool selection runs on descriptions, so most failures here are description failures, and most correct answers are description fixes rather than new machinery.

Tool descriptions are the primary selection mechanism

A good description states the input formats it accepts, example queries, edge cases, and the boundary — when to use this tool rather than the similar-looking one next to it.

Minimal descriptions ("Retrieves customer information" / "Retrieves order details") on tools that accept similar identifiers produce exactly the misrouting you would predict.

The trap — the fix is to expand the descriptions. Not a keyword-parsing routing layer in front of the model (over-engineered, and it discards the model's language understanding), not a pile of few-shot examples (token overhead that leaves the root cause in place), and not consolidating the two tools into one (a defensible architecture change, but far more work than a "first step" warrants).

Naming and splitting

  • Rename to eliminate functional overlap: analyze_content beside analyze_document is a misrouting engine. extract_web_results, with a web-specific description, is not.
  • Split a generic tool into purpose-specific ones with defined input/output contracts: analyze_document becomes extract_data_points, summarize_content, verify_claim_against_source.
  • Read the system prompt too. Keyword-sensitive wording there can create unintended tool associations that override well-written descriptions.

tool_use and tool_choice

SettingBehaviourUse for
"auto"Model may call a tool, or may just return textOrdinary conversational agents
"any"Must call a tool; may choose whichGuaranteeing structured output when several extraction schemas exist and the document type is unknown
{"type":"tool","name":"..."}Must call that toolForcing extract_metadata to run before enrichment steps; the rest follows in later turns

Structured error responses

MCP signals failure with the isError flag. But the flag alone is not enough — a uniform "Operation failed" leaves the agent with no basis for choosing a recovery.

Return structured metadata: errorCategory (transient / validation / permission), an isRetryable boolean, and a human-readable description.

CategoryExampleRetryable
TransientTimeout, service unavailableYes, with backoff
ValidationMalformed or invalid inputNo — it will fail identically
BusinessPolicy violation — refund exceeds the limitNo. Add retriable: false and a customer-friendly explanation the agent can relay
PermissionNot authorised for this operationNo
The trap — a valid empty result is not an error. Zero matches means the query succeeded and found nothing. A timeout means access failed and someone must decide whether to retry. Conflating them is a documented distractor.

Handle errors at the right level

A subagent recovers locally from transient failures. It propagates upward only what it cannot resolve — and when it does, it sends what was attempted, the partial results it has, and possible alternatives.

see also error propagation across agents

Two-tool token binding

When a preview step must be impossible to skip, bind two tools: the first returns a token, the second will not act without it. A single tool with a dry_run: false parameter can simply be called with dry_run=false on the first attempt.

Same principle as the enforcement gate one domain over: architecture that makes the wrong order impossible, rather than instructions asking for the right one.

Distributing tools across agents

  • Too many tools degrades selection. 18 tools where 4–5 would do multiplies the decision space.
  • Out-of-specialisation tools get misused. Give the synthesis agent search tools and it will search.
  • Scope by role, with narrow cross-role exceptions for genuinely high-frequency needs.
  • Constrain rather than generalise: replace fetch_url with a load_document that validates document URLs.
see also least privilege for subagents

MCP server configuration

Project scope — .mcp.json At the project root. Version-controlled. Shared team tooling. Every teammate gets it on clone or pull.
User scope — ~/.claude.json In the home directory. Not version-controlled. Personal and experimental servers, personal auth.
  • Environment variable expansion in .mcp.json — ${GITHUB_TOKEN} — shares the server configuration without committing anybody's secret.
  • Tools from all configured servers are discovered at connection time and are available simultaneously. Project and personal servers coexist.

Resources, and when not to build

  • MCP resources expose content catalogs — issue summaries, documentation hierarchies, database schemas. Their purpose is to give the agent visibility into what exists so it stops making exploratory tool calls to find out.
  • Tools are for actions; resources are for catalogs.
  • For a standard integration — Jira and its like — take the existing community server. Reserve custom servers for genuinely team-specific workflows.

When the agent prefers Grep to your MCP server

Selection runs on descriptions, so a familiar built-in beats a capable MCP tool whose description does not spell out what it uniquely offers.

Do: enhance the MCP tool's description — its capability, its outputs, what the built-in cannot provide.

Don't: disable Grep to force the issue — that breaks every legitimate content search. And don't add a blanket "always prefer MCP tools" system-prompt rule — blunt, keyword-sensitive, and wrong in the cases where the built-in genuinely is the right tool.

The built-in tools

ToolJobReach for it when
GrepSearches inside files — contentFinding callers of a function, locating an error string, tracing imports
GlobMatches file names and pathsEnumerating files by pattern — **/*.test.tsx
ReadLoads full file contentsFollowing an import, tracing a flow after Grep located it
WriteWrites a full fileWhole-file creation, or the Edit fallback below
EditTargeted change via a unique text anchorSingle-occurrence modification
BashShell executionRunning commands — not a substitute for the file tools
The trap — "find every file referencing the deprecated formatDate" is Grep, because the target is file content. Glob would only match files named formatDate. And "find all the test files" is Glob — Grepping for the word "test" both over-matches and misses.

When Edit fails

Edit fails when the anchor text is not unique — it cannot decide which occurrence you meant.

The sanctioned fallback is Read + Write: load the whole file, modify, write it back.

Not retrying Edit with a shorter anchor — shorter strings are more likely to collide, not less. Not reaching for sed through Bash.

Explore incrementally

Grep to find the entry points, then Read to follow imports and trace flows.

Reading every file upfront "for full context" burns the context window on irrelevance. Globbing the whole tree and reading each match is the same anti-pattern wearing a different tool.

To trace a function used across wrapper modules: first identify all the exported names, then search for each name across the codebase.

Claude Code Configuration & Workflows

20% — roughly 12 questions. This domain rewards knowing exactly which file goes where and what each one is for. A large share of items are answerable from a single fact: is this configuration version-controlled and shared, or is it sitting in somebody's home directory.

The CLAUDE.md hierarchy

LevelLocationShared?
User~/.claude/CLAUDE.mdNo — that user only, never in version control
Project.claude/CLAUDE.md or root CLAUDE.mdYes — every teammate on clone or pull
DirectoryA CLAUDE.md in a subdirectoryYes, but bound to that directory

They concatenate from root down toward the working directory — this is layering, not one level silently overriding another.

The trap — the new team member who does not follow a convention everyone else follows. The convention lives in somebody's ~/.claude/CLAUDE.md and was never in the repository. Move it to project level.

Keeping it modular

  • @import pulls in external files so each package's CLAUDE.md includes only the standards relevant to it.
  • .claude/rules/ holds topic-specific rule files — testing.md, api-conventions.md, deployment.md — instead of one monolith.
  • /memory shows which memory files are actually loaded. It is the diagnostic when behaviour differs between sessions or between developers.

Path-scoped rules

A file in .claude/rules/ with YAML frontmatter carrying a paths field of glob patterns loads only when the file being edited matches.

paths: ["terraform/**/*"]

Two payoffs: conventions apply automatically and deterministically, and irrelevant context stays out of the window.

When to prefer this over a subdirectory CLAUDE.md: when the files sharing a convention are spread across the tree rather than gathered in one folder. Test files living next to the code they test (Button.test.tsx beside Button.tsx) are the standing example — **/*.test.tsx catches them all; a directory-bound file cannot.

The trap — the three near-misses. Consolidating everything under headers in the root CLAUDE.md relies on Claude inferring which section applies. Skills need invoking, which contradicts "automatic". A CLAUDE.md per subdirectory cannot follow files scattered across many directories.

Slash commands

Project — .claude/commands/ In the repository, version-controlled, automatically available to every developer who clones or pulls. This is where a team's /review command belongs.
Personal — ~/.claude/commands/ Home directory, not shared.

Watch for a distractor proposing a .claude/config.json with a commands array. No such mechanism exists.

Skills and their frontmatter

Skills live in .claude/skills/ as SKILL.md files. Three frontmatter options are examinable:

OptionWhat it doesReach for it when
context: forkRuns the skill in an isolated sub-agent context The skill produces verbose output (codebase analysis) or exploratory context (brainstormed alternatives) you do not want bleeding into the main conversation
allowed-toolsRestricts tool access during execution Limiting a skill to file writes so it cannot take destructive actions
argument-hintPrompts for required parameters The developer invokes the skill with no arguments

Skills or CLAUDE.md? Skills are on-demand, for task-specific workflows. CLAUDE.md is always loaded, for universal standards.

Personal variants: a skill at ~/.claude/skills/ lets you customise without touching the team's. Give it a different name if you do not want to shadow theirs.

Plan mode or direct execution

Plan mode Large-scale change, several valid approaches, architectural decisions, many files. Monolith to microservices. A library migration touching 45+ files. Choosing between integration approaches with different infrastructure implications. It lets you explore and design safely before committing, which is what prevents expensive rework.
Direct execution Simple, well-scoped, understood. A single-file bug fix with a clear stack trace. Adding one date validation conditional to one function.

The two combine: plan the migration, then execute the planned approach directly.

The trap — "start direct and switch to plan mode if it turns out complex." When the stem already tells you the work spans dozens of files and requires boundary decisions, the complexity is stated, not emergent.

The Explore subagent

Isolates a verbose discovery phase and returns a summary, keeping the main conversation's context intact through a multi-phase task.

see also subagent delegation for context

Iterative refinement

  • Concrete input/output examples. When prose descriptions get interpreted inconsistently, 2–3 worked examples of the transformation communicate what the prose could not.
  • Test-driven iteration. Write the suite first — expected behaviour, edge cases, performance requirements — then iterate by feeding back the failures.
  • The interview pattern. Have Claude ask you questions before implementing, surfacing considerations you had not thought of — cache invalidation strategy, failure modes — in a domain you do not know well.
  • Batching feedback. Interacting problems go in one detailed message, because fixing them separately means each fix disturbs the others. Independent problems can be handled sequentially.

Making CI reviews useful

  • CLAUDE.md is how you give CI its context — testing standards, fixture conventions, review criteria. This is also the lever that stops test generation producing low-value tests.
  • Session context isolation: the session that generated the code is a weaker reviewer of that code than an independent instance, because it carries its own reasoning forward.
  • On re-runs after new commits, include the prior findings and instruct Claude to report only new or still-unaddressed issues. Otherwise developers get the same comment three times.
  • Supply the existing test files when generating tests, so it does not propose scenarios the suite already covers.

Prompt Engineering & Structured Output

20% — roughly 12 questions. Two halves. The first is about precision: specific criteria and worked examples beat exhortation. The second is mechanical: schemas, tool use, validation, and the Batches API, where the facts are crisp and the marks are cheap if you know them.

Explicit criteria beat vague instructions

Works "Flag comments only when the claimed behaviour contradicts the actual code behaviour." Categorical, checkable, and it defines which issues to report (bugs, security) and which to skip (minor style, local patterns).
Does not work "Be conservative." "Only report high-confidence findings." "Check that comments are accurate." Confidence-based filtering is not a criterion.

Why precision matters commercially: one category with a high false-positive rate undermines developer trust in the accurate categories too. The whole tool gets ignored.

The repair: temporarily disable the offending category to restore trust while you improve its prompt. And define severity levels with concrete code examples for each, so classification is consistent.

Few-shot examples

When detailed instructions have already failed to produce consistent output, more detailed instructions will not fix it. Examples will.

What they are for, specifically:

  • Ambiguous cases. 2–4 targeted examples that show the reasoning for why one action was chosen over a plausible alternative. Aim at the cases where it actually goes wrong.
  • Format. Demonstrating the exact output shape — location, issue, severity, suggested fix.
  • Generalisation. Well-chosen examples let the model extend its judgement to novel patterns, rather than matching only the cases you listed.
  • Extraction variety. Documents with inline citations versus bibliographies, methodology sections versus embedded details, narrative versus tabular. This is the fix for required fields coming back empty.
  • False positives. Examples distinguishing acceptable patterns from genuine issues.
The trap — 10–15 examples of clear, unambiguous requests. They spend tokens on the cases that were never failing. Target the ambiguity.

Guaranteeing structure with tool use

Tool use with a JSON schema is the reliable route to schema-compliant output. Define the extraction tool with the schema as its input parameters and read the data from the tool_use response.

What it guarantees and what it does not: a strict schema eliminates JSON syntax errors. It does not prevent semantic errors — line items that do not sum to the stated total, a value placed in the wrong field. Those need validation.

see also tool_choice modes in full

Designing the schema

  • Optional and nullable fields for information the source document may not contain. A required field pressures the model to fabricate a value to satisfy it. This is the direct answer to "the model invents data that isn't in the document".
  • Enums with an escape hatch: an "other" value plus a detail string keeps the category set extensible; an "unclear" value handles genuine ambiguity honestly.
  • Format normalisation rules go in the prompt alongside the strict schema, to absorb inconsistent source formatting.

Retry with error feedback

On a validation failure, send a follow-up containing the original document, the failed extraction, and the specific validation error. That is what lets the model self-correct.

Know when retrying is pointless. Format mismatches and structural output errors are recoverable. Information that is simply absent from the source is not — if the value only exists in an external document you did not supply, no number of retries will conjure it.

Self-correction and feedback loops

  • Extract calculated_total alongside stated_total so discrepancies surface instead of passing silently.
  • Add a conflict_detected boolean for internally inconsistent source data.
  • Add a detected_pattern field to structured findings, recording which code construct triggered each one. When developers dismiss findings, that field is what lets you analyse the false-positive pattern systematically instead of guessing.

The Message Batches API

PropertyDetail
Cost50% saving
LatencyUp to a 24-hour processing window, no guaranteed SLA
Tool callingNo multi-turn tool calling within a request — it cannot execute a tool mid-request and feed the result back
Correlationcustom_id joins requests to responses

Match the API to the latency tolerance. Overnight reports, weekly audits, nightly test generation: batch. A blocking pre-merge check a developer is waiting on: synchronous.

The trap — "switch both workflows to batch and poll for completion." "Often faster than 24 hours" is not an SLA, and a blocking check cannot be built on a hope. Equally, an iterative review that fetches related files mid-review through tool calls cannot use batch at all.

Two calculations you may be asked to make: submission frequency against an SLA — 4-hour submission windows to guarantee a 30-hour SLA given a 24-hour worst case — and failure handling, where you resubmit only the failed documents by custom_id, chunking any that exceeded context limits.

Refine the prompt on a sample first. First-pass success on a large batch is worth more than iterating through resubmissions.

Multi-pass and multi-instance review

Self-review is weak because the model still holds the reasoning it used to generate the code and is unlikely to question it. An independent instance without that context catches more.

Split large reviews: a per-file pass for local issues, then a separate integration pass for cross-file data flow. This is the answer when a 14-file review comes back with deep feedback on some files, superficial comments on others, missed bugs, and contradictions — flagging a pattern in one file and approving the identical pattern in another.

The trap — a bigger context window does not fix attention dilution. Nor does making developers split their pull requests (that moves the burden without improving the system), nor running three passes and reporting only issues that appear in two — which would suppress real bugs that are caught intermittently.

Verification passes: have the model report confidence alongside each finding so review attention can be routed by it.

Context Management & Reliability

15% — roughly 9 questions. The smallest domain and the one candidates most often under-prepare. Its through-line: precise facts degrade when they pass through summarisation, and the fix is almost always to lift them out of the summarised stream rather than to summarise better.

The API is stateless

Claude has no server-side memory. It "remembers" only because your application includes the prior messages in the messages[] array of each request.

The trap — options implying a session_id parameter, or a vector database as the mechanism for ordinary multi-turn memory. Neither is right. A vector store is for retrieval over months of history, not for a normal conversation.

Precision survives outside the summary

Progressive summarisation condenses exactly the things you cannot afford to lose: amounts, percentages, dates, order numbers, statuses, what the customer explicitly said they expected.

Extract the transactional facts into a persistent case-facts block included in every prompt, outside the summarised history. For multi-issue sessions, persist the structured issue data — order IDs, amounts, statuses — into its own context layer.

The trap — "rewrite the summarisation prompt to preserve numbers" still depends on perfect execution every time. "Raise the summarisation threshold" buys time and fixes nothing.

Lost in the middle

Models handle the beginning and the end of a long input reliably and may drop findings from the middle.

Put the key-findings summary at the start of aggregated input, and organise the detail under explicit section headers.

Not rotating which agent's output comes first — that shuffles who gets dropped without changing the attention pattern. Not compressing everything under 20K tokens — that risks losing the critical material outright.

Trim the tool output

Tool results accumulate and consume tokens out of all proportion to their relevance — 40+ fields come back from an order lookup when 5 matter. Trim to the relevant fields before they land in context.

The same logic upstream: when a downstream agent has a tight budget, have the upstream agent return structured data — key facts, citations, relevance scores — rather than verbose content and reasoning chains. And require subagents to carry metadata (dates, source locations, methodological context) in their structured output so synthesis can be accurate.

Behavioural drift, and what it is not

When system-prompt adherence decays across turns at a small token count — 2,500 tokens, 7 turns — the cause is accumulated assistant responses diluting the system prompt's influence.

Not context window overflow, which is impossible at that size. Not "the system prompt only applies to the first turn" — it is included in every request.

Long-term recall

For retrieving a specific exchange out of months of history — 85K tokens of it — use semantic embeddings and retrieve the relevant exchanges. Progressive summarisation has already compressed the specific conclusion into an abstraction that cannot be recalled precisely.

When to escalate

Reliable triggers The customer asks for a human. Policy is silent or ambiguous on their specific request. The agent cannot make meaningful progress.
Unreliable proxies Self-reported confidence scores — poorly calibrated, and an agent already wrong on hard cases is confidently wrong. Sentiment analysis — frustration does not correlate with case complexity.

The fix for bad escalation calibration is explicit criteria in the system prompt with few-shot examples showing when to escalate and when to resolve. That is the proportionate first response, before any classifier or ML infrastructure.

  • An explicit request for a human is honoured immediately — no investigation attempt first.
  • Frustration alone is not an escalation. Acknowledge it, offer resolution if the issue is within your capability, escalate if they reiterate the preference.
  • Policy gaps escalate. Competitor price matching, when the policy only addresses your own site, is a gap — not a hard case.
  • Multiple customer matches: ask for another identifier. Never pick one by heuristic.

Error propagation across agents

Return structured error context: the failure type, what was attempted, any partial results, and possible alternatives. That is what lets the coordinator decide intelligently — retry with a modified query, try another route, or proceed with what it has.

Two anti-patterns, both plausible-looking:

  • Silent suppression — catching the timeout and returning an empty result set marked successful. It prevents any recovery and quietly ships an incomplete report.
  • Global termination — propagating the exception to a top-level handler that kills the whole workflow, when recovery would have worked.

A generic "search unavailable", even after exhausting retries locally, hides the context the coordinator needed. And distinguish an access failure from a valid empty result — they demand opposite responses.

Where sources were unavailable, annotate the synthesis with coverage gaps: what is well-supported, what is not, and why.

see also structured MCP error responses

Long sessions over large codebases

The symptom of context degradation: the model starts giving inconsistent answers and referring to "typical patterns" instead of the specific classes it discovered earlier.

TechniqueWhat it buys you
Scratchpad filesKey findings persist across context boundaries; the agent re-reads them for later questions
Subagent delegationVerbose exploration stays isolated — "find all test files", "trace the refund flow dependencies" — while the main agent keeps the high-level thread
Phase summariesSummarise before spawning the next phase's agents, and inject that summary into their initial context
State manifestsEach agent exports state to a known location; on resume the coordinator loads the manifest and injects it. This is your crash recovery.
/compactReduces context usage during extended exploration
The trap — reaching for /compact mid-task when the real need is isolation. Compacting loses the precision the implementation phase requires; an Explore subagent keeps the verbose output out of the main thread in the first place.

Human review and confidence calibration

  • Aggregate accuracy masks segment failure. 97% overall can hide one document type or one field performing badly. Analyse accuracy by document type and by field before reducing human review.
  • Stratified random sampling of high-confidence extractions gives you an ongoing error rate and surfaces novel error patterns you were not looking for.
  • Field-level confidence scores are useful once calibrated against a labelled validation set. Uncalibrated self-reported confidence is not a routing signal.
  • Route to humans the low-confidence extractions and those from ambiguous or self-contradictory source documents. Reviewer capacity is the scarce resource; spend it where it changes outcomes.

Provenance through synthesis

Attribution is lost at the summarisation step, when findings are compressed without their claim–source mapping. Require subagents to emit structured claim–source mappings — source URL, document name, the relevant excerpt — and require synthesis to preserve and merge them.

  • Conflicting statistics from credible sources are annotated with their attributions, not silently resolved by picking one. The document analysis agent completes its work with both values included and flagged; the coordinator decides how to reconcile before synthesis.
  • Publication and collection dates belong in the structured output. Without them, a genuine temporal difference reads as a contradiction.
  • Structure the report to separate well-established findings from contested ones, preserving each source's original characterisation and methodological context.
  • Render by content type — financial data as tables, news as prose, technical findings as structured lists. Flattening everything into one format destroys information.

The look-alikes

Every pair below has appeared as two options that read almost identically. The left column is the answer; the right is the plausible one sitting next to it. If you learn nothing else on the morning of the exam, learn this page.

Where the convention lives

Project scope.claude/CLAUDE.md or root CLAUDE.md. Version-controlled. Everyone gets it.
User scope~/.claude/CLAUDE.md. Not shared. One person only.

Stem shape: a new team member does not follow a convention the others do.

Which MCP config file

~/.claude.jsonHome directory, personal and experimental servers.

Rules, memory, or skill

Root CLAUDE.md with headers · per-directory CLAUDE.md · skillsInference, directory-bound, or requires invocation. None gives automatic path-based application.

Personal skill shadowing a project skill

A skill at ~/.claude/skills/commit/SKILL.md overrides the project's .claude/skills/commit/SKILL.md of the same name — which is how you customise for yourself without forking the team's or inventing a new command name.

Hub or mesh

Whose fault is the gap

The coordinator's decompositionAll subagents succeeded, topics are still missing → they were never assigned. Fix the coordinator prompt.

What a failure reports

Structured error contextFailure type + attempted query + partial results + alternatives. Coordinator can choose.
"Search unavailable"Retry or abort, and nothing else. Also: suppressing it as an empty success, or killing the whole workflow.

Timeout or zero results

Access failureA timeout. Retry with backoff, or escalate the decision to the coordinator.
Valid empty resultZero matches. The query worked. This is not an error.

Misrouting between similar tools

Fix the signalExpand the descriptions: inputs, examples, edge cases, boundaries against the neighbouring tool.
Compensate for a bad signalA pre-routing keyword classifier. More few-shot examples. Consolidating the tools.

Prompt instruction"Always call get_customer first" — plus few-shot examples of it. Probabilistic, and money is involved.

The night before

One page. Read it, close the laptop, sleep. If a line here does not immediately unpack into the reasoning behind it, that is the page to reopen — and only that page.

Thirty lines

  1. stop_reason: "tool_use" continues the loop; "end_turn" ends it. Never parse text for either.
  2. Tool results go back into conversation history. That accumulation is how the model reasons forward.
  3. The coordinator is the only hub. Subagents never talk to each other.
  4. Subagents inherit nothing. Put everything they need in the prompt.
  5. allowedTools must include "Task" or the coordinator cannot delegate.
  6. Parallel means several Task calls in one response.
  7. All subagents succeeded but coverage is missing → the decomposition, not the subagents.
  8. Critical sequence → programmatic gate. Prompt wording is probabilistic.
  9. PostToolUse normalises results coming in; interception hooks block actions going out.
  10. Escalation handoff carries customer ID, root cause, amount, recommended action — the human has no transcript.
  11. Stale tool results → fresh session with an injected summary, not --resume.
  12. fork_session branches from a shared baseline to compare approaches.
  13. Tool descriptions are the selection mechanism. Fix them before adding anything.
  14. Errors carry errorCategory, isRetryable, and a readable reason.
  15. Zero results is a success. A timeout is an access failure. Different responses.
  16. 4–5 tools per agent. Eighteen degrades selection.
  17. tool_choice: "auto" may return text, "any" must call something, forced names the tool.
  18. .mcp.json is shared and version-controlled; ~/.claude.json is personal. ${VAR} expands in the former.
  19. MCP resources are catalogs; MCP tools are actions.
  20. Grep looks inside files. Glob matches paths. Edit fails on a non-unique anchor → Read + Write.
  21. Project config is in the repo; anything under ~/ is one person's only.
  22. .claude/rules/ with a paths glob is the only automatic, path-triggered mechanism.
  23. context: fork isolates a skill's output; allowed-tools restricts it; argument-hint prompts for parameters.
  24. Plan mode for architectural, multi-file, multiple-valid-approaches work. Direct execution for a scoped fix.
  25. -p for CI. --output-format json with --json-schema for parseable findings. CLAUDE_HEADLESS and --batch do not exist.
  26. Specific criteria, not "be conservative". False positives in one category poison trust in all of them.
  27. Few-shot examples aimed at the ambiguous cases — 2–4, with the reasoning shown.
  28. Tool use with a schema kills syntax errors, not semantic ones. Nullable fields stop fabrication.
  29. Batch: 50% off, up to 24 hours, no SLA, no mid-request tool calls, custom_id to correlate. Never for blocking work.
  30. The API is stateless. Precise facts live in a case-facts block outside the summary. Key findings go first, because of the middle.

If you are stuck on an item

  1. Name the room. Which of the six scenarios is this, and which domains does it favour?
  2. Re-read the verb. Root cause, first step, or evaluation — they want different answers.
  3. Delete the fictions. Any option resting on a flag or parameter that does not exist is gone.
  4. Delete the over-builds. A classifier, a trained model, or a new infrastructure layer, when a description or prompt fix has not been tried, is rarely the answer to "first step".
  5. Ask where the fault actually is. If the stem tells you every component succeeded, the fault is in what they were asked to do.
  6. Ask whether this needs a guarantee. If money, identity, or policy is involved, prefer the deterministic option over the persuasive one.
  7. Check how many responses the item wants. It tells you. Read it.

Two minutes a question. Mark the genuinely uncertain ones and move; a question you leave half-solved costs you the two easy ones behind it.
