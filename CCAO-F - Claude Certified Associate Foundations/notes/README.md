# notes/

Working notes. One file per official lesson, plus one per Tier-2 product-surface reading block.

## Naming

`L1_Claude-Platform-and-Model-Foundations.md` … `L7_Troubleshooting-and-Optimization.md` for the seven
content lessons. `T2A_Projects-and-Knowledge.md`, `T2B_Plan-Tiers-and-Admin.md`, and so on for the
Help Centre reading.

## How to write them

Notes are raw material for the corpus, so write them in the shape the corpus needs. A note that
summarises a lesson is close to useless; a note that captures a decision is directly convertible.

For every idea worth keeping, record:

- **The decision it governs** — "given X, do Y rather than Z"
- **The discriminator** — the one factor that decides between Y and Z
- **The constraint or limit** that makes it a real answer rather than a preference — a plan tier, a
  cap, a permission, a retention rule
- **The wrong belief it corrects**, written the way someone would actually say it

Anything that does not fit that shape probably belongs in the corpus as background, or nowhere.

## The altitude reminder

This is a no-code exam. When a note starts describing an API parameter, an SDK call, or a terminal
command, it has drifted up a tier and out of scope. The test: could someone who has never opened a
terminal use this note to answer a question? If not, rewrite it or drop it.

Plan-tier and limit facts are worth more here than they were on CCAR-F. "Project instructions are
paid-plan only" is a complete, examinable decision rule. Capture those verbatim with their source.

## Provenance

Every note states its source at the top — lesson name and timestamp, or URL and retrieval date.
Community sources are labelled as such. A note without provenance cannot feed the corpus, because the
corpus can only be generated from verified material.
