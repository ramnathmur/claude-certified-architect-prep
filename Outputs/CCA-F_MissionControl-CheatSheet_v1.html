§1.1

The Agentic Loop

Agent behavior is a sequence of API calls; stop_reason — not response text, not an iteration counter — tells the orchestrator whether to keep going.

  • tool_use → extract tool_use blocks, execute, append tool_result, call Claude again.
  • end_turn → stop the loop, return the final text to the user.
  • max_tokens / stop_sequence → handled per application logic, not silently ignored.
Trap

"What determines when to stop the loop?" → check stop_reason. Parsing text for "I'm done" is the wrong mechanism.

Trap #5 → Docs drift: stop_reason set → Source: D1 §1.1
§1.2

Hub-and-Spoke (Coordinator-Subagent)

One coordinator orchestrates specialized subagents; subagents never talk to each other directly — everything flows back through the hub.

  • Coordinator's allowedTools must include "Task" to spawn subagents at all.
  • Multiple Task calls issued in one coordinator response run in parallel.
  • Subagents have isolated context — they see only what the coordinator explicitly puts in their prompt.
Trap

"Synthesis agent lacks context about what the web-search agent found" → coordinator must pass results explicitly in the subagent's prompt; nothing is inherited automatically.

Trap #6 → Source: D1 §1.2
§1.3

AgentDefinition Configuration

Every subagent type is defined by three levers — description, system prompt, and tool restrictions — that shape what it is, how it behaves, and what it can touch.

  • description tells the orchestration layer what the agent type is for; system_prompt sets behavior; allowed_tools enforces least privilege.
  • A coordinator's config must list "Task" in allowed_tools — without it, delegation is architecturally impossible.
  • Rewriting the system prompt to "instruct it to delegate" cannot grant a tool the configuration withholds.
Trap

"Coordinator never delegates; it attempts everything itself" → check for Task in allowedTools first, not the prompt wording.

Source: D1 §1.3
§1.4

Goal-Oriented vs Procedural Coordinator Prompts

Coordinator prompts should state goals and quality criteria, not step-by-step scripts — the same model-driven-decision principle as the agentic loop (§1.1), applied at the orchestration level.

  • Goal-oriented: state the objective + quality bar (e.g. "≥3 independent sources per claim"); subagents adapt strategy as findings emerge.
  • Procedural: literal step-by-step scripts are brittle and break the moment results don't match the plan.
  • Fix for shallow, checklist-like output = rewrite toward goals — not add more subagents, not add more detailed steps.
Trap

"Research coordinator produces shallow, checklist-like results" → rewrite toward goals/quality criteria. More steps deepens the rigidity that caused it.

Source: D1 §1.4
§1.5

Structured Context Passing & Attribution

Separate content from metadata (source URL, document name, page number) when passing findings between agents — merge them into free text and citation attribution gets lost during aggregation.

  • Pass complete findings from prior agents directly into the next subagent's prompt, not a summary of a summary.
  • Require subagents to emit metadata (dates, sources) as structured fields, not embedded in prose.
  • Conflicting statistics between sources → preserve both with attribution and flag the conflict; never silently pick one.
Trap

"Report has wrong or missing citations" → root cause is content+metadata merged as free text. "Remember to cite sources" as a prompt fix can't cite metadata the agent never received in structured form.

Source: D1 §1.5
§1.6

Task Decomposition

Decomposition is the coordinator's single most critical responsibility — narrow decomposition looks like a subagent failure, but it isn't one.

  • If every subagent executes correctly but coverage is incomplete or wrong-domain, the root cause is the coordinator's decomposition.
  • Coordinator must explicitly partition the research space before delegating — assign distinct subtopics per agent.
  • Two agents investigating the same subtopic wastes tokens without adding depth; fix is partitioning up front, not de-duplicating after.
Trap

Research on "AI's impact on creative industries" that only covers visual art, with every subagent returning correct results → the coordinator decomposed too narrowly. Not a web-search, synthesis, or filter problem.

Trap #7 → Source: D1 §1.6
§1.7

Fixed Pipelines vs Dynamic Adaptive Decomposition

Two named decomposition patterns — pick a fixed sequential pipeline for predictable, templated work; pick dynamic adaptive decomposition when the scope is only discovered along the way.

  • Fixed pipeline / prompt chaining: steps known up front (Document → Metadata extraction → Validation → Enrichment) — use where reproducibility matters, e.g. a review that always follows the same template.
  • Dynamic adaptive: subtasks are generated from intermediate findings — map structure first, prioritize high-impact areas, adapt as dependencies surface.
  • Large PRs (10+ files): split into per-file local passes plus a separate cross-file integration pass — a single pass causes attention dilution and inconsistent comments across files.
Trap

"Add comprehensive tests to a legacy codebase" → dynamic adaptive (map → prioritize → adapt), not a fixed pipeline and not one giant single-pass prompt over everything.

Trap #17 → Source: D1 §1.7
§1.8

Coordinator Iterative Refinement Loop

Synthesis is not one-shot — the coordinator evaluates the synthesis output for gaps, re-delegates targeted queries, and re-invokes synthesis until coverage is sufficient.

  • Gap evaluation and loop termination belong to the coordinator — part of its aggregation-and-validation role (§1.2), not the synthesis agent's job.
  • Re-delegation uses queries targeted at the specific gap, not a broad re-run of everything.
  • The loop needs a defined sufficiency criterion (quality criteria, §1.4) — looping without one is its own failure mode.
Trap

Synthesis has coverage gaps → coordinator re-delegates + re-invokes synthesis. Letting the synthesis agent search the web itself breaks least-privilege tooling (§1.11).

Source: D1 §1.8
§1.9

Error Propagation in Multi-Agent Systems

A failing subagent must return structured error context — failure type, what was attempted, partial results, alternatives — never a generic status, never silence.

  • Transient (timeout, network) → retry with backoff. Permanent (syntax, auth) → don't retry, log and continue. Valid empty (0 results) → accept as a finding.
  • A timeout is an access failure needing a coordinator decision; "0 results" is not a failure at all — distinguish them explicitly.
  • Never catch-and-silently-return-success; never terminate the whole workflow for one subagent's failure.
Trap

"0 results" ≠ failure. It's a valid, informative response — don't conflate it with a timeout that requires a retry decision.

Trap #8 → Trap #9 → Source: D1 §1.9
§1.10

Coverage Annotations (Graceful Degradation)

When upstream inputs are incomplete, synthesize with what's available, annotate which conclusions are well-supported vs gapped, and propagate the uncertainty upward.

  • Complete synthesis using available data → annotate coverage → propagate uncertainty, in that order.
  • "Web search returned 3/5 source categories" → structure the output with coverage annotations; don't return an error, and don't proceed silently as if nothing were missing.
Source: D1 §1.10
§1.11

Least Privilege for Subagent Tools

Each subagent gets only the tools its defined scope needs — "give every agent the full tool set for flexibility" is the opposite of the correct design.

  • Synthesis agent needing to verify mostly-simple facts → give it a narrow verify_fact tool; route complex verification through the coordinator, not full web-search access.
  • Agent misusing a broad tool (e.g. fetch_url for ad-hoc search) → fix at the interface level with a narrower tool (load_document), not a prompt instruction telling it not to misuse it.
Trap

"Give each subagent type the full tool set for flexibility" → wrong. Per-type tool restriction IS the mechanism for least privilege and separation of responsibilities.

Source: D1 §1.11
§1.12

When to Escalate to Human

Four legitimate escalation triggers — an agent should never invent policy to avoid escalating one of them.

  • Policy gap: agent can't determine the correct action within defined policy (e.g., competitor price-matching not covered by own-site rules).
  • Explicit request for a human, or unable to make progress after multiple retries.
  • High-stakes ambiguity: a wrong decision could cause significant harm.
Trap

Competitor price-match request, no policy coverage → escalate. Applying own-site rules by analogy is a wrong interpretation; refusing with an unstated policy is inventing one.

Source: D1 §1.12
§1.13

Structured Handoff Protocols

Escalation is a compiled summary, not just a flag — the human agent has no access to the conversation transcript, so the handoff payload is everything they will ever see.

  • Core fields the exam names: customer ID, root cause analysis, refund/amount, recommended action — plus actions already taken and the escalation reason.
  • Root cause of humans re-asking customers for info the AI already collected = a generic flag or free-text note instead of a structured summary.
  • Giving humans raw transcript access isn't the fix — they lack it by design, and a transcript just forces a full re-read.
Trap

"Human agents keep re-asking for info the AI already collected" → fix with a structured handoff summary; not transcript access, not re-running tools, not escalating earlier.

Source: D1 §1.13
§1.14

Critical Sequencing and Preconditions

When correct order is mandatory (verify identity before acting), enforce it with a programmatic precondition — prompt instructions are probabilistic, code-level gates are deterministic.

  • Support agent skipping get_customer before lookup_order picked the wrong account 15% of the time — fix: block lookup_order in code until identity is verified.
  • Strengthening the system prompt or adding few-shot examples of the right order are both still probabilistic fixes.
  • Rule: for security-critical sequencing, enforce at the code level, not the prompt level.
Trap

"Strengthen the system prompt to always call get_customer first" → still probabilistic. Use a programmatic precondition instead.

Trap #11 → Source: D1 §1.14
§1.15

Parallel Execution

Multiple Task calls emitted in a single coordinator response run in parallel — issuing them across separate turns runs them sequentially instead.

  • Use for independent research tasks, multi-issue customer requests, multi-dimensional analysis.
  • Billing dispute with 3 independent issues (double-billed + discount + cancellation) → decompose into 3 parallel investigations with shared customer context, then synthesize.
  • Sequential investigation of independent issues means a higher tool-call count and redundant data fetching for no benefit.
Source: D1 §1.15
§1.16

Session Management: Resume, Fork, Fresh Start

Three session-continuity tools for three different situations: --resume when context is still valid, fork_session to compare approaches from one shared baseline, and a fresh session with an injected summary when prior tool results have gone stale.

  • --resume <session-name> continues a saved conversation; risk is stale tool results if files changed since.
  • fork_session branches inherit context up to the fork point, then diverge — compares two approaches without re-running the same expensive analysis twice or letting the explorations contaminate each other.
  • If you do resume after code changes, name exactly which files changed for targeted re-analysis — don't trust stale results and don't re-explore the whole codebase.
Trap

"Three files were refactored since yesterday's session" → resume + explicitly name the changed files; don't resume blindly, don't restart from scratch.

Source: D1 §1.16
§1.17

Independent Review Instances

A generator can't reliably self-check its own reasoning — run a second, independent instance with no visibility into the first instance's reasoning to catch what confirmation bias rationalized away.

  • Mirrors human peer review: a fresh perspective catches non-obvious bugs the generating instance talked itself past.
  • Extended thinking on the generation stage doesn't fix this — it's still the same instance checking its own work.
  • Self-review instructions added to the generation prompt are still one instance, same confirmation bias.
Trap

Claude Code reasons through edge cases, concludes its approach is correct, but a non-obvious bug still ships → fix is a second independent reviewing instance, not more self-review.

Source: D1 §1.17

§2.1

Tool Use Loop & tool_choice Basics

Claude requests a tool call via a structured block; the application executes it and hands the result back — this loop is the mechanical backbone of every agentic turn.

  • Define tools with name, description, input_schema (JSON Schema); the app executes the call, then appends a tool_result block so Claude can continue.
  • The tool_use block carries id, name, input — the id is what matches the eventual tool_result back to this exact call.
  • tool_choice: {"type":"auto"} (default, Claude may skip) / {"type":"any"} (must call something) / {"type":"tool","name":"X"} (must call X) — configuration depth in §2.5.
Trap #5 → Source: D2 §2.1
§2.2

Tool Descriptions Are the Selection Signal

Descriptions are the primary input Claude uses to pick a tool — when routing goes wrong, fix the description before reaching for infrastructure.

  • A good description states: what it does, what input it accepts, when to use it vs similar tools, and when NOT to use it.
  • Near-identical tools (analyze_content vs analyze_document) caused ~45% misrouting — the fix was renaming + clarifying scope, not adding a classifier.
  • Merging two ambiguous tools into one (lookup_entity) is the wrong move — it loses the semantic precision that would fix the routing.
Trap

Misrouting → adding a pre-routing classifier compensates for a bad signal instead of fixing it. Fix descriptions first, always.

Trap #10 → Source: D2 §2.2
§2.3

Four Error Categories & the isError Flag

MCP tools signal failure via isError, but the exam expects the agent's response to depend on WHICH category of error it is — not just that one occurred.

  • Transient (retry, ideally inside the tool first) · Validation (fix input, re-call) · Business (never retry — explain the policy outcome) · Permission (escalate — retry is wasted effort).
  • A business-rule denial (refund outside the policy window) is a valid answer, not a tool failure — return retriable: false + a customer-friendly explanation, never a generic "Operation failed".
  • Empty results are a SUCCESS (isError absent/false); a query that could not run is the real error — conflating the two corrupts agent decisions in both directions.
Trap

Returning isError: true for zero matches makes the agent retry a query that already worked; returning an empty list when the DB is down makes it report false data.

Trap #8 → Trap #9 → Source: D2 §2.3
§2.4

Two-Tool Token-Binding for Mandatory Preview

When a destructive action must always be previewed first, split it into two tools bound by a single-use token — architecturally enforced, not merely instructed.

  • preview_remove_member returns impact details + a single-use confirmation token; execute_remove_member requires that token as a parameter.
  • Beats a single tool with a dry_run: boolean param — the agent can just bypass it by calling with dry_run=false directly.
  • Also beats server-side timing heuristics (fragile), orchestration-layer confirmation prompts (extra infra), and prompt instructions (probabilistic, not guaranteed).
Trap #12 → Trap #11 → Source: D2 §2.4
§2.5

Tool Count, Least Privilege & tool_choice Depth

Fewer, role-scoped tools improve selection reliability; tool_choice can guarantee structured output or force a specific first step.

  • Official numbers: 18 tools vs 4–5 degrades selection reliability — restrict each subagent to the 4–5 tools its role needs; more detailed descriptions alone don't fix a decision space that's too large.
  • Least privilege: replace an overly generic tool (fetch_url) with a constrained one (load_document) — enforced at the interface, not by a prompt rule.
  • Sanctioned exception: a narrowly scoped cross-role tool (verify_fact) for high-frequency needs — complex cases still route through the coordinator.
  • Forced-first-step pattern: {"type":"tool","name":"extract_metadata"} on turn 1, then relax to "auto"/"any" for later turns — forcing it on every turn locks out the other tools entirely.
Trap #11 → Docs drift → Source: D2 §2.5
§2.6

MCP Primitives, Config Scope & Resources-as-Catalogs

MCP exposes tools, resources, and prompts; config file location decides who shares your server setup, and resources can save exploratory tool calls entirely.

  • Three primitives: Tools (actions, like API endpoints), Resources (read-only data, like files/DBs), Prompts (reusable templates) — all servers' tools are discovered at connection time.
  • .mcp.json (project root) = shared, version-controlled team config; ~/.claude.json (user home) = personal overrides/auth — use ${VAR_NAME} substitution to keep credentials out of the repo.
  • MCP Resources act as content catalogs (an issue summary, a schema) — giving the agent a map of what exists WITHOUT burning tool calls on exploratory guessing.
  • Prefer existing community servers for standard integrations (Jira, GitHub, Slack); build custom servers only for unique, team-specific workflows.
Trap

A more capable MCP tool (semantic code search) still loses to a familiar built-in (Grep) if its description doesn't spell out the advantage — fix the description, don't remove the built-in.

§2.7

Hooks — Deterministic Control Around Tool Calls

Hooks are code, not prompts — they fire before/after tool execution regardless of what the LLM decides, which is exactly why they're the right layer for anything safety-critical.

  • PreToolUse fires before the tool executes — validate, block, or modify params (e.g., block a bulk delete affecting >50 records and route to escalation).
  • PostToolUse fires after the tool returns — primary use is centrally normalizing inconsistent output formats (Unix timestamps, ISO dates, numeric codes) from sources you don't control.
  • Hooks are deterministic; system-prompt instructions are probabilistic — for safety-critical enforcement, use a hook, not a prompt rule.
Trap #11 → Source: D2 §2.7
§2.8

Prefer Prompted Bundling Over Composite Tools

When an agent calls two tools sequentially across separate turns, the preferred fix is prompting it to bundle both requests into one turn — not building a new composite tool.

  • Composite tools (e.g., get_customer_with_orders) hide the composition and add a new tool to maintain.
  • Exam-preferred fix: instruct Claude to bundle related tool requests into a single turn — the model can naturally request multiple tools at once.
Source: D2 §2.8
§2.9

Built-in Tool Selection: Grep, Glob, Edit, Read/Write

The built-in tools split cleanly by job — content search vs path matching, targeted edits vs full rewrites — and codebase investigation should build understanding incrementally, never via bulk upfront reads.

  • Grep = content search (function names, error strings, call sites); Glob = file-path pattern matching (**/*.test.tsx) — "find callers of X" is Grep, "enumerate test files" is Glob.
  • Edit requires a UNIQUE text anchor; if the anchor matches more than once, Edit fails — the sanctioned fallback is Read (full file) → modify → Write (full file), never a shorter anchor or Bash sed.
  • Incremental investigation: Grep entry points → Read files → Grep usages → Read consumers → repeat. Reading the whole repo upfront "for full context" is the exam's named anti-pattern.
  • Renamed/wrapped functions need every export alias identified first (Grep/Read the wrapper modules), then Grep each alias — Grepping only the original name misses wrapper call sites.
Trap

A non-unique Edit anchor should be fixed with Read+Write, not a shorter anchor — shorter strings are MORE likely to be non-unique, not less.

§3.1

CLAUDE.md Hierarchy & Memory Diagnosis

Four levels of memory files load together into context, root to working directory — they don't override each other, they stack.

  • Levels: User ~/.claude/CLAUDE.md → Project → Directory → .claude/rules/*.md (path-scoped)
  • Concatenated load order — every discovered file's instructions reach Claude; conflicts are resolved by editing files, not by one level "winning"
  • @path imports keep CLAUDE.md modular (no space before path, max nesting depth 5)
  • /memory lists loaded files — first diagnostic step when a rule "works on one machine but not another"
Trap

"Lower levels override higher levels — a directory-level CLAUDE.md replaces the project-level one" is wrong. There is no documented override-precedence mechanism between levels; they concatenate.

Trap #1 → Docs drift D4 → Source: D3 §3.1
§3.2

.claude/rules/ — Path-Scoped Conditional Rules

Rules auto-load only when Claude touches files matching their glob, keeping irrelevant conventions out of context.

  • YAML frontmatter paths: lists glob patterns (e.g. **/*.test.tsx)
  • Use for conventions scoped to file type/directory (hooks in components, async/await in API handlers) — deterministic path matching, not model inference
  • vs. CLAUDE.md (always-on, every session) and Skills (on-demand, workflow-specific)
Trap

Root CLAUDE.md organized under headings relies on model inference, not deterministic file-path matching — wrong tool for "different convention per directory."

Trap #3 → Source: D3 §3.2
§3.3

Skills — allowed-tools & context: fork

SKILL.md frontmatter is where you scope what a skill may do, and can isolate a skill's exploration output into its own subagent context.

  • description shows in the slash-command menu; argument-hint prompts for required args
  • allowed-tools is the SKILL.md frontmatter key that scopes tool access for the skill (e.g. [Write, Read])
  • context: fork runs the skill in an isolated subagent context — large output or rejected alternatives never pollute the main session
Trap

Official exam framing: allowed-tools restricts tool access during skill execution. Current product docs instead frame it as a permission pre-grant (unlisted tools just fall back to a normal prompt). Answer the exam per the official framing — restriction.

Docs drift D1 → Trap #13 → Source: D3 §3.3
§3.4

Custom Slash Commands — .claude/commands/

File location decides who gets the command — repo-level is shared with the team, home-level is personal only.

  • Project-wide (all teammates): .claude/commands/ in the repo, version-controlled
  • Personal (just you): ~/.claude/commands/, not shared via VCS
  • $ARGUMENTS holds the text typed after the command name
  • Legacy .claude/commands/ and current .claude/skills/ are unified — both create /name commands

§3.5

Personal vs Project Skill Precedence

A personal skill silently overrides a project skill of the same name — the one documented precedence exception in the whole memory/skills system.

  • ~/.claude/skills/commit/SKILL.md overrides .claude/skills/commit/SKILL.md when names match
  • Correct way to customize /commit privately: same name, personal location — not a renamed command like /my-commit

§3.6

Planning Mode vs Direct Execution

Match execution mode to task scope — plan first for architectural ambiguity, execute directly when the approach is already clear.

  • Planning mode: read-only exploration (Read/Grep/Glob), presents a plan before any side effects — for large scope, multiple valid approaches, changes across many files
  • Direct execution: implement immediately — well-defined spec, routine change, single-file fix with a clear stack trace
  • Combined approach: plan → user approves → direct execution
Trap

"Start in direct execution and switch to planning when it gets hard" is wrong — reactive switching is expensive. Plan upfront when the task demands it.

Source: D3 §3.6
§3.7

Iterative Refinement — Four Convergence Techniques

Four named techniques converge on correct output faster than blind re-prompting (official Task 3.5).

  • Interview pattern: let Claude ask clarifying questions before implementing — one interview turn beats several correction cycles on underspecified tasks
  • Test-driven iteration: write tests first as an objective, machine-checkable "done" — feed concrete failures, not prose bug reports
  • 2–3 concrete input/output examples anchor an ambiguous transformation better than more adjectives in the prose
  • Batch interacting/interdependent fixes into one message; keep independent fixes sequential, one at a time
Trap

"Always report one issue per message" is wrong when issues interact — e.g. a locking fix and a retry fix that depends on it belong in one detailed message, or the separate patches can conflict.

Trap #16 → Source: D3 §3.7
§3.8

CI/CD Integration — Non-Interactive Mode

Claude Code needs an explicit flag to run non-interactively in a pipeline, plus the prior run's findings fed back in to stay consistent across re-reviews.

  • claude -p "..." (or --print) processes the prompt, prints to stdout, exits — without it Claude waits for input and the pipeline hangs

Fix the Descriptions First

Tool misrouting's root cause is usually descriptions that don't distinguish similar tools — fix the signal before adding machinery to compensate for it.

Exam trap

Rule: fix the signal (the description) before adding a new layer that compensates for the bad signal.

Key Distinction #10
#11

Prompt Instructions vs Programmatic Preconditions

Prompt Instruction Only

"Always call get_customer first" is probabilistic — the LLM may not follow it. Fine for general guidance, not for anything safety- or security-critical.

Programmatic Precondition

Block lookup_order in code until get_customer has succeeded — deterministic, code-enforced, and the right call when sequencing is safety- or security-critical.

Exam trap

Reliability is the decisive axis: a prompt instruction is a request the model can ignore; a programmatic precondition is a guarantee the code enforces. Critical sequencing needs the guarantee.

Key Distinction #11
#12

Two-Tool Token-Binding vs dry_run Boolean Parameter

Single Tool, dry_run: bool

The agent can simply call the tool with dry_run=false directly — skipping the preview is architecturally possible, so mandatory preview is only a prompt-level hope.

Two-Tool Token-Binding

No execution token exists without a completed preview call — skipping the preview is architecturally impossible, a code-level guarantee.

Exam trap

When a preview step must be mandatory, only the two-tool token-binding design makes skipping it impossible. A dry_run boolean just makes skipping it inadvisable.

Key Distinction #12
#13

context: fork in Skills vs Running in the Main Session

Main Session

Output is stored directly in the main conversation — large output or rejected alternatives bleed into every subsequent turn.

context: fork

Output is isolated in a subagent context — isolation prevents contamination, leaving nothing to bleed into subsequent turns.

Exam trap

Use context: fork for discovery, analysis, exploration, and brainstorming; keep implementation, design, and conversation in the main session where continuity matters.

Key Distinction #13

API and Integration

#14

Message Batches API vs Synchronous API

Batches API (tempting for cost)

50% cost savings, but fire-and-forget with up to 24-hour latency and no SLA — it cannot execute a tool mid-request and return the result to Claude.

Synchronous API (required here)

Standard cost, immediate latency, and full support for multi-turn tool calls — the only option when a task calls tools mid-flow.

Exam trap

An iterative code review that fetches related files mid-review via tool calls cannot use the Batches API — batch is fire-and-forget and cannot execute tools and return results to Claude within the same request.

-p / --print Flag vs Other Approaches for CI/CD

-p / --print

CLAUDE_HEADLESS=true

Does not exist — a fabricated environment variable, not a real flag.

Prompt Engineering

#16

Few-Shot Examples vs Instruction Refinement for Format Consistency

More Detailed Instructions

Already failing — adding more explicit text to instructions that aren't working doesn't fix inconsistent output format.

Few-Shot Examples

Showing the exact required format gives the model a concrete pattern to match, rather than more prose to interpret.

Exam trap

When instructions alone produce inconsistent output format, the fix is a concrete example of the target format — not a longer, more detailed version of the same instructions that were already failing.

Key Distinction #16
#17

Per-File Review Passes vs Single-Pass Full-PR Review

Single-Pass, All Files

Attention is diluted across every file — some get shallow review, some deep, and it's inconsistent which is which.

Per-File + Integration Pass

High, consistent attention quality per file, with a separate pass for cross-file issues — correct for large PRs.

Exam trap

"Use a larger model with a bigger context window" is wrong. A bigger context window doesn't fix attention quality — more tokens available doesn't mean consistent attention per token.

Key Distinction #17
#18

Targeted Ambiguous Examples vs Generic Examples for Misrouting

10-15 Generic Examples

Clear, unambiguous requests for each tool — doesn't address the ambiguous edge cases actually causing the misrouting.

4-6 Targeted Examples

Examples aimed at the specific ambiguous cases where misrouting occurs, each with rationale for the correct choice.

Exam trap

Volume doesn't fix misrouting — relevance does. Examples must target the exact ambiguous cases, not pad out coverage of cases that were never confused in the first place.

Key Distinction #18
#19

State Explicit Assumptions vs Ask Multiple Clarifying Questions

Ask 4+ Clarifying Questions

Causes a 35-40% abandonment rate — users leave before the task even starts.

State Assumptions, Invite Correction

Proceed with stated reasonable assumptions and invite corrections — eliminates abandonment while staying transparent.

Exam trap

Hidden defaults are a third, silent failure mode: using unstated defaults instead of asking leaves the user confused when the response doesn't match their intent. Only stating the assumption out loud solves both abandonment and confusion.

Key Distinction #19

Context Management

#20

"Lost in the Middle" Mitigation

Rotate Agent Output Order

Rotating which agent's output appears first doesn't fix the underlying attention pattern — it just moves which content gets deprioritized.

Key-Findings Summary + Headings

A key-findings summary at the start plus explicit section headings gives the model anchor points regardless of position.

Exam trap

Summarizing everything down to under 20K tokens is also wrong — that trades the middle-attention problem for a new one: losing critical information outright.

Key Distinction #20
#21

Persistent Case-Facts Block vs Summarization Improvements

Improve the Summarization Prompt

Still relies on perfect execution every single turn — one slip and a precise number is gone for good.

Persistent Case-Facts Block

Extract transactional facts into a block that lives outside the summarized history — it survives compression entirely.

Exam trap

Increasing the summarization threshold only buys time — it doesn't fix the fundamental precision loss, it just delays when it happens.

Key Distinction #21
#22

Subagent Isolation for Discovery vs Main-Session Discovery

/compact Mid-Task

Compacts the main session mid-task, but loses the precision needed for the implementation phase that follows.

Explore Subagent

Isolates verbose discovery output in a subagent context and returns only a concise summary to the main session.

Exam trap

Verbose discovery that would exhaust main context belongs in an isolated subagent — not compressed in place, where precision loss compounds into the next phase.

Key Distinction #22
#23

Behavioral Drift: Accumulated Responses vs Context Window Overflow

Context Window Overflow

Tempting explanation for degrading behavior — but impossible at 2,500 tokens, nowhere near any context limit.

Accumulated Assistant Responses

Across turns, accumulated assistant responses dilute the system prompt's relative influence on the conversation — the real root cause even at low token counts.

Exam trap

A third false explanation to rule out: "the system prompt only applies to the first turn" — false, it's included in every request. The real cause is dilution by volume, not scope.

Key Distinction #23
#24

Semantic Retrieval vs Progressive Summarization for Long-Term Recall

Progressive Summarization

Compresses specific conclusions into abstractions — by the time you need the detail back, it can no longer be recalled precisely.

Semantic Embeddings + Retrieval

Retrieves the relevant exchanges themselves from months of history — preserves the specific detail instead of compressing it away.

Exam trap

For specific recall from very long histories (think 85K tokens of conversation), retrieval beats summarization precisely because summarization is lossy by design.

Stateless API Memory Pattern

Claude Needs a session_id

False — the API is stateless. There's no server-side session for Claude to attach memory to.

The App Manages messages[]

Claude "remembers" prior conversation only because the application includes prior messages in the messages[] array on every request.

Exam trap

A second exam trap: "Claude needs a vector database to maintain conversation memory" is also false. Simple multi-turn memory is just the messages[] array — vector databases are for retrieval over long histories (months), not standard conversations.

Built-in Tools

#26

Grep (Content Search) vs Glob (Path Pattern Match)

Glob for Content

Matches file *names* only — **/formatDate* only finds files literally named formatDate, not files that merely call it.

Grep for Content

Searches *inside* files — the right tool to find every file that references a function, error string, or import, regardless of filename.

Exam trap

Locate every file that references a deprecated formatDate function → Grep for formatDate (the target is file content). Conversely, grepping for the word "test" to find test files matches unrelated files and misses test files with no literal word match — that's a Glob job (**/*.test.tsx).

#27

Retry Edit with a Shorter Anchor

Shorter strings are *more* likely to be non-unique, not less — this makes the ambiguity worse, not better.

Fall Back to Read + Write

Load the full file, modify it, write the full file back — reliable when no unique anchor exists for a targeted Edit.

Exam trap

Edit fails because its anchor isn't unique. The sanctioned fallback is Read + Write, not forcing it with Bash sed — that bypasses the tool designed for the job.

Incremental Investigation (Grep → Read) vs Bulk Read Upfront

Read Every File First

Burns context window on files that turn out irrelevant, chasing "full context" before knowing what's actually relevant.

Grep → Read, Incrementally

Content search locates entry points; targeted reads then follow imports and flows — context window spent only on what matters.

Exam trap

"Read every file first to get full context" is wrong — start with Grep to find entry points, then Read to trace. Globbing the whole tree and Reading every match before searching is the *same* anti-pattern: discovery should be content-search-driven, not exhaustive upfront reading.

Breaks legitimate content-search cases entirely — and the root cause was never that the built-in exists.

A blunt "always prefer MCP tools" system-prompt rule is also wrong — it's keyword-sensitive and misroutes cases where the built-in genuinely is right.
