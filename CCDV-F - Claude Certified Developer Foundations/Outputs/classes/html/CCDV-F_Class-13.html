    Who Is Waiting?

    One question decides between the synchronous API and the Batches API, and it isn't about volume. It's about whether a human is sitting there. If nobody is, speed is something you are paying for and not using — and this is the shape of the exam's own first sample question.

    What you leave holding
    1. Latency tolerance is the axis. Volume is not.
    2. Batch: submit, get an id, poll, download. Lower per-token cost, up to 24 hours.
    3. Batch latency is non-deterministic — often much faster, never promised.
    4. Reaching for batch in a user-facing flow passes tests and fails in production.
    5. Claude through a cloud vendor is the same model on a different control plane.

    01 · The discriminator

    The axis is who is waiting

    By the end of this screen you'll classify any workload in one question, and know why volume is a decoy.

    People reach for batch because a job is big. Volume is not the criterion. A thousand requests that a user is waiting on is still synchronous work; one overnight job of forty requests is still batch-shaped.

    Ask who is waiting for the answer. If it's a person, right now, you need it now. If it's a dashboard somebody opens tomorrow morning, you don't — and paying for speed you don't use is the whole of the mistake.

    Use casePatternWhy
    A user uploads a photo and expects an immediate classificationSynchronousReal-time response required. Batch latency is unacceptable for interactive use
    A nightly pipeline classifies 5,000 customer recordsBatchLatency is not a constraint. Both the cost reduction and the asynchronous processing are valuable
    An evaluation run tests a new prompt against 2,000 examplesBatchOffline task, no real-time requirement
    A chatbot replies to a user's messageSynchronousThe user is waiting; batch would introduce unacceptable delay

    Notice rows two and three are the same shape wearing different clothes — and that your own eval runs are textbook batch work. Running 2,000 eval cases synchronously is a habit that costs money for nothing, every time you tune a prompt.

    02 · Mechanics

    What the Batches API actually does

    By the end of this screen you'll know the shape of the contract, including the part that is deliberately not a promise.

    You submit a set of requests in one call, receive a batch_id, poll for completion, and download the results when it finishes.

    And it solves a real problem beyond cost. At scale, firing synchronous calls means your application is either burning threads or holding thousands of concurrent connections against rate limits. Batch removes that entirely — you hand over the work and stop holding anything open.

    The failure mode that passes every test

    Reaching for batch in a user-facing flow produces a system that passes tests and fails in production, because in testing you were the only user and you weren't really waiting. The user is, and the batch isn't.

    03 · Other front doors

    Claude through a third-party vendor

    By the end of this screen you'll know what changes and what doesn't when Claude is reached through a cloud provider — and what you must check rather than assume.

    Claude is also available through cloud vendors' own platforms rather than direct from Anthropic. Organisations choose that route for reasons that have nothing to do with the model: existing contracts and committed spend, data-residency requirements, a security review already completed for that provider, or simply a rule that all vendors go through one procurement path.

    The model is the same. The control plane is different — authentication, billing, region selection, quotas, and which platform features are available.

    That last item is the one that bites, and I want to be precise rather than confident here, because it moves. A concrete instance from the material we've already covered: the Files API is not available on Bedrock or Vertex. So the multimodal reuse pattern from Class 12 — upload once, reference a file_id thereafter — is simply not on the table there, and a design that assumed it has to fall back to inline payloads with the request-size cost that implies.

    The habit, rather than a list

    Feature parity between the direct API and vendor-hosted deployments is not guaranteed and changes over time. So the discipline is to verify availability for your deployment platform at build time, for every platform feature your design leans on — rather than learning which ones are missing during integration. I'm not giving you a list to memorise here, because a list is precisely the thing that would be wrong by the time you sat the exam.

    What carries over unchanged: the Messages API shape, prompting, tools, the context window, and every principle in this course. What you check: auth, region, quotas, and feature availability.

    Recap

    What you're leaving with

    1. Who is waiting decides it. Volume is a decoy.
    2. Batch: submit, id, poll, download. Up to 100,000 requests or 256 MB.
    3. Up to 24 hours, non-deterministic. "Often faster" is not a guarantee you can design against.
    4. Batch also removes thread and connection pressure, not only cost.
    5. Vendor-hosted Claude is the same model, a different control plane. Verify feature availability; don't assume parity.
    Before Class 14

    A compliance team needs 40,000 archived contracts summarised. Results feed a quarterly report due in three weeks. The lead has written a spec calling for the synchronous API with a worker pool, "because batch could take up to 24 hours and we need to be able to show progress to the steering committee."

    Is the reasoning sound? What would you say?

    The constraint is real and the conclusion doesn't follow. The report is due in three weeks and nobody is waiting on any individual summary — that is batch's shape exactly, and 24 hours against a three-week deadline is not a latency problem.

    The actual requirement hiding in that sentence is progress visibility, which is a different thing from latency, and it has a cheaper answer than rebuilding the whole job synchronously. Split the work into several batches and report completion per batch — you get a progress figure for the steering committee and keep the per-token discount.

    And the worker-pool version costs more than it looks: full synchronous pricing, plus thread and connection pressure against rate limits, plus a retry and resume story you now own. This is the distractor family worth recognising — a legitimate technique, proposed for a stated reason that turns out to be a requirement in disguise.
