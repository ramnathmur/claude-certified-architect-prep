    Nothing Is Holding an Object Open for You

    When you stream a response, nobody hands you a message. You get a series of small notes, each describing one change, and you are the one who has to build the message out of them. Do that carelessly and the request that breaks is not the one you got wrong — it's the next one.

    01 · Events, not an object

    Somebody is reading you an address

    By the end of this screen you'll know what job streaming actually hands to your code, and it's a bigger one than "show it sooner."

    Put the API down for a minute. Somebody rings you to give you a delivery address, and the line is bad.

    You don't get an address. You get pieces of one. "Forty-two…" then a crackle, then "…Bridgewater…", then a second of nothing, then "…Road." You're writing it down as it arrives.

    Now, you already know how to do this, and you do it without thinking. You don't send the courier out after "Forty-two." You wait for the person to say that's the whole address. And you wait not because you're being careful, but because "Forty-two" isn't a short address. It isn't an address at all. It's a piece of one, and a piece of an address will send a van to a street that doesn't exist.

    That phone call is streaming. Every property that makes it awkward is a property of a streamed response, and the awkwardness is not a flaw in the design — it's the cost of hearing the first word before the last one has been spoken.

    Here's the mapping, and it's exact. The person talking is the model. The crackly line is the stream. Each burst of sound is an event. The pad you're writing on is the partial state your handler is holding. And "that's the whole address" is a specific event with a name, which we'll get to in a moment.

    So what changes when you turn streaming on? In a normal request, the API hands you one finished message with every content block complete. In a streamed request, it sends you a running commentary on a message while it is being built, and your code listens and reassembles.

    The message you end up holding is identical either way. Same blocks, same text, same tool calls. What you've taken on is the assembly — and, more importantly, the judgement about what to do if the commentary stops halfway.

    Said the other way round, because this is the part that trips people: the model is not holding an object open at the far end that you are reading from. There's no live handle, nothing to poll, nothing that stays open. Each event is its own small message, complete in itself, describing one change. Your handler applies it to the pad and waits for the next one.

    There are six events. Once you've read the phone call above, the table is mostly confirmation of what you'd guess.

    EventWhat it signalsWhat your handler does
    message_startA new message begins — the shell, empty content, initial usageSet up an empty content array to collect blocks in
    content_block_startA block opens, with its type (text, tool_use, thinking) and indexMake a slot at that index. A tool_use block opens with a name and id but no input yet
    content_block_deltaAn incremental piece of one block — a text fragment, a fragment of tool JSON, a thinking fragmentAppend to the block at that index. Tool inputs arrive as partial JSON spread across deltas
    content_block_stopThat block is completeFinalise it. For tool_use, this is the first moment the JSON is complete enough to parse
    message_deltaTop-level changes — the stop_reason and final usageRecord the stop reason. It tells you whether the model finished or stopped for another reason
    message_stopThe stream is completeThe assembled array is now the finished message. Treat it exactly like a non-streamed response

    content_block_stop is "that's the whole address." message_stop is "that's the whole call, goodbye." You need both, and they mean different things.

    02 · The thing itself

    One stream, printed out

    By the end of this screen you'll have seen the six events in the order they actually arrive, and watched a tool's arguments assemble themselves out of nothing.

    This is one real exchange. Claude says a sentence, then calls a tool that reads a file. Two content blocks, so you'll see the block events twice — once at index 0 for the text, once at index 1 for the tool call. I've trimmed the long ids and left everything structural intact.

    Read the right-hand column. That's the accumulator — your pad by the phone. Look at what's on it after the second delta: {"path": "src/ma. That is not "most of" a JSON object. Hand it to a JSON parser and it throws, because a string was opened and never closed and an object was opened and never closed. There is no partial credit.

    Walk the middle of that listing once more, because it's the whole class. At content_block_start for index 1, you learn a tool is coming and you learn its name — read_file — and its input is an empty object. The model has committed to calling the tool and has not yet said what to call it with.

    Then three deltas dribble in the arguments as text. Not as JSON — as fragments of a string that will eventually be JSON. And only when content_block_stop lands at index 1 is the accumulated string a complete, parseable object.

    Notice also that the two blocks don't interleave. Index 0 opens, fills, and closes before index 1 opens. The block events nest inside the message events, and they nest cleanly.

    03 · The rule

    Don't act on half a block

    By the end of this screen you'll know which block corrupts state, and you'll have committed to an answer about what happens when you jump the gun.

    The rule is the courier rule. Don't send the van until somebody says that's the whole address. In the API: don't parse, and don't run, a tool_use block until content_block_stop has arrived for its index.

    Text blocks are forgiving about this. If you paint a half-finished sentence on a screen, the rest arrives a moment later and the user sees it appear. That's the entire point of streaming and it costs you nothing.

    tool_use blocks are not forgiving, and the reason is the one you saw on the pad: the input is a string being built toward valid JSON, and it is invalid at every moment except the last one. Parse it early and you get one of two outcomes. Either the parser throws, which is the lucky case because you find out immediately. Or — and this is the one that hurts — the fragment happens to close cleanly and you run the tool with some of the arguments missing.

    The bottom two lines of that figure are a second rule, one level up, and they're where the rest of this class lives. Blocks go on the pad; turns go in the history. And the discipline is the same at both levels: nothing gets committed until the event that says it's finished.

    Predict before you turn the page

    Your handler has a bug: it appends the assistant turn to conversation history as soon as it sees content_block_stop for the last block it happens to have received — rather than waiting for message_stop. On a clean network, every stream completes normally.

    Does this bug ever show up in production, and if so, when?

    Yes, and only when a stream is cut short. On a clean network the last content_block_stop is immediately followed by message_delta and message_stop, so committing early and committing correctly happen a few milliseconds apart and look identical.

    Cut the connection between the last content_block_stop and message_stop and the two stop being the same thing. The handler commits a turn that the model never finished — and worse, it commits one where a later block may have been half-built or entirely absent.

    Which is why the bug is invisible in testing. It needs a network failure inside a window a few milliseconds wide. It will find that window in production, because production runs the request a great many more times than your test suite does.

    04 · The pairing rule

    Why the bill arrives late

    By the end of this screen you'll be able to state the invariant that rejects a corrupt history, and to say which request the error will land on.

    Back to the phone for one more moment, because the analogy has one more thing to give.

    Suppose the line drops mid-address and you file "42 Bridgewater" in the address book anyway. Nothing goes wrong. The call is over, you hang up, the day ends fine. The failure happens tomorrow, when a courier pulls the book, reads an address that was never finished, and drives to a road that doesn't exist. And when the depot investigates tomorrow's failed delivery, everything about tomorrow looks correct. The van was fine, the driver was fine, the manifest was fine. The fault was written into the book a day earlier by somebody who has gone home.

    That is precisely the shape of the streaming bug, and it's the reason it's hard to trace.

    Here's the mechanism. Conversation history is not a free-form log — it has a structural rule that the API checks on every request:

    The tool pairing invariant

    Every tool_use block in an assistant turn must be answered by a tool_result block carrying the same id, in the immediately following user turn. One for one, ids matching, nothing in between. A tool_use with no partner, or a tool_result answering an id that was never issued, makes the whole request invalid.

    Now put the two together. A half-built tool_use block gets committed into history. Your code never ran that tool — it couldn't, the arguments were incomplete — so it never produced a tool_result to pair with it. The history now holds an assistant turn with an unanswered tool_use.

    That history is fine sitting on disk. It only becomes a problem when you send it, which happens on the next request. The API validates the turns you've supplied, finds the unpartnered block, and rejects the call.

    So when you meet this in the wild, the symptom reads like nonsense: a request fails, you inspect it, it looks perfect, you re-run it and it works. Everything about the failing request is innocent, because the failing request is innocent. It's carrying somebody else's mistake.

    And one clue points straight at the cause if you know to look for it. The failures will correlate with network conditions rather than with prompt content — intermittent, worse on bad connections, indifferent to what you asked. Prompt bugs don't care about the network. This one is made of nothing else.

    Work the invariant

    An assistant turn comes back with two tool_use blocks — toolu_01A and toolu_01B. Your code runs the first tool successfully. The second tool throws an exception inside your own code before producing anything.

    You still want to continue the conversation. What must the next user turn contain, exactly?

    Two tool_result blocks — one for toolu_01A and one for toolu_01B. The invariant counts blocks and matches ids; it does not ask whether your tool succeeded.

    So the failed one still gets a tool_result carrying id toolu_01B, with the error described in its content and its error flag set. That's the designed path: an error is a result. Reporting the failure back is what lets the model recover, apologise, or try a different approach.

    The tempting wrong answers are both structural. Dropping the second block leaves a tool_use unpartnered and the request is rejected. Dropping the whole turn throws away a successful tool call for no reason. And note what this buys you conceptually — a tool that fails and a tool that succeeds occupy the same slot in the structure, which is why "the tool errored" is something the model can be told rather than something that breaks the conversation.

    05 · Interruption

    When the line drops

    By the end of this screen you'll know why keeping what you collected is the damaging move, and what to do instead.

    Streams end early. A dropped connection, a timeout, a client that navigates away — any of these can stop the events before message_stop arrives. This is normal. It is not an exceptional condition you can design away, and code that assumes streams always complete is code that works until it doesn't.

    The instinct when a stream cuts out is to keep what you've got. You have most of a response sitting there; throwing it away feels wasteful. That instinct is the bug. It's the one that files "42 Bridgewater" in the book.

    Be precise about which half of the damage matters, because the two cases are not equally bad:

    • A partial text block shown to a user is cosmetic. The sentence stops mid-word, it looks untidy, and nothing downstream is harmed. Survivable.
    • A partial tool_use block written into history is structural. It corrupts the next turn by the mechanism you just worked through, and it does so silently.

    So the discipline splits along that line. Display whatever you have — that's what the user already saw arriving. Commit nothing.

    Three habits

    Track completion on purpose. A turn is usable only once message_stop has arrived. Until then, what you've accumulated is provisional, and your code should be able to say which of the two it's holding.

    On an interruption, discard the partial turn and retry the original request. Not repair it, not salvage the good blocks — discard it. A turn assembled from a cut stream has no guarantee of being structurally complete, and you cannot tell by looking.

    Check stop_reason before continuing a loop. tool_use means your assembled calls are ready to run. Any other value means you're on a different path — the model finished its turn, or hit a limit — and running tools would be wrong.

    And there's a decision hiding behind all of this. Streaming buys perceived responsiveness and charges you partial-state handling. On a backend job where no human is watching the tokens appear, a non-streamed call removes this entire class of bug for free.

    That's worth sitting on for a second, because it's a design judgement rather than a coding one. Every habit on this screen exists to manage a risk you took on voluntarily. If nobody is watching the response arrive, you bought nothing and you're paying for it in handler complexity. Class 13 asks the same question about latency, and the answer has the same shape: find out who is waiting before you optimise for them.

    06 · Multimodal input

    Images cost budget before anything is read

    By the end of this screen you'll be able to compute an image's context cost in your head, and pick a delivery method on a single question.

    Claude doesn't look at an image the way you do. It cuts the image into a grid of small squares — 28 pixels by 28 pixels each — and every square becomes one visual token. So the cost of an image is just the number of squares you can cut it into: ⌈width/28⌉ × ⌈height/28⌉.

    The formula looks more forbidding than the idea. Take a 1,000×1,000 screenshot. A thousand divided by 28 is about 36, so you get a 36×36 grid, which is 1,296 tokens. Do that arithmetic once by hand and you'll never need the formula again.

    One wrinkle before the arithmetic is safe. Each model has a maximum native resolution — a long-edge limit and a visual-token limit — and anything above either is downscaled before it's patched. So the formula runs on the scaled dimensions, not the ones in your file. These limits differ by tier and have changed between model generations, so confirm the current numbers when you build rather than trusting the ones in your head.

    Three ways to send one, and the question that decides

    The question is reuse, and everything else follows from it. Ask how many times this image will travel to the API. Once? Many times? That single answer picks the method, and the table below is really just that answer written out three ways.

    MethodOverheadRight when
    Inline base64 The full encoded payload travels with every request A one-off image, where an upload step would add complexity for no payoff
    URL reference No payload — but you take on a dependency that the URL is stable, public and reachable at request time Already hosted at a stable public URL you control. Not for anything behind auth or signed with a short expiry
    Files API Upload once, get a file_id, and every later request carries the ID instead of the bytes The same asset appears across multiple requests or turns. Beta, and not available on Bedrock or Vertex

    Watch what happens in a multi-turn conversation, because that's where the difference stops being academic. History is replayed on every request. An image sent as base64 is re-sent in full on turn two, and turn three, and turn twelve — you pay the payload every time. A file_id is a short string that weighs nothing no matter how long the conversation runs.

    PDFs work the same way, with block type document instead of image. Same three source options, an optional title and context, and no required name field.

    07 · What to memorise

    Where to spend your memory

    By the end of this screen you'll know which of today's facts you can derive under pressure and which ones you simply have to carry.

    This class mixed two kinds of fact, and treating them with equal reverence is how people end up revising badly. Some of what you learned today follows from how the thing works, and you could rebuild it from first principles in an exam room with nothing in front of you. The rest is a number somebody chose, and no amount of reasoning will recover it.

    Close to physics — reason from it
    • A stream is events, not an open object. Nothing is held at the far end.
    • Tool input is a string becoming JSON, so it is invalid until the moment it is complete.
    • Every tool_use needs a matching tool_result in the next turn — including the ones whose tools failed.
    • A corrupt history fails on the request that sends it, not the one that wrote it.
    • Replayed history means a re-sent payload costs again; a reference doesn't.
    • Images are cut into fixed squares, so cost scales with area.
    This release's convention — recognise it
    • The six event names, spelled exactly.
    • 28×28 pixels per patch. A chosen number.
    • Per-model resolution ceilings — these have already changed between generations.
    • The Files API being beta, and unavailable on Bedrock and Vertex.
    • PDFs using document rather than image.

    Learn the right-hand column, because the exam names mechanisms in its options and you'll have to recognise them in a lineup. But don't confuse it with the left. From the left column you can answer a question nobody taught you — and every one of the right column's entries is a thing that could be different next year without anything you understand becoming wrong.

    Recap

    What you're leaving with

    1. A stream is events, not an object. You assemble; you decide what happens if it stops. Nobody is holding anything open for you.
    2. Tool input is invalid JSON until content_block_stop. Don't send the courier until somebody says that's the whole address.
    3. Every tool_use needs a matching tool_result next turn — failures included, carrying the error.
    4. Discard an interrupted turn. Saving it corrupts the next request, not this one, which is why it's hard to find.
    5. Images cost patches — width over 28 times height over 28 — spent before your prompt is read.
    6. Reuse decides delivery. Base64 for one-offs, file_id for anything that recurs.
    Before Class 13

    A team streams responses in an agent loop. Their handler is correct: it commits the assistant turn only after message_stop, and discards partial turns on interruption. They are still seeing intermittent failures about tool blocks, still correlated with poor network, and the failing request still looks innocent on inspection.

    Given that the assembly bug is already fixed, what else produces exactly this signature — and how would you tell the two apart from the logs?

    The break is on the other side of the pair. The assembly is fine, so the tool_use blocks are complete — but the tool execution is being interrupted. The stream completes, the turn commits correctly, the handler starts running the tools, and then the client dies, times out, or is cancelled mid-execution. Now history holds a well-formed tool_use that never got its tool_result written, and the next request is rejected by the same invariant, from the opposite direction.

    It correlates with the network for the same reason as before — whatever kills connections also kills the process holding them — and the failing request looks innocent for the same reason: it's carrying a defect committed one call earlier.

    How to tell them apart. Look at the tool_use block in the rejected history. If its input is malformed or truncated, the stream assembly broke. If its input is complete and well-formed and there's simply no tool_result following it, assembly was fine and execution was cut. One log line recording the parsed input at commit time separates the two permanently.

    And the fix is the same shape as the first one. Treat "tool ran" as a commitment that isn't final until its result is written. On recovery, either finish the pair by writing a tool_result that reports the interruption as an error, or discard back to the last complete pair. What you must not do is leave the turn half-answered, because the invariant does not care why the partner is missing.
