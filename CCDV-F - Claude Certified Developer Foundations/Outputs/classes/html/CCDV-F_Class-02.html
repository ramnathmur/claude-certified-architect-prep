    What the Assistant Knows on Monday Morning

    Last class the board got rewritten before every sentence. Here's the question we didn't ask: what happens to it when everybody goes home? Memory is not a feature you switch on. It is a decision about what gets copied off the board before it's wiped — and it costs far more to make late than early.

    What you leave holding
    1. The board is wiped at the end of a session, and nothing survives that you didn't write down.
    2. Four scopes, four different currencies of cost. None of them is free.
    3. In-context isn't a memory strategy — it's what you get when you haven't chosen one.
    4. The shape of development is not the shape of production, and that gap hides the bug.

    01 · The wipe

    What happens to the board when everybody goes home?

    By the end of this screen you'll be able to say what "memory" actually means here, in mechanical terms rather than as a product feature.

    It gets wiped, and it doesn't come back. There is no board tomorrow.

    In fact there was never really a board at all — there was a request, and a reply, and then nothing. The board is a thing your program keeps rebuilding out of a transcript it's holding onto.

    So if you want your agent to know something on Monday that it learned on Friday, somebody has to write it down somewhere that is not the board.

    That's the whole of what memory means here. Not a feature you switch on — a decision about what gets copied off the board before it's wiped, and where you put the copy.

    And like most decisions, it is cheap to make early and expensive to make late. The rest of this class is about why that gap is so much wider than it looks.

    02 · The four scopes

    Four ways of remembering a patient

    By the end of this screen you'll hold all four memory scopes as one picture rather than four definitions.

    Forget computers for a minute. Think about doctors, because doctors solved this problem a hundred years ago and they solved it four different ways depending on the situation.

    The last one deserves a hard look, because people call it a memory strategy and it really isn't. In-context state doesn't survive a session ending. It doesn't survive a clear command. It's what you get when you haven't chosen anything yet.

    It's the appointment, not the file.

    Next. None of the four is free, and the costs are in different currencies — which is what makes the choice interesting rather than obvious.

    03 · Four currencies

    What each one costs

    By the end of this screen you'll be able to name the specific failure each scope buys you, not just its benefit.

    ScopeWhat it costsWhat you lose
    In-context No retrieval cost at all — it's already on the board. But the bill grows with the length of the conversation, and grows quadratically in the model's work. Everything, the moment the session ends.
    External storage Latency on every call that touches it, plus read-and-write code you now own forever. A database and a few hundred lines — not hard, just not nothing. Nothing on the persistence side.
    Summarised Cheaper per session than replaying the whole history. The summarisation step is itself a prompt you wrote. Whatever the summariser decided not to keep — silently, on every compression, forever.
    Stateless Nothing at all. There is nothing to store or fetch. Any follow-up that depends on an earlier session. There's no route to it.
    The one that hides

    Summarised memory's failure is the dangerous one, because it doesn't look like a failure. A vague summarisation prompt drops task-critical state on every compression and the file still reads as complete. Nobody gets an error. The agent simply, permanently, does not know a thing it was told.

    04 · Postmortem

    The agent that filled the window on session four

    By the end of this screen you'll recognise a memory-architecture failure wearing a tool-selection failure's clothes.

    A team built an agent to help a support engineer work through escalation cases. In development it ran beautifully. The developer would sit down, work a case in one continuous stretch, ten or fifteen turns, and the in-context state held the whole history perfectly. It shipped. Nobody measured how many tokens a session was actually using.

    Then production, which had a different shape.

    Each individual session was shorter than in development — an engineer would check in, ask a few things, go away. But they came back the next day, and the next, on the same case. And the state kept accumulating across those sessions.

    By the fourth session the history being injected at the start ran to more than forty thousand tokens. Before a single tool call. Add the system prompt and the tool schemas and the agent had burned over forty-five thousand tokens of its budget before doing one useful thing. Then the tool calls started, each adding its output to the board, and somewhere in the middle of the analysis the budget ran out.

    From the outside, the agent started returning incomplete results. And the team's first diagnosis was that it was picking the wrong tools.

    It was never a tool problem. It was a memory architecture problem wearing a tool problem's clothes.

    05 · Timing

    Why an hour of work is the expensive answer

    By the end of this screen you'll know why the same refactor costs one thing at design time and something else entirely three weeks after launch.

    The refactor is mechanical. Pull the accumulated history out of live context, put it in a database, inject only the part each session needs. A few hundred lines, and a database the team already has. At design time it would have been a slightly longer afternoon and nobody would remember it.

    What it cost was when.

    That hour happened under production pressure, with users complaining and a deadline already running. And it wasn't really an hour — the storage layer, the retrieval logic, what to inject and what to leave out, every one of those is a decision. Decisions made in a hurry with people watching are worse decisions and slower ones.

    The thing that let it happen

    The shape of development was not the shape of production. One long session against many short ones with state piling up between them. Those are different problems, and in-context memory handles them completely differently. The developer had no way to see it, because their own usage pattern hid it — the same blindness as Alex Morgan's laptop in Class 1, wearing a different costume.

    The habit that prevents it is dull and it works. Before choosing in-context, add up what a session will actually contain — history, plus system prompt, plus tool schemas — and compare that number to the window. Measure the real shape, not the one you use while building.

    Checkpoint

    Your agent works perfectly in every test you run. What single number tells you whether it will still work in production — and on which session would you measure it?

    Total tokens at session start — accumulated history plus system prompt plus tool schemas — before any tool call, measured against the window.

    And measure it on a session several days into a real workflow, never a fresh one. A fresh session is precisely the shape that hid the problem during development.

    06 · The ladder

    How to actually choose

    By the end of this screen you'll have the decision as three questions asked in order, with in-context correctly excluded from the list.

    Two more things worth holding.

    State kept outside can be shared — between sessions, between users, between several agents working the same case. State on the board is trapped in one conversation. If two agents need to know the same thing, in-context was never going to work.

    And the choice is not once and forever. An agent that starts stateless can grow into needing storage. What you don't want is to discover that at three in the afternoon with a queue of complaints.

    Recap

    What you're leaving with

    Memory is not something the model has. It is something you decided to write down.

    1. The board is wiped when the session ends, so anything that survives, survives because you put it somewhere else.
    2. Four scopes, four currencies. Tokens, latency, lost detail, or no continuity at all. Nothing here is free.
    3. In-context isn't a strategy — it's the absence of one, and it covers only within a session.
    4. Summarised memory fails silently, because the file looks complete whether or not the missing line mattered.
    5. Development shape hides production shape. Measure tokens at session start on a realistic session, before you commit.
    Before Class 3

    A team ships an agent that helps an analyst work a quarterly financial close — a process running over several days, the analyst returning each morning.

    Three weeks after launch, users report it "gets confused towards the end" and "forgets what we agreed on Tuesday." The team's leading theory is that they need a more capable model, and a budget request is already being drafted.

    What's your theory? And what single number would you make them produce before anyone spends anything?

    They ran out of context window, not model capability. And the reason the wrong diagnosis is the natural one: the symptom of a full context window is indistinguishable from a model that isn't clever enough. Nothing errors, nothing crashes — the thing just gets vaguer and drops details.

    Those two complaints are two failures with one root. "Forgets Tuesday" is cross-session: that state was never written down, so there was nothing to recall. "Gets confused towards the end" is within-session: the board filled and the line that mattered got buried. One architectural fix removes both.

    The number: tokens at session start — history plus system prompt plus tool schemas — on a session four or five days into a real close. And before signing that budget request, check whether the more capable model even has a larger window. Often it doesn't, and you'd pay more per token to hit the same wall slightly later.
