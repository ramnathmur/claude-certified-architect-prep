    The Bread That Stopped Rising

    You didn't change the recipe. The recipe was never the system. Configuration is the written record of what was true when it worked — and without it, "it got worse" is a complaint rather than a question you can answer.

    What you leave holding
    1. Five things decide behaviour, and your git log records one of them.
    2. Model changes are statistical and undocumented, which is why pinning matters more here.
    3. A prompt is source code. Convenient to edit and impossible to attribute are the same property.
    4. An undeclared dependency doesn't travel badly — it doesn't travel at all, and fails silently.
    5. Configuration doesn't make a system deterministic. It makes it attributable.

    01 · The system, not the recipe

    You didn't change the recipe

    By the end of this screen you'll have the shape of the whole class in one homely picture.

    You've been making the same loaf for two years. Same recipe, same oven, same hands. Last Tuesday it came out flat and it's been flat ever since.

    You didn't change the recipe. So what changed?

    Well — the flour is from a different mill, because the shop ran out of your usual. The yeast is a new packet from a new box. It's November now and the kitchen sits four degrees colder than it did in September. And your oven has been drifting low for a while, slowly enough that nobody noticed.

    The recipe was never the system. The recipe was one part of a system, and the other parts were changing quietly the whole time.

    Now: can you find out which one did it? Only if you wrote down what they were. If your notes say "flour: bread flour," you're finished — you can't get back to the flour that worked. If they say "flour: Shipton Mill, batch 4471," you can go and buy that flour and settle the question in an afternoon.

    03 · Model pinning

    Pinning the model, and why it matters more here

    By the end of this screen you'll be able to say exactly how a model upgrade differs from a library upgrade — and why no changelog can close the gap.

    In ordinary software you pin library versions, and you do it because a minor upgrade might change behaviour in some documented way you'd rather review first. Sensible, dull, well understood.

    Model versions are the same practice for a much sharper reason.

    A library upgradeA model upgrade
    The change isdiscrete and documentedstatistical and undocumented
    You find out byreading the changelognoticing your eval score moved three points
    What brokea named function returns something differentnothing in particular. Everything is slightly different
    Can it be enumerated?Yes — that's what a changelog isNo. It's a different function from text to text

    Slightly different phrasing. A slightly different rate of choosing tool A over tool B. There's no line item explaining it because there's no line.

    Point at a specific dated version, not a moving alias. Upgrade deliberately, as a change with a date attached, and re-run your evals when you do.

    The blueprint names this outright — breaking behaviour changes across model releases — and it's on the exam because it's what bites people who assumed newer is a free upgrade.

    The failure it prevents, precisely

    Without pinning: your model changed on a Tuesday, your prompt changed on a Wednesday, your quality dropped on a Thursday, and there is genuinely no way to tell which one did it. With pinning, one of those dates leaves the suspect list.

    04 · Prompts and packages

    A prompt is source code

    By the end of this screen you'll have the two remaining moving parts under the same discipline as your code.

    Say it plainly, because a lot of teams don't act like it: the prompt is the part of your system that most directly determines what it does. That makes it source code, and it gets treated like source code. In version control. Reviewed before it changes. With a diff you can read and a date and a name attached.

    The common failure is a prompt living somewhere convenient and unversioned — a database row, an admin panel, a config service — precisely so it can be tweaked quickly without a deploy. Which works, right up until somebody says "it got worse sometime last month" and there's no history to look at, no diff, and nobody quite remembers what they changed.

    Convenient to edit and impossible to attribute are the same property described twice.

    Plugins bring what they declare, and nothing else

    Back to Alex Morgan from Class 1, because this is the same lesson at a different altitude.

    A plugin bundles skills, hooks, subagents and MCP servers into one installable thing. What it does not bundle is anything the author was relying on but never listed: the deny rule that made a hook safe on their machine, the environment variable set in their shell profile, the script sitting one directory up.

    Those things were part of the working system. They just weren't part of the package.

    So it isn't a dependency that travels badly

    It's one that doesn't travel at all — and worse, fails silently, because the install succeeded and everything looks fine right up to the exact step that needed it.

    Declare what you depend on. Validate it at install time so a missing one announces itself immediately. Test the install on a clean machine — not because clean-machine testing is virtuous, but because it's the only test where your own assumptions aren't quietly holding the thing up.

    Go deeper — the same logic runs upward

    An organisation can deploy plugins centrally through managed settings, and managed settings sit above user and project settings — so something deployed at that level cannot be overridden locally. That's deliberate: it's how a company makes a control actually hold rather than merely recommending it. Class 5 does the full hierarchy.

    05 · What it buys

    Reproducible is not the same as identical

    By the end of this screen you'll know what pinning actually delivers, and why people are disappointed when they expect the wrong thing.

    Pin everything — model version, prompt, skills, settings, temperature — run the same input twice, and you can still get two different answers. That's sampling. It isn't a bug and it isn't a configuration failure. Class 6 covers why.

    So what did all that pinning buy?

    With everything pinned, run your evals and you get a distribution — some spread, some average. Run them next week and you get the spread again. If the average has moved outside that spread, something real changed and you have a short list of what it could have been. If it hasn't, that's just the day.

    Without pinning, every measurement is a mixture of variance and drift and you can never separate them. You end up arguing from anecdote — which is where the "we need a better model" conversation from Class 2 comes from.

    Configuration doesn't make the system deterministic. It makes the system attributable. That's the thing worth having.

    Recap

    What you're leaving with

    Configuration is not paperwork. It is the difference between a question you can answer and a complaint you can only argue about.

    1. Five moving parts, one in git. Model, prompt, skills and plugins, settings, undeclared dependencies.
    2. Model changes are statistical and undocumented. Pin to a dated version and re-run evals when you move.
    3. A prompt is source code, and unversioned convenience is unattributable by construction.
    4. An undeclared dependency doesn't travel at all, and fails silently at the exact step that needed it.
    5. Pinning buys attribution, not determinism. It gives the scatter a shape so a shift becomes visible.
    Before Class 5

    A team runs a support-triage agent. On the 3rd they upgraded to a newer model, expecting an improvement. On the 5th somebody tightened two sentences in the system prompt to fix a complaint about tone. On the 9th, a plugin they use for ticket lookup auto-updated.

    On the 12th, someone notices misroutes are up by about a third. The prompt is in git. The model is pointed at a moving alias. The plugin version isn't recorded anywhere.

    Which can they investigate, and which are they guessing about? And — the one that matters — suppose they'd pinned everything perfectly. What would they still need?

    The prompt they can investigate. It's in git. Diff it, revert it, re-run.

    The model they cannot. A moving alias means they can't establish what ran on the 3rd, or on the 12th, or whether it changed again on the 8th while nobody was looking. "The upgrade on the 3rd" isn't even a well-defined event — which is strictly worse than not upgrading, because now they don't know what they have.

    The plugin they cannot. No recorded version, so no way back to the one that worked. One of three is answerable; two are permanent guesses. And the misroutes could be caused by none of the three — a shift in what customers wrote that fortnight produces the same graph.

    What they'd still need: a baseline, and a definition. Configuration tells you what changed. It cannot tell you whether the result got worse, because "up by about a third" compares to a number nobody wrote down. And "misroute" has to be defined tightly enough that two people counting the same tickets get the same figure, or the metric moves when the counter's mood moves. That is what an eval is — configuration makes inputs attributable; evals make outputs measurable — and either one alone leaves you guessing.
