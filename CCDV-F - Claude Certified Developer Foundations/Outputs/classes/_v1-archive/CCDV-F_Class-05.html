    Signs, and Interlocks

    A sign is followed most of the time. An interlock doesn't have a most of the time. Claude Code gives you both, plus two more mechanisms — and the whole skill of configuring it is knowing which of the four a given piece of knowledge belongs in.

    01 · The workshop

    Three kinds of safety measure, and they aren't the same thing

    By the end of this screen you'll have the whole mechanism map as one physical picture, before any of it is named.

    Walk into a good workshop and you'll see three different kinds of safety measure. It's worth noticing that they're genuinely different things, rather than three flavours of the same thing.

    Claude Code gives you all three, plus a fourth — the apprentice you send to the library so you don't have to carry the books back.

    02 · Two questions

    The frame, and why plan mode exists

    By the end of this screen you'll be able to sort any Claude Code feature without memorising a list, and say when plan mode is the right default.

    Claude Code is the harness from Class 1, made configurable. Every feature in it answers one of exactly two questions.

    What gets onto the board?What are the hands allowed to do?
    CLAUDE.md, rules files, skills, subagents, slash commands, /clear permission modes, allow and deny rules, hooks

    Sort any feature into one of those two and it stops being a list to memorise.

    The loop: explore, plan, code

    Hand Claude Code a task and it doesn't start typing. It reads files and traces the logic first — that's the explore phase. Then it proposes a plan, a structured description of the edits it intends. Only once you've approved that does it code.

    Two reasons that sequence matters. It produces better work, because the thing understands the codebase before touching it. And it's where permission modes plug in.

    Plan mode holds it in explore, blocking every edit and every shell command until you release it.

    Which answers "plan mode or just let it run": plan mode is for an unfamiliar codebase or high-stakes work, where the cost of a wrong action is high enough that you want to read the intention before the action.

    03 · Permission modes

    The six modes

    By the end of this screen you'll read any mode by asking two questions, and you'll know which two names mislead.

    For each one, the questions are always: what does it auto-approve, and what does it still gate?

    ModeAuto-approvesStill gates
    defaultReads onlyEvery edit and every shell command
    acceptEditsReads, edits, and common filesystem commands inside the working directoryAll other shell commands; writes outside the working directory; protected paths
    planReads only — researches and proposes, writes nothingEverything, until you approve a plan
    autoEverything, but a separate classifier reviews each action firstProduction deploys and migrations, mass deletes, credential exfiltration, force-push to main
    dontAskOnly what you pre-approved in an allow rule, plus read-only commandsEverything else — denied outright, with no confirmation queue
    bypassPermissionsEverything. No prompts, no safety checksNothing, apart from a last-resort prompt on catastrophic deletes
    The two whose names point the wrong way

    dontAsk is not the relaxed one. It's the strictest one. It doesn't stop asking because it trusts you — it stops asking because anything not explicitly allowed is denied and there's nobody to ask. Built for locked-down CI, not for reducing friction while you work.

    auto is a research preview, not a safety guarantee. The classifier reduces prompts; it does not make the thing safe. Availability depends on plan and model version.

    bypassPermissions belongs only inside a disposable container. On a workstation against a live codebase it removes every prompt between the agent and your files — and unlike every other mode, it also removes the protected-path guard.

    05 · The discriminator

    Which mechanism carries this piece of knowledge?

    By the end of this screen you'll have four questions that pick the mechanism — this is the exact ground that cost marks last time.

    What it loadsWhenContext costWhat belongs in it
    CLAUDE.md The whole file, prepended at session start Every session, unconditionally Permanent, and dilutes as it grows Universal project constraints, commands, framework decisions
    Rules file The file, scoped by a paths glob in its frontmatter Only when Claude touches a matching file Nothing until triggered Path-specific guidance that would be noise everywhere else
    Hook Nothing. Runs your script at a lifecycle event At the event, every time Almost none Enforced guardrails, automatic side effects, audit logging
    Subagent Task context only, isolated from your session When dispatched Returns a summary, not the history Exploration, and anything whose output would bloat the main board
    The discriminator, in four questions

    Is it true everywhere in this project? → CLAUDE.md

    Is it true only in one part of the code? → a rules file with a paths glob

    Must it happen every single time, regardless of what the model decides? → a hook

    Would doing it flood the board? → a subagent

    Go deeper — where the scoping actually comes from

    A rules file's scoping comes from the paths glob in its YAML frontmatter, not from where the file sits. You can organise .claude/rules/ into subdirectories, but that structure is organisational only — a rules file with no paths field loads unconditionally at launch, with the same priority as CLAUDE.md, wherever it lives.

    So "never modify the database schema" belongs in CLAUDE.md because it applies everywhere. "All SQL in the database module must include an explicit transaction boundary" belongs in a rules file scoped to src/db/**/*.sql.

    06 · Convention or guardrail

    The distinction that cost you marks

    By the end of this screen you'll have a reflex: when the requirement is "always" or "never," an instruction is the wrong kind of thing.

    Put a line in CLAUDE.md saying "run Prettier after every file edit," and the agent will do it most of the time. It's a sign on the wall. It's read, it's weighed against everything else on the board, and it's usually followed.

    Configure a PostToolUse hook that runs Prettier, and it happens every single time, without exception, because the hook fires independently of anything the model decided. It's the interlock.

    Not a weaker version of the right mechanism — the wrong kind of thing entirely. You're writing a sign where the job needs an interlock.

    The lifecycle events

    EventWhen it runsWhat it's for
    PreToolUseBefore the call — the only one early enough to blockExit code 2 stops the action and writes the reason back as feedback the agent sees. Access control at the configuration layer instead of hoping
    PostToolUseAfter the call — cannot blockSide effects: formatters, triggering tests, audit logs
    UserPromptSubmitBefore the model sees your promptInject context or validate the request
    SessionStart / SessionEndSession opens or closesInitialise state, check required services are reachable; teardown and final audit writes
    StopThe model has finished respondingNotifications, cleanup, committing the audit log
    NotificationClaude needs permission, or has been idle 60 secondsRoute those signals somewhere

    Note which one blocks. Only PreToolUse runs early enough to have a say.

    Checkpoint

    Your team requires that every commit message include a ticket ID. Somebody proposes adding it to CLAUDE.md. What do you say, and what would you build instead?

    CLAUDE.md gets you a commit message with a ticket ID most of the time, and the failures are invisible until somebody audits the log months later.

    "Every commit" is an always, so it wants a PreToolUse hook — the only event that runs early enough to block. It inspects the pending commit, exits 2 if the ID is missing, and writes the reason to stderr so the agent sees the feedback and corrects. That fires regardless of permission mode, regardless of what else is on the board, and regardless of what the model decided.

    07 · Nuance and judgement

    Two corrections to Class 1

    By the end of this screen you'll have the subagent story exactly right, and a single question for placing every human review gate.

    Class 1 said subagents don't inherit the parent's CLAUDE.md. That's partly wrong, and it depends which subagent.

    The built-in Explore and Plan subagents skip CLAUDE.md and git status deliberately, to stay fast and cheap. So project rules genuinely aren't in their context. The general-purpose subagent loads both. If you delegate to Explore and a CLAUDE.md rule gets ignored, nothing malfunctioned — that context was never loaded.

    And on skills: custom subagents don't see your skills automatically and must list them in their own frontmatter. Built-in agents have no preloaded skills at all — if you need skill-backed behaviour, the route is a custom subagent that names them.

    What stands

    Permissions do inherit. So the asymmetry from Class 1 holds — context doesn't travel, authority does — and now you know its exact shape.

    Where the human gate goes

    Permission modes decide what the agent does without asking. They don't decide where you still need to look. That rests on one question: what is the worst outcome if this runs without a person checking it?

    Worst casePlacement
    Low cost, reversible — a formatting fix inside the working directory Let it through. Requiring approval buys oversight you don't need and slows the work. This is what acceptEdits is for
    Hard to undo, or reaching somewhere sensitive — a write outside the working directory, a destructive shell command, a security-relevant file Gate it. A deny rule enforces this deterministically; default or plan keeps the prompt in place while you decide
    Code the team has marked sensitive The agent is never the only gate. Its work is an input to a human decision, however confident it or its own review sounds

    The gate placement and the mode choice are the same decision seen from two sides. The mode sets the default for a whole session; the gate is where you override that default for the one action whose cost is too high to leave to a default.

    One more failure mode worth naming

    CLAUDE.md's main problem is size. Every instruction you add makes every other instruction a smaller fraction of the board, so a file that grows with each new idea gradually dilutes the one rule that would have caught a real mistake. Hold it to constraints that change behaviour and move everything else into skills. (/init writes you a starter by scanning the codebase — a decent baseline that needs editing before you trust it.)

    Recap

    What you're leaving with

    Four mechanisms, one question each. And one reflex worth more than the whole table.

    1. Two piles. Every feature is about what gets on the board, or what the hands may do.
    2. Six modes, read by what they auto-approve and what they still gate. dontAsk is the strictest, not the loosest.
    3. Four settings levels, and an enterprise deny rule is the only control that survives a developer in a hurry.
    4. Always or never means a hook. Only PreToolUse can block.
    5. The gate goes where the worst case is worst — not where the mode happens to end.
    Before Class 6

    A team has a rule: nothing may touch infra/production/ without a named human approving it. It's written in CLAUDE.md, in bold, at the top. It held for four months.

    Then a developer, mid-refactor and moving fast, switches to bypassPermissions because the prompts were slowing them down. Twenty minutes later a file in infra/production/ has been edited.

    Why didn't the rule hold? What mechanism would have, and at which settings level? And — the one that matters — that developer wasn't being reckless; they were being slow and fixed it the way the tool allowed. What does that tell you about where a control has to sit relative to the person it constrains?

    Why it didn't hold. A CLAUDE.md line is text on the board. It's weighed against everything else there and followed most of the time — and bypassPermissions removes the prompts that were doing the actual stopping, including the protected-path guard. Bold type doesn't change what kind of thing a sentence is.

    What would have held. A deny rule at the enterprise level, or a PreToolUse hook deployed through managed settings. Enterprise settings cannot be overridden by users or project files, and a deny rule beats an allow rule in any mode — including a bypass mode. Anything at project or user level is removable by the person it is meant to constrain.

    And the real lesson. A control that the constrained person can switch off isn't a control — it's a preference with good intentions. Notice the developer did nothing malicious: they hit friction and used a documented feature to remove it. Any control you'd want to survive that has to sit at a level they cannot reach. Which is the same idea as the interlock: enforcement has to sit outside the thing being constrained.
