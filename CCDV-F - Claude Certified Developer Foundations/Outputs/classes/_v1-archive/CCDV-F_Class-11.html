    Everything You Fetched Is Still There

    Every tool result Claude returns gets appended to the window and stays there for the rest of the session. In a single-turn prompt that's invisible. In an agent running twenty tool calls it's the whole problem — and the fix is deciding, in advance, what enters, what comes back as a summary, and what never enters at all.

    01 · The mechanism

    Tool results go in and never come out

    By the end of this screen you'll know why agents fill their window so much faster than conversations do.

    Class 6 said the window holds everything at once. Class 9 said the agent loop works by asking, acting, and reporting the result back. Put those two together and you get the fact this class is built on.

    Every tool result is appended to the window and stays there for the rest of the session. The 4,000-token file you read on turn three is still being re-sent on turn nineteen, at full length, whether or not anything still depends on it.

    The number that catches people

    In production, tool outputs are often three to five times longer than test fixtures. Real documents, real API responses, real error dumps. So the window that held twenty turns in development fills at turn eight against real traffic — and the cost of not planning for that is an outage, not a slowdown.

    The question for any agent workflow is whether you decided in advance what goes into the window, what comes back as a summary, and what never enters at all. Those three choices are context engineering.

    02 · The toolkit

    Four strategies, and what each one loses

    By the end of this screen you'll pick by what you can afford to lose, which is the only axis that separates these.

    All four reduce what's in the window. They are not interchangeable, because each discards something different — and the loss is the discriminator, not the mechanism.

    StrategyWhat it doesWhenWhat continuity you lose
    Pruning Jump back to an earlier message and continue from there, removing everything after it Claude went down an unproductive path, or debugging back-and-forth accumulated that won't help the next task The work done after the rewind point. Anything useful learned in that stretch has to be relearned
    Compaction Summarise the history into a condensed version that preserves what Claude has learned Approaching the ceiling but you want to keep working on the same feature with the knowledge built up Whatever the summary didn't capture. And you won't be told what that was
    Clearing Start a new conversation with empty context The next task is completely different, and prior context would only bias or confuse Everything. Anything needed across sessions has to live somewhere persistent
    Subagent handoff Spawn a subagent with its own window, holding only the task and context it needs; it returns a summary A self-contained subtask — especially exploration, where the journey clutters and the answer is short Visibility into how it got there. The intermediate steps are discarded with its context

    In Claude Code these are /compact and /clear. On the API, compaction has a server-side beta strategy the platform performs for you, with manual summarisation as the client-side alternative — and clearing is simply a new session.

    03 · The prompt inside the prompt

    What survives compaction is something you wrote

    By the end of this screen you'll treat the summariser prompt as production code, because that is what it is.

    When you implement manual compaction, you write the summariser prompt yourself. And that prompt determines what the agent will know for every subsequent turn.

    Summariser promptWhat you get
    "summarise the conversation so far" A general summary that may drop task-critical state: which files were modified, what was decided at a branch point, what error was hit and how it was resolved
    "summarise the conversation, preserving all file paths modified, all decisions made, and any errors encountered and their resolutions" A summary the agent can actually work from

    Task-critical state loss from an under-specified summariser is one of the most common sources of multi-session agent failure. Not an edge case — a leading cause.

    And notice why it's so hard to catch. Compaction produces something that reads like a complete account. Nothing errors. The agent carries on confidently, missing one decision it made an hour ago, and you find out when it contradicts itself. That's Class 3's confident-output problem arriving from inside your own architecture.

    So the discipline: name the state your task actually depends on, in the summariser prompt, explicitly. Generic instructions produce generic summaries, and generic is exactly what drops the branch decision.

    04 · Decomposition, and recap

    When the task is too big for a window

    By the end of this screen you'll have the one move that isn't about trimming.

    When a task is too large for a single context window, increasing the window is not a solution. It buys you a bigger number and the same shape of problem.

    The solution is to decompose the task and pass only the relevant context to each part. A subagent receives a scoped task, the minimum context it needs, the results of prior steps that are directly relevant, the tools required, and clear exit conditions. The parent collects the results.

    That keeps per-turn cost low and makes long-horizon tasks tractable — and it's Class 1's point arriving as an architecture: the empty head is the product.

    And the restraint that goes with it

    Pruning, compaction and handoffs all add implementation overhead. Apply them only where context cost is a real constraint. A single-turn prompt or a short workflow doesn't need any of this — measure actual token usage against your model's limit before adding management machinery. Best designed at the architecture stage rather than patched in under production pressure, which is Class 2's lesson in a different costume.

    Recap

    1. Tool results accumulate and stay. The agent's own work fills its window.
    2. Four strategies, four losses. Pick by what you can afford to lose.
    3. The summariser prompt is production code, and a vague one drops the state that mattered, silently.
    4. Production tool output is three to five times your fixtures. Measure against real traffic.
    5. Too big for a window means decompose, not enlarge.
    Before Class 12

    A research agent reads company filings and answers questions about them. It works. But on long sessions it starts giving answers that contradict things it said earlier in the same session.

    The team has compaction enabled, and their summariser prompt says "summarise the conversation so far."

    What's happening — and why is the intermittency exactly what you'd predict?

    Compaction is dropping the findings. A generic summariser prompt produces a summary of what the conversation was about rather than what it established — so the specific figure pulled out of a filing forty turns ago doesn't survive the compression. The agent then answers the same question again from the current context and gets a different number. It isn't contradicting itself; it never had the first answer any more.

    Why intermittent: it only happens after a compaction has run, which only happens on long sessions. Short sessions never compact, so they're always consistent — which is also why this passed every test.

    The fix is in the summariser prompt: name the state the task depends on. "Preserving every figure extracted and the filing it came from, and every conclusion stated." And the deeper fix is Class 2's ladder — findings that must survive belong in external storage, not in a summary that is lossy by design.
