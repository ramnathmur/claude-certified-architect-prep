    Why the Same Question Gives Two Answers

    The model does not pick the next word. It produces a probability distribution over possible next words and then draws from it. Almost everything that feels strange about working with this thing follows from that one sentence — including why your test suite keeps failing on correct answers.

    What you leave holding
    1. Tokens are the unit of input, output, cost and budget. Not words.
    2. The window holds everything at once, and has two different edge behaviours.
    3. Non-determinism is sampling working correctly, not the system failing.
    4. So you assert on properties, never on exact text.
    5. On the newest models, the sampling dials are gone — steer by prompting instead.

    01 · The unit

    Tokens are the unit of everything

    By the end of this screen you'll be counting in the same unit the API bills in, which is not the unit you naturally think in.

    Claude doesn't read characters, and it doesn't read words. It reads tokens. How many characters go into a token depends on the tokenizer, and that differs between model generations — so any "roughly four characters per token" rule of thumb is model-dependent and worth confirming rather than assuming.

    What matters more is what gets counted. Everything does:

    • your prompt
    • the conversation history
    • the tool definitions — the schemas, whether or not any tool gets used
    • every tool result
    • and the response the model generates

    Tokens are the unit of pricing and the unit of budget. When you estimate what a feature costs, or whether an input will fit, you are counting the same thing both times.

    Which is why the habit worth building is thinking in tokens rather than in words or pages. It is the unit the bill arrives in and the unit the window is measured in, and translating between two units in your head is where estimates go wrong.

    02 · A fixed budget

    The window, and its two different edges

    By the end of this screen you'll know the two ways a request can hit the ceiling, and why only one of them looks like an error.

    The context window is the total number of tokens the model can take in for a single request. It holds everything at once: system prompt, the full conversation so far, injected documents, every tool result, and the model's own output.

    That last item is the one people forget, and it produces the second edge.

    Both edges point at the same discipline: a long-running session requires the application to trim or summarise history before each call. That's Class 2's ladder, arriving here as a mechanical consequence rather than an architectural preference.

    And the reason it surprises people

    In development the window rarely fills, because test inputs are short. In production, longer inputs and more turns fill it faster. That gap between the two shapes is the same gap that filled the window on session four.

    03 · Sampling

    Why the same prompt can give a different answer

    By the end of this screen you'll be able to explain the variation mechanically, rather than treating it as flakiness.

    A language model does not pick one fixed next token. At each step it produces a probability distribution over possible next tokens, and then samples from it.

    Settings shape that distribution rather than replacing it. A lower temperature concentrates probability on the most likely tokens and makes output more repeatable. A higher one spreads it out and makes output more varied.

    And on the newest models the dials are gone

    The newest Claude models do not accept non-default sampling parameters. Setting temperature, top_p or top_k returns a 400. Behaviour on those models is steered through prompting instead. Confirm current parameter support in the API reference when you build — this is exactly the kind of thing that moves between generations.

    04 · Consequences

    What this does to your tests

    By the end of this screen you'll know which assertion to write and which one guarantees a flaky suite.

    Non-determinism is the direct consequence of sampling: identical inputs do not guarantee identical outputs. And that changes what a test can meaningfully claim.

    A test that asserts the exact text of a response will be inconsistent — not because the model is wrong, but because the model can express the same correct answer many ways. The test isn't detecting a defect. It's detecting a synonym.

    Don't assertAssert instead
    The response equals this exact stringThe required field is present
    The summary reads exactly like thisThe value is in range
    The wording matches the golden outputThe structure parses

    Assert on the property that must hold, not on the text that happened to come back.

    And when the thing you actually care about is meaning rather than structure — is this summary faithful, is this classification right — structure assertions can't reach it. That is the job of an eval with a model-graded judge, which is Class 26.

    Checkpoint

    A colleague says your feature is "non-deterministic, so it can't really be tested." What's wrong with that, in one sentence?

    It confuses the output being non-deterministic with the property you care about being non-deterministic. "Returns valid JSON with a currency field in ISO format" is either true or false on every single run — perfectly testable. What isn't testable is a golden string, and that was never the thing that mattered.

    Recap

    What you're leaving with

    One mechanism — a draw from a distribution, one token at a time — and everything odd about the system falls out of it.

    1. Tokens are the unit of input, output, cost and budget. Tool schemas count even when no tool is called.
    2. Two edges. Input too big is rejected outright; input that fits but generates too much comes back truncated with a stop reason and no error.
    3. Sampling is a draw, and temperature reshapes the distribution rather than removing the draw.
    4. The newest models refuse the sampling dials with a 400. Steer by prompting.
    5. Assert on properties, never on text. For meaning, you need a judge.
    Before Class 7

    A document-summarising endpoint has run fine for months. This week, support reports that summaries of the longest documents "seem to stop halfway through a sentence." No errors in the logs. No exceptions. The 4xx rate is unchanged. Latency is normal.

    What's happening, and what one field would you look at first?

    They're hitting the second edge. The input fits, so nothing is rejected and there is no 4xx to raise the rate — but the long documents leave so little headroom that generation reaches the ceiling partway through the summary. The model stops and returns what it had.

    Look at the stop reason on those responses. A truncated answer with model_context_window_exceeded is indistinguishable from a complete one unless something reads that field — which is why checking it belongs in the parser rather than in the investigation. And the fix is upstream: trim or summarise the input so the output has room, rather than treating it as a generation problem.
