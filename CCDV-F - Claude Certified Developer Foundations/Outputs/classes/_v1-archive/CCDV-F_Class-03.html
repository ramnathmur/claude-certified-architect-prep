    You Can Only Guard the Edges

    Every other component you've built on has an inside you can open up. This one doesn't. There is no line where it went wrong. So every control you have sits at the two edges — what you let in, and what shape you insist on getting back.

    What you leave holding
    1. You cannot audit the middle, so control lives at the edges or nowhere.
    2. The shape you ask for decides whether a wrong answer is detectable.
    3. A required field with no escape hatch makes a guess the only permitted output.
    4. Confidence is a property of the writing, not of the world.
    5. The boundary that matters is between text you authored and text that showed up.

    01 · The opaque part

    You cannot audit the middle

    By the end of this screen you'll know why the usual debugging instinct has nowhere to attach, and where that leaves you.

    If a function in your code returns the wrong number, you can step through it. Set a breakpoint, watch the variables, find the line where it went wrong. Every ordinary piece of software you've worked with has an inside you can open up and look at.

    This doesn't. There's no line where it went wrong. There's a very large pile of arithmetic that produced a plausible next token, and then another, and nothing in there corresponds to a step in a reasoning you could check.

    So if you can't inspect the middle, where does control live?

    02 · The output edge

    Start with a cheque

    By the end of this screen you'll see what a schema is actually for — and it isn't parsing convenience.

    A bank cheque asks for the amount twice. Once in digits, once written out in words.

    Nobody does that for elegance. They do it because a slip of the pen gives you two versions that disagree, and disagreement is something a clerk can see.

    The shape you ask for decides whether a wrong answer can slip through wearing the right clothes.

    03 · Unrepresentable

    Everything coming back is text

    By the end of this screen you'll be able to look at a field and say whether a wrong value would be caught or would pass.

    There's no mode where the machine starts emitting objects. It's text. It's always text. "Structured output" means text that happens to parse as JSON, produced by something that has seen an enormous amount of JSON and is good at producing more.

    So the structure is a convention it's following, not a guarantee the system enforces. Good conventions, followed well, most of the time. Not a promise.

    Which makes the question for every field: if the model gets this one wrong, do I find out?

    Ask for status as…A plausible replyWhat your code does
    free text"shipped"Accepts it. Correct, by luck.
    free text"probably shipped"Accepts it. A string is always valid.
    free text"shipped (partial — 2 of 3)"Accepts it, and something downstream now treats a partial shipment as complete.
    one of four values"probably shipped"Rejects it. You know.

    You've lost nothing by constraining it — the model was never going to be more correct in free text. You've gained the ability to tell.

    Make the wrong answer unrepresentable. A fixed set of values, say so. A number, ask for a number. Two fields that must agree, ask for both and check.

    04 · The escape hatch

    The box everybody forgets

    By the end of this screen you'll know why a required field is an instruction to invent, and what to add instead.

    You ask for a field called confidence_score. The scan was unreadable. What comes back?

    A number. A perfectly sensible-looking number.

    And you should have predicted that, because of how the thing works. It's predicting the likeliest continuation of the text in front of it. After a field name like confidence_score, what usually follows in every document it has ever seen? A number. Almost never a refusal.

    You created a position where the likely completion is a value — then were surprised to get one.

    Give it a legal way out

    An explicit "unknown" in the enum. A nullable field with instructions on when null is correct. A separate readable: true/false alongside the value. Any of them turns "I couldn't tell" into a legal move.

    A schema with no box for "could not tell" hasn't stopped the model being uncertain. It has stopped you finding out. It's the paper form with no "not applicable" — people write something in every box, because the box is there and blank looks like a mistake.

    Checkpoint

    You add "unknown" to an enum and the model still almost never picks it. Nothing is broken. What did you most likely leave out?

    The condition under which "unknown" is the right answer. Adding a legal value makes it possible; it doesn't make it likely. Loading is a prediction, and a bare "unknown" sitting in a list is a rare continuation.

    Say plainly, in the instruction, when to use it — "use unknown when the field is illegible or absent, rather than inferring from context." Now the refusal is the likely completion in exactly the cases you wanted it.

    05 · Two assumptions

    Assume it's malformed. And ignore how sure it sounds.

    By the end of this screen you'll have the realistic failure list, and one instinct deliberately switched off.

    Write the parser as though the text is broken

    Even with a good schema, eventually it is. The realistic failures aren't exotic:

    • A field missing entirely.
    • A number arriving as a string.
    • A single item where you expected a list of one.
    • The JSON wrapped in a chatty sentence and a code fence.
    • The response cut off mid-object because it hit the output limit.

    That last one deserves naming, because truncation is where "it worked in testing" misleads most — short test inputs never truncate. Validate before you use. Fail loudly. A parser that silently returns an empty object on malformed input will hide a production problem for months.

    Confidence tells you nothing

    Your instincts will fight this one. When a person is unsure you can usually hear it — they hedge, they slow down, they say "I think." You've spent your whole life reading that signal and it's mostly reliable.

    That signal isn't here. A wrong answer comes back in exactly the same voice as a right one: same fluency, same steadiness, same air of having checked.

    And it has to be that way

    Fluency is what the thing was built to produce. Correctness is a property of the world. Nothing in the machinery connects the two — so there is no tell to learn, and getting better at reading it will not help you.

    So "it sounded sure" is not evidence. If you need to know whether an answer is right, something outside the model has to check: a validation rule, a lookup against a real record, a second pass, a human. The exam blueprint names this outright — skepticism toward confident output.

    06 · The input edge

    What goes on the board

    By the end of this screen you'll be able to say why a prompt line asking the model not to use a field is not a control — and what is.

    You cannot put something in front of the model and ask it not to look. There is no private region of the board. Everything you send is in the request, and everything in the request was read.

    That sounds obvious stated plainly, and people design around it constantly — sending the whole customer record because it was easier than selecting fields, then adding a line to the prompt saying "do not use the national ID number." That line is a request to the thing making predictions. It is not a control.

    A content boundary is a decision made before the text goes out, in your code, about what to include. Redact it, or don't send it. There is no third option.

    And be clear how far "sent" reaches: into the request, into your logs, into whatever observability tooling you've wired up, and potentially into the reply. Every one of those is a place that data now lives.

    Instructions you wrote, versus text that arrived

    Some of the text on the board you wrote — your system prompt, your rules, your schema. Some of it arrived: a fetched web page, an uploaded document, the output of a tool, an email body.

    Put arrived content somewhere clearly marked as data, say plainly that it's data and not instruction, and — the part that actually works — make sure nothing it says can trigger an action on its own. You already know why from Class 1: the model can only ask.

    The boundary that matters isn't between safe content and unsafe content. It's between text you authored and text that showed up.

    Recap

    What you're leaving with

    One principle, applied at both ends: you cannot reach into the middle, so you shape what enters and you shape what must come back.

    1. There is no breakpoint. Control at the edges, or nowhere.
    2. A schema makes errors announce themselves. Parsing convenience is the smaller benefit.
    3. Required plus unconstrained makes a guess the only legal output. Give it a way to say it doesn't know, and say when to use it.
    4. Fluency and correctness are unconnected. Verification has to come from outside.
    5. A prompt line is not a redaction. Decide before the text leaves your code.
    Before Class 4

    You extract five fields from scanned supplier invoices — vendor, invoice number, date, currency, total — across about twenty thousand documents a night. Your schema declares all five as required strings.

    Three weeks in, finance says the extracted numbers are "mostly right."

    Why is "mostly right" a worse report than "twelve per cent wrong"? And name two schema changes that would have made this a different conversation.

    "Mostly right" is a report about detectability, not accuracy. If the pipeline could tell good extractions from bad, finance would have said "twelve per cent got rejected, here they are" — a number, and a pile you can inspect. That they can only say "mostly right" means the wrong ones and the right ones are in the same pile wearing the same clothes, and a human eventually noticed by feel. The model's accuracy may be identical in both worlds. What differs is whether anyone can tell which twelve per cent to go and look at.

    Required plus string is the trap. A required field must be filled; a string accepts anything. Hand that a smudged scan and the model's only legal move is a plausible-looking string, because blank isn't available and "I couldn't read it" isn't a string it was invited to write.

    Change one — give it a way out. Nullable fields with an instruction on when null is right, or a readable: false alongside. An unreadable scan then produces a row you route to a human rather than one that quietly enters the ledger.

    Change two — stop using strings for things that aren't strings. total as a number; a string total carries "1,234.56", "1.234,56" and "approximately 1200" equally happily. currency as an enum of ISO codes, so "$", "US Dollars" and "USD" can't be silently accepted as three different things. date in one fixed format. And a free third: ask for the line items too, and check they sum. That's the cheque.
