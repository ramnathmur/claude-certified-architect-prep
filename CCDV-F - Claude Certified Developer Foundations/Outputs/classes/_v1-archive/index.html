Claude Certified Developer — Foundations

Twenty-nine classes, each built around a single idea the material is derived from rather than listed under. The test of a class is not whether you can repeat it — it is whether you can answer a question about a case the class never covered.

Which is also the test the exam sets

53 items, 120 minutes, closed book, 720 to pass on a 100–1,000 scale. Every item is a short scenario stating a constraint, followed by options that are all legitimate techniques — only one of which fits. You select; you never produce. There are no per-domain minimums, so effort follows weight rather than anxiety.

Concepts first. Mock papers come after the teaching, not interleaved — sitting a paper on untaught material measures nothing and burns the item pool. 14 of 29 are taught.

Application shape

  • 01 You Can't Reach Through a Telephone Claude is text in, text out, on somebody else's machine. An instruction is text you got onto a board that is only so big; a capability is whatever the person at the other end has within reach.
  • 02 What the Assistant Knows on Monday Morning Memory scope is a design-time decision about what survives the board being wiped. Every scope trades cost against reach, and choosing late costs more than choosing badly.
  • 03 You Can Only Guard the Edges You cannot audit the middle, so control lives at what you let in and what shape you insist on getting back. The shape decides whether a wrong answer is detectable.
  • 04 The Bread That Stopped Rising Configuration is the written record of what was true when it worked. Without it a run is not reproducible and a regression is not attributable.
  • 05 Signs, and Interlocks Claude Code is a harness with a permission model. Every feature controls either what enters the board or what the hands may do — and a sign is not an interlock.

How the model behaves

  • 06 Why the Same Question Gives Two Answers The model predicts one token at a time from everything on the board. Non-determinism is sampling working as designed, not the system failing.
  • 07 Two Dials, and When Each One Pays Thinking is tokens spent before answering. Effort is a dial on how many, and it pays only where the task has a search space to explore.
  • 08 There Is No Best Model Capability, latency and cost are one budget with three names. A new release can move the exchange rate.
  • 09 What the SDK Is Hiding An SDK is a typed wrapper over an HTTP request. Everything it hides is still happening, and the things that break are in the part it hid.

Getting good output

  • 10 Stop Rewording It The model sees one flat text. Position is as load-bearing as wording, because position is how the text says what is authoritative and what is data.
  • 11 Everything You Fetched Is Still There The board is a working set you curate, not a log you append to. Everything left on it is re-read and re-charged every turn.
  • 12 Nothing Is Holding an Object Open for You Every feature on the API is a way of getting more onto the board, more out of it, or the same thing more cheaply.
  • 13 Who Is Waiting? Latency tolerance is the axis. If nobody is waiting, speed is something you are paying for and not using.
  • 14 Pay Once for the Part That Never Changes Cost is tokens times price times turns. Caching attacks the first term by making an unchanged prefix nearly free to resend.

Tools

  • 15Tool implementationA tool description is a prompt. Tools are selected the way skills are — by prediction over the text on the board, not by a lookup.
  • 16Output handlingModel output is untrusted input from a confident stranger. Confidence in the text carries no information about whether it is right.
  • 17Debugging and error handlingA failure lives in one of three places: what you sent, what came back, or what you did with it. Isolate which before changing anything.

Agents

  • 18Workflow or agentYou buy an agent when you cannot enumerate the steps in advance. You pay for it in determinism.
  • 19Agent patternsEvery agent pattern is a way of keeping the board small while the task stays big.
  • 20Abstraction frameworksA framework is somebody's opinion about the loop, made concrete. Choose by which opinion matches your architecture.
  • 21Building with the Agent SDKThe loop is the product. Hooks are where you put the things too important to leave to a prediction.

Solution and engineering work

  • 22Requirements from a business briefA requirement becomes testable at the moment it names a constraint. Until then it is a preference.
  • 23Systems life cycleThe cost of a decision rises with how late it is made. Life-cycle frameworks exist to move decisions earlier.
  • 24Software engineering foundationsThe exam tests these as judgement under constraint, the same as everything else — not as definitions.

Security

  • 25AI application securityAny text the model read is untrusted, whoever fetched it. The boundary that matters is between instructions you wrote and text that arrived.
  • 26Guardrails, layering, least privilege, hooksA control the model can choose to ignore is not a control. Enforcement sits outside the thing being constrained.
  • 27Identity, secrets and key managementAn agent's blast radius equals the credentials it holds, not the instructions it was given.

Reusability

  • 28Built-in, custom, skill or MCPChoose by who maintains it and how many applications need it, not by which is most capable.
  • 29MCP server developmentMCP turns a capability into an independently versioned service instead of a feature of one application.
How the classes are written

One idea per class, stated early. The constraint is shown before the rule, so the rule becomes obvious rather than memorable. Analogies carry the full load or they are cut, and at least one in every class comes from outside software.

Each class separates what is close to physics — things you can reason from — from what is simply this release's convention, so you know where to spend memory. And each ends with a question that needs the whole class rather than any one screen.
