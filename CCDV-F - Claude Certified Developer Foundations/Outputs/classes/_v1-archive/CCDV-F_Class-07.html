    Two Dials, and When Each One Pays

    You can spend tokens before the answer, letting the model think. Or spend them inside the prompt, showing it examples. Both cost the same currency, both are set independently of which model you run, and both are wasted on the wrong kind of task.

    What you leave holding
    1. Model choice and reasoning mode are separate decisions, set separately.
    2. Thinking earns its cost where there is a search space, and is wasted on lookups.
    3. Adaptive thinking with an effort setting replaced the fixed token budget.
    4. Examples pin down a shape that description keeps missing.
    5. Adding examples can let a cheaper model do the job — the levers interact.

    01 · Independence

    Which model, and whether it thinks, are different questions

    By the end of this screen you'll stop treating "use a better model" and "let it think" as the same move.

    Choosing which model to run is one decision. Whether the model reasons before answering is a separate decision, and you make it per call.

    They compose, which means there are four positions rather than one slider.

    02 · Reasoning

    Adaptive thinking, and the dial that replaced the budget

    By the end of this screen you'll know what to set, what is deprecated, and where thinking is simply wasted money.

    On current models the reasoning mode is adaptive thinking: the model decides when and how much to think, and you tune the depth with an effort setting rather than a fixed token budget.

    Two things that changed

    The older budget_tokens control is deprecated, and on the newest model generations it returns a 400.

    Thinking content is omitted from responses by default on the newest models. If you need to show it, request summarised display.

    And per-model defaults differ — some of the newest models think adaptively by default, or always. So "does this model think unless I tell it to?" is a question with a per-model answer, worth confirming rather than assuming.

    Where thinking earns its cost

    Reasoning pays on hard, multi-step problems. It is wasted on lookups and classification.

    That's worth having as a test rather than a slogan. Ask whether the task has a search space — several candidate approaches, where working through one and rejecting it changes the answer. Debugging has that. Planning a multi-file refactor has it. Deciding which of six categories a support ticket belongs to does not: there is nothing to explore, only something to recognise, and paying for deliberation buys you a slower version of the same label.

    Thinking is tokens spent before the answer. If working through the problem wouldn't change the answer, you're buying nothing.

    03 · Examples

    Zero-shot, one-shot, multi-shot

    By the end of this screen you'll know what an example does that a paragraph of instructions can't.

    Separate from how you word a prompt is how many worked examples you put inside it.

    • Zero-shot — the instruction and no examples. Describe the task, ask for the result.
    • One-shot — one example of the input paired with the desired output.
    • Multi-shot (or few-shot) — several such pairs.
    Worth being precise about

    The examples are not training data. Nothing is being learned or retained. They sit in the prompt, on the board, and they show the model the exact shape of the answer you want — which a description alone often fails to pin down.

    That's the real distinction. A description tells the model what you want about the answer. An example is the answer, and shape is much easier to copy than to infer. Casing, field order, how an edge case gets rendered, whether an empty list is [] or omitted — a paragraph keeps missing those; one correct example settles them all at once.

    The trade

    Every example costs tokens on every call, and consumes context budget. So this is the same trade as thinking, spent at a different moment.

    Reach for zero-shot when the task is simple and the output shape is obvious. Move to one- or multi-shot when the output has a specific structure, casing or edge case that a description keeps missing. One or two correct examples usually fix that faster than another paragraph of instructions.

    Add the smallest amount of prompt that produces a reliable result.

    04 · Interaction, and recap

    The levers interact

    By the end of this screen you'll have the joint decision rather than three separate ones.

    A more capable model often succeeds zero-shot on a task where a smaller model needs a few examples to match the structure.

    Which means examples are not only a quality lever. Adding examples can let a cheaper model do the job — you are trading a permanent per-call token cost against a permanent per-token price difference, and which way that lands depends on your volume and your prompt length.

    Try the simplest model and the fewest examples that meet your eval. Add capability or examples only where the eval says you need them.

    Notice what that sentence rests on. "Where the eval says" is doing the work — without a measurement, every one of these decisions is somebody's impression. Class 26 builds the eval; this class just tells you which dial to reach for once you have one.

    Recap

    1. Model choice and reasoning mode are independent, set separately, giving four positions.
    2. Adaptive thinking plus an effort setting. budget_tokens is deprecated and 400s on the newest models; thinking content is omitted by default.
    3. Thinking pays where there is a search space, and is wasted on classification.
    4. Examples pin down shape, cost tokens on every call, and are not training data.
    5. Examples can substitute for capability, so the two decisions are made together.
    Before Class 8

    A team runs a support-ticket classifier over six fixed categories, at high volume. Quality is acceptable but the bill is uncomfortable. Somebody proposes turning on a higher reasoning effort so the model "thinks more carefully about the ambiguous ones."

    What's wrong with that, and what would you try instead?

    It's the wrong dial, and it moves the bill the wrong way. Classification into six fixed categories has no search space — there is nothing to work through, only something to recognise. Deliberation buys a slower, more expensive version of the same label. And the proposal was made to fix cost, while raising effort raises cost.

    Try the opposite corner. Drop to a cheaper model with thinking off, and spend a few tokens on examples instead — particularly worked examples of the ambiguous cases that are actually causing the misses. That's the interaction from this screen: examples buying back the capability you gave up. Then let the eval say whether the quality drop is acceptable, rather than anyone's impression.
