    Pay Once for the Part That Never Changes

    Your bill is tokens times price times turns. The four strategies in Class 11 attacked what enters the window. Two API features attack what you pay for what's already there — and one of them lets you measure the pressure before a request fails instead of after.

    What you leave holding
    1. Caching reuses the processing done on a stable prefix. Prefix is the whole idea.
    2. Mark a breakpoint with cache_control, type ephemeral. Up to four.
    3. System prompt and tool schemas are the highest-leverage thing to cache.
    4. One edit near the top of a request invalidates everything after it.
    5. count_tokens measures a request without running it.

    01 · Caching

    Prompt caching, and why "prefix" is the load-bearing word

    By the end of this screen you'll know what caching can and cannot do, from the mechanism rather than the marketing.

    Prompt caching stores the processing work done on a stable prefix of your request, so follow-up requests can reuse it instead of reprocessing the same tokens. The first request writes the prefix to cache; subsequent requests that send identical content up to that point pay a fraction of the original cost.

    Now think about what "prefix" forces to be true. The reuse only works from the start of the request up to your breakpoint. Change a single token near the top and everything after it is different, so nothing downstream can be reused.

    The strongest candidates are the parts of a request that rarely change across turns: a long system prompt, a large tool-definition set, or a reference document you query repeatedly.

    You enable it by marking a cache breakpoint — a cache_control field of type ephemeral on the last block you want cached. You can place up to four breakpoints.

    For a multi-turn session with a stable system prompt and tool schemas, caching those prefixes once and reusing them across turns is the highest-leverage cost reduction available.

    Which is worth sitting with alongside Class 6. Those tokens were being re-sent and reprocessed on every single turn anyway — caching doesn't stop them being sent, it stops you paying full price to reprocess what hasn't changed.

    02 · Token counting

    Measure the pressure before the request goes out

    By the end of this screen you'll have the instrument that turns every "measure it first" instruction in this course into something you can actually do.

    The count_tokens endpoint takes the same request body as a messages call and returns the token count without running inference.

    Two uses, and they're different jobs:

    • In development — verify your context budget assumptions hold against real tool outputs, not just test fixtures. This is the instrument for Class 11's three-to-five-times problem. You don't have to guess whether production output will fit; you can measure a real one.
    • In production — gate requests that would exceed the window before they error. Which turns Class 6's first edge from an incident into a branch in your code.

    Every time this course has said "measure it," this is the thing that measures it. It costs a call and no inference.

    And notice what it makes possible that guessing doesn't: you can compare two prompt designs, or the real cost of a tool schema set, or what a document actually adds, as numbers — before committing to any of them.

    Recap

    What you're leaving with

    1. Cost is tokens × price × turns. Class 11 attacked the first term; caching attacks what you pay for it.
    2. Caching reuses a stable prefix. Reuse runs from the start of the request to your breakpoint, and no further.
    3. Order decides everything. One changing line above your stable content invalidates the lot.
    4. System prompt plus tool schemas is the highest-leverage prefix in a multi-turn session.
    5. count_tokens measures without inferring. Gate on it in production; validate assumptions with it in development.
    Before Class 15

    A team enables prompt caching on a multi-turn support assistant. They set a cache_control breakpoint after their 3,000-token system prompt and tool schemas. Cache hit rate comes back at essentially zero, and the bill doesn't move.

    Nothing is misconfigured — the breakpoint is exactly where it should be. What would you look for?

    Something above the breakpoint is changing every request. The breakpoint being in the right place is necessary and not sufficient — what matters is that everything preceding it is byte-identical each turn.

    The usual culprits are small and look innocent: a timestamp or "today's date" injected at the top of the system prompt, a session or user id interpolated into it, a greeting personalised with the customer's name, or tool schemas generated in a non-deterministic order so the JSON differs between runs. Any one of those makes the prefix new every time, and a new prefix has nothing to hit.

    The fix is ordering, not configuration. Move the volatile content below the breakpoint — the date and the user id belong in the turn, not in the system prompt — and make schema serialisation deterministic. And count_tokens plus the usage figures on the response will tell you whether it worked without waiting for a monthly bill.
