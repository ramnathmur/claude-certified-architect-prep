    Nothing Is Holding an Object Open for You

    A streamed response is not a live thing you read from. It is a series of small messages, each describing one change, and you are the one assembling them. Get that wrong and you corrupt the next turn rather than the current one — which is why it's hard to notice.

    01 · Events, not an object

    What streaming actually changes

    By the end of this screen you'll know exactly what job streaming hands to your code — and it's a bigger one than "display it sooner."

    In a non-streamed request the API hands you one complete message with every content block fully formed. In a streamed request it sends a series of events describing the message as it is being built. Your code listens and reassembles.

    The message you end up with is identical to what a non-streamed call would have given you. The difference is that you assembled it, and you decided what to do if the events stopped early.

    It helps to know what is not happening: the model isn't holding a live object open for you. Each event is its own small message describing a single change, and your handler applies it to the partial state it's been building.

    EventWhat it signalsWhat your handler does
    message_startA new message begins — the shell, empty content, initial usageSet up an empty content array to collect blocks in
    content_block_startA block opens, with its type (text, tool_use, thinking) and indexMake a slot at that index. A tool_use block opens with a name and id but no input yet
    content_block_deltaAn incremental piece of one block — a text fragment, a fragment of tool JSON, a thinking fragmentAppend to the block at that index. Tool inputs arrive as partial JSON spread across deltas
    content_block_stopThat block is completeFinalise it. For tool_use, this is the first moment the JSON is complete enough to parse
    message_deltaTop-level changes — the stop_reason and final usageRecord the stop reason. It tells you whether the model finished or stopped for another reason
    message_stopThe stream is completeThe assembled array is now the finished message. Treat it exactly like a non-streamed response

    02 · The rule

    Don't act on a partial block

    By the end of this screen you'll know which block corrupts state and why the damage lands on the next request.

    The tool_use block is the one to watch. Its input arrives as a partial JSON string spread across many delta events, and that string is not valid JSON until content_block_stop closes the block.

    So code that parses the input or runs the tool before the block closes either chokes on malformed JSON, or — worse — runs with half the arguments missing.

    03 · Interruption

    When the stream stops early

    By the end of this screen you'll know why keeping what you collected is the damaging move.

    A dropped connection, a timeout, a client disconnect — any of these can end the event series before message_stop arrives. And the failure that really bites is treating whatever you've collected as if it were complete.

    The two cases are not equally bad, and it's worth being precise about which is which:

    • A partial text block shown to a user is a cosmetic glitch. Ugly, survivable.
    • A partial tool_use block written into history is a structural problem that corrupts the next turn.
    Three habits

    Track completion on purpose. A turn is usable only once message_stop has arrived. Until then, what you've accumulated is provisional.

    On an interruption, throw the partial turn away rather than saving it, then retry the request. Committing a half-built turn is exactly what breaks the following one.

    Check stop_reason before continuing a loop. tool_use means your assembled calls are ready to run. Any other value means you're on a different path, not the tool path.

    Streaming buys perceived responsiveness and charges you partial-state handling. On a backend job where nobody is watching, a non-streamed call removes the entire risk class for free.

    04 · Multimodal input

    Images cost budget before anything is read

    By the end of this screen you'll be able to compute an image's context cost and pick a delivery method on one question.

    Claude views images in patches. Each 28×28-pixel block is one visual token, so an image costs ⌈width/28⌉ × ⌈height/28⌉ visual tokens.

    Run the arithmetic once and it sticks

    A 1,000×1,000 image is 36×36 patches — about 1,296 visual tokens. At that rate ten high-resolution screenshots consume as much context as a detailed system prompt, and they consume it before Claude has read a character of your instructions.

    Each model has a maximum native resolution — a long-edge limit and a visual-token limit — and these differ by tier, with the newest models accepting substantially larger images. Anything over either limit is downscaled first, so the formula runs on the scaled dimensions. Confirm current per-tier limits when you build; they've changed between generations and will again.

    Three ways to send one, and the question that decides

    MethodOverheadRight when
    Inline base64 The full encoded payload travels with every request A one-off image, where an upload step would add complexity for no payoff
    URL reference No payload — but you take on a dependency that the URL is stable, public and reachable at request time Already hosted at a stable public URL you control. Not for anything behind auth or signed with a short expiry
    Files API Upload once, get a file_id, and every later request carries the ID instead of the bytes The same asset appears across multiple requests or turns. Beta, and not available on Bedrock or Vertex

    The question underneath all three is reuse. Send the same image twice and base64 has paid twice; the file_id carries no payload weight at all as history grows, which is exactly the property you want in a multi-turn conversation.

    PDFs work the same way with block type document instead of image. Same source options, an optional title and context, no required name field.

    Recap

    What you're leaving with

    1. A stream is events, not an object. You assemble; you decide what happens if it stops.
    2. Tool input is invalid JSON until content_block_stop. Act only after it.
    3. Discard an interrupted turn. Saving it corrupts the next request, not this one.
    4. Images cost patches — width over 28 times height over 28 — spent before your prompt is read.
    5. Reuse decides delivery. Base64 for one-offs, file_id for anything that recurs.
    Before Class 13

    A team streams responses in an agent loop. Intermittently, a request fails with an error about tool blocks — but the request that fails is always fine on its own, and re-running it works. The failures correlate loosely with periods of poor network.

    What's happening, and where is the bug actually located?

    A stream is being interrupted mid-tool_use, and the handler is saving what it collected into conversation history anyway. That leaves a half-built tool_use block in the turn, and the tool pairing rules reject it — on the next request.

    Which is why the failing request looks innocent. The bug isn't in it. The bug is in the previous turn's assembly, one call earlier, and re-running the failing request works because the retry doesn't carry the corrupt history.

    The fix: commit the assistant turn only after message_stop. On interruption, discard the partial turn and retry the original request. And the poor-network correlation is the clue that should have pointed here first — intermittent, environmental, and nothing to do with the content of any prompt.
