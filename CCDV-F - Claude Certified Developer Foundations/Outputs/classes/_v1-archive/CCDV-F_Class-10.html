    Stop Rewording It

    When a prompt fails, the instinct is to say the same thing more clearly. That instinct is almost always wrong. A failing prompt is usually missing a structural piece, and the way it fails tells you which one — so the job is diagnosis, not eloquence.

    What you leave holding
    1. Four failure modes, each pointing at exactly one missing technique.
    2. A prompt that gets longer every iteration is a prompt nobody diagnosed.
    3. System prompt, XML tags, few-shot, output constraint — four different jobs.
    4. Clearer wording cannot fix a missing boundary. Nothing can, except a boundary.
    5. Don't stack all four on a task that needs one.

    01 · The wrong instinct

    Why rewording almost never fixes it

    By the end of this screen you'll be able to say why a whole class of prompt problems is immune to better phrasing.

    A prompt that works once in interactive use often breaks in production against inputs nobody tested. And the reflex, universally, is to add words and run it again.

    Think about what rewording actually changes. It changes how you say something. It does not add a piece that was absent.

    If Claude is crossing the boundary between your instructions and your input data, clearer phrasing will not fix it. There is no wording of "please don't confuse these two things" that creates a boundary. Only a boundary creates a boundary.

    Same for format. If the output shape keeps drifting, "please format this correctly" adds a sentence and no constraint. The parser is still going to get whatever plausible text arrives.

    The tell

    When a prompt keeps getting longer with every pass rather than more precise, that is the sign you're skipping the diagnosis step and just adding words. Five re-prompts with the output still wrong means five attempts at the wrong kind of fix.

    03 · The toolkit

    Four techniques, four different jobs

    By the end of this screen you'll know which job each one does, so you don't reach for a hammer when the boundary is what's missing.

    System prompts — the behavioural contract

    They carry the rules for the whole session. Role, output format, anything that must not change between conversations. Write them once and treat them as your persistent instruction layer. When one is underspecified there is nothing holding role, scope and format steady as the conversation runs on — which is exactly why that failure gets worse deeper in.

    XML tags — the boundary

    Use them when the prompt mixes inputs with instructions. Ask Claude to debug code using provided documentation and, without tags, the code and the documentation look the same. Wrap them in descriptive names — <my_code>, <docs> — and the boundary becomes unambiguous.

    You don't need official XML tag names. Descriptive names that match your content work best.

    Few-shot examples — show, don't describe

    One correct input-output pair gives the exact shape to match, which a written instruction often fails to pin down. Wrap them in consistent structure — <sample_input> and <ideal_output> — so the boundary between example and prompt stays clear.

    And a good trick: take your examples from your highest-scoring eval outputs rather than writing them from scratch. They're already known-correct, and they're already in your own domain's language.

    Output constraints — the last line before the parser

    Specify exactly what you need: field names, types, length limits, whether to include a preamble, and what to do when data is absent. That last one is Class 3's escape hatch, arriving here as a prompt technique.

    Worked example — the same classifier, before and after

    Before: "You are a support classifier. Classify the ticket." Claude returns Billing on some runs, billing on others, and occasionally a whole sentence. The router expects a fixed label set and breaks on the variation.

    After: the system prompt sets the contract — exactly one of BILLING, TECHNICAL, ESCALATION; return only the label; no other text. XML-tagged pairs show the exact casing. Three techniques doing three distinct jobs: the contract, the boundary, and the shape.

    04 · Limits

    When not to, and where prompting stops working

    By the end of this screen you'll know both when four techniques is too many and when four is not enough.

    SituationWhat to do
    A well-specified output contract with edge cases that examples can cover Stack all four. This is what they're for
    A simple task that needs one technique Simplify. "Summarise this paragraph" does not need few-shot examples and an output schema
    A prompt growing longer each iteration rather than more precise Stop and diagnose. Five re-prompts with the output still wrong means the failure type was never named

    And now the honest limit

    Everything on this screen shapes output by writing instructions into the prompt and hoping Claude follows them. That works most of the time.

    But go back to Class 5's distinction, because it applies here exactly. A prompt is a request. It's a sign on the wall. The model can still return a stray sentence, a wrong field name, or malformed JSON — and it will do so precisely on the input you never tested, because that's the one your instruction wasn't written against.

    A prompt-level instruction to return only JSON holds on the cases you tried and slips on the one you didn't. That is not a prompting failure. It is what a request is.

    There's an API mechanism that closes that gap — structured outputs, which constrains generation against a schema so a violating response cannot be produced at all. That's the interlock to this screen's sign, and it belongs with the rest of output handling in Class 16.

    Checkpoint

    Your extraction prompt has worked for a month. Today it returned a perfect JSON object wrapped in the sentence "Here's the extracted data:" and the parser threw. A colleague is adding "IMPORTANT: return ONLY JSON, no preamble" to the prompt.

    Diagnose it properly. Which row of the table is this, and is their fix right?

    Row one — wrong shape, so the missing piece is an output constraint. And their fix is the right category: "no preamble" is exactly the kind of thing an output constraint is supposed to specify, and it was genuinely absent.

    But notice what it can't do. It worked for a month, which means the instruction wasn't the problem on any tested input — it slipped on one variant. Adding a firmer sentence makes the same slip less likely, not impossible, and you'll find out it slipped again the same way you found out this time. If this parser matters, the answer is a schema constraint that the API enforces on every token, not a more emphatic request. Capital letters are not an enforcement mechanism.

    Recap

    What you're leaving with

    1. The fix is structural, not phrasing. Rewording changes how you say it, not what's absent.
    2. Four failures, four missing pieces. The symptom names the technique.
    3. System prompt = contract. XML = boundary. Few-shot = shape. Constraint = the parser's last line.
    4. A growing prompt is an undiagnosed prompt.
    5. Prompting has a ceiling, because a prompt is a request. Class 16 has the enforcement.
    Before Class 11

    A summarisation feature has a system prompt that started at four lines and is now two pages. Each production complaint added a paragraph. It currently mostly works, but it is slow, expensive, and nobody on the team will touch it because they can't tell which parts are load-bearing.

    What went wrong, and what would you actually do on Monday?

    What went wrong: every complaint was answered by adding words rather than by naming the failure type. Two pages is not a thorough prompt, it's a log of undiagnosed incidents — and it's expensive because, from Class 6, the whole system prompt is re-sent and re-read on every single call.

    Monday: don't rewrite it, and don't trim it by taste. Take the actual complaints it accumulated and sort each into one of the four failure types. That tells you which paragraphs were reaching for a technique the prompt already has — those are the redundant ones — and which were reaching for one it never had, which is where a real fix is missing.

    And the reason nobody will touch it is the thing worth fixing first: there's no eval. Without one, any deletion is a gamble, which is why two pages of prompt becomes permanent. With one, you can cut a paragraph and know within minutes whether it was holding anything up.
