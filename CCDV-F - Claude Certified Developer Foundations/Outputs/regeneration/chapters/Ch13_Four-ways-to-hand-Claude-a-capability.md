# Four ways to hand Claude a capability

"Tool" has meant one specific thing across the last three chapters: a schema Claude reads, matched against a request, with your application running the code behind it once Claude asks. Chapter 11 covered writing that schema well enough that Claude picks the right one. This chapter asks an earlier question: whether the capability belongs in a tool's shape at all, or in one of three other shapes that do the same job differently.

A firm needs to check a customer's credit before it signs a contract. It has four ways to get that capability. It can turn on the credit check already built into its accounting software. It can pay a developer to write one against the credit bureau's API. It can write the procedure into the underwriting handbook and have an analyst follow it. Or it can set up a dedicated connection to the bureau, run as its own standalone service, that sales, risk and both subsidiaries all draw on. Each option gets the firm the same result today: a credit decision it can act on. They diverge the day something about the capability has to change.

Those four choices sit on one axis: who has to act, and what has to happen, when the capability needs to change. That axis is the one Claude's four options sit on too.

A **built-in tool** is Anthropic's version of the check bundled into the accounting software. Anthropic decides what the check does and when it's updated; the firm may or may not be the one running it day to day, but has no say over the definition, and its part is switching the check on. Six of these run entirely on Anthropic's own infrastructure: web search, web fetch, code execution, an advisor tool, tool search, and the MCP connector. A second group, including bash, the text editor and computer use, ships with a schema Anthropic wrote, but your application still executes every call; chapter 11 covers that server-versus-client split in depth, and this chapter treats both groups as one category, because both share the property that matters here: you accept what Anthropic built rather than writing it yourself. The billing follows the same split: a client tool is priced as an ordinary part of the request, while several of the server tools carry their own separate charge, because Anthropic is the one running the infrastructure behind them. Turning on web search for a support bot that occasionally needs a current shipping-carrier outage is the built-in case in miniature: Anthropic already solved searching the web, and there is nothing this application needs from that capability beyond what the shipped version already provides. One wrinkle worth a sentence and no more: "built-in" is not a single universal list. The Messages API, Claude's Managed Agents, and the Agent SDK each ship their own default set, overlapping on things like bash and web search without being identical, because each is a different piece of infrastructure with its own defaults.

The developer's script, in Claude's world, is a **custom tool**: you write the schema, your application executes the code behind it, and every parameter, every edge case and every fix is yours to ship. Nothing here has been trained into Claude the way an Anthropic-authored schema has, so a custom tool works only as well as its description tells Claude what it does and when to use it, which is the whole subject of chapter 11. A firm's own pricing engine, reachable only from inside its own network and carrying business rules nobody outside the firm could write a schema for, is the custom-tool case: nobody else is going to write this, and nobody else needs to. In the credit-check world, this is the version where the firm's own developer owns the connection to the bureau directly. If the bureau changes its API tomorrow, the developer who wrote that connection is the one who finds out.

**Skills** are the handbook pages. A Skill is a markdown file with a description, carrying instructions rather than code, that Claude reads when the description matches the task in front of it. Its frontmatter needs nothing more than a name and a description to exist. Loading happens in layers: only the name and description sit in context at the start of every session, the full body of instructions loads once the description actually matches a task, and anything the Skill bundles beyond that, a template, a script, a reference file, loads only if Claude decides it needs it. A Skill only tells Claude how to proceed, a procedure or a piece of policy, and Claude carries out that instruction using whatever tools it already has. A code-review checklist specific to how one team likes pull requests written up is the Skill case: entirely instructional, nothing to connect to, and exactly the kind of thing that would otherwise be typed fresh into every session. Changing a Skill means editing a file. No application gets redeployed. That makes it the fastest of the four to update.

Set up the dedicated bureau connection inside Claude's world and you have built an **MCP server**: a separate process, run independently of any single application, that publishes tools, data and prompt templates to whichever client connects to it. That client could be Claude Code, your own application, or a teammate's application, and all three share the same server instead of each rebuilding the link to the bureau themselves. An internal service that already serves three applications and gets updated by a team you don't manage is the clean MCP case: reusable across applications, maintained independently of any one of them. The connection might be staffed by the firm's own risk-operations team, or bought in from a specialist who runs it for several clients at once. Either way, keeping it current is one team's job, done once, rather than every consuming application's job, done separately. What it can reach is also unusually broad: whatever the server itself can reach, which is the opposite end of the scale from the sandbox a Skill runs inside. Underneath, MCP is a small piece of architecture: a host application, Claude Code or your own, creates a client for each server it talks to, and each server can expose tools it executes, resources it hands over as data, and prompt templates for structuring a request. Chapter 14 covers building and hosting one; this chapter needs only the shape of it.

The analogy stops at procurement. Turning on a built-in tool is a configuration change inside your own account; nobody invoices you the way the bureau invoices the firm. The ownership question is what survives the jump.

Derive the rule from those four definitions rather than memorizing them separately. Every one of them answers the same question in a different way: who has to act when the world underneath the capability moves. Start with what the capability is for. If it needs to change how Claude behaves once Claude already has what it needs, rather than reach or fetch anything new, it is a Skill, however much the task looks like it needs a tool. Anthropic states this split as its own rule for two of the four: "MCP connects Claude to data; Skills teach Claude what to do with that data." A checklist, a policy for reading a report Claude will already have in front of it: both change Claude's behavior without reaching anything new, which keeps it out of the tool and MCP categories entirely. The two can sit together instead of competing for the same job. A Skill can sit on top of an MCP server, documenting how to use the very system the server connects to, which is exactly the connect-plus-know-what-to-do-with-it pairing the line above describes.

If the job is connecting to something, resolve it in order. First, check whether Anthropic already runs an acceptable version: if so, a built-in tool is the answer, and building your own spends effort on a capability Anthropic already maintains for free. If not, look at who else needs it and who is responsible for keeping it correct once the outside system changes. One application, one team, full control over both ends: a custom tool. More than one caller, or a dependency on an external system that changes on a schedule nobody on your side controls: an MCP server, because that option was built to be maintained once and shared. Answer both questions and you know which shape fits, and whose job it will be to fix it when something upstream changes.

Cost inside the context window moves in the same direction as ownership. A built-in tool's definition sits in the request whether or not it gets used, the same as a custom tool's schema. A Skill costs almost nothing until triggered: description only, full instructions on demand. An MCP server's tool list loads at connection time, with the full schema for any one tool arriving only once that tool is actually called. None of that changes which of the four is correct for a given job, but it explains why switching on ten built-in tools you rarely use is a worse habit than it looks: every one of them is paid for on every request, used or not.

Break the rule against a case built to look like a Skill. A team deploying straight against the Claude API, rather than Claude Code, wants Claude to review a return request: read the customer's message, check a live inventory system to see whether the item is back in stock, and apply the company's own refund policy above a certain value. Someone starts writing a Skill. The description-and-instructions shape fits every surface feature.

The mechanism disagrees. A Skill invoked through the Claude API runs inside a code-execution sandbox with no network access at all. It cannot make an external call, regardless of what its own instructions say to do. A Skill written to check live inventory is a Skill whose first instruction it cannot carry out. In the credit-check world, this is the handbook page handed to an analyst who has memorized the entire policy but has been given no phone and no terminal: extremely well instructed, and unable to check a single file.

The mechanism wins by splitting the job: it puts each half where it belongs, the Skill included. The inventory check needs a tool, a custom one if this application is the only caller, an MCP server if other applications need the same stock check. The refund policy, the part that is genuinely just procedure, still belongs in a Skill sitting on top of whichever one gets built. Package both into one Skill that also tries to reach the network, and it fails quietly in exactly the spot that mattered.

This chapter's rule stops at which shape. Two things sit immediately on the other side of that decision and belong to other chapters. Deciding that an MCP server is the right shape is not the same job as building one. Chapter 14 picks up from exactly that decision already made: choosing stdio against HTTP as the transport, registering the server at one of four scope levels, writing per-tool permission rules, and keeping its credential out of the same file as its configuration, so a leaked config file does not also leak the secret that authenticates it. Nothing in that list changes which of the four options belongs here.

Skills get a second pass in chapter 20 too, from a different angle: as a primitive inside Claude Code specifically, alongside how the CLI discovers them, triggers them by name, and packages them for a team to share. A Skill's fundamental shape stays the same between here and there. Only the surrounding tooling differs.

One more limit, stated plainly: a Skill is not a security boundary. Its instructions can direct Claude to call tools in ways its stated purpose never mentioned, so a Skill from a source you do not already trust is closer to installing unreviewed software than to reading a document. That question comes after this chapter's answer, once a Skill is already the shape you picked.

The tell: a stem naming a second consumer, "reusable across applications," "another team needs it too," "maintained independently of your release cycle." That phrase moves the answer to an MCP server. Its absence, with Anthropic already covering the behavior, points to a built-in tool. Its absence without that coverage points to a custom tool.

Four items, in the exam's own shape.

1. A customer-support application built directly against the Claude API needs Claude to pull each customer's current shipping status from the company's own order database mid-conversation. Exactly one application uses this today, and the team that owns the database also owns the support application. Select one.
   - A. Write a custom tool: you define the schema, and your application executes the lookup against the order database.
   - B. Turn on Anthropic's built-in web search tool so Claude can find the shipping status.
   - C. Build an MCP server exposing the lookup, so other teams can reuse it if they need to later.
   - D. Add an instruction to the system prompt telling Claude to check the order database before answering.

2. A team deploying directly against the Claude API drafts a Skill that documents their return-policy rules and also instructs Claude to call the company's live inventory system to check stock before approving a refund. Select one.
   - A. Add a note in the Skill telling Claude not to attempt the inventory check unless network access happens to be available.
   - B. The Skill's sandbox has no network access on the Claude API; the inventory check needs a tool or MCP server, and the policy rules can stay in the Skill.
   - C. Move the whole thing into an MCP server, including the return-policy text that never needed network access in the first place.
   - D. Set `tool_choice` to force the Skill to run before Claude responds.

3. Four separate internal applications, owned by four different teams, each need to look up a vendor's sanctions-list status before approving a payment. The sanctions-list provider updates its matching rules on its own schedule, several times a year, and none of the four teams controls that schedule. Select one.
   - A. Build an MCP server wrapping the sanctions-list lookup, maintained on its own, that all four applications connect to.
   - B. Turn on Anthropic's built-in web search tool, since the sanctions list is published on the web.
   - C. Add the same system-prompt instruction to all four applications, telling Claude to always check sanctions before approving a payment.
   - D. Stand up a company-wide integration gateway that proxies every external lookup the firm will ever need, and connect Claude to that.

4. Claude Code is already connected to an MCP server that exposes tools for the company's ticketing system: creating tickets, updating status, and searching. The support team also wants Claude to apply their specific triage rubric, how to score urgency and who to escalate to, every time it works with a ticket. Select two.
   - A. Keep the existing MCP server for the ticket actions.
   - B. Add a Skill documenting the triage rubric, which Claude applies once it already has ticket data from the MCP server.
   - C. Replace the MCP server with a Skill that both creates tickets and scores urgency.
   - D. Skip the Skill and put the full triage rubric in the system prompt every session instead.

## Reference, not revision

The self-test above does not draw on anything below. These are the specific numbers and field names Anthropic publishes, and they can change without changing the decision rule above.

- A `SKILL.md`'s frontmatter needs only `name` and `description`. `name` is capped at 64 characters, lowercase letters, numbers and hyphens only, and cannot contain the words "anthropic" or "claude." `description` is capped at 1,024 characters.
- Progressive disclosure has three costs: roughly 100 tokens per Skill for its name and description, loaded at every session start regardless of use; under 5,000 tokens for the SKILL.md body, loaded only once triggered; and nothing at all for bundled scripts or reference files until Claude actually opens them.
- Invoking a Skill through the Claude API means passing a `skill_id` inside the `container` parameter alongside the code-execution tool; Skills only run inside that container.
- Anthropic's pre-built Skills, PowerPoint, Excel, Word and PDF, are available on the Claude API, claude.ai and the major platform partners, but not inside Claude Code.
- Managed Agents ships its own eight-tool default set (`bash`, `read`, `write`, `edit`, `glob`, `grep`, `web_fetch`, `web_search`) as a single toolset entry. The Agent SDK ships a different list again: file operations, search, execution, web access, plus orchestration primitives including Skill and Agent themselves. Neither list matches the Messages API's built-in set described above, and none of the three is worth memorizing beyond knowing they differ.
