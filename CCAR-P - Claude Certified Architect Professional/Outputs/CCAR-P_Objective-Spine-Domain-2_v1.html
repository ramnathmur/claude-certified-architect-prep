A policy-servicing assistant, 12,000 conversations a day

The assistant answers coverage questions, updates contact details, initiates claims, and escalates anything above a value threshold. Today: 12,000 conversations a day, averaging fourteen turns. Compliance requires a standing policy text on every model call. Five objectives, one system, and the same decision keeps serving two of them.

2.1Choose per call path, not per system

Two call paths, two answers. Intent classification runs at the front of every turn: bounded, high-volume, in front of a user waiting on a screen, so it takes the lowest tier clearing its benchmarked accuracy bar on real transcripts. Coverage reasoning reads policy language against a described situation and must hold several conditions together, so it takes a higher tier.

Headroom no requirement demands is cost paid on every call. Four inputs, in order: task complexity sets the floor, the accuracy bar is a number, the latency budget is a hard gate, volume multiplies both.

Exam shapeA candidate that misses the latency gate is disqualified before any cost comparison happens. Reading the accuracy column first is how a design that cannot ship gets chosen.

2.2Put the rule where it has authority

Register, refusal boundaries, the clarifying-question rule and the escalation triggers live in the system prompt, stated as concrete testable conditions. The value threshold also exists as a code-level check on the claim-initiation tool's arguments, because that one must never be argued past. Capabilities the assistant does not need are not exposed at all.

A guardrail in a system prompt is a strong default, not an enforcement boundary. The system prompt is the only place with durable authority across turns. Anything that must never happen is enforced outside the model.

The trapAn option answering a "must never" requirement with better prompt wording has answered the wrong band. A prompt instruction is persuadable; an absent tool is not.

2.3Diagnose the failure, then pick the instrument

Zero-shot handles most turns. The classifier carries five few-shot examples sitting on the one boundary measurement showed it confusing: "change my address" against "change the address on an open claim", each with a one-line rationale. Coverage reasoning carries a reasoning cue. The classifier does not, because it is single-step and the cue would cost latency on all 12,000 conversations for nothing.

Four to six examples targeted at the ambiguous boundary, not ten to fifteen easy ones. A reasoning cue buys room for intermediate computation, so it returns nothing on a single-step task and adds output tokens to every call.

Measured, not arguedOn a 400-item ambiguous sample: instruction only 71%, a rewritten instruction 74%, twelve examples of clear cases 72%, five examples on the boundary 93%.

2.4Compress the low-density part only

A case-facts block holds policy number, claim ID, amounts, agreed adjustments and current status. It is updated as facts appear and positioned outside the summarised region. Earlier discussion is summarised, the last several turns stay verbatim, and tool results are trimmed to relevant fields before entering context. A long policy document read into a call gets a key-findings block at the top and section headings throughout.

The API is stateless, so every call resends the whole history, and compression has to be non-uniform because the information is not. Precision-critical facts are extracted verbatim; low-density discussion is summarised.

Three different bugsAmnesia at three turns is missing history. Cost climbing over fifty turns is the resend, growing with the square of turn count. A missing mid-document finding is position. None of the three is the window.

2.5Order the template by stability

The template puts compliance policy, tool definitions and stable few-shot examples first, in a fixed order, forming a cacheable prefix. At fourteen turns a conversation and 12,000 conversations a day, that prefix would otherwise be reprocessed roughly 168,000 times daily. The case-facts block, summarised history, retrieved documents and the current message follow, in ascending order of volatility.

Caching reuses a byte-identical input prefix, never the output, so the stable block must be unchanged and first. Byte-identity is necessary and not sufficient: invalidation cascades forward from the first changed byte.

The flagWhen a scenario names latency and cost together, this is the answer. A request ID rendered at the top of the system prompt takes the hit rate to zero, and nothing errors.

One decision, two objectives. Ordering the template by stability served both caching in 2.5 and modular reuse across teams. Trimming tool results served both the token cost in 2.4 and attention quality. Putting the escalation threshold in the system prompt and in code served both 2.2's behavioural coherence and its enforcement. That coupling is why this domain reads as five objectives and behaves as one.
