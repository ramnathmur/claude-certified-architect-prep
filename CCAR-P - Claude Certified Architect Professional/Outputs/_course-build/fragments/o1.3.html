Should 50,000 monthly invoices go through a fixed five-step pipeline or through an agent, a model that picks its own next step? Of the 50,000, 96% (48,000) come from 40 known vendors in stable formats, and 4% (2,000) are one-offs, malformed or new. The pipeline cannot process the 2,000. The agent can process all 50,000, but it spends agent-level cost and response time on the 48,000 that never needed it.

The corpus lays the options out as a five-rung ladder. First is the plain call: one prompt, one response. Second is an augmented LLM, a large language model (LLM) given retrieval (fetching documents at request time), tools (functions it can call) or memory (information kept between interactions). Third is a workflow, which runs fixed steps in your code. Fourth is the agent, and fifth is a multi-agent system, a coordinator over specialists.

Move right only when the rung to the left demonstrably cannot meet a requirement the scenario states. Each move right costs more: the same request can take different routes (nondeterminism), and response times spread out (latency variance). Calls multiply, and with them the tokens (words and word parts) you pay for. Results get harder to evaluate, and a wrong action reaches further (a wider blast radius).

Ask whether the paths can be written down in advance§1.3

A set of paths is enumerable when you can list every route a request may take before it runs. Enumerable paths belong in code. If the next action depends on a discovery that cannot be listed in advance, the model has to choose it. That requirement alone pays for an agent. Without it, sitting further right earns no credit.

Branching does not make a path unlistable. Take a request that is classified and sent to one of five specialised handlers. The five branches are written down, so the model chooses from a fixed menu. That is routing, and it is still a workflow.

Needing data is a different question from choosing the path. When a task needs current or private data and the path is fixed, retrieval solves it. The result is an augmented LLM, and it adds no nondeterminism to the control flow, the order in which steps run.

Traffic can be mixed. In the opening example, 96% of invoices share a known format and 4% are novel. Give each population, meaning each group of similar requests, the cheapest rung that handles it. A workflow takes the 96%. A validation gate, a check inside the workflow that sends failures down a different route, hands the other 4% to an agent on an exception route.

Go deeper: what Anthropic's own post says about patterns

This is not a corpus rule. It comes from Anthropic's post "Building effective agents", published 19 December 2024. The post defines workflows as systems where models and tools are orchestrated through predefined code paths, and agents as systems where models dynamically direct their own processes and tool usage. Its basic building block is a model enhanced with retrieval, tools and memory, the same combination the ladder's second rung names.

The post names five workflow patterns: prompt chaining, routing, parallelisation, orchestrator-workers and evaluator-optimiser. Prompt chaining splits a task into a sequence of steps. Routing classifies an input and directs it to a specialised follow-up task. Parallelisation runs subtasks at the same time, either as independent sections or as repeated runs that vote.

In orchestrator-workers a central model breaks the task down, delegates to worker models and synthesises their results. Its subtasks are determined by the orchestrator from the specific input and are not pre-defined, which separates it from parallelisation. In evaluator-optimiser, one call generates a response while another evaluates it, in a loop.

On when to use agents, the post says they suit open-ended problems where the required number of steps is difficult or impossible to predict and a fixed path cannot be hardcoded. It also recommends the simplest solution possible, and says agentic systems often trade latency and cost for better task performance.

Read the setup for the sentence that rules a workflow out§1.4

The opposite error is staying too far left. Three phrases in a setup rule the workflow out: "scope is not known up front", "each step depends on what the previous step discovered" and "the relevant tools are identified at runtime". Any one of them makes the path unlistable, which eliminates the workflow before the options are compared.

A workflow forced onto an unlistable task silently handles only the enumerated part. Adding tests to a legacy codebase of unknown structure shows why. The code has to be mapped first, and what the map shows decides the next step, so no fixed script can react to it. An agent with dynamic adaptive planning revises its plan as dependencies surface.

The two designs differ in the shape of their cost. A workflow's cost is a point, because every request makes the same calls. An agent's cost is a distribution, because some requests take many more calls than the average. Budget against the tail (the slowest and costliest few percent of requests) and not against the mean (the average).

A stated service-level agreement (SLA), a commitment about performance such as response time, filters designs before they are compared. A p95 target means that 95% of requests must finish within the limit, so it measures the tail, and an agent whose mean passes can still fail it.

Simplicity is the default. A task with a known path, such as the same six-section review for every submission, gets a fixed pipeline (prompt chaining: each step's output feeds the next).

When the scenario states that the path cannot be known in advance, the simpler rung is wrong and loses the item. A team that wants an agent because the workflow "feels rigid" has stated no requirement, so ask which path cannot be listed.

Go deeper: the invoice pipeline, costed and timed

This is a worked example, not a corpus rule. Assume $3 per million input tokens and $15 per million output tokens; these are round figures for the arithmetic, not a quoted price. The pipeline makes 5 calls per invoice, each with 4,000 tokens in and 500 out. That is 20,000 in and 2,500 out, which costs $0.0975 per invoice and $4,875 a month across 50,000 invoices.

The agent averages 9 calls per invoice. Because the Messages API is stateless (the model keeps no conversation between calls), each call sends the full history so far, so assume an average of 12,000 tokens in and 400 out per call. That is 108,000 in and 3,600 out: $0.378 per invoice and $18,900 a month, or 3.9 times the pipeline.

The hybrid sends 48,000 invoices through the pipeline at $0.0975 and 2,000 to the agent at $0.378. That is $4,680 plus $756, or $5,436 a month. The 2,000 also pay for the three pipeline calls made up to the gate, at $0.0195 each, which adds $117 and makes $5,553.

That is 13.9% above the pure pipeline, against 288% above for the pure agent. It prices every exception invoice at the agent's average, though the exceptions are the hard cases.

For the timing in the figure, assume each call takes 1.5 seconds. The pipeline always takes 5 calls, or 7.5 seconds. The agent averages 9 calls, or 13.5 seconds, and its 95th-percentile invoice takes 20 calls, or 30 seconds. Against a p95 limit of 15 seconds, the pipeline passes, and the agent's mean passes while its p95 fails.

An open-ended investigation can only be scoped by exploring first, such as adding tests to a legacy codebase of unknown structure.

  • CorrectUse an agent with adaptive planning: map the structure, prioritise high-impact areas and adapt as dependencies surface.

The first is a fixed pipeline. The review has the same six sections every time, so its paths can be listed, and "feels rigid" states no requirement that an agent would meet. The second is an agent with adaptive planning. Scope is discovered by mapping first, so no fixed script can react to what the mapping finds.
