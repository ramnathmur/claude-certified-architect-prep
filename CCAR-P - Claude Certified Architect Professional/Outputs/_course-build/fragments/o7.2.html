On Monday a team has two tasks for its AI coding tool. One is a library migration across 45 files, with three plausible ways to sequence it. The other is a single-file bug with a clear stack trace. Starting both in the same way is the mistake, and the difference between them has nothing to do with how hard each one looks.

Six months after adoption, an executive asks whether the investment paid off. The team's answer is that invocations have grown every month. This objective covers the choices in between: how to start a task, how to correct one that went wrong, how to run the tool in a pipeline, and what to measure afterwards.

Plan when the approach is undetermined, and execute when it is fixed§7.3

Plan mode explores, understands and designs, then presents a plan before executing. It uses read-only operations, so it has no side effects. Direct execution implements immediately. The combined pattern is to plan for investigation and design, have a human approve, then execute directly against the approved plan. The documented trap is to start directly and switch to planning when the task gets hard.

The discriminator is whether the approach is already determined, and not the size or difficulty of the task. If several valid approaches exist and choosing wrong means expensive rework, plan first. If the spec fixes the approach, execute. A plan is also a reviewable artifact, which satisfies approval and audit requirements that a finished diff does not.

Restructuring a monolith into services across dozens of files has many valid approaches, and a wrong one is expensive to unwind. Adding an integration with several valid approaches makes the approach the decision. A migration touching 45 or more files has blast radius, and a reversal halfway is costly. In a change-controlled environment, a multi-approach refactor needs a plan, because the plan is the artifact the approval process attaches to.

Implementing a function against a well-defined input and output spec needs direct execution, since a planning round would be pure overhead. So does a single-file bug fix with a clear stack trace, where there is nothing to decide. A large task whose approach was settled in an approved design also executes directly, since size is not the discriminator.

Match the technique to the failure you can see§7.4

When a first attempt goes wrong, the stem usually shows the signature of the failure, and the signature selects the technique. The corpus names five: the interview pattern, test-driven iteration, concrete examples, feedback batching and review isolation. Batching covers two cases, so the figure has six rows.

If each generated version misses a different requirement, the brief is incomplete, and iterating on the output never completes a brief. Use the interview pattern: have the model ask its clarifying questions before it implements. If correctness can be checked as an assertion and prose bug reports get partial fixes, write the test suite first and iterate by feeding concrete failures back.

Tests are a machine-checkable definition of done, and prose edge cases are read inconsistently.

If the shape of the output varies from run to run under an unchanged instruction, add 2 to 3 concrete input and output pairs, since examples show the format and the decision logic unambiguously. Lengthening the prose description is rejected, because it is still ambiguous and only longer.

For review feedback, put interacting issues in one detailed message, because separate fixes to interacting issues contradict each other. Independent issues go one at a time, so that each change stays easy to verify. A session that generated code is less effective at reviewing it, because it retains its reasoning context and is unlikely to challenge its own decisions, so use an independent instance.

Make the output machine-readable at the source§7.5

To run Claude Code in a pipeline, use claude -p "<prompt>", equivalently --print. It processes the prompt, prints to stdout and exits. Without it, the pipeline hangs waiting for input. The corpus lists options that do not exist and must be rejected: --batch and CLAUDE_HEADLESS=true. Redirecting stdin from /dev/null is a workaround and not the mechanism.

A person reading prose tolerates variation, and a program parsing fields does not. For structured output, --output-format json forces JSON and --json-schema enforces a schema for safe downstream parsing.

The project instruction file can supply testing standards, fixture conventions and review criteria to the CI run, and existing test files in context prevent duplicate test generation. A review that posts near-duplicate comments on every push needs the prior run's findings fed in, with an instruction to report only new or still-unaddressed issues.

The Batch API is 50% cheaper and allows up to 24 hours, with no latency guarantee. A custom_id matches outputs to inputs. It cannot execute a tool mid-request and return the result.

An overnight tech-debt report that nobody is blocked on suits it. A blocking pre-merge check does not, because a developer is waiting. Non-urgent analysis that fetches related files mid-analysis also stays synchronous, since batch cannot execute tools during a request and the flexible deadline is irrelevant.

Go deeper: what the CLI documentation confirms, and a batch saving

These are dated notes, not corpus rules (live docs, read 2026-10-27). Anthropic's CLI reference describes claude -p "query" as a query through the SDK that then exits. It can take piped input. --output-format accepts text, json and stream-json, and applies in print mode. --json-schema returns validated JSON matching a schema, also in print mode only. --permission-mode accepts plan among its values, which is how a session can start in plan mode.

A worked example, not a corpus rule, with invented costs. A nightly report that costs $200 run synchronously costs $100 as a batch, using the 50% discount in Anthropic's model documentation (live docs, read 2026-10-25). The saving applies only if the report needs no tool call partway through and can wait, since batch allows up to 24 hours and gives no latency guarantee.

Measure the delivery outcome, against a baseline set before adoption§7.6

The value of AI tooling is the change in the delivery outcome it was adopted to improve. Invocation counts, seats onboarded, hours in the tool and lines of generated code accepted are not value. The discipline has three parts: name the metric before adoption, establish a baseline, and state the confound, the other change in the period that could explain the result.

Activity data has one legitimate use, as a leading indicator during rollout, since low adoption explains a flat outcome metric.

Match the metric to the adoption rationale. To shorten delivery cycles, use cycle time from first commit to merge. To reduce defect escape, use defects found in production per release. To cut review latency, use the time from review requested to review completed. To accelerate onboarding, use the time from a new engineer's start date to their first merged non-trivial change.

Reject any metric chosen after the data was collected, because a metric selected because it moved is not evidence. Reject any with no pre-adoption baseline, because a figure with nothing to compare against is a number and not evidence. State the confound yourself: the team size changed, the release process changed, or a large refactor landed mid-quarter. Naming it is the difference between a measurement and a pitch.

Go deeper: a baseline and a confound in numbers

This is a worked example, not a corpus rule, and its numbers are invented. In the quarter before adoption, cycle time from first commit to merge averaged 5.2 days. Six months later it averages 4.1 days, a fall of 21.2%.

That is a result worth reporting, and only with its confound beside it. If the release process also changed in the period, say so, and say how much of the change you cannot separate. Invocations that grew every month would have been equally true if cycle time had not moved at all.
