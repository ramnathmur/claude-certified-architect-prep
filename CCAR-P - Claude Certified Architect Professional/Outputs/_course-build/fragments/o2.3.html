A support agent has two tools that overlap: search_orders and lookup_account. In one week the routing log shows 300 wrong calls out of 5,000 requests, which is 6%. Every one of the 300 is a request that both tools could answer, such as "where is my refund?", which can mean an order's status or a billing record. The other 4,700 route correctly.

One engineer proposes adding twelve examples of obvious requests to the prompt. Another proposes five examples of requests like the refund one. The first group of examples describes cases that already work, and the second describes the cases in the log.

Aim the examples at the cases that fail§2.3

Few-shot prompting puts worked examples in the prompt. Use it when prose instructions produce inconsistent output, or when a specific case is ambiguous. A prompt with instructions and no examples is zero-shot, and the guide's objective names it next to few-shot. The corpus gives no decision rule for it, so this chapter states none.

The corpus sets two sizes. When a model formats output inconsistently despite clear instructions, add 3 to 4 examples of the exact required format. When it misroutes an ambiguous request between two tools, add 4 to 6 examples aimed at exactly that ambiguity, each with a stated rationale for the tool chosen. In the opening case, the five examples go on requests that fit both tools.

The proposal to add 10 to 15 examples of clear-cut, unambiguous cases is rejected. Examples teach by pattern-matching to what they show, and the clear-cut requests are the 4,700 that already route correctly. Volume spent there takes context window space and leaves the 300 where they were.

The same logic applies to examples already in the prompt. If they were drawn from the easiest, most common cases, replace them with examples drawn from the observed failure distribution, whatever their count. At the other end, when a single well-chosen example already resolves an ambiguous formatting case in testing, ship with it. Padding to an arbitrary count adds nothing.

Go deeper: what Anthropic's prompting guidance says about examples

This is a dated note, not a corpus rule. Anthropic's prompting guidance (live docs, read 2026-10-25) asks for examples that are relevant, diverse and structured. Diverse means they cover edge cases and vary enough that the model does not pick up an unintended pattern.

Structured means each example sits in an <example> tag, with several wrapped in <examples>. The page says to "Include 3-5 examples for best results", and also notes that worked examples shape how Claude reasons inside its thinking.

The page's range of 3 to 5 sits close to the corpus's 3 to 4 and 4 to 6 and does not match either. Answer exam items with the corpus numbers. Guides are due to be updated on 17 November 2026, so watch for a change in wording.

A worked example, not a corpus rule: one example for the opening case reads as an input and a decision. Input: "Where is my refund?" Tool chosen: lookup_account. Reason: the customer asks about money returned, which sits on the billing record, and gives no order number. The stated reason is what lets the model separate this request from one that names an order.

Add a reasoning cue only where the task has steps§2.4

A chain-of-thought cue asks the model to write out its reasoning before the answer. Add one when the task has several steps to get through: multi-step math, multi-stage analysis, a comparison across N items, or a stepwise transformation. Leave it off a single-step task, such as translating one sentence. There is nothing to reason through, and the cue only adds tokens (the word pieces the model reads and writes) and latency.

A multi-step task does not always need the cue. If it already reasons correctly and consistently without one, verified in testing, don't add it. The cue's cost in tokens and latency is paid for by a measured accuracy gap, and a task that already performs correctly has no gap to close.

Sometimes the task shape calls for deliberation and a latency budget limits it. Then use a bounded or structured cue, such as a scratchpad of fixed length, instead of open-ended chain-of-thought. It keeps most of the accuracy benefit inside the budget.

Go deeper: pricing a cue, and what the API calls thinking

This is a worked example, not a corpus rule. A translation feature handles 200,000 requests a month. Suppose a cue made each reply carry 150 extra output tokens, an assumption chosen for the arithmetic. That is 30,000,000 tokens a month. Anthropic's model overview (live docs, read 2026-10-25) lists Claude Sonnet 5.5 output at $10 per million tokens, so the cue costs $300 a month and the translations come out no better.

For latency, assume the model writes 80 tokens a second, again an assumption. An open-ended chain of 600 tokens of reasoning takes 7.5 seconds before the answer starts. A scratchpad capped at about 120 tokens takes 1.5 seconds, which fits a 3-second budget.

The API also has a separate thinking feature. Live docs read on 2026-10-25 say the manual form, set with budget_tokens, is deprecated on the Claude 4.6 models and rejected with a 400 error from 4.7 onward. Adaptive thinking, with depth set by an effort setting, replaces it. Thinking tokens are billed as output tokens and count toward the context window.

Inference: the corpus rows above concern a cue written in the prompt, and the thinking parameter is a separate control, covered with model choice in O2.1.

Remember

  1. When instructions have already failed, add examples. Use 3 to 4 for output format and 4 to 6 aimed at an ambiguity. Examples teach by resemblance to what they show.
  2. Reject 10 to 15 clear-cut examples. Replace convenient examples with ones drawn from the observed failures, and ship a single example that resolves the case in testing.
  3. A reasoning cue belongs on multi-step tasks: math, analysis, comparison across N items, stepwise transformation. A single-step task gets none.
  4. If a multi-step task is already correct and consistent without a cue, verified in testing, leave the cue out. A measured accuracy gap is what pays for it.
  5. When a latency budget would be breached, use a bounded or structured cue such as a short fixed scratchpad, instead of open-ended chain-of-thought.
