A sponsor opens the first meeting with three sentences. "We want a multi-agent system to handle our intake." "It has to be as accurate as possible." "Our board will accept 95% accuracy." Each sentence sounds like a requirement, and none of them can be designed against or checked. The first names a solution, the second sets no target, and the third gives a number that does not say what an error costs.

An architect who builds what was named, or who pushes back that the request is vague, has skipped the work that discovery exists to do. The corpus puts it in three steps, and each one leaves the sponsor with something they can hold delivery to.

Find the decision behind the request§6.1

A stakeholder who arrives with a chosen solution has still not stated a problem. The corpus discriminator is whether the business decision the system serves has been stated, or only a solution the stakeholder has pre-selected. Discovery ends when that decision is written down. The architect's first output is the problem and the decision it feeds, and never a component list.

If a sponsor asks for "a multi-agent system to handle our intake", elicit the intake problem and the decision it feeds, then assess whether the named pattern fits. The pattern may be right, and it cannot be assessed against a problem nobody has stated. If the elicited problem does not need the pattern, say so, offering the simpler design and what it gives up. The problem licenses the pattern, and the order matters.

If a sponsor states a business outcome with no solution attached, the precondition is already met, and you can move to bounding the requirement. If the team proposes benchmarking candidate models before the problem is stated, defer it, since a benchmark number cannot be read without a target and an error cost.

Turn an aspiration into something verifiable§6.2

The discriminator is whether the stated requirement can be verified: is there a number, a method and a set. Three phrasings are unbounded: "as accurate as possible", "reliable enough for production" and "at least as good as our team". A bounded requirement has four parts: a target number, a measurement method, an evaluation set and the cost of an error. The sponsor's answer is a signed acceptance criterion that they can hold delivery to.

If a sponsor says "as accurate as possible", establish the accuracy the use case requires and what a wrong answer costs, before design. No design can be shown to have met or missed an unbounded target.

If the requirement is bounded but the evaluation set is not specified, specify a held-out set stratified to the real input mix, meaning cases kept aside from tuning and sampled so that each type of input is represented. An unstratified set reports a number for a population that does not exist.

If the sponsor cannot state the cost of an error, keep eliciting. The cost of an error is a design input for a probabilistic system and not a footnote, because it determines the threshold, where review sits and which direction errors lean. Once the requirement is bounded and measured and the mix is known, move to design.

Let the cost of each kind of error set the threshold§6.3

The discriminator is whether a false positive and a false negative cost the same. A false positive is an alert on something that was fine, and a false negative is a miss. The asymmetry decides three things: the confidence threshold, the direction in which the model is biased, and where human review sits. In regulated flows the expensive direction is usually the undetected miss, and the regulator defines it.

If missed fraud costs 200 times a false alert, bias toward recall and route flagged cases to human review, since the cheap error is the one a human can dismiss in seconds. If a false rejection blocks a legitimate customer payment while a missed one is recoverable the next day, bias toward precision and set a higher action threshold, because the expensive error is the irreversible one.

If a sponsor asks only for "95% accuracy" and neither direction is priced, return to discovery and price both directions, since one accuracy target cannot express an asymmetric cost. Where both directions cost roughly the same and are correctable, a single accuracy target is adequate, because there is nothing to trade off.

Go deeper: where a threshold comes from when the costs are known

This is a worked example, not a corpus rule, and the costs are invented. Suppose a false alert costs $5 of review time and a missed fraud costs $1,000, which is 200 times as much. For a transaction with fraud probability p, leaving it alone costs p times $1,000 on average, and flagging it costs (1 minus p) times $5. Flagging is cheaper when p exceeds 5 over 1,005, which is 0.5%.

The cost ratio puts the threshold close to 0.5%, and the large number of flags that follows is the reason human review sits behind them. A single accuracy target says nothing about this cost, which is why the cost ratio and not a default cutoff sets the threshold.

InferenceExpect a stem in which the sponsor names a solution, a vague target or a single number, and options that start design or measurement too early.

A sponsor opens the engagement by naming the architecture they want.

A triage system where a missed high-severity case is far costlier than a false alert.

  • CorrectBias the system toward flagging, set the confidence threshold from the cost ratio, and route flagged cases to human review.
  • WrongWRONG-AXISTune for the highest overall accuracy on the evaluation set. It optimises an aggregate that weights both error directions equally when the business does not.
  • WrongREPAIRAdd a post-hoc audit that samples missed cases weekly. It detects the expensive error after it has already been paid for, instead of biasing against it upstream.

Design shapeA sponsor requests a document-processing system that is "as accurate as possible". The answer establishes the accuracy the use case requires, how it will be measured and what an error costs, before design.

Selecting the highest-capability model and the most thorough pipeline is OVERSPEC, since it buys an unpriced guarantee against a target nobody has stated. Escalating to the sponsor's leadership that the requirement is too vague to work with is DISCARD, because it treats requirement definition as an obstacle to the architect's work and not as the work.

Say it backA sponsor wants "a multi-agent system, as accurate as possible, at 95% accuracy". The product flags suspected fraud, where a miss costs far more than a false alert. How do you run the first conversations?

Start with the decision the system feeds, and assess the multi-agent pattern against that problem. Bound "as accurate as possible" into a target number, a method, a stratified held-out set and the cost of an error. Price both error directions. Then bias toward flagging, set the threshold from the cost ratio, and put human review behind the flags, instead of tuning for one accuracy figure.
