An HR assistant serves 4,000 employees. Its document store holds three tiers: general policy for all staff, manager guidance for about 400 people managers, and compensation planning for 12 HR business partners, which is 0.3% of staff. The figures are illustrative. A review finds two gaps.

The first is a delete_document tool that no workflow uses.

The second is that every search runs under one service account with read access to all three tiers, and a filter drops restricted chunks after the search. When an ordinary employee asks about pay bands, the compensation plan ranks first, the filter removes it, and the answer is built from the chunks ranked fourth and fifth. The plan's text has still been in the model's context and in the trace store.

Remove the capability when the scenario says it is not needed§3.2

Least privilege means the capability does not exist. Compensating controls are logging, confirmation prompts, time-window restrictions and rate limits. They are correct when the privilege is genuinely required and its risk must be managed. They are wrong when the scenario states that the capability is not needed. The tell is in the scenario's wording: if it says the agent does not need the capability, remove it.

Take an agent that holds a write or delete capability no workflow uses. Remove it from the tool set. The privilege is the gap, and nothing else closes it. Logging records afterwards that the unwanted action happened and never prevents it. Restricting the capability to business hours narrows a time window and leaves the privilege whole, so the unwanted action is acceptable at 2 pm.

When a workflow genuinely requires a consequential capability, keep it and add human confirmation and audit logging. Confirmation is the right control for an action that is needed and consequential. When the capability is needed only for one narrow case, replace the broad one with a narrow capability scoped to that case, since narrowing the privilege beats gating the broad one.

Compliance may require proof of who did what. Add audit logging for that, together with removal of unneeded privileges. Logging satisfies an audit requirement and is no substitute for scoping.

Enforce entitlement in the query, as the user§3.3

Authentication establishes who is calling. Authorization establishes what that caller may reach. The default gap in an agent system is that the agent calls tools under its own service credential, so the user's entitlements are stripped at the tool boundary. Every user collapses into one identity at the point where data is reached.

Security people call this the confused deputy: a privileged component acting for a less privileged caller whose limits were lost on the way.

The corpus discriminator is whether entitlement is enforced in the query or after the content has been retrieved. When it is enforced afterwards, restricted content enters context and the trace store even though it is filtered out of the answer.

Auditors require enforcement that can be proved at the point of access. A filter in the query is enforced where the data is reached, under the propagated identity, while a filter in application code is only asserted.

With a multi-tier document store, one service account and post-retrieval filtering, propagate the user's identity and apply an entitlement filter as part of the retrieval query. Restricted chunks are then never candidates, never ranked and never traced.

If the vector store cannot filter at query time, keep separate indexes per entitlement tier and route each request by the caller's tier. That takes more infrastructure, and enforcement becomes structural and no longer depends on a code path.

A shared third-party integration may need each action attributable to the person who took it, which the corpus calls the operator. Substitute a per-user credential for the one shared service token, because both attribution and revocation need a per-user identity.

If someone proposes a system-prompt rule stating what the agent may not access, reject it. Prompt-level rules are probabilistic, and security enforcement must be deterministic.

Go deeper: three gaps in the filter-after design, and the cost of a probabilistic rule

This is a worked example, not a corpus rule, and its figures are invented. The post-retrieval filter in the opening has three gaps. It spoils answers: when a restricted chunk ranks first, the filter drops it and the answer rests on lower-ranked material, with no sign to the user that this happened.

It lives in application code, so any path to the index that bypasses that code has no authorization at all, such as a debugging endpoint or a batch summarising job. And the trace store holds chunks that were filtered out of the answer, in a system whose own access controls were never designed for compensation data.

A system-prompt rule has a cost in numbers too. A control that holds 99% of the time fails 400 times a day at 40,000 requests a day. A deterministic filter in the query has no such failure rate.

Where the exam bites

KnownThe guide's Sample 1 is this chapter's least-privilege question. A support agent can read tickets, draft replies, issue refunds and delete user accounts, and staff only ever need to read tickets and draft replies. The question asks which change best reduces risk, applying least privilege. The answer removes the refund and delete tools from the agent's configuration.

The guide's reason is that least privilege removes capabilities the role does not require, which eliminates the attack surface rather than monitoring or guarding it. Adding logging and adding a confirmation prompt are detective or compensating controls. Swapping in a larger model has nothing to do with authorization scope. This project tags the logging and the confirmation prompt DETECTIVE-FOR-PREVENTIVE. The Trap families page defines each label below.

The corpus words the same rule as its own scenario:

  • WrongHALF-MOVEKeep it and log every use for audit review. Logging records afterwards that the unwanted thing happened and never prevents it.

A multi-user assistant reaches a tiered document store under a single service account and filters restricted results out of the answer.

  • CorrectPropagate the requesting user's identity to the retrieval layer and apply the entitlement filter inside the query.
  • WrongREPAIRKeep post-retrieval filtering and add a second review pass over the drafted answer. It fixes downstream what the query could have prevented upstream, and the restricted content is already in context and in traces.
  • WrongWRONG-AXISAdd an instruction to the system prompt telling the agent which tiers it may cite. This treats an access-control problem as an instruction-following problem.
Say it backAn agent has a delete tool that no workflow uses, and the team proposes logging every delete. Separately, a RAG assistant searches under one service account and drops restricted chunks from the answer. What do you recommend in each case?

Remove the delete tool. The scenario says nothing needs it, so logging would only record a misuse after it happened. For the assistant, propagate the user's identity to retrieval and put the entitlement filter in the query, so restricted chunks are never retrieved, ranked or traced. Filtering the answer is too late, because the content has already reached context and the traces.
