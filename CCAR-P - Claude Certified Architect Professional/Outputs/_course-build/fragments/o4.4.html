On Monday morning, the share of sampled answers marked wrong from a support assistant jumps from 4% to 19%, a rise of 15 points. The knowledge base was re-indexed on Sunday night. The model version, the prompt and the response times are unchanged. The answers are fluent and confident, and they are wrong. The figures are illustrative.

Someone proposes moving to a more capable model, since "the model has started hallucinating". The model is the layer that changed least and costs most to swap, so what does the symptom point at?

Check data and retrieval first, and the model last§4.10

The corpus gives an order: data and retrieval, then prompt and context, then model mismatch. Each earlier layer poisons everything downstream, and checking it is far cheaper. The discriminator is which layer the symptom's timing and shape point at, and not which layer is quickest to swap. By the timeline rule, a sharp drop with a change immediately before it makes the change the hypothesis.

Match the symptom to the layer. Confidently wrong right after a refresh or re-index points at retrieval and indexing, and the model, which did not change, is not the cause. Wrong on one document or query type and correct elsewhere points at data coverage or chunking and not a general capability deficit. Correct facts with the required format or steps missing points at the prompt.

Format that varies across runs despite explicit instructions needs few-shot examples (§2.3), and more prose has already failed. Failing only on long inputs, with mid-document facts missed, is context structure and position (§2.6), not an exceeded window.

Forgetting a fact from two turns ago in a short conversation is the application not resending history (§2.5), since the API is stateless: it keeps nothing between calls, and the application must send the history each time. Failing broadly on multi-step reasoning, with retrieval verified and the prompt clean, is model mismatch.

"Hallucination" names three faults in the corpus. If the context contained the answer and the claim was unsupported, the fault is grounding or the prompt, and the fix is cited spans plus a verbatim check.

If retrieval returned nothing relevant, fix retrieval and add an explicit refusal or escalation path. If the claim was fabricated under truncation or compaction, it is a context-management fault (compaction means summarising older context to make room), and the fix is to extract the critical facts verbatim into a structured block that the summary never touches.

Go deeper: what checking retrieval first looks like

This is a worked example, not a corpus rule, and its counts are invented. The team keeps 50 questions with gold passage IDs. Before the re-index, the gold passage was in the top five results for 44 of them, a Recall@5 of 0.88. After the re-index it is in the top five for 30, a Recall@5 of 0.60.

That is a drop of 28 points in a layer that sits before the model, and it accounts for the wrong answers without any change to the model.

An upgrade to a larger model would have kept the same missing passages and produced fluent answers on top of them. The check is one script run against a fixed question set.

Where the exam bites

KnownThe guide's Sample 3 is this chapter's failure, and it is the one official Domain 4 sample. A RAG system suddenly returns confident but incorrect answers after a document refresh, while latency and model version are unchanged, and the question asks where to investigate first. The answer is the retrieval and indexing step.

The guide's reason is that confident-but-wrong answers after a refresh, with the model and latency unchanged, point to retrieval feeding the model poor context, for example a broken re-index or mismatched embeddings. The other options blame silent weight changes, a low temperature and a shrunken context window, and none of them would be triggered specifically by a document refresh. O3.5 covers why indexes degrade after a refresh. The Trap families page defines the labels below.

Say it backAfter a re-index, a RAG assistant gives confident wrong answers, and a teammate says the model has started hallucinating. Separately, an assistant forgets a customer's name from two turns ago. Where does each investigation start?

For the re-index, start with retrieval and indexing: measure Recall@k against gold passages and inspect the chunking of the refreshed documents. The model did not change, and the timeline names the re-index as the hypothesis. For the forgotten name, check whether the application resends the conversation history, because the API keeps nothing between calls and a short conversation cannot have exceeded the window.

Remember

  1. Diagnose in this order: data and retrieval, then prompt and context, then model mismatch. Each earlier layer poisons the ones after it, and checking is cheaper.
  2. A sharp drop right after a change makes the change the hypothesis. Confidently wrong right after a refresh means retrieval and indexing.
  3. Wrong on one document or query type means coverage or chunking. Right facts with wrong format means the prompt. Inconsistent format despite instructions needs few-shot examples.
  4. Long-input misses are structure and position. Forgetting two turns back is the application not resending history.
  5. Three hallucination causes, three fixes: grounding with cited spans, retrieval plus a refusal path, and context management with verbatim critical facts. Model mismatch is a conclusion, never an opening move.
