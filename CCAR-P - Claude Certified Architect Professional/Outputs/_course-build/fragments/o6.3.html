In one week, four people ask about the performance of the same document-classification service, which handles 40,000 items a month and routes 12% of them to human review, or 4,800 reviews. The operations lead is staffing the review queue. The finance director is deciding a renewal. The compliance owner is about to sign off. The engineering lead is tuning the system. The figures are illustrative.

An architect who sends all four the same dashboard has given each of them a pile of true numbers and left each to find the one that bears on their decision. What should each person see, and what should the contract with the client promise?

Choose the metric from the decision in front of the person§6.5

The corpus discriminator is which decision this particular stakeholder is about to make. A useful metric is tied to that decision and is stated together with what it does not cover. The failure mode is a set of metrics that are real, measurable and irrelevant to the decision in front of that person. Pick the metric from the pending decision, and not from what the monitoring stack already emits.

For the operations lead, report the volume reaching human review and its variance. The finance director gets cost per processed item and its trajectory at projected volume, since model accuracy in isolation does not price a renewal. The compliance owner gets the override rate and audit-trail completeness on the regulated segment. The engineering lead gets per-segment accuracy, latency percentiles and a failure taxonomy.

Handing a stakeholder the full monitoring dashboard to select from looks thorough and transparent. It transfers the architect's interpretation job to someone without the context to do it. More metrics is not a fuller picture, because a figure that does not inform the decision in front of the person is noise. State the blind spot of each metric alongside it.

Qualify an accuracy commitment, and commit only what the provider controls§6.9

The discriminator is whether the commitment depends on inputs the provider does not control. Availability and latency are provider-controlled and are committed normally. An accuracy commitment has four parts: what is committed, on what population, how and how often it is measured, and what is excluded. A stated metric with no stated exclusions is read as covering everything.

If a client wants "95% accuracy" in the contract, commit per segment, with the scoring method, the cadence and the excluded segments named. Accuracy depends on the client's future input mix, which the provider does not control. A provider that offers only availability and latency and no accuracy commitment is insufficient, because it pushes all performance risk to the client and leaves them unable to plan.

If the client's input mix is contractually fixed and monitored, a tighter accuracy commitment is defensible, since the uncontrolled variable has been controlled. For latency on a provider-hosted endpoint, commit a percentile and not a maximum, because tail latency on a shared service is not fully controllable.

Go deeper: how a flat number can fail with no change in the system

This is a worked example, not a corpus rule, and its figures are invented. In the pilot, 70% of the documents were standard and scored 98%, and 30% were scanned forms that scored 88%. The pilot's overall accuracy was 95%, and a team that commits that number flat is promising it for every future mix.

If the client later sends 40% standard and 60% scanned forms, the same system scores 92%. The system did not change, and the contract was missed. A per-segment commitment of 98% on standard documents and 88% on scanned forms would have been kept in both mixes.

Make feedback a recurring loop that grows the evaluation set§6.10

The discriminator is whether the mechanism recurs and whether each item becomes an evaluation case. A structured loop captures four things: the input, the system output, the expected output and the reviewer. Expectations drift in one direction, toward believing the system is more capable and more finished than it is. They re-inflate at every demonstration, so keeping expectations in line is a routine and not a single event.

If a sponsor's expectations inflate after a successful demo, establish a recurring review that shows real performance on real inputs against the agreed criteria. A single correction does not hold against continuous drift. A single well-argued memo is necessary and not sufficient, since it fixes today's gap and none of next quarter's.

If users report failures in a shared chat channel, restructure the intake so that it captures input, output, expected output and reviewer, and feeds the evaluation set. Anecdotes have no frequency and cannot be prioritised. If feedback is collected and the evaluation set never grows, the loop is broken, because the system is measured against a set that diverges from what it processes.

Remember

  1. Choose each stakeholder's metric from the decision they face, and state what it does not cover. A dashboard is not an answer, and more metrics is not a fuller picture.
  2. Commit availability and latency normally, with latency as a percentile. Qualify an accuracy commitment with its population, method and cadence, and exclusions, and commit per segment.
  3. Do not commit the pilot aggregate flat, and do not refuse to commit accuracy at all. A fixed and monitored input mix permits a tighter figure.
