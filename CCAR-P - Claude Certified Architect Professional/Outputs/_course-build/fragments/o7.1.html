Four engineers work in one repository. Three of them get generated code that follows the team's naming convention. The fourth joined last week and gets code that does not. Nobody changed the model, the prompt or the code, and the new engineer's pull requests keep failing review on the same point.

The convention sits in the other three engineers' personal configuration files, on their laptops. It never reached the repository, so a fresh clone inherits none of it. Which configuration belongs where, and which of it is a request and which is a rule?

Put shared standards where a clone inherits them§7.1

The corpus lists four levels of instruction file: user (~/.claude/CLAUDE.md), project (CLAUDE.md or .claude/CLAUDE.md in the repository), directory-level files, and .claude/rules/*.md. They are concatenated from the root down to the working directory. The live documentation (read 2026-10-27) adds that files above the working directory load at launch, and files in subdirectories load when Claude works with files there. Every discovered file contributes, and the corpus documents no override precedence between CLAUDE.md levels.

Project-level files are version-controlled and reach everyone who clones. User-level files reach one person and are invisible in code review. The test is whether a thing survives a clone and reaches someone who was not present: if it does not, it is not enablement. When three engineers apply a convention and a new fourth does not, move the convention from their user-level files into the project file and commit it.

The command /context shows what actually loaded into the current session, and /memory answers a different question, which is where the memory files are.

A partner team that wants your Claude Code setup needs version-controlled shared configuration, skills and commands, plus an onboarding path to follow, because the artifact is inherited and nothing depends on who attended what. A recorded walkthrough is rejected: it is durable and frozen, and teaches the old setup with full confidence on the day it changes. A shared chat channel for questions is rejected as reactive support and not an inherited artifact.

Poor results on a large legacy codebase, blamed on repo size and contributor count, point to missing committed context: write the conventions and structure into the project files.

A personal override is available too. One engineer who wants a private /commit behaviour places ~/.claude/skills/commit/SKILL.md, and a personal skill overrides a project skill of the same name, so teammates are unaffected. A subdirectory file added to "override" the project file is rejected, since files concatenate and a conflict leaves the model with two contradictory instructions.

Ask when it must apply, then how hard it must hold§7.2

Choose a mechanism with two questions, in order. First, when must this be in effect: always, on matching paths, or on invocation. Second, how hard must it hold: as guidance, as a capability boundary, as isolation, or as unconditional enforcement. A behaviour that a configuration mechanism governs is corrected at that mechanism, and not by prose placed beside it.

Universal coding standards belong in the project CLAUDE.md, since they are needed every session and on-demand invocation would depend on memory.

A convention that applies only to test files and bleeds elsewhere belongs in a .claude/rules/ entry with a glob for the test paths, which is deterministic path matching and not the model's inference from headings.

A 500-line CLAUDE.md that mixes standards, pull-request checklists and deploy steps should keep the universal standards, move workflow procedures to skills and file-scoped conventions to rules. Always-loaded tokens are paid every session, and occasional procedures should cost nothing when unused. Moving everything into skills is rejected, because universal standards would then need explicit invocation every time.

When a skill uses a tool it should not touch, scope allowed-tools in that skill's frontmatter. Adding "do not use that tool" to the skill body is rejected, since advisory prose competes with context and does not set the condition.

When a skill's exploratory output crowds the main task out of context, set context: fork, which runs the skill in an isolated subagent context and returns only the result. "Be concise" is rejected because it asks the model to simulate isolation instead of imposing it.

A rule that must hold every time, whatever any prompt says, needs deterministic enforcement: a hook, or a deny rule in the settings permissions (§7.8). Instruction prose is weighed against other context, and enforcement is not. A style preference proposed for deterministic enforcement is rejected, since it turns a suggestion into a hard failure that someone must merge a config change to undo.

Go deeper: the token cost of a long file, and what the documentation says

This is a worked example, not a corpus rule, and the sizes are assumptions. Suppose a line costs about 12 tokens, so a 500-line CLAUDE.md is 6,000 tokens at the start of every session. With 1,000 sessions a day across a team, that is 6,000,000 tokens a day. Cutting the file to 120 lines of universal standards gives 1,440,000, and the moved procedures cost nothing until invoked.

Anthropic's Claude Code documentation (live docs, read 2026-10-27) agrees with the direction. It says CLAUDE.md files are concatenated and not overridden, and it advises under 200 lines per file, because longer files consume more context and reduce adherence. It describes path-scoped rules as loading when matching files are opened, and it says instructions are context and not enforced configuration.

Its import syntax allows a depth of four hops. The corpus warns that sources disagree on that number, so never key an answer on it.

One point in the documentation differs from the corpus row. It describes allowed-tools as tools Claude may use without asking permission while the skill runs, and disallowed-tools as tools removed from the pool. The exam rule stays as the corpus states it, and a real design should test which key does what on the version in use.

Enforce in settings and hooks, since instructions only shape what Claude tries§7.8

Permission rules sit in settings.json under permissions, in three arrays: allow, ask and deny. Entries name a tool and optionally a pattern, such as Bash(git push *). Claude Code enforces them, and the model does not. Instructions in a prompt or CLAUDE.md shape what Claude tries to do, and they do not change what Claude Code allows.

If a capability must never be exercised, whatever any prompt says, add a deny rule in the settings permissions. A strongly worded CLAUDE.md instruction is rejected, since it shapes what Claude tries and does not change what is allowed.

If an action must happen every time a tool runs, such as a format, a test or an audit entry, use a hook on the relevant event, scoped by a matcher. A reminder to run the formatter in the project file is rejected, because it competes with everything else in context.

If a tool call must be stopped before it executes, use a PreToolUse hook or a deny permission rule, since both act before execution and a log acts after. When a narrow allow exists and a broad deny also matches, the call is denied: the first match in the deny, ask, allow order wins. A team style preference proposed for a hook or a deny rule is rejected as over-specification.

Settings precedence runs from managed enterprise policy, then the command line, then .claude/settings.local.json, then .claude/settings.json, then ~/.claude/settings.json. Nothing below managed policy overrides it. If an organisation must guarantee a rule survives every local override, use managed policy settings. The shared project file is .claude/settings.json, which everyone who clones receives, and the local file is one developer's personal override.

Instruction files and settings files behave in opposite ways. Instruction files concatenate, and none overrides another. Settings files have a winner: a single-value key takes its value from the highest scope, while list keys such as permissions.allow, ask and deny merge across every scope, and the merged rules run deny, ask, allow. A deny in any scope beats an allow in any scope. Inference: a managed-policy value on a single-value key still outranks every lower scope.

Go deeper: what the hooks documentation says

These are dated notes, not corpus rules (live docs, read 2026-10-27). Anthropic's hooks guide describes hooks as user-defined shell commands run at lifecycle points, which gives deterministic control, so that certain actions always happen instead of relying on the model. It configures them in the settings files, under the user and project settings.json.

A PreToolUse hook runs before a tool call and can block it: a script that exits with code 2 blocks the action and passes its message to Claude as feedback, and a hook that exits 0 can print JSON with a permissionDecision of deny.

When several hooks match, the most restrictive answer applies, in the order deny, defer, ask, allow. The memory documentation adds that CLAUDE.md is context and not enforced configuration, and that blocking a tool or path is done with a permissions deny rule in managed settings or with a hook.

Where the exam bites

KnownThe guide's three samples sit in Domains 2, 3 and 4, so none of them is a sample for this domain. Its Sample 1, on removing capabilities, is a Domain 3 item. Inference: a deny rule applies the same removal-first logic.

The scenarios below come from this project's own set, and the Trap families page defines each label. InferenceExpect options that fix the symptom with a prompt, a reminder or a wiki page, and one that changes the mechanism.

A newly hired engineer's generated code omits a convention the other three engineers always get.

  • CorrectThe convention is in the other engineers' user-level configuration and not at project level. Move it into the version-controlled project configuration and confirm with /context.
  • WrongREPAIRHave the new engineer prefix every prompt with the convention. It patches each session downstream of a configuration gap that a committed file closes once, and it fails silently the first time they forget.
  • WrongHALF-MOVEAdd the convention to a team wiki page and link it in the onboarding email. It transfers the knowledge to a human and never reaches the model's request at all.

A skill must be prevented from performing destructive operations.

  • CorrectSet allowed-tools in the skill's SKILL.md frontmatter to the minimal set it needs.
  • WrongREPAIRAdd an instruction inside the skill body telling it not to perform destructive operations. It asks the model to honour a boundary that the frontmatter can impose, and it competes with everything else in context.
  • WrongWRONG-AXISConfigure the restriction in .mcp.json or the project CLAUDE.md. The intent is right and the mechanism is wrong, since skill tool scoping lives in SKILL.md frontmatter.

An agent must never be able to force-push, and a CLAUDE.md instruction saying so has not held.

  • CorrectAdd a deny rule for the force-push command pattern to the settings.json permissions.
  • WrongREPAIRRestate the prohibition more forcefully and in more places in CLAUDE.md. Instructions shape what Claude tries and do not change what Claude Code allows, so more prose is more of what already failed.
  • WrongHALF-MOVEAdd an allow rule listing every git command the agent may run, on the grounds that an allow-list is stricter. It narrows the default path and does not stop a matching call the way an explicit deny does, and it breaks every legitimate command nobody thought to list.

Design shapeA rule must hold on every developer machine and cannot be overridden locally. The answer is managed policy settings. Putting it in the project .claude/settings.json and requiring review is HALF-MOVE, since review controls what is committed and not what runs. Putting it in the project CLAUDE.md is WRONG-AXIS, because instruction files concatenate and cannot produce a rule that wins a conflict.

Say it backA new hire's code misses a convention the others get. Separately, an agent keeps running a command that a CLAUDE.md line forbids, and a coding standard sits in a 500-line CLAUDE.md beside deploy steps. What do you change in each case?

Move the convention from the others' user-level files into the committed project file and check with /context. For the forbidden command, add a deny permission rule, because instructions shape what Claude tries and do not change what is allowed. In the long file, keep the universal standards, move procedures to skills and file-scoped conventions to .claude/rules/, and leave the always-loaded part short.

Remember

  1. Shared standards go in committed project files, since user-level files are not in version control and a clone inherits none of them. Verify with /context.
  2. Instruction files concatenate, and none overrides another. A personal skill overrides a project skill of the same name. A recorded walkthrough and a chat channel are not inherited artifacts.
  3. Pick a mechanism by two questions: when it applies (always, on paths, on invocation) and how hard it holds (guidance, boundary, isolation, enforcement). Fix a behaviour at its mechanism and not with prose beside it.
  4. Keep always-loaded files to universal standards. Procedures go to skills, and path-specific conventions go to .claude/rules/ with globs.
  5. Instructions shape what Claude tries. A deny rule or a hook changes what happens. Permissions resolve deny, ask, allow, first match wins, and specificity never counts.
  6. Managed policy sits above every local override. Do not convert a style preference into a hook or a deny rule.
