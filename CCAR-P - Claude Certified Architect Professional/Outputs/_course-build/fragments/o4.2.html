An extraction system reads four types of document, and its evaluation set reports 97.6% overall accuracy. The four types make up 78%, 15%, 5% and 2% of traffic, and they score 99%, 98%, 90% and 60%. The 2% type fails 40% of the time. The team proposes to auto-process everything the model is confident about, and customers keep reporting errors the dashboard cannot see.

The evaluation set has only 50 cases. At natural frequency the rarest type gets 1 of them, and one case cannot measure a rate. The figures are illustrative. Six corpus sections cover what went wrong: what is in the set, how it is reported, who grades it, how far the grader can be trusted, which layers it scores, and how repeated attempts are counted.

Fix the composition of the set before its size§4.3

A set built from cases the system already handles overstates performance. Source them in order: real production traces first, then synthetic cases, then hand-written cases for failures that are expected and not yet seen. A working set of 20 to 50 hand-verified cases beats hundreds of unverified synthetic ones. Keep roughly equal numbers of should-fire cases, where the check ought to trigger, and shouldn't-fire cases, where it ought to stay quiet.

The corpus discriminator is whether the set's composition or its size is the defect. A set that is missing failure modes is never repaired by adding more of what it already contains. A 500-case set reports 96% while customers still report failures: rebuild it from real production failures and report by segment. Expanding it to 2,000 cases drawn the same way multiplies the bias and tightens the interval around a wrong number.

Unverified cases add a score and no information, so 600 synthetic cases with an unknown label error rate are cut to 40 hand-verified ones. A set of only failure cases hides false alarms, and a set of only clean cases hides misses, so add the matching cases to each.

For a genuinely new capability with no production traces, hand-write cases and label the whole set provisional. Failure modes taken from the spec are hypotheses until real traces confirm them.

Report by segment, because an aggregate hides the failing one§4.4

An aggregate of 97% can conceal a 40% failure rate on a rare segment. Build the evaluation set to answer per-segment questions and not to mirror production frequency. Over-sample the rare, high-cost segments relative to their share of traffic. A segment needs enough cases to support a rate, about 30 as a working floor, and one case is not enough.

Inference: a report on four segments therefore needs about 120 cases, more than the working size of 20 to 50 in §4.3, which is the minimum for a first hand-verified set.

An over-sampled set stops mirroring traffic, so its overall figure differs from the production figure. A single production number needs the segments re-weighted by traffic share.

The gate on reducing oversight is that every segment clears the bar independently, and not the weighted average. If a team proposes auto-processing everything above an aggregate confidence threshold, analyse accuracy by document type and field first. The aggregate averages away the segment that fails 40% of the time.

The same logic runs live. For an ongoing audit of an automated path, take a stratified random sample across document types and field categories, since novel error patterns surface first in the high-confidence stream. Reviewing only the lowest-confidence extractions leaves the automated path unmeasured where volume is highest. Sampling only the most common document type under-samples the worst segments by construction.

Use code wherever the answer is exact§4.5

Layer the graders in order. Deterministic code checks filter first, a model grader scales the judgement of subjective quality, and humans calibrate periodically. The corpus discriminator is whether the property has an exact, machine-decidable answer. If it does, a model grader is a strictly worse instrument, however good its rubric.

Code reaches schema validity, field match, numeric comparison, regular expressions, forbidden-pattern and PII scans, execution against tests, tool-call ordering, refusal when required, and the existence of a citation span. Check citations with a verbatim string comparison and not a model grader, since judges are near chance on citation validity. The corpus cites roughly 38% as the score judges reach on citation validity in studies, a figure not checked here.

Subjective properties go to a model grader. "The answer must be in the right register for a regulated communication" takes a model grader with a binary rubric, since no code check reaches tone. "The summary must be faithful to the source" takes a model grader for faithfulness, with an overlap metric as a cheap floor, and the overlap metric alone is not enough.

A human's job is to label ground truth and to calibrate the grader.

The corpus sets one solvability bar. If two domain experts would not independently reach the same verdict, no automated grader is trustworthy at any threshold. Where two adjusters disagree on the verdict, use human adjudication and re-scope the evaluation row, because unstable ground truth defeats every automated grader.

Measure the grader before believing its scores§4.6

Write a model-graded rubric as binary sub-criteria, where the whole output passes only if every hard criterion passes. A 1 to 5 scale hides mid-scale uncertainty, drifts between runs, needs larger samples and aggregates poorly. The grader must come from a different model family than the generator. A same-family grader brings self-preference bias and shared blind spots, and the failures it cannot see are the generator's own.

The discriminator is whether the grader itself has been measured. An unvalidated grader's scores describe the grader and not the system. Before believing any score, hand-label a sample and measure agreement between grader and human, with about 75% as a starting bar and not a settled constant. For a new tone grader, hand-label 20 to 50 cases, run the grader, compute agreement, then decide.

Several cases follow from that. An agreement of 0.62, meaning 62%, calls for rebuilding the criterion as binary sub-criteria and re-validating, because a fuzzy scalar is the most common cause of low agreement.

If agreement is still below the bar after rework and no deterministic fallback exists, drop the row and record why. If only a same-family grader is available, use it, mark the row degraded, and never report it as ground truth. A grader six months in production with no re-audit needs periodic human calibration again.

The known biases are position (favouring the first or last option), verbosity (rewarding length) and self-preference. The guards are to randomise and swap the order of options and aggregate both runs, to use binary criteria that control for length, and to use an out-of-family grader.

Go deeper: what a 40-case agreement check can and cannot show

This is a worked example, not a corpus rule, and its counts are invented. A team hand-labels 40 cases and the grader agrees with the human on 31. That is 77.5% agreement, above a starting bar of 75%. If it agrees on 25, the figure is 62.5%, below the bar.

With 40 cases, one case moves the figure by 2.5 points. Inference: a 20 to 50 case sample therefore works as a screen. It separates a grader that is clearly poor from one that is plausible, and it cannot settle a close call, which is why the corpus calls the bar a starting point.

Grade each layer, so a blended score cannot hide the broken one§4.7

A RAG system has two layers. Retrieval is scored with Recall@k (the share of the gold passages found in the top k results) and context precision, against gold passage IDs. Generation is scored with faithfulness (whether the answer follows its sources) and answer relevancy. Both layers must clear their own bar. A single blended score is a defect.

Faithfulness computed over the wrong passages means nothing, and retrieval is the more common failure. With Recall@5 of 0.55 and faithfulness of 0.97, read both bars: the system fails on retrieval, because high faithfulness to the wrong passages is not quality.

An agentic system has two layers as well: the trajectory, meaning the tool selection and step order, and the outcome, meaning the final state and task completion. A correct result reached by a wrong or irreversible path is a failure. An agent that completes the task but deleted a record on the way fails the trajectory row. An agent with correct tools in the correct order and the wrong final state fails the outcome row.

For multi-turn systems, attribute the first failing turn and not only the final state. An assistant that recovers by turn 6 from a turn-2 error still reports the turn-2 failure, since a late correction masks a defect that will not always correct itself.

Count attempts by what a failed one costs§4.8

pass@k passes when at least one of k attempts succeeds, so it measures reachable success. pass^k passes only when all k attempts succeed, so it measures reliability. The discriminator is whether a failed attempt is absorbed by a downstream check or reaches the world.

Use pass@k where a validator or a test catches failures and triggers a retry, such as code generation with a test runner that reruns on failure, or a tool call behind a schema validator that retries on rejection. Use pass^k where every attempt is visible to a user or acts in the world: an answer shown directly to a customer has no retry, so each attempt is the product.

Any step that takes an irreversible action is a gate, whatever the aggregate score says. An agent that must confirm with a human before an irreversible action is graded pass^k = 1.0, since one silent irreversible action in k attempts is a failed control. Reject a confirmation gate reported as pass@5 = 1.0, because a gate that fires once in five attempts would score as passing.

Go deeper: the same system under both readings

This is a worked example, not a corpus rule. Suppose a step succeeds on 90% of attempts and attempts are independent, which is an assumption. The chance that at least one of five attempts succeeds is 1 minus 0.1 five times over, which is 99.999%. The chance that all five succeed is 0.9 five times over, which is 59.0%.

The same step is nearly certain to succeed at least once in five tries, yet all five succeed only 59% of the time. Behind a retrying validator the first number is the one that matters. In front of a customer, or on a step that acts in the world, the second is.

Rebuild the set from real production failures and report by segment, because more cases from the same source only repeat the bias. Remember

  1. Fix the composition before the size: real traces first, 20 to 50 hand-verified cases, balanced should-fire and shouldn't-fire. A bigger set drawn the same way is the same bias.
  2. Report by segment. Over-sample rare, high-cost segments to about 30 cases each, and let every segment clear the bar before oversight is reduced.
  3. Code first for anything exact: schema, verbatim citations, PII. A model grader for tone and faithfulness. Humans label and calibrate.
  4. Validate a model grader against 20 to 50 hand-labelled cases, with binary criteria and a different model family. Mark a same-family grader degraded and re-audit periodically.
  5. Grade RAG as retrieval plus generation and agents as trajectory plus outcome, and attribute the first failing turn.
  6. pass@k where a retry absorbs failure, pass^k where an attempt is visible or acts in the world, and any irreversible-action gate is pass^k = 1.0.
