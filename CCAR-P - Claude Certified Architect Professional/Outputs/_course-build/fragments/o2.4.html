A support chat runs for 50 turns, and each turn, a customer message and the reply, adds about 300 tokens (a token is a word or a piece of a word). The first call sends 300 tokens. The fiftieth sends 15,000. Added up over the whole chat, the calls send 382,500 tokens, which is 25.5 times the 15,000 the conversation contains. The figures are illustrative.

One fact about the API produces that multiple: it keeps nothing between calls. The same fact explains why the model can seem to forget something said two turns ago. Once history has to be resent, a second problem follows: what to keep as it grows, and where to place the parts that must not be missed.

Resend the whole history on every call§2.5

Claude's API is stateless: every call stands alone, with no server-side memory. So every request must carry the complete conversation history in the messages array. All continuity is the application's job to build and resend on every request.

Two symptoms look alike and have different causes. If Claude "forgot" something from two turns ago in a short conversation, the application is not including the prior messages. The context window (the most tokens a request may hold) cannot be full that early.

If latency and cost rise as a conversation passes 50 turns, the full history is being resent every call, so more turns mean more tokens. Longer model responses and a slow database do not explain it.

To cut the tokens resent without losing continuity, summarise or truncate older turns, and keep resending the full messages array, summary included, on every call. Full here means everything that was kept: the summary plus the turns that remain.

Two client sessions for one user need the same handling: the application merges their histories and passes the combined history explicitly. The API will not correlate sessions, because a stateless API has no session identity and a shared identifier on the request does not create one.

Put what matters where attention holds§2.6

"Lost in the middle" names a pattern in long inputs. The model uses the beginning and the end reliably, and its attention to the middle is weaker. A synthesis agent given a long document can therefore miss a critical finding that sits halfway through it. The mitigation is structural: key findings first, explicit section headings, and structured data instead of verbose prose.

Shortening the input under an arbitrary token limit is the wrong fix. It risks cutting exactly the information that was missed. The structural fix puts the findings where the model reads closely. Rotating which source appears first across runs only changes whose content sits in the weak middle position.

The scope of the fix varies. If one precision-critical fact sits mid-document and the failure is fabricating that single value, pull the fact into a short structured highlight near the top or end, and leave it in place as well. If many facts matter equally and none dominates, convert the input to explicit headed sections grouped by topic, even without one findings-first summary.

If the total input is short, well under the model's effective context, ordering does not matter. The effect is a function of total input length, and a short input does not trigger it. Applying restructuring to such input is overhead with no measured benefit.

Go deeper: a highlight block, and what the documentation adds

This is a worked example, not a corpus rule. An agent summarises a 120-page contract, and the notice period of 90 days sits in a clause on page 61. The summary states 60 days. Leave the clause where it is, and add a block at the top of the input: Key terms: notice period 90 days (clause 14.2, page 61). The model now meets the value at a position where attention holds.

Anthropic's prompting guidance (live docs, read 2026-10-25) advises placing long documents of 20,000 tokens or more near the top of the prompt, above the query and instructions, and wrapping each in document tags. It reports that a query at the end improved quality by up to 30 percent in its tests.

The context-window page also names "context rot", a decline in accuracy and recall as the token count grows, which is why curating the context matters as much as having room.

Extract what must stay exact, compress the rest§2.7

The tested pattern is a hybrid. Extract the critical facts into a structured block, summarise the general discussion, and keep the recent turns verbatim, meaning word for word. A long session might hold amounts, identifiers and an allergy alongside general chatter. Summarising everything uniformly blurs those facts into vague paraphrase. Keeping only the most recent tokens drops any critical fact mentioned early.

A decision made early may need to hold for hundreds of turns. Pin it into a persistent structured block that is included on every call, separate from the rolling summary, the running summary of older turns. A rolling summary can drift or drop a fact across repeated summarising passes. A pinned fact has a stable slot that the summarising process never touches.

Summarising should run incrementally, as new turns roll off the retained window. One pass at the very end of the conversation either handles an unbounded amount of history at once or arrives too late to control token growth during the conversation.

When retrieved documents and conversation history share one bounded window, give each source its own budget. Truncating whichever was added last lets one source crowd out the other unpredictably, depending on assembly order. An explicit per-source budget keeps both available.

Go deeper: what the documentation says about windows and overflow

These are dated notes, not corpus rules (live docs, read 2026-10-25). The four current models have a 1M-token context window by default, with a 128K-token maximum output. Everything counts toward the window: the system prompt, every message including tool results, images and documents, tool definitions, and the model's own output including thinking. A cached prefix still counts, because caching changes the price of a prefix and not its size.

For long conversations the page names server-side compaction as the primary strategy, a beta feature on Claude 4.6 and later, and describes context editing, which clears old tool results or thinking blocks. An input already over the window returns a 400 error. On Claude 4.5 and newer models, an input plus max_tokens that goes over the window is accepted, and generation can stop with the reason model_context_window_exceeded.

The corpus examples use bounded windows. A window of 1M tokens makes the budgeting problem rarer in practice and leaves the rules above in force, because the pinned block, the verbatim facts and the per-source budgets address accuracy and cost as well as capacity.

Remember

  1. The API is stateless. Every call carries the whole history in the messages array, and cost grows with it.
  2. A fact forgotten two turns ago means the application did not send it. A cost climbing past 50 turns means the full history is resent. Summarise or truncate old turns and still resend the array.
  3. Two sessions share context only if the application merges the histories. No session identifier does it.
  4. Attention is strong at the start and end of a long input. Fix a lost finding with findings first, headings and structured facts, not by shortening.
  5. One critical mid-document fact gets a short highlight near the top or end. A short input needs no restructuring.
  6. Extract exact facts, summarise the chatter, keep recent turns verbatim. Pin fixed decisions, re-summarise incrementally, and budget each source on its own.
