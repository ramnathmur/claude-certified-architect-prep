An application sends the same 8,000-token policy prompt with every request, followed by a customer message of about 100 tokens. Each request is therefore 98.8% identical to the one before it. At 100,000 requests a day, 800,000,000 of the tokens the service sends are repeats. The figures are illustrative.

Two kinds of repetition appear in this objective. The first is repeated text inside one application, which caching can reuse. The second is repeated prompts across teams, where each team keeps its own copy of something similar and the copies slowly drift apart.

Put the static part first and keep it identical§2.8

Prompt caching lets Claude reuse a cached prefix, the opening stretch of a prompt, across requests. The prefix has to be byte-identical and stable. That means static content goes first and dynamic content goes last, outside the cached prefix. Caching cuts latency, measured as time-to-first-token (how long until the reply begins), and cost together.

For an identical large system prompt and policy followed by a varying user message, order the static content first and enable caching. Truncating the policy loses content the application needs. Moving it into a few-shot block (§2.3) creates no stable prefix to reuse. Caching also does not store replies: it reuses an input prefix, and only while that prefix is identical and first.

Any change inside the prefix invalidates the cache for the whole block, even a single token. Suppose a block is byte-identical except for a timestamp at its very start. Move the timestamp out to after the cached prefix. Dynamic content must sit strictly after the stable part.

Caching only pays within its retention window, the time a cached prefix stays available, 5 minutes by default (the fold below has the dated detail). If a large static prefix is a caching candidate but requests arrive only once every 20 minutes, longer than that window, accept that caching will not help and evaluate other cost and latency levers. Each request recomputes the prefix from scratch.

When two downstream tools each need a different static block, structure the prompt as the shared prefix, then the per-tool static block, then the dynamic content. Putting the common part first keeps the cache hit rate on the shared portion across tool variants, where the per-tool part first would force a full-prompt divergence for each.

The minimum cacheable prompt is 512 tokens on the four current models, and a shorter prompt runs uncached with no error. The default lifetime is 5 minutes, or 1 hour with "ttl": "1h", and each use refreshes it at no extra cost. Caching is requested by adding a cache_control marker, {"type": "ephemeral"}, at the end of the part to be cached, and a request may carry up to 4 such breakpoints.

Price multipliers on the base input price are 1.25 times for a 5-minute write, 2 times for a 1-hour write, and 0.05 times for a read on Sonnet 5.5.

A worked example, with the Sonnet 5.5 input price of $2 per million tokens from the model overview: the 8,000-token prefix costs $0.016 a request uncached and $0.0008 as a read. At 100,000 requests a day that is $1,600 against $80, a saving of $1,520 a day, plus a write whenever the cache expires, which steady traffic rarely allows.

The 20-minute row differs in practice. At the default lifetime, a request every 20 minutes writes the prefix each time, at $0.02 against $0.016 uncached, so caching would cost more. The page's 1-hour option keeps such a prefix warm, at a 2 times write price. Inference: the corpus rule assumes the default window. Share versioned components instead of private copies§2.9

A modular prompt is assembled from shared parts. A Skill packages instructions that Claude loads when a task needs them. The team-scale answer for either is versioned, shared, reviewable components, instead of per-project copy-paste. Domain 7 applies the same logic to Claude Code configuration.

When several teams each keep their own copy of a similar system prompt, behaviour drifts silently, with no single source of truth. Consolidate them into versioned shared components. A change in behaviour then becomes one reviewable event, instead of a separate silent drift in each of N copies.

Version the shared component explicitly. When one is updated and some consumers are deliberately still pinned to the older version for a staged rollout, explicit versions let each team pin and upgrade independently. Without versions, every consumer has to accept every edit immediately, and everyone gets every change the moment it is made.

Suppose a team needs 90% of an existing shared Skill and one constraint differs. Parameterise or extend the Skill for that constraint, and do not fork a full copy. A fork becomes a second, silently drifting copy, which is the failure versioned reuse exists to prevent.

With many small single-purpose snippets and no way to find them, teams re-author the same snippet independently. Keep a discoverable, indexed catalog of shared components. Version control fixes drift once a component is found. It does nothing for a team that never learns the component exists.

Go deeper: how Skills load, and what they cost in tokens

These are dated notes, not corpus rules (live docs, Agent Skills overview, read 2026-10-25). A Skill is a directory with a SKILL.md file, loaded in three levels. The name and description of every Skill are always loaded, about 100 tokens each. The body of SKILL.md, under 5,000 tokens, loads when the Skill triggers. Bundled files and scripts load only when needed, and a script's output enters the context and its code does not.

A worked example, with assumed sizes. A team has 20 Skills with 4,000-token bodies. Loading every body up front would put 80,000 tokens in the context. Loading by level puts 2,000 tokens of descriptions there and adds a 4,000-token body when one Skill triggers, 6,000 in all.

The page limits a name to 64 characters of lowercase letters, numbers and hyphens, and a description to 1,024 characters that must say what the Skill does and when to use it.

Custom Skills do not sync across surfaces: the API, Claude Code and claude.ai each hold their own. Claude Code reads .claude/skills/ in a project and shares Skills through plugins. The page also warns to use Skills only from trusted sources, and to audit them like installed software.
