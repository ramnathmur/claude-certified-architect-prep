A support assistant's only safety control is an output classifier, and it has started taking actions that users never requested. Suppose a document in a customer's upload contained an instruction, and the assistant followed it. The classifier, which reads what the assistant says, saw nothing wrong with the sentence. The assistant can also issue refunds of up to $10,000 with no one in the loop.

The team's instinct is to retrain the classifier on the new failure. That makes the one existing layer better, and it leaves the design at one layer. What would a design look like in which this failure could not reach a refund?

Stack independent layers, matched to consequence§5.1

The corpus names four layers: input validation before the call, output filtering after it, scoped permissions, and human approval on consequential actions. The discriminator is whether the design has independent layers or one control carrying everything. The layers fail independently, so an incident has to clear all four. Adding a fifth flavour of one layer adds almost nothing, since it shares that layer's blind spot.

Most layers are cheap: input validation, schema checks and permission scoping are small deterministic checks. One tuned safety classifier costs more to build and covers less.

The failure mode of a single control is that it is bypassed by exactly the case it was not written for, with nothing behind it to catch the miss. Replacing four simple checks with one fine-tuned safety model gives correlated coverage from one mechanism, and independence is what layering buys.

Match the layers to the consequence. Where an output classifier is the only control on a customer-facing assistant, add pre-call input validation, tool scoping and a human gate on consequential actions.

If input validation, output filtering and scoped tools exist and the assistant can still issue refunds of up to $10,000 unattended, the uncovered layer is human approval on that irreversible action. A low-consequence internal drafting tool with no external output and no tools needs only input validation and output schema checks.

Go deeper: what independence is worth in numbers

This is a worked example, not a corpus rule, and every figure is invented. If each of four layers misses 10% of attempts and the misses are independent, the share that gets past all four is 0.1 four times over, which is 0.01%. Out of a million attempts, one layer lets 100,000 through and four let about 100 through.

The result depends on the independence. If two layers share a blind spot, such as two checks built on the same classifier, their misses overlap, and more gets past both than the product suggests. That is the corpus's point about replacing four simple checks with one tuned model, and about adding a fifth flavour of one layer.

Remove the capability, or take it out of the model's hands§5.2

Least privilege means removing an unneeded capability, and not logging or confirming its use. If the task does not require the capability, delete it, because monitoring, confirming and rate-limiting all presuppose that the capability still exists. This matches the answer logic of the guide's sample on least privilege, covered in O3.2.

When the agent needs the capability sometimes and misuse is consequential, use the strongest form: move the model out of the action path. The model emits a structured request, and a separate service that holds the credential validates it and executes. The privilege stays outside the model while the capability remains available. The stakeholder answer is: "The assistant cannot do X. It proposes; the existing system decides."

The cases follow from consequence. If an agent holds a write or delete tool it has never legitimately needed, remove the tool, and the failure class disappears instead of being mitigated.

If it needs the capability routinely and misuse is low-consequence and reversible, keep the tool and add logging, since removal would break the task. A proposal to keep a dangerous tool and log every invocation is rejected as the primary control, because logging is detection and the action still executes.

A confirmation step is the right control when the capability is needed and consequential (§3.2). It is a half-move when the scenario says the capability is not needed, because then it should be removed.
