A claims assistant must reach five systems: a claims database, a policy document store, a fraud-scoring service, an issue tracker and a medical-necessity review. A team proposes giving the model a tool for every one of them, so that "the agent can decide". That answer is wrong for at least two of the five, and for different reasons.

Take the fraud score, which must run on every claim above a threshold. If it is a tool and the model skips it on 1% of the 20,000 qualifying claims a day, 200 claims go through unscored every day. The skip rate is invented, and the point holds at any rate above zero.

Ask who decides what happens next§3.13

The corpus discriminator is one question: who decides what happens next, your code, the model, or another agent? The cost gradient runs in one direction. A direct API call is cheaper than an MCP tool call, and an MCP tool call is cheaper than an agent-to-agent handoff. Each step up buys flexibility and spends determinism, meaning the same input always taking the same path.

Use a direct API or CLI call (a command-line tool) for a known, mandatory, deterministic step. If a record must be fetched on every request and the ID is already known, call the API in pre-processing, because no model decision exists to make.

If a control must run on every qualifying request, call it directly from the orchestration layer and do not expose it as a tool. A tool lets the model choose not to call it.

Use MCP when the model should choose. An MCP tool is an action the model chooses to call. If the agent should decide whether and when to search a document store, that is an MCP tool, since the decision depends on the conversation.

An MCP resource is read-only content the model can consult. If the agent needs to know what content exists before it queries, expose a catalog as a resource, which gives it the map as readable context instead of exploratory model turns.

For a standard third-party system such as an issue tracker, source control or chat, use an existing community MCP server, after vetting it. Claude Code's documentation warns that servers which fetch external content can expose you to prompt injection (live docs, read 2026-10-26). Custom effort belongs on workflows nothing else covers.

Use agent-to-agent when the other side brings its own judgment, context and accountability: work that needs separate domain judgment and separate audit attribution, where the determination must be owned by the other function.

Go deeper: what the MCP and Claude Code documentation say

These are dated notes, not corpus rules (live docs, read 2026-10-26). The MCP architecture page describes a host, such as Claude Code, that creates one client for each server. A server offers three primitives: tools, which are executable functions, resources, which are data sources that give context, and prompts, which are reusable templates. A client finds them with list requests such as tools/list, and the listings can change.

The page names two transports, stdio for local servers and Streamable HTTP for remote ones, and recommends OAuth for the remote case.

In Claude Code, claude mcp add registers a server. HTTP is recommended for remote servers, and the older SSE transport is deprecated. A server loads at local scope by default, at project scope through a .mcp.json file shared with the team, or at user scope across all projects, and Claude Code asks for approval before using project-scoped servers in an interactive session.

The docs warn to verify that you trust each server before connecting it, because servers that fetch external content can expose you to prompt injection.

The protocol page also notes that a client combining many servers can use progressive tool discovery instead of loading every tool at once, which is the subject of O3.8. No agent-to-agent specification was read for this chapter. The part of the architecture page read here does not say whether the model or the application triggers the read of a resource, and the corpus rule treats a resource as content the agent can consult.

A compliance scoring service must run on every claim above a threshold, and the team proposes exposing it as an agent tool.

  • WrongARCHITECTEDDelegate the scoring to a dedicated compliance agent that decides when to run. It buys a full inference loop and a second failure surface to perform what is a function call with fixed inputs.

Design shapeThe project's lesson text adds a related shape. An agent needs to know what documents exist before it searches. The answer is a catalog exposed as an MCP resource. Pasting the catalog into the system prompt bloats every request with content that goes stale when the catalog changes. A list_everything tool needs the model to remember to call it and spends a turn on what a resource supplies as context.

Say it backAn assistant must run a fraud check on every large claim, search a policy store when a question needs it, and file a ticket in a widely used issue tracker. Which mechanism fits each, and why?

The fraud check is a direct API call from the orchestration layer, because it is mandatory and a tool would let the model skip it. The policy search is an MCP tool, since whether and when to search depends on the conversation. The ticket goes through an existing community MCP server, because the tracker is a standard third-party system and a custom server would repeat maintained work.
