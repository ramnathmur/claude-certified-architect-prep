A support team runs an AI triage system on 12,000 tickets a month. Reviewers change the category on about 4% of them, which is 480 corrections a month. What the architecture does with those corrections decides whether the system ever improves. If a fix overwrites the field, the correction is lost. If it is stored as an event and routed somewhere that changes behaviour, the team gains 480 labelled examples a month.

A system has four stages: input, processing, output and feedback. The corpus's reading is that the fourth is the one omitted when a system ships.

The chapter's second idea is placement. Each rule goes at the earliest stage that can enforce it, because a filter further downstream only repairs what an earlier stage could have prevented. To place a rule, ask which stage first has what it needs to enforce it, and if two stages can, take the earlier one.

Feedback is closed only when something changes§1.9

A loop is closed when a correctness signal reaches something that changes the system's behaviour. Signals come in three kinds. Implicit ones are almost free: a reviewer edits a draft, overrides a category or rejects a suggestion. Explicit ones take effort, such as ratings or a labelling queue.

Outcome signals are the most decisive and often the slowest. Whether a ticket reopened shows within days, while the loss ratio (claims paid against premiums earned, in insurance) takes a year to settle. A fast signal, such as the override rate or the reopen rate, is added as a proxy alongside the slow one.

The gap between what the model produced and what the human shipped is labelled data that costs almost nothing to collect. It only counts if the correction is stored as an event beside the original prediction.

Then it has somewhere to go. Two destinations are the evaluation set (the fixed test cases the system is scored against) and the prompt or its few-shot examples (sample inputs and answers shown to the model). The others are the retrieval and indexing layer, the routing thresholds that decide what goes to a human, and the choice of model.

Someone has to own that step, and a regular review of the disagreement cases is one way to do it.

Logs, dashboards and monitoring alerts do not close a loop. They record what happened without saying whether it was right, so they change nothing by themselves.

Go deeper: three signals wired for the triage system

The 480 overrides are one of three signals worth wiring (a worked example, not a corpus rule). In practice an override is one stored row: the ticket ID, the model's category, the reviewer's category, the prompt version and a timestamp. Rows where the two categories differ are the disagreement cases, and sampling them into the evaluation set is a single query.

The triage system also drafts a first reply. The edit distance between that draft and what the agent actually sent is a second signal: heavily edited drafts go into the evaluation set, and lightly edited ones confirm the pattern is working. Both of these are implicit signals.

The third is the reopen rate at seven days, joined back to the original category and confidence. It is an outcome signal that arrives within days, which is why it works as a fast proxy, and it can catch a failure the other two miss: a confident, plausible triage that resolves the ticket wrongly. Each signal has a named destination, which is what makes it feedback.

Put each rule at the earliest stage that can enforce it§1.10

Start at the front. The input boundary does three jobs: it acquires the data from a webhook, a queue or an upload, it validates and normalises it, and it decides what to trust. Content from outside your control is untrusted until the boundary decides otherwise. The boundary also fixes what the rest of the system can never recover, because context that was not captured here does not exist downstream.

Processing is the model call plus the code around it. The common mistake is giving the model work that code does exactly: arithmetic, lookups, schema validation, threshold checks and required sequencing. Redaction is the same kind of work, and it belongs at the boundary, before the model sees anything.

Take a support agent that sometimes acts on the wrong account because it skipped identity verification. A firmer prompt makes skipping less likely. A programmatic precondition is a check in code that blocks the account-action tool until the verification call returns a verified identifier, and that rules skipping out.

The output is a contract, and whoever consumes it sets the terms. A service that routes on the result needs a field it can parse and an explicit confidence value it can compare with a threshold, because routing is code and code cannot act on prose. How the confidence value is produced and calibrated is a separate design question, and routing only needs the field to exist.

A human reviewer needs the reasoning and the citations beside the verdict.

Remember

  1. Four stages: input, processing, output, feedback. Feedback is closed only when a correctness signal reaches something that changes behaviour.
  2. Logs, dashboards and alerts record what happened and carry no correctness label. They are not feedback.
  3. The cheapest labelled data is the gap between what the model produced and what the human shipped, stored as an event. A slow outcome signal needs a fast proxy.
  4. The input boundary acquires, validates and normalises, and decides what to trust. Context not captured there does not exist downstream.
  5. Arithmetic, lookups, schema checks, redaction and mandatory order belong in code. "Must always" gets a precondition in code, because a prompt cannot guarantee it.
  6. The output contract is set by its consumer: a service needs a parseable field and a confidence value, a reviewer needs reasoning and citations.
