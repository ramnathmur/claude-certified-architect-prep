A team convention holds in some Claude Code sessions and fails in others. Same repository, same week, same machine. A teammate finds that writing the convention at the top of every prompt in capitals makes it hold in four sessions out of five. Of 50 sessions a week, that leaves 10 failures. The failures are now occasional enough that the team stops investigating them.

The workaround has done something worse than leave a gap. It has hidden the pattern that would have located the cause. A symptom that appears in some sessions and not others is usually conditional and not random, and the first job is to find the condition.

Find the layer that owns the symptom§7.7

The method is to identify the layer that owns the symptom. Bisection, halving the change set until the culprit appears, assumes determinism that an agentic system does not have. The corpus gives a ladder of six rungs, taken in order. Inference: each rung is usually a cheaper question than the one below it.

Rung 1 asks whether the content is loaded, and /context shows what actually loaded into the session. Rung 2 asks whether it sits in the right layer for the strength required: guidance, tool scope, isolation or enforcement (§7.2). Rung 3 asks whether context is polluted or stale. Use context: fork to isolate verbose work. /compact risks losing exact values, dates and specifics, and mid-task it is rejected, because the loss lands on exactly the values the implementation still needs.

Rung 4 asks whether the tooling is wired and scoped, and least privilege means removing the unneeded capability and not logging or confirming its use. Rung 5 is retrieval and indexing, the first suspect when accuracy drops after a data change. Rung 6, the prompt or the model, comes last. The evidence rule is that output varies between runs, so a fix is demonstrated against a test set and not one clean run.

Read the stem for what it excludes. Behaviour that differs between engineers on the same repository points at configuration scope, user level against project level, and rules out the model and tool versions. Behaviour that works in some sessions and not others on the same machine points at conditional loading, so check what /context reports, since conditional is not intermittent.

A fact from two turns ago missing in a short conversation means the application (an API-based one, as in §2.5) is not sending the history, and rules out an exhausted window. Accuracy that collapsed right after a document refresh, with confident answers, is retrieval and indexing, since confident and wrong is correct reasoning over wrong retrieved content.

A subagent that holds a tool and never uses it correctly is a wiring and permissions problem and not prompt wording. Exploratory output that pushed the original task out of focus is context pollution, and the verbose step is forked.

When a rule did not hold, move it to enforcement§7.8

The ladder's second rung asks how hard a rule must hold. When the answer is "every time, whatever any prompt says", the symptom's owner is the wrong layer: the rule sits in guidance and needs enforcement. Instructions in a prompt or CLAUDE.md shape what Claude tries to do, and permission rules are enforced by Claude Code and decide what is allowed.

These are the eight §7.8 rules, seen from the debugging side, and O7.1 lays out the settings and precedence in detail.

If a capability must never be exercised, add a deny rule in the settings permissions, and reject a more strongly worded CLAUDE.md line. If an action must happen every time a tool runs, such as a format, a test or an audit entry, use a hook scoped by a matcher, and reject a reminder in the project file.

If a call must be stopped before it executes, use a PreToolUse hook or a deny rule, since a log acts after.

A narrow allow and a broad deny that both match give a denial, because the first match in the deny, ask, allow order wins and specificity is irrelevant. To guarantee that a rule survives every local override, use managed policy settings, since nothing below it in the precedence order can override it. A team style preference proposed for a hook or a deny rule is rejected as over-specification.

KnownThe guide's three samples sit in Domains 2, 3 and 4, so none of them is a sample for this domain. InferenceExpect a stem full of environmental detail where each detail eliminates a layer, and options that patch the symptom or swap the model.

A convention holds in some Claude Code sessions and not others, in the same repository during the same week.

  • CorrectRun /context in a working session and a failing one and compare what loaded. The rule is in a file that is not consistently discovered: the wrong level, the wrong directory, or a path-scoped glob that does not match.
  • WrongREPAIRRestate the convention at the top of every prompt in capitals. It patches each session downstream of a loading problem, and mostly-working suppresses the diagnostic signal.
  • WrongDISCARDMove to a more capable model on the grounds that instruction-following is inconsistent. It replaces a working component to explain a symptom the configuration layer already accounts for.

An agent must never be able to force-push, and a CLAUDE.md instruction saying so has not held.

  • CorrectAdd a deny rule for the force-push command pattern to the settings.json permissions.
  • WrongREPAIRRestate the prohibition more forcefully and in more places in CLAUDE.md. Instructions shape what Claude tries and do not change what Claude Code allows, so more prose is more of what already failed.
  • WrongHALF-MOVEAdd an allow rule listing every git command the agent may run, because an allow-list is stricter. It narrows the default path and does not stop a matching call the way an explicit deny does, and it breaks every legitimate command nobody listed.

Design shapeA rule must hold on every developer machine and cannot be overridden locally. The answer is managed policy settings. Putting it in the project .claude/settings.json and requiring review is HALF-MOVE, since review controls what is committed and not what runs. Putting it in the project CLAUDE.md is WRONG-AXIS, because instruction files concatenate and cannot produce a rule that wins a conflict.

Say it backA convention holds in some sessions only, and separately an agent ignores a "never force-push" line in CLAUDE.md. Where does each investigation start, and what is the fix?

For the convention, run /context in a working session and a failing one and compare what loaded, since conditional behaviour has a condition and the model is the last suspect. For the force-push, the rule needs enforcement: add a deny permission rule, because the CLAUDE.md line shapes what Claude tries and does not change what is allowed.

Remember

  1. Find the layer that owns the symptom, in order: is it loaded (/context), is it in the right layer, is context polluted, is the tooling wired and scoped, retrieval and indexing, and the prompt or model last.
  2. Read the stem for what it excludes. Differences between engineers point at scope, some sessions and not others at conditional loading, confident wrong answers after a refresh at retrieval.
  3. Behaviour that works sometimes is conditional and not random. A workaround that works four times in five hides the signal.
  4. Do not /compact mid-task when exact values are needed. Fork verbose work with context: fork.
  5. A rule that must always hold moves to enforcement: a deny rule, a hook, or managed policy. Permissions resolve deny, ask, allow with the first match winning, and a style preference is not converted into a hard failure.
