A service has a p95 limit of 2,800 ms and gets a latency complaint. Nobody has stage timings. A team decides to halve the retrieval step. A profile, which nobody has run yet, would show that it takes 224 ms, or 8% of the budget. Halving it saves 112 ms, which is 4% of the total, and the complaint stays.

Generation takes 2,016 ms, 72% of the budget, and nobody looked. The figures are illustrative.

Every token is a cost line and a latency line at once. Which levers cut both, which cut one, and which only look like savings?

Profile first, cache first, and remove nothing the requirement needs§4.11

Profile which stage dominates the budget before optimising anything. The fields that make a profile possible are listed in O4.6. With no stage-level timing, a latency complaint is answered by profiling first, since halving a stage worth 8% of the budget buys only 4%. The corpus discriminator is whether a saving preserves everything the requirement demands. Reordering for cache reuse loses nothing, and truncation loses content.

The highest-value lever is prompt caching: static content first and dynamic content last (how long a cache lasts, the smallest prompt it works on and the write premium are covered in O2.5), which cuts time-to-first-token and cost together with no quality loss (§2.8).

Any variation in the prefix, such as a timestamp, a session ID or a user name, destroys reuse. If a large identical policy preamble is sent on every request and latency and cost are both named, order it first and cache it.

Cutting the preamble by 60% is a compliance regression where the removed sections are required. Summarising it with an extra model call adds a full invocation and degrades precision.

For a quality floor plus a budget ceiling with mixed task difficulty, use a cascade: a smaller model for the routine class, escalation for the rest, with the trigger validated for each segment and not assumed. The trigger is the rule that decides a request needs the larger model, such as a confidence signal or a failed check (§5.8 lists the valid signals).

A nightly batch job with a latency complaint wants batch or async processing and output shaping (trimming what the model is asked to write, so fewer output tokens are generated), because nobody is watching a cursor and streaming changes nothing there.

If retrieval fetches the top 20 passages, reduce it to those that clear the relevance floor (a minimum retrieval score, set in advance like any bar), since noise in the middle of the window costs tokens and accuracy.

Go deeper: a cascade priced, and the batch rate in the documentation

This is a worked example, not a corpus rule, and the prices are invented. A service makes 100,000 requests a day, and 80% are routine. A large model at $0.02 a request would cost $2,000 a day.

A cascade sends the 80,000 routine requests to a small model at $0.002, which costs $160, and the other 20,000 to the large model, which costs $400. The total is $560 a day, a saving of $1,440, or 72%.

That saving holds only if the small model clears the quality floor on the routine class. The corpus says to validate the escalation trigger for each segment, because a segment where the small model falls short has to escalate or the saving becomes a regression.

On batch, Anthropic's model documentation (live docs, read 2026-10-25) says Batch API requests are 50% cheaper. A nightly job that costs $2,000 on demand would cost $1,000 as a batch, a case where nobody waits for the result.

Say it backA team halves a 224 ms stage to fix a latency complaint, and another wants to cut a 60% share of the policy preamble to save tokens. What do you ask for, and what do you recommend instead?

Ask for stage timings first. Halving a stage worth 8% of the budget buys 4%, and the dominant stage may be elsewhere. Reject the cut if the removed sections are required, because it is a compliance regression. Put the static preamble first and enable prompt caching, which reuses the same content and lowers both latency and cost.
