An insurance operations team puts four kinds of content behind one assistant: policy manuals with numbered clauses, an API reference for the claims system, a support-ticket archive, and a product specification table with 12,000 rows. No single chunking strategy fits all four. The objective is matching how you cut and index each kind of content to the shape it already has.

RAG, or retrieval-augmented generation, exists because the model's weights hold general knowledge, while your organisation's specifics live elsewhere, change on their own schedule and carry access rules. A RAG pipeline fetches those specifics at request time and puts them in front of the model.

It has five stages. Ingestion loads and cleans the documents. Chunking cuts them into pieces. Embedding turns each piece into a list of numbers, a vector, that places similar meanings close together. Indexing stores the vectors so the nearest ones can be found quickly. Retrieval fetches the best matches for a question. Diagnosing RAG starts by asking which stage failed.

Cut where the document already has seams§3.8

Define a chunk as the smallest span of a document that still makes sense when read completely out of context. That rules out a fixed 512-token window (a token is a word or part of a word) as a universal default, because a window cuts wherever the 512th token lands: mid-clause, mid-table, mid-function.

It also tells you where to cut instead. A human author already marked the seams, in clauses, endpoints, tickets and functions, and those are the places where meaning is self-contained. A support ticket stays whole for the same reason: one reply makes no sense without the problem statement above it. Overlap of 10 to 15% is insurance against a sentence straddling a boundary. Good boundaries still come first.

  • A policy manual with numbered clauses and a heading hierarchyChunk on clause boundaries, and carry clause number, heading path, effective date and jurisdiction as metadata.Version and jurisdiction are a correctness requirement for time-sensitive lookups.
  • An API reference with one regular section per endpointChunk per endpoint, whole.Splitting parameters from the description produces two unusable chunks.
  • Support threads of 3 to 40 messagesChunk per ticket, not per message.A single reply is unanswerable without the problem statement above it.
  • A wide relational table of product specificationsDo not embed it. Expose it as a structured query tool.Row embeddings are mostly noise, and aggregation has no vector-space answer.
  • Unstructured prose with no headings at allUse fixed-size windows with overlap, as the fallback.The fallback is correct only where no structure exists to follow.

Put the missing context into the chunk§3.9

A chunk pulled from the middle of a long document loses the title and heading hierarchy that made it interpretable. "This limit does not apply to renewals" means nothing on its own. Ask one question: is the chunk missing context, or missing content? If it is on topic but ambiguous, prepend the document title and heading path to the chunk text before embedding, so the context lands inside the vector and not only in metadata.

Enlarging chunks looks like a shortcut and costs precision. A bigger chunk spreads its embedding across more topics, so it matches queries less sharply. Contextualization adds what was missing without adding unrelated text to the same vector.

Metadata keeps its own job, which is filtering, for example down to the policy version in force on a claim's date. It does not influence semantic similarity, so a heading path held only in metadata should also be prepended to the embedded text.

  • Retrieved chunks are on topic but ambiguous out of contextPrepend the title and heading path before embedding.It puts the missing context into the vector, not only into metadata.
  • Retrieved chunks are genuinely cut off mid-ideaFix the boundary so it follows the document's structure.The problem is the cut, not the size.
  • Precision drops as chunk size growsReduce the size and contextualize instead.A larger chunk spreads its embedding across more topics.
  • Metadata already holds the heading path but it is not embeddedAlso prepend it to the embedded text.Metadata can be filtered on, but it does not influence semantic similarity.
Go deeper: what Anthropic's Contextual Retrieval adds

This is not a corpus rule. It comes from Anthropic's post of 19 September 2024. The title-and-heading prefix described above is the cheap, structural version. Contextual Retrieval has Claude write a short explanation specific to each chunk, usually 50 to 100 tokens. That explanation is prepended to the chunk before embedding and before the keyword index (BM25, which matches exact terms) is built.

In Anthropic's tests the top-20 retrieval failure rate, the share of relevant chunks that miss the top 20 results, fell from 5.7% to 3.7% with contextual embeddings alone, a reduction of 35%. Adding contextual BM25 took it to 2.9%, a reduction of 49%, and reranking on top (a second pass that re-orders the retrieved chunks by relevance) took it to 1.9%, a reduction of 67%.

The post gives no recommended chunk size. It says only that chunk size, boundaries and overlap can all affect retrieval.

Keep chunking, embeddings and index in step§3.10

An index is a coupled unit of three things: the chunking scheme that produced the chunks, the embedding model version that turned them into vectors, and the vector index that stores the result. Change one without the others and the space becomes inconsistent.

At query time the user's question is embedded too, and it must be embedded by the same model version as the index. Vectors from a different embedding model sit in a different geometry, so similarity scores between them are not reliable. The system raises no error and keeps answering fluently, with wrong answers.

So when a RAG system turns confidently wrong the morning after a document refresh, start with retrieval and indexing. The model and the prompt did not change, and the refresh is the only thing that moved.

Work through four checks in order: was the re-index complete, did the chunk schema change, did the embedding model version change, and were stale vectors for deleted documents left behind. Look at the prompt and the model only after all four have cleared.

You can catch this before users do. After every re-index, run golden queries (a fixed list of real questions whose correct chunk IDs you already know) and block promotion when the hit rate, meaning how often the known-right chunk comes back, drops.

Go deeper: the refresh incident, step by step

Six weeks after launch, a nightly reload of the policy manuals runs, and the manuals themselves have not changed. The next morning the assistant answers coverage questions confidently, and retrieval scores have dropped across the board. This is a worked example, not a corpus rule.

Check 1 compares the chunk count in the index with the count the source should produce. If the source should yield 10,000 chunks and the index holds 7,000, the shortfall is 30%, which points at a partial run. Check 2 diffs the chunk-schema version.

Check 3 compares the embedding model version recorded on the index with the one used at query time, and a mismatch there is a silent failure. In this example check 3 finds it: the ingestion job used a floating model version, an alias that points at whatever the latest version is, and it moved. The fix pins the version to the index and re-embeds the whole corpus.

To build golden queries, collect real questions users ask, record the chunk IDs that should come back for each, and keep the list fixed. Take the hit rate of the last good index as the baseline, and block promotion of any new index that falls below it.

KnownThe guide's Sample 3 is this chapter's failure. The answer is the retrieval and indexing step.

The other three options blame silent weight changes, a low temperature and a shrunken context window. The guide's reason is that none of them would be triggered specifically by a document refresh, and the stem also says the model version is unchanged.

  2. Fixed windows are the fallback for prose with no structure. Overlap of 10 to 15% insures against a cut sentence and does not replace good boundaries.
  3. Data queried by filter or count is not embedded. Give it a structured query tool.
