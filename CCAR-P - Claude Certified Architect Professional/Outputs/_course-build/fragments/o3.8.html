An enterprise agent can reach 60 tools across 8 systems, and each tool definition averages about 200 tokens. Every request therefore carries 12,000 tokens of tool definitions, which is 600,000,000 tokens a day at 50,000 requests. The median request uses 1.4 tools and touches exactly one system, so most of that surface is irrelevant to the request that paid for it. The figures are illustrative.

One option is to load a short index of the eight systems and fetch the detail only for the system a request needs. That is cheaper in tokens, and it adds a step. When is the step worth taking, and when is loading everything the better answer?

Compare the token saving with the discovery round-trip§3.14

A monolithic surface loads everything on every request, and the full token cost is paid whether or not any of it is used. Progressive discovery loads a compact index and fetches detail on demand. The corpus discriminator is whether the surface is large enough for the token saving to exceed the cost of the discovery round-trip.

Progressive discovery has two costs. Requests that need expansion pay one extra model turn. And there is a discovery failure mode: the agent may miss a capability that exists because the index entry did not make it visible. Two mitigations come with it. Write index entries as a usable map, and promote high-frequency capabilities into the base surface so that the common path never pays the round-trip.

With 60 tools across 8 systems and a median request touching one system, use a namespace-level index with on-demand expansion. A namespace here is one system's group of tools, and its index entry says what lives there and when to come. If trace data shows six tools account for 61% of calls, promote those six into the base surface. The common path then stops paying the round-trip.

Monolithic wins in three cases. First, a small stable surface: five stable tools load all at once, and below roughly ten tools discovery costs more than it saves. Second, a latency budget that cannot absorb a round-trip, because the trip costs more than the surface does.

Third, content needed on every single request has nothing to discover: order it first and cache it, which is a caching answer. A large document catalog the agent should know about is exposed as a readable resource, so the map stays current and is consulted on demand.

Go deeper: the arithmetic, and what Anthropic's tool search does

This is a worked example, not a corpus rule, and the sizes are assumptions. Eight namespace entries of 150 tokens make a 1,200-token index. A request that expands one namespace adds about 7.5 tools, which is 1,500 tokens, so such a request carries 2,700 against 12,000. Promoting six tools of 200 tokens each raises the base to 2,400 tokens, and the 61% of calls that those six serve need no expansion.

If expansion costs an extra 250 ms, an assumption, then a request that needs it takes 250 ms longer. The saving buys that only when the surface is large. At 5 tools of 200 tokens, the whole surface is 1,000 tokens, and the index alone would be most of it.

Anthropic's tool search tool (live docs, read 2026-10-26) is this pattern as a feature. Tools marked defer_loading: true stay out of the context until Claude finds them by search, with 5 matches returned by default, and the page advises keeping the 3 to 5 most frequently used tools non-deferred. That echoes the corpus's promotion rule, though the page says 3 to 5 tools where the corpus example promotes six.

Every definition is still sent in the request so that the search can run, but deferred ones are kept out of the model's context until they are found. The prompt prefix is untouched, so caching is preserved.

The page recommends tool search at 10 or more tools or more than 10,000 tokens of definitions. It suggests standard tool calling for fewer than 10 tools, or when every tool is used in every request. It says selection accuracy degrades beyond 30 to 50 tools. The corpus's figure of roughly ten tools agrees with the page.

Say it backOne team has 60 tools and wants to load a short index and expand on demand. Another has five stable tools under a tight latency budget and wants to do the same. A third needs a 3,000-token policy block on every request. What do you say to each?

The first team is right. The surface is large and a request touches little of it, so use an index with expansion and promote the busiest tools into the base. The second should load all five tools, because a round-trip costs more than the small surface does. The third is a caching case: order the block first and cache it, since nothing is being discovered.
