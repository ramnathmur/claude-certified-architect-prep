One morning the daily bill for an assistant is three times what it was, response times are up, and the quality score has not moved. Nothing was announced. The team's logs hold the final answer and a timestamp for each request, which is enough to show that the bill rose and not enough to say why.

The logs did not capture which prompt version served each request, or how many input tokens were read from the cache. If they had, the cause would take a minute to find. What should a production log contain so that a metric that moves can be tied to a layer and a release?

Log for attribution, so a moving metric can name its cause§4.12

Evals measure a frozen set, and monitoring measures the distribution nobody anticipated. Both are required, and a system that passed its evals can still drift in production. The corpus discriminator is whether the logged fields let you say which layer and which release moved a metric.

The one field that cannot be left out is the prompt version and model identifier on every request. Without it, no change in a metric can be tied to a release.

That is the corpus's minimum log. It also names online proxies, such as the escalation rate, retry rate, thumbs-down rate, conversation length and abandonment, which move before the offline metrics do. Sample live traffic for quality in strata, across segments and across verdict classes, and include the high-confidence automated stream. Alert on rates, on segment rates and on leading indicators, and not on individual events.

Two fields in that record need a gloss. A guardrail verdict records whether each guardrail layer allowed or blocked the request. The outcome signal is the online proxy for how the request ended, such as an escalation, a retry or a thumbs-down.

The signature to learn is cost and latency moving together while quality holds. That points at the token or caching layer and not at model behaviour. When the quality metric moves and the cause is unknown with only final outputs logged, add the prompt and model version, the retrieved IDs, the tool calls and the staged latency. Output alone cannot name the layer that produced it.

A dashboard of aggregate averages needs per-segment breakdowns, since it reproduces the masking trap in real time. Alerting on every individual error gets ignored within a week, so alert on rates. If only complaints and flagged outputs are sampled, add stratified sampling of the high-confidence stream, because novel error patterns appear first where nobody is looking.

After an incident, "add monitoring" is accepted as prevention and not as the root-cause fix, since instrumentation diagnoses the next incident and not this one. In a regulated sector, redact real-traffic logs at write time, define retention and restrict access. The evaluation sample inherits the same obligations.

Go deeper: why a lost cache raises the bill about threefold

This is a worked example, not a corpus rule, and the 75% share is invented. Anthropic's model documentation (live docs, read 2026-10-25) prices a cache read at 0.1 times the base input price for most current models, and at 0.05 times on Opus 5.5 and Sonnet 5.5. Take 0.1 times. If 75% of input tokens were cache reads, the input cost per unit was 0.325 of the full price.

Suppose a new prompt version puts a timestamp at the start of the static block, so the cache never hits. The input cost becomes 1.0, which is 3.1 times the earlier figure.

Output tokens and quality are unchanged, so where input tokens are most of the bill, the whole bill follows that ratio. The prefix is also processed again on every request, which fits the higher latency. Only the cache-read count and the prompt-version field make this visible in a minute.
