7.1Put the rule where the model actually sees it

Three engineers get generated code with consistent error handling. The fourth, three weeks in, does not. All four share the repository, the branch, the tool version. Running /context in a session where the convention held and one where it did not shows why in ninety seconds: three engineers wrote it into their own user-level file, never in version control. The fourth cloned the repository and got everything in it, which does not include three home directories.

Configuration is what turns a rule someone knows into a rule present whether or not anyone remembers it. Instruction files concatenate from root to working directory; only the project-level file travels with a clone. Two questions place any rule: when must it hold, and how strongly.

The 0%-scoring reflexA prompt instruction beside an existing mechanism is not a fix: when they disagree, the mechanism is what is actually true. A deny permission rule beats a narrower allow regardless of specificity, and settings files resolve by strict precedence where instruction files merely concatenate.

7.2Move the work earlier in the process

A review bot posts a median of nine comments on every pull request, and engineers have quietly agreed to ignore it. Three complaints, three mechanisms: it repeats itself because re-runs do not carry prior findings; it flags a deliberate, undocumented convention because the project instruction file never states it; its comments land as one wall of prose because nothing asked for structured output.

The gains come from moving where in the process work happens, not from typing faster. Four techniques match four diagnostics: interview for a missing requirement, tests first for checkable correctness, input/output examples for a varying shape, one message when issues interact.

Two more 0%-scoring trapsSwitching to plan mode once a task "gets hard" arrives after the structural decisions are sunk; plan when the approach is undetermined, whatever the size. Invocations and seats measure adoption, not value: name the outcome metric and its baseline first.

7.3Check what loaded before you theorise

The team's API error-envelope convention holds in some sessions and not others, same repository, same week. Comparing /context between a session where it held and one where it did not shows the cause: the convention lives in a path-scoped rule glob for src/api. Sessions started inside that directory load it; sessions started elsewhere do not. It was never intermittent, only conditional. Capitalising the instruction by hand worked four times in five, which suppressed the very signal that would have found the real cause.

Six rungs, cheapest first, each ruling out a family of causes: loaded, right layer, stale context, tooling scoped, retrieval, and only then the prompt or model. A fix that works most of the time on a non-deterministic system is a suppressed signal, not a partial one.

Read the stem for exclusions"Same repository, different engineers" points at user-level scope. "Started right after a refresh" points at retrieval. "Works in some sessions, not others" points at conditional loading, not intermittency.

Follow the mechanism, not the topic. The project-level file that let every future hire inherit the rule in 7.1 is the same file the review bot in 7.2 needed for its conventions. The path-scoped rule that gave a convention its glob in 7.1 is the exact mechanism 7.3 diagnoses when a behaviour is conditional rather than intermittent. Three objectives, one small set of mechanisms, applied to configuration, to workflow, and to its own failure.
