Domain 1 · 17% · 6 objectives

Solution Design & Architecture

The throughline: a business problem arrives as an outcome, never a specification, and the whole domain is the discipline of turning that outcome into an architecture, then stating what it bought in units the business already measures.

Scenario running underneath all six: a regional insurer cutting claims cycle time. 8,000 first-notice-of-loss claims a month, 6.4 days to a first decision, 40 handlers, denials requiring a licensed adjuster.

1.1 · Translating a business problem into a decision

"We take too long to issue quotes" names no system and can't be built. Translation converts an outcome into a decision: a specific, recurring point in a workflow where someone looks at inputs and produces a judgment. Four properties argue for automating a decision: scale past human capacity, a repeatable pattern with observable feedback, machine-readable context, and throughput that justifies the build cost.

Five signals argue the opposite, and the exam hides them in the setup paragraph, not the options: irreversible and rare decisions with no learning surface, a statutory human decision-maker, novel creative judgment with no repeatable pattern, a human relationship that is itself the product, and a human gating every iteration.

1.2 · Wiring the decision into a system

Four stages, and most deployed systems ship without the fourth. Input acquires, validates and sets the trust boundary, everything crossing it from outside your control is untrusted content, and information not captured here doesn't exist downstream at any price. Processing is the model call plus deterministic code; arithmetic, lookups and schema validation belong in code, not the model. Output is a contract with a schema, a destination and a named consumer.

Feedback is the stage most often missing, and a loop only closes when the signal reaches something that changes behavior. Implicit signals, a reviewer's edit or override, are the workhorse: they're a labeled training pair you're already paying to produce, generated the moment a human corrects an output.

1.3 · Picking the cheapest rung that holds

Five rungs, each pricing capability against cost: plain call, augmented LLM, workflow, agent, multi-agent. The discriminator is enumerability, can you write down in advance the set of paths a request might take? If yes, code it as a workflow. Choosing a rung is choosing a model size one level up: reach for the smallest one that clears the bar, not the newest-sounding one.

A real system is rarely on one rung. Invoice processing at 50,000 a month, 96% from known vendors in stable formats, 4% one-off or malformed, rewards a hybrid over either pure design.

1.4 · Giving the hard path a coordinator

One coordinator, several specialist subagents, no direct channel between them, everything flows through the hub. That single constraint is the whole design, and it means nearly every multi-agent exam item is really about one of four things the coordinator owns: decomposition, context passing, error handling, termination.

Context isolation is both the benefit and the hazard: it's why subagents don't pollute each other's reasoning, and why a synthesis agent produces a report with missing citations when the coordinator passed merged text instead of content plus metadata.

1.5 · Decomposition: one rule for splitting, one for stopping

Split until each unit has one evaluation criterion and one failure mode. Stop when coordination overhead exceeds the benefit. Both halves matter, over-decomposition is a real failure mode: every split adds a handoff, and every handoff loses what was implicit in the shared context.

A 14-file pull request run as one pass dilutes attention unevenly and misses cross-file issues. Split into 14 parallel per-file passes (criterion: local correctness) plus one integration pass over the structured summaries (criterion: cross-file consistency), and a quality drop tells you which pass to fix.

1.6 · Stating value in the unit the business measures

Five pillars, five different units: efficiency (input per output), transformation (a capability that didn't exist before), productivity (output per person), cost (total, including human review), performance SLA (a commitment). A stated SLA is a filter applied to the option set before comparison, not a tiebreaker for when two designs look close.

A five-step chain at 1.5s per call is 7.5s against a 3.5s p95 commitment; it fails before accuracy even gets weighed. Moving two steps off the request path by precomputing at ingest passes with margin. The trap is choosing the technically superior design that fails the named pillar, its accuracy figure will be real, and it will already be disqualified.

Follow one thread back

The regulatory constraint found in 1.1 set the risk-tier seam in 1.5, which set the human gate in 1.2's output routing, which is the sentence that satisfies the Chief Risk Officer in 1.6. That chain is what "end-to-end architecture" means, and it's what the exam is testing when it buries a constraint in the setup paragraph.

Where this echoesThe feedback destination meets Domain 4's evaluation loop. Least privilege, remove the tool rather than instruct against it, meets Domain 3's authorization objective and Domain 5's strongest guardrail layer. Confidence-tier decomposition meets Domain 4's optimization cascade, described from two directions.
Checkpoint · Domain 1

Design A is more accurate and uses a seven-call agentic loop. Design B is slightly less accurate and uses a three-step workflow. The scenario names a contractual four-second p95 commitment, and a single call runs about 1.5s.

Which one, and at what point in your reading should you have known?

Answer first, then open
Design B, and you should have known before reading either option.

Seven calls at 1.5s is about 10.5s at p95, against a 4-second commitment. Design A isn't a worse choice, it's a disqualified one, and its accuracy advantage never gets weighed because there's nothing to weigh it against. A stated SLA is a filter applied to the option set before comparison starts, not a tiebreaker reached for once two designs look close.

Domain 2 · 13% · 5 objectives

Claude Models, Prompting & Context Engineering

The throughline: five objectives that read separately and behave as one, because the same decision routinely serves two of them at once.

Scenario running underneath all five: a policy-servicing assistant, 12,000 conversations a day, fourteen turns average, compliance requiring a standing policy text on every call.

2.1 · Choosing a model per call path

Intent classification runs at the front of every turn, bounded and high-volume in front of a user waiting on a screen, so it takes the lowest tier clearing its accuracy bar. Coverage reasoning must hold several conditions together, so it takes a higher tier. Two call paths, two answers, decided in order: task complexity sets the floor, the accuracy bar is a number, the latency budget is a hard gate, volume multiplies both.

2.2 · Putting the rule where it has authority

Register, refusal boundaries and escalation triggers live in the system prompt, the only place with durable authority across turns. Anything that must never happen is enforced outside the model entirely: the value threshold also exists as a code-level check on the claim-initiation tool's arguments, because that one must never be argued past.

2.3 · Diagnosing the failure, then picking the instrument

Zero-shot handles most turns. The classifier carries five few-shot examples sitting on the one boundary measurement showed it confusing, each with a one-line rationale, four to six targeted examples, not ten to fifteen easy ones. Coverage reasoning carries a reasoning cue; the classifier doesn't, because it's single-step and the cue would cost latency on all 12,000 conversations for nothing.

2.4 · Compressing the low-density part only

The API is stateless, so every call resends the whole history, and compression has to be non-uniform because the information is not. A case-facts block holds policy number, claim ID and agreed adjustments, updated as facts appear, positioned outside the summarized region so a compression pass can never touch it. Earlier discussion is summarized; recent turns stay verbatim.

2.5 · Ordering the template by stability

Caching reuses a byte-identical input prefix, never the output, so the stable block must be unchanged and first. At fourteen turns and 12,000 conversations a day, an uncached preamble would be reprocessed roughly 168,000 times daily. Byte-identity is necessary and not sufficient: invalidation cascades forward from the first changed byte, so a request ID rendered at the top of the system prompt takes the hit rate to zero, and nothing errors.

The coupling is the point

Ordering the template by stability serves both caching and modularity at once. Trimming tool results serves both token cost and attention quality. Putting a guardrail in the system prompt and in code serves both behavioral coherence and enforcement. That's why this domain reads as five objectives and behaves as one.

Where this echoesCaching meets Domain 4's optimization objective: static content first, then enable caching, is the same answer in both domains. The guardrail layering meets Domain 5: a "must never" needs a non-persuadable layer, which is Domain 5's four guardrail layers with scoped permissions as the strongest. The missing-fact row meets Domain 3: no prompting technique creates knowledge, which routes a problem to retrieval design instead of another week of prompt iteration.
Checkpoint · Domain 2

A team enables prompt caching on a service with a 6,000-token static preamble. Cost doesn't move. The preamble is byte-identical across requests, assembled by code that appends retrieved context first, then the preamble, then the user message.

What's wrong, and why did "byte-identical" mislead them?

Answer first, then open
The preamble is identical, and it isn't a prefix.

Caching matches on the leading portion of the input, in order, from the first byte. Retrieved context sits in front of the preamble and changes on every request, so the match fails at position zero and nothing after it is ever reached. Being unchanged earns nothing unless the unchanged block is also first, stability and position are two separate requirements, and the team verified only one of them.

Domain 3 · 19% · 8 objectives

Integration

The throughline: every integration decision spends something, tokens, latency, a round trip, a privilege, to buy something else. The exam rewards converting that trade into numbers instead of describing it with adjectives.

Scenario running underneath all eight: a claims assistant for 900 adjusters, 180,000 requests a day, a 3,000ms contractual p95.

3.1 · Tool surface and the two costs

Adding a tool feels free, nobody's ever been stopped in a design review for adding one, but it has two separate costs. The first is tokens: every tool's name, description and schema gets serialized into the request whether or not it's used. The second is harder to see and it's the one that actually breaks production: selection accuracy.

The model picks a tool by matching descriptions against the request, and that gets harder faster than the tool count grows, because new tools tend to land next to ones already there, search_documents beside find_files beside query_knowledge_base. Think of it as a classifier: accuracy doesn't degrade with the number of classes, it degrades with how separable they are.

3.2 · Identity and the confused deputy

Identity and permission are supposed to travel together: established at the edge, carried down through every layer, each layer enforcing what that identity may reach. Agentic systems break this without raising any error at all. The agent runs as a service account, so a tool call sees the agent's credentials, not the user's, and every user collapses into one identity right where the data gets touched.

3.3 · Pricing the accuracy-latency trade

"We should use the faster model" is an opinion, and the loudest person in the room wins it. "Our p95 budget is 3,000ms, generation already takes 1,900, reranking costs 300 for a 4-point gain, that leaves 260" is a decision you can defend and revisit.

A document-triage pipeline sits at 2,800ms against a 3,000ms p95. Three accuracy proposals, self-critique, a bigger model, deeper retrieval, all genuinely improve accuracy and all blow the budget, because every one adds a new stage. The move that works is elsewhere: a 3,400-token static block sits after the retrieved chunks instead of before them. Move it to the front, cache it, and the freed budget funds the bigger model inside the original SLA.

3.4 · Watching a system that doesn't explain itself

A normal service puts a failure and its cause close together. An agentic system's output is the last step in a chain of decisions and doesn't explain itself, so a confidently wrong answer and a confidently right one look identical if the final response is all you check. The unit here is the trace, not the log line.

The sampling strategy is where intuition points the wrong way. A claims assistant at 200,000 requests a day gets about 2,000 escalations. Uniform 1% sampling catches about 20 of them, nowhere near enough to characterize what's failing.

3.5 · Chunking and the coupled index

Lift "this limit does not apply to renewals" out of a document with no heading above it. Which limit? Unanswerable, and that's the failure chunking exists to prevent: a chunk has to make sense read completely on its own. Split on structure, and prepend the document's heading path into the chunk text itself before it's embedded. The heading path in metadata alone would not fix this.

The chunking scheme, the embedding model and the vector store are one coupled system. Change one without the others and similarity scores become arithmetic without meaning, and nothing errors. The tell is timing: wrong citations starting right after a reindex point at retrieval, not the model.

3.6 · Matching mechanism to query shape

"RAG" and "vector search" have quietly become one word, and that collapse is where most retrieval mistakes come from. An error code like ERR_5521 carries almost no meaning for an embedding model to compress, it's rare and lands closer to other rare tokens than to the document that explains it, while every article about upgrade errors clusters tightly on the same topic. Ask a vector index why the code happens, and it hands back five perfectly on-topic articles, none of which mention it.

3.7 · Who decides what happens next

Three mechanisms connect an agent to something outside it, and one question sorts them: who decides what happens next? Your code deciding is a direct API call, cheapest and most under-used. The model deciding is MCP. Another agent deciding is agent-to-agent, costing the most because it's a full second inference loop on top of everything else.

3.8 · The discovery crossover

Loading everything up front guarantees visibility and pays a token cost on every request. Loading a compact map instead adds a round trip and a new failure of its own: the agent can miss a capability that exists because the map entry didn't make it obvious. This is a crossover with a real location, not a maturity ladder, tested in both directions.

What ties all eight together

A scenario built to test one objective almost always has a second one wired underneath it. The caching decision in 3.3 funds the reranking stage in 3.6. The entitlement filter in 3.2 lives inside the query that limits what 3.4's observability pipeline is even allowed to store.

Check every option against four shapes Does it add a component to patch something a narrower configuration already solves (architected), does it deliver more than was asked for (overspec), does it remove a working mechanism instead of tuning it (discard), or does it sound responsive while leaving the real decision untouched (half-move)?
Checkpoint · Domain 3

A scenario names a large static preamble, a p95 SLA, and asks how to fit in a higher-capability model. A colleague proposes trimming the preamble to save tokens.

What's the better move, and which two objectives does it actually satisfy at once?

Answer first, then open
Reorder the preamble to the front and cache it. Don't trim it.

Trimming a required policy block is a correctness regression wearing an optimization's clothes. Reordering and caching frees the same budget without removing content, and it answers 3.3 (latency-cost arithmetic) and 3.6/3.8's caching-as-prefix logic at once, the coupling this domain's hardest items test for.

Domain 4 · 16% · 6 objectives

Evaluation, Testing & Optimization

The throughline: a number only counts as a metric if crossing its threshold would change what you do. Everything else in this domain is either building that number honestly or spending it wisely.

4.1 · What makes a metric a metric

A real metric needs four things: a specific failure being counted, a denominator, a named segment, and a threshold declared before anyone saw a result. That last one carries most of the weight, set the bar after the scores come in and you've described what you got, not set a bar.

Five families fail differently. Accuracy needs a ground truth written in advance. Latency is a distribution, report p95 or p99, and keep time-to-first-token separate from total completion time. Cost is per unit of business work, not per token. Safety needs an achievable target, zero is unreachable on an open-ended task. Security is a separate axis from safety, what the system permits rather than what the model says.

4.2 · Building an eval set that isn't lying to you

Twenty to fifty hand-verified cases beat several hundred unverified synthetic ones: an unverified case contributes a score with no information behind it. 500 cases at a 6% label-error rate caps measurable accuracy at 94%, and teams burn weeks chasing points that were never real.

Natural-frequency sampling is exactly backwards. A document set running 78% invoices and 2% handwritten remittances, sampled at natural frequency across 50 cases, gets one handwritten case, and one case can't produce a failure rate. Stratify instead, thirty cases as a working floor per segment you're accountable for.

4.3 · Change control, treating a prompt like production code

A prompt has no type system, no compiler, and no unit of change smaller than the entire behavior. Measurement runs in a fixed order for a reason: regression proves nothing that worked broke, but says nothing about live traffic, which is what a controlled A/B checks next; an A/B proves a declared-metric win but says nothing about a seasonal pattern, which is what a staged rollout checks last.

4.4 · Diagnosing what actually broke

Most engineers reach for the model first because a swap is one line and feels decisive. Every layer upstream poisons everything downstream, so the order is data and retrieval first, then prompt and context, then model mismatch, and it's economically right too: checking retrieval costs an afternoon, checking the model costs weeks.

Hallucination is three separate failures wearing one symptom: grounding (the answer was there and the model departed from it), retrieval (nothing relevant came back), context management (something got dropped by compaction). Same symptom, three fixes.

4.5 · Making it cheaper and faster without breaking it

A token is a line of cost and a line of latency at once, cutting tokens usually helps both. Measure which stage dominates before optimizing anything: halving a stage that's 8% of the budget buys 4%. Caching a static preamble is the highest-value lever by a wide margin, and it's the only one that buys cost and latency together without spending any quality.

4.6 · Watching it in production

An eval set tells you what happened on cases you chose. Monitoring tells you what's happening on traffic you didn't. The field everyone skips is model identifier and prompt version, logged on every request, without it every investigation starts as archaeology through a deploy log.

The loop closing over a year

Six thresholds set before anyone knows what the system will score. A 400-case set stratified to over-sample the 2% of traffic carrying 30% of the risk. Every prompt edit gated. A grounded-answer drop in month four diagnosed at retrieval, not the model, and the step people skip when the relief sets in: the newly found failure becomes twelve new eval cases.

Where it echoesThe golden-query gate that blocks a bad reindex in Domain 3 is this domain's regression set, applied to retrieval. The human-review budget in Domain 5 is this domain's stratification argument. Domain 6's insistence on p95 over the mean is this section's metric discipline.
Checkpoint · Domain 4

A team reports 96% accuracy on a 500-case eval set. Customers keep complaining. Someone proposes enlarging the set to 2,000 cases collected the same way.

Will that fix it? What should happen instead?

Answer first, then open
No. It multiplies whatever bias the original 500 already carried.

If the set was built by keeping interesting examples and dropping messy ones, it already reports excellent performance while hiding the failures that matter. More of the same collection method tightens the confidence interval around a number that was never true. The fix rebuilds from real production failures, stratified by the segments you're accountable for.

Domain 5 · 14% · 5 objectives

Governance, Safety & Risk Management

The definition everything follows from: a guardrail is a constraint that holds independently of what the model generates. Put the constraint in the prompt and you've built a request, not a guardrail.

5.1 · Four layers, one strongest

Input validation acts before the call. Output filtering acts only after, too late if generating the content was itself the harm. Human approval acts right before the consequential action. Scoped permissions spans the whole timeline, removing the possibility rather than constraining behavior, the strongest of the four because there's no moment at which it can be too late.

5.2 · Two facts generate the whole failure catalogue

The model samples from a distribution over plausible continuations: that produces confabulation, an uninformative stated confidence, and stale content reported faithfully. Instructions and data arriving through the same channel produces prompt injection, direct and indirect.

Per-step accuracy compounds multiplicatively in a chain: a six-step pipeline at 96% per step lands at about 78% end to end, and every step passed its own test. The fix interrupts the compounding with a deterministic checkpoint, not a better model moving each step a point or two.

5.3 · Spending the review budget

Two variables decide human-review allocation: consequence (reversibility matters more than magnitude) and confidence, which must come from something genuinely independent of the model, never its own stated confidence. Past a consequence threshold, confidence stops being a routing variable at all, the human's job there is accountability, not accuracy.

5.4 · Compliance as an architecture problem

A regulation is an obligation that has to hold regardless of system behavior, so it can only ever be enforced architecturally. Every compliance scenario reduces to three questions: where's the boundary, what crosses it field by field, what proves that to an auditor a year later.

5.5 · Fairness as a system property

An aggregate accuracy figure is a weighted average, and a weighted average hides exactly the disparity you're looking for: 91% overall can be 94% majority, 78% minority. The two most popular fixes, removing the protected attribute and adding a fairness line to the prompt, are the two that destroy your ability to measure fairness at all.

The one question that catches nearly every wrong answer

Does this control hold regardless of what the model generates? A prompt instruction is a tendency. A documented risk changes nothing about behavior. A self-reported confidence is a sample from the same distribution as the claim it's judging. If the honest answer is "usually," the question was asking about a guarantee.

Checkpoint · Domain 5

Five options from five different questions: strengthen the system prompt, document the residual risk, upgrade to a more capable model, route on the model's confidence score, report aggregate accuracy.

They're wrong in five different-looking ways. What's the one thing they share?

Answer first, then open
Every one is a tendency standing in for a guarantee.

None of them holds regardless of what the model happens to generate today. That's the definition of a guarantee this domain keeps testing, and it's why the domain keeps routing correct answers back to code, permissions and people instead of prompts.

Domain 6 · 14% · 5 objectives

Stakeholder Communication & Lifecycle Management

What every phase does to a different object: takes a claim about a probabilistic system and makes it bounded, measured, and re-checkable. That's what makes five objectives one discipline.

6.1 · Discovery and the falsifiable requirement

"Route claims as accurately as possible" can't be tested, so no design can ever be shown to have met it. A bounded requirement has four parts: the target number, the measurement method, the evaluation set, the cost of an error.

6.2 · Communicating decisions and trade-offs

A single headline number is normally good practice, and for a system varying sharply by case type it's actively misleading: 94% on standard claims and 61% on the complex tail report an aggregate of 87%, which moves whenever the mix moves. Give the board 91% end-to-end with human triage included instead.

6.3 · Feedback loops and SLAs

Committing to "95% accuracy" without qualification is a promise about the customer's future input distribution, which you don't control. A real commitment needs four parts, and the one everyone omits, what's excluded, is the one that prevents the dispute.

6.4 · Documentation and implementation guidance

An architecture decision record has four parts, and two age differently: the decision and alternatives are stable, but the constraints that drove it expire. "We chose X after 86.7% against Y's 88.0%, because 1.3 points didn't justify 2.1 seconds" can be re-run in ten minutes when the constraint changes, instead of forcing a full re-derivation nobody remembers the inputs to.

6.5 · Lifecycle, and the two boundaries that carry the marks

At pilot-to-scale, the architect owes an explicit list of which pilot assumptions may not survive scale: inputs, support load, and a 1-in-500 failure that's invisible in 200 cases and eighty events a day at scale. At delivery-to-operations, code and a demo give a receiving team the ability to run the system and no ability to tell whether it's still right, because degradation here is silent.

Where this echoes

The evaluation suite handed over at the second boundary is Domain 4's eval set with a routine attached. The segmented report beating the flattering aggregate is the identical fix to Domain 4's masking trap and Domain 5's fairness objective. An SLA's population clause is Domain 1's value-pillar filter wearing a different name.

Checkpoint · Domain 6

A COO built a staffing plan on "the system is 87% accurate." The complex tail is about to grow from 22% to 35% of volume.

What happens to the 87%, and what should have been reported instead?

Answer first, then open
It falls to about 82%, with nothing about the system having changed.

0.65×94 + 0.35×61 ≈ 82.4. The model performs exactly as it always did; the aggregate moved because the mix moved. Reporting 94% standard, 61% complex, 91% end-to-end with triage instead would have let the COO staff for a growing triage queue rather than experience a mix shift as the system getting worse.

Domain 7 · 7% · 3 objectives

Developer Productivity & Operational Enablement

Exam weight: roughly four or five items out of 63, no domain floor. Learn it once, thoroughly, and put marginal study time into Domain 3 instead. Everything below follows from one fact: a model at the moment of a request is a function from text to text, with no memory of yesterday.

7.1 · Configuration and the mechanism reflex

Claude Code loads instruction files from a user level (one person, invisible in code review, doesn't travel with a clone) through a project level (everyone who clones the repo). This is a concatenated load order, not an override precedence: if two files disagree, the model sees both, and the fix is editing the files, not hoping one wins.

The mechanism reflex, this domain's own documented weak spot: when the model does the wrong thing, adding a prompt instruction beside an existing mechanism is the tempting fix and the wrong one whenever a mechanism already governs the behavior. A prompt instruction is advisory input the model weighs against everything else. A mechanism, allowed-tools scoping a skill, a deny rule in settings.json, sets a condition outside the model's discretion. Settings files resolve deny, then ask, then allow, first match wins, specificity never enters into it, a broad deny beats a narrow allow.

7.2 · Workflows: moving work earlier, not typing faster

The gains that justify real investment come from where in the process work happens. The interview pattern moves requirements earlier: the model asks about cache invalidation and staleness tolerance before code exists, the exact questions you'd otherwise discover by shipping the wrong thing three times. Four refinement techniques map to four distinct symptoms, and the less obvious batching rule is what the exam tests: interacting issues go in one message, independent ones get iterated separately.

7.3 · Debugging: which layer, not which line

Output varies between runs on identical input, and "the input" is never one thing, it's a system prompt, concatenated instruction files, retrieved documents, and prior turns all assembled into one request. The question becomes which layer owns this symptom, and the ladder runs cheapest first: is the content loaded, is it in the right layer, is context polluted, is tooling scoped correctly, is it retrieval, only last, the prompt or the model.

Where this echoes

The mechanism reflex meets Domain 3's authorization objective and Domain 5's strongest guardrail layer: remove the capability rather than instruct against it, one reflex, three domains. The diagnostic ladder meets Domain 4: check what feeds the model before blaming the model, same order, same economics, different tool.

Checkpoint · Domain 7

A skill keeps flooding the main conversation with exploratory output. A teammate adds "be concise, summarise only your findings" to the skill body. It helps, mostly.

What's the mechanism fix, and what does "it helps, mostly" actually tell you?

Answer first, then open
context: fork in the skill's frontmatter.

That runs the skill in an isolated subagent context so its output never enters the main conversation. The instruction asks the model to simulate not polluting the context; the frontmatter key makes pollution structurally impossible. "It helps, mostly" is a suppressed signal, not a partial fix: it removes the symptom often enough that nobody investigates, and the underlying condition is still there for the run where it matters.
