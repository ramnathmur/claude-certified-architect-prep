Evaluation, Testing & Optimization

Every other domain asks whether you can build the thing. This one asks whether you can tell, afterward, that it's actually working — and prove it to someone who won't just take your word for it.

The six objectives on the guide read like six separate skills, but they're really one loop with a direction to it. You define what "working" means as a number with a threshold attached. You build a fixed set of cases that number gets measured against. You use that set to gate every change before it touches real traffic. When production tells you something broke, you diagnose it in a fixed order instead of by hunch. You make the system cheaper and faster, but only inside the quality bar you already declared. And you instrument production so it reports back to you — partly to catch the next break, and partly to feed the eval set failures its authors never thought to imagine.

An evaluation set built at design time only contains the failures its authors could think of. Production contains the ones they couldn't.

If you never route production failures back into your eval set, you're measuring your own imagination, with increasing precision, forever. That's the whole point of the loop, so it's worth sitting with before anything else.

At Professional tier there's a fifth question riding on top of all of this: can you defend the decision? Not just which eval design is technically correct, but which one is affordable at 200,000 requests a month, which one survives a regulator asking how you know, and how you explain a tradeoff to a stakeholder who thinks "97% accurate" is a complete sentence. One structural note before we start: because pass/fail runs on total score with no domain floor, a weak Domain 4 is survivable in the arithmetic of passing this exam. It is not survivable in practice — the reflexes built here show up again in Domain 3's observability objective, Domain 5's human-in-the-loop validation, and Domain 6's SLA conversations.

1. What actually makes a metric a metric

Here's a test you can apply to almost anything a team calls a metric: if the number crossing its threshold wouldn't change anything you do, it's decoration, not a metric. Most of what teams collect fails this test immediately. A metric only earns its keep when it has a specific failure being counted (not "quality" — "the fraction where the model's answer contradicts the gold label"), a denominator to compare against, a segment of the population it describes, and a threshold declared before anyone saw any results. Set the bar after the scores come in and you haven't set a bar — you've just described what you got.

The guide names five families of metric, and they're separate for a real reason: they fail in different ways and get owned by different people.

Accuracy is task fidelity against a ground truth — the one family that requires you to have already decided what "correct" means, because you need a label to compare against. Latency isn't a single number, it's a distribution, and the mean is nearly useless for an SLA because the users who give up and leave are sitting in the tail — report p95 or p99 instead. And there's a distinction inside latency worth getting right: time-to-first-token versus total completion time. For a chat interface where someone's watching a cursor, TTFT is what they actually experience as responsiveness. For a batch job nobody's staring at, only the total matters — get this backwards and you'll optimize the wrong half of the pipeline.

Cost should be measured per unit of business work, not per token. Tokens are the unit you're billed in, and the one unit nobody outside engineering can reason about. "$0.08 per resolved ticket" is a sentence a finance stakeholder can hold you to. "1.4 million tokens a day" is telemetry that means nothing to them.

Safety is a rate of policy-violating output over a stated denominator, and the thing to get right here is achievability. On an open-ended generative task, a target of zero isn't an ambitious goal — it's an unachievable number, and the first time you miss it, the whole metric quietly stops being enforced because everyone's already decided it's aspirational. Set a small non-zero rate instead — say, under 0.1% of ten thousand outputs flagged for toxicity — and save the hard zero for properties a deterministic check can actually guarantee, like zero outputs containing a field marked as someone else's personal data.

And security is a genuinely different axis from safety, which is exactly the kind of distinction this exam likes to test. Safety is about what the model says. Security is about what the system permits — whether an injected instruction hiding in a retrieved document can reach a tool, whether an agent's credentials are scoped to only what it needs, whether data can leave through a tool call. You measure security against an adversarial test suite, not a quality rubric, and a system can be perfectly safe and completely insecure at the same time. Two different failure modes, two different owners.

How the exam tends to phrase this

A scenario hands you a requirement in adjectives — "the system needs to be fast, accurate, and safe" — and asks which measurement plan you'd adopt. The wrong answers cluster in predictable ways: metrics that are easy to collect rather than decision-relevant (average response length, tokens per day), a single composite quality score that sounds tidy and tells you nothing when it drops three points, a threshold "calibrated once we see baseline performance" — the after-the-fact bar wearing a lab coat — or a safety metric quietly applied to what's actually a security requirement.

2. Building an evaluation set that isn't lying to you

This is the longest part of the domain, and it's where the exam's best traps live, so it's worth slowing down.

Start from the first principle: an eval set is a measuring stick, and a measuring stick only works if it stays the same length. If the cases change between runs, a score change tells you nothing — you can't distinguish "the system got better" from "the test got easier." Which has an uncomfortable consequence: your set will go stale, and refreshing it destroys comparability with everything you measured before. You handle that by versioning the set and re-baselining on purpose, not by quietly editing cases in place because one looked wrong to you last Tuesday.

Where should the cases come from? Real production traces first, synthetic cases second, and hand-written cases only for failure shapes you have good reason to expect but haven't actually seen yet. The reasoning is blunt: the failures you imagine from a spec are not the failures that actually occur. A set built entirely from a design document just encodes its authors' mental model of the system — and the entire point of evaluation is to test that model against reality, not confirm it. Treat every case written from imagination as a hypothesis until a real trace proves the failure exists.

Here's a number that surprises people the first time: twenty to fifty hand-verified cases beat several hundred unverified synthetic ones. It sounds backwards until you think about what an unverified case actually contributes — a score, with no information behind it, because you don't actually know whether its label is correct. Run the arithmetic: a set of 500 cases with a 6% label-error rate has a hard ceiling on measurable accuracy at 94%, and you can burn weeks chasing the last six points of a number that was never real.

The bias that ruins most eval sets quietly

A team collects examples while building the system, keeps the ones that were interesting to look at, and drops the ones that were too messy to bother labeling. What's left is a set assembled almost entirely from cases the system already handles well — and it will report excellent performance while concealing every failure that actually matters. Adding five hundred more cases collected the same way doesn't fix this. It multiplies the same bias tenfold and hands you a tighter confidence interval around a number that was wrong to begin with. The fix has to be compositional — rebuilding around the segments and failure modes you actually need to report on — not volumetric.

Why natural frequency is the wrong sampling rule

The instinct most people bring to sampling is exactly backwards: sample the eval set to match production frequency, so the number "represents reality." A document-extraction system runs 78% invoices, 15% purchase orders, 5% credit notes, 2% handwritten remittance advices. Sample fifty cases at natural frequency and the handwritten segment gets exactly one case — and you cannot measure a failure rate on one case. You can't even detect a 40% failure rate on one case; you'll see a single pass or a single fail, and either one is noise, not signal.

So build the set to answer the question you actually have to answer. If you have to report accuracy by document type, every type needs enough cases to support a rate — thirty as a working floor — and the rare, expensive segments get over-sampled relative to their share of traffic, not under-sampled. If you need an aggregate figure afterward, reconstruct it by weighting.

The masking trap

An aggregate accuracy of 97% can be hiding a 40% failure rate on a rare document type, because overall metrics average away segment failures — and the segments they hide are disproportionately the rare, weird, expensive ones nobody wants to think about. Before anyone reduces human review on the strength of an aggregate number, every segment has to clear the bar independently.

One more balancing move worth knowing: for every failure your eval set is meant to catch, include a near-miss case where the system behaves correctly and a brittle grader would wrongly flag it. A set built only from failures hides false alarms; a set built only from clean cases hides misses. Aim for roughly equal counts, and treat that as a requirement rather than a nicety as stakes rise.

Three instruments, three different jobs

This is what the guide means by "mixed methodologies" — it's really asking whether you know these are three distinct tools, not one grading pipeline with three settings.

The first instrument is a deterministic check: exact match, schema validation, a regex, a numeric comparison, running the output against unit tests, a PII pattern scan. These are exact, reproducible, effectively free at any volume, and immune to grader error — and the range of things they can catch is wider than people assume. Schema validity, whether a cited span actually exists in the document, forbidden-field presence, numeric tolerance, tool-call ordering, refusal-when-required — all of that is code-checkable. Use these first, always, and never route something code-checkable to a model grader instead. Citation validation is the sharpest illustration of why: asking a model "is this citation accurate?" scores around 38% agreement with ground truth in published evaluation — worse than a coin flip — while checking whether the quoted string literally appears in the cited document is exact and costs nothing to run.

The second instrument is a model grader working from a rubric, for exactly the properties code can't reach — tone, coherence, whether an answer actually resolves the question that was asked. Four things make this instrument trustworthy rather than decorative. Decompose the rubric into binary sub-criteria instead of a 1-to-5 scale, because nobody can consistently say what separates a 3 from a 4 — the boundary drifts between runs. Use a grader from a different model family than whatever's generating the output, because a same-family grader shows self-preference bias and shares the generator's blind spots, so the exact failures it can't see are the exact failures the system is likely to produce. Validate the grader against real human labels before you believe anything it says — hand-label a sample, run the grader on the same sample, measure agreement, and treat something like 75% as a starting bar to calibrate from, not a fact carved anywhere official. And know its biases going in: it favors whichever option it saw first, it rewards length regardless of whether length helped, and if only a same-family grader is available, its output gets reported as degraded, never as ground truth.

The third instrument is a human, whose job is calibration, not grading at scale — establishing the labels the deterministic checks compare against, producing the sample the model grader gets validated on, periodically re-auditing that grader to catch it drifting. There's a hard limit worth remembering: if two domain experts wouldn't independently reach the same verdict on a case, no automated grader can be trusted on that case at any threshold. That's not a grading problem to solve with a better rubric — it's a sign the case needs re-scoping.

Put the three together and the order is always the same: deterministic checks filter, the model grader scales, humans calibrate periodically. Picture a support assistant producing 2,000 answers a day. Deterministic checks run on all 2,000 at zero marginal cost, and maybe 110 fail here and never see the next layer. The model grader runs on the surviving 1,890, scoring four binary criteria, at a fraction of a cent each. And fifty cases a week — stratified across segments and across pass/fail verdicts, not just the worst-looking ones — get human review, with grader-versus-human agreement tracked over time so nobody notices only after the grader has quietly drifted out from under them.

Shapes that need more than one score

A RAG system needs two separate rows — one for retrieval, one for generation — because a faithfulness score computed over the wrong passages is a meaningless number: the answer can be perfectly faithful to material that never actually answers the question. Agentic systems need two rows as well: trajectory (was the right tool called, in a sensible order) and outcome (did the final state actually satisfy the goal), because a correct answer reached through a wrong or irreversible path is still a failure. If an agent deleted a record and then reported the correct value from before the deletion, grading the outcome alone calls that a pass. And multi-turn systems need you to attribute the first turn that broke, not just the final state, because a late self-correction can mask an early defect that won't always self-correct next time.

One more distinction worth having ready: pass@k counts a success if at least one of k attempts worked — the right measure when something downstream catches a bad attempt and retries. pass^k counts a success only if all k attempts worked — the right measure when every single attempt is user-visible or does something in the world. An agent that books account changes might use pass@3 ≥ 0.90 for task completion, because a validator catches a bad plan before it executes. But the row that checks "did it confirm before any irreversible action" needs pass^5 = 1.0, because one silent irreversible action out of five tries is one too many.

The exam's favorite shape here is a healthy-looking number next to an unhappy reality: 96% accuracy on a 500-case set, and customers keep complaining anyway. Here it's wrong: it multiplies whatever bias the set already had and tightens the confidence interval around a number that was never true. The right answer rebuilds the set from real production failures and reports by segment.

3. Change control — treating a prompt like production code

A prompt is production code with no type system, no compiler, and no unit of change smaller than "the whole behavior." Edit one sentence and you can move accuracy on a segment you weren't even thinking about. The only safety net is measurement, run in a fixed order every time: regression evaluation first, then a controlled A/B against the current prompt on metrics declared in advance, then a staged rollout.

Each step exists because the one after it can't do its job alone. Regression goes first because an A/B costs real user traffic, and a change that already fails your held-out set has disqualified itself before it should ever touch a live cohort — the regression set is also the only place rare segments get proper coverage, since you deliberately over-sampled them there. The A/B comes next because the regression set can't tell you how the change behaves on the live distribution, at production latency, under production load. Staged rollout comes last because even a clean two-week 50/50 split hasn't exposed the change to every seasonal pattern or the Monday-morning traffic spike.

Designing the A/B so the result actually means something takes a few disciplines. Change one variable at a time — swap the prompt and the model and the retrieval depth in one variant, and a win only tells you the bundle helped, with three suspects and no way to isolate which one earned it later. Randomize at a stable unit like user or session, never at the request level, or a single conversation flips between prompt versions mid-thread and corrupts both the conversation and the metric. Declare the primary metric and the guardrails before the test starts — guardrails like latency, cost, or safety rate can only block, never justify shipping on their own. Fix the duration and sample size in advance and don't peek and stop the moment things look good, because that inflates your false-positive rate in a way that feels completely reasonable while you're doing it. And report by segment as well as in aggregate, because the same masking trap from the eval-set discussion applies here too.

What this looks like on a real system

A support assistant handling 40,000 requests a week, proposing to add three targeted few-shot examples to fix two tools the agent keeps confusing. The regression run on the 400-case set shows tool-selection accuracy on the ambiguous subset climbing from 0.71 to 0.93, overall accuracy holding steady — nothing regressed, so it earns a live test. The A/B is declared up front: primary metric is first-contact resolution, guardrails are p95 latency under 4.0 seconds and cost under $0.11 per resolved ticket, split 50/50 by user, two weeks. Resolution rate moves from 0.82 to 0.86, latency ticks from 3.4 to 3.6 seconds — inside the guardrail — cost ticks from $0.094 to $0.099 — inside the guardrail — and the gain concentrates exactly where predicted, with nothing else regressing. It ships, staged at 10%, then 50%, then 100%.

Notice that the extra tokens weren't free — they cost half a cent and two-tenths of a second — and the change shipped anyway, because those costs were declared as guardrails in advance and they cleared, not because nobody noticed them.

4. Diagnosing what actually broke

Here's the empirical fact that should reorganize how you debug any of this: when an LLM system degrades, the fault sits in what feeds the model far more often than in the model itself. Every layer upstream poisons everything downstream — swap the model while retrieval is still broken and all you've done is change the phrasing of a wrong answer. So the diagnosis order is data and retrieval first, then prompt and context, then model mismatch — and it's not just empirically correct, it's economically correct too. Checking retrieval against known-good passage IDs takes an afternoon. Swapping the model means a re-benchmark, a re-tune, a cost renegotiation, and re-running every eval you have.

Failure signatures worth memorizing

Symptom → most likely layer
SymptomLayer

Wrong on one document type, correct elsewhereData coverage / chunking — segment-shaped, not general
Facts correct, format or steps missingPrompt / instructions — the knowledge arrived, the instruction didn't

Forgets something from two turns ago, short conversationApplication bug — stateless API, history not resent
Fails on multi-step reasoning, retrieval and prompt already verified cleanModel mismatch — the conclusion, not the first move

Hallucination is three different failures

Treating hallucination as one phenomenon produces one reflexive fix — usually an instruction not to make things up — that addresses none of the actual causes.

The model can make an unsupported claim when the context did contain the answer — it had the material and departed from it, a grounding problem, fixed by requiring a citation for every claim plus a deterministic check that the cited span exists. It can make an unsupported claim when retrieval returned nothing relevant — it filled a vacuum, a retrieval problem plus a missing refusal path. Or it can fabricate under context pressure, when something got dropped by compaction and the model reconstructed it from nothing — a context-management problem, fixed by extracting precision-critical facts verbatim instead of summarizing everything uniformly. Same symptom, three different root causes, and the evidence that tells you which one you have is sitting in your logs: what was retrieved, what was actually in the context window, whether the claim has a resolvable source.

Worked case

A policy assistant's grounded-answer rate falls from 0.94 to 0.71 over a week. The team's first instinct is a bigger model. Following the order instead: retrieval Recall@5 has collapsed from 0.92 to 0.55. Root cause — a corpus refresh restructured headings, the chunker now splits mid-table, and the entitlement tables answering the most common question class are split across two chunks that individually score below the relevance floor. The investigation stops there. The model was never touched, and a bigger model would have produced a more articulate answer built on exactly the same missing passages.

The general lesson underneath: when quality drops sharply and something changed right before it, the thing that changed is your hypothesis. Sharp drops have causes. Gradual drift has drivers, which is a different kind of investigation. The exam's version of this always pairs a symptom with a timeline detail — a corpus refresh, a re-index, a prompt release — and the timeline detail is the answer key. The official guide's own sample question follows exactly this shape: a RAG system turning confidently wrong right after a document refresh points at retrieval and indexing, not the model.

5. Making it cheaper and faster without breaking it

A token is simultaneously a line of cost and a line of latency, so cutting tokens usually helps both at once, and adding context to chase accuracy usually hurts both at once. Optimization in this domain means moving along that curve on purpose, inside a quality bar already declared — and the rule that governs everything else here is: measure which stage actually dominates before you optimize anything. Halving the time of a stage that's 8% of your latency budget buys you 4%.

The single highest-value lever, by a wide margin, is prompt caching. When a large block of content is byte-identical on every request — a system prompt, a policy document, a tool schema — put it first, put whatever varies last, and turn caching on. The stable prefix gets reused instead of reprocessed, cutting time-to-first-token and cost together, at no quality cost, because nothing about the content changed. It's also, per the guide's own sample question, the answer whenever a scenario names latency and cost in the same sentence. Two things can silently break it: the prefix has to be genuinely identical — a timestamp or session ID rendered into it kills the cache instantly and invisibly — and the static content has to actually come first.

After that: route the routine majority of traffic to a smaller, faster model and escalate only the hard minority, but validate the escalation trigger on a labeled set rather than assuming it. Retrieval discipline matters more than people expect — fetching the top 20 passages instead of the top 5 costs tokens on every request and often hurts accuracy, because the extra passages are noise sitting exactly in the middle of the context window, where attention is already weakest. Output shaping matters because output tokens are usually the expensive side of the ledger and drive latency token by generated token. For long conversations, extract the facts that have to stay exact into a structured block and summarize everything else, because uniform summarization is how a dollar amount quietly turns into "approximately." And know what streaming actually buys you: it reduces how fast the first tokens arrive, not total completion time and not cost — a real win for an interactive chat interface, nothing at all for an overnight batch job.

The caching lever, with real numbers

A claims assistant sends an 8,000-token static policy preamble on every request, 200,000 requests a month. Without caching, that preamble gets billed and reprocessed 200,000 times — 1.6 billion input tokens a month that are byte-for-byte identical every single time, sitting in front of every request's first token because it has to be processed before generation can even start. Reorder it to the front, enable caching, and the prefix stops needing reprocessing — cost drops, time-to-first-token drops, nothing about the policy content changed.

The trap version of this answer

Someone proposes cutting the preamble from 8,000 tokens to 3,000 by trimming "the parts we rarely need." That produces a bigger number on the slide, and it also removes required policy content from a regulated determination process — a compliance regression wearing an optimization's clothes, exactly the trade a Professional-tier item is built to test. The stakeholder sentence for the real fix: we reordered the prompt so the unchanging policy text gets cached instead of resent, which cut cost and response time without removing any policy content. Nobody in that conversation needs to hear the word "token."

6. Watching it in production

An evaluation set tells you what happened on a fixed set of cases. Monitoring tells you what's happening on traffic nobody anticipated, and the eval set can never substitute for it, because a frozen input distribution is precisely what makes it a good measuring stick and precisely what makes it blind to drift. Production needs its own instrumentation, and that instrumentation has one organizing requirement: attribution. A metric moving is only useful information if you can say what moved it.

The field that matters most, and the one people skip: model identifier and prompt version, logged with every request. Without it, a quality change can never be tied back to a release, and every investigation starts as archaeology through a deploy log. Alongside that: retrieved document IDs and relevance scores, token counts split by input/output/cache-read, and latency broken out by stage rather than reported as one aggregate number nobody can act on.

Production also gives you cheap proxies that move before an offline evaluation ever would: escalation rate rising usually means the system is hitting more cases it can't handle, retry rate rising means outputs are failing some downstream check, thumbs-down rate rising is a quality regression the deterministic checks don't cover. None of these is a quality measurement on its own, and that's exactly what makes them worth alerting on — they move first, before anyone's opened the eval harness. Run the model grader continuously too, on a stratified live sample — not the whole stream, and not only the flagged cases, since novel error patterns show up first in the high-confidence stream, precisely where nobody's looking. And alert on rates and segments, not individual events, favoring leading indicators like cache-hit rate over lagging ones like user complaints.

A story worth keeping

Cost per request triples overnight, latency climbs almost two seconds, every quality metric stays completely flat. The cache-hit-rate panel shows a drop from 0.93 to 0.11 at 2:14am. The prompt-version field shows a release landed at 2:10 — someone had inserted a rendered timestamp into the system preamble for debugging, which made the prefix different on every request and silently killed cache reuse. Time to diagnosis: about four minutes, because two fields existed. Without them, that's a week of bisecting deploys while finance asks pointed questions. Notice the shape of the clue: cost and latency moved together while quality didn't move at all, and that combination points at the token or caching layer specifically, because a genuine model-behavior change would have disturbed quality too.

One more thing that's easy to treat as an afterthought and shouldn't be: production logs of a real system contain real user data. Redact at write time rather than read time, set an actual retention period, restrict who can see it. In a regulated sector this isn't hygiene, it's a control with an auditor's name attached to it, and any eval sample pulled from those logs inherits the same obligation.

7. How it all runs as one system

Take that claims assistant through a full year and watch each objective hand its output to the next. Week one: six metrics, thresholds agreed with the business sponsor before anyone knows what the system will actually score — the only time that conversation is honest. Weeks two and three: 400 cases pulled from real submitted claims, stratified so the 2% that are handwritten remittance advices — carrying 30% of the actual risk — get real coverage, every case hand-verified by an adjuster. Every prompt edit after that runs the regression set first, then a declared A/B, then a staged rollout, no exceptions.

Then, in month four, grounded-answer rate drops from 0.94 to 0.71. The diagnosis order runs exactly as designed: retrieval first, which has in fact collapsed following a corpus refresh that broke table chunking. The model is never touched. The fix is a chunking change, verified against the regression set before anything ships — and the newly discovered failure mode becomes twelve new cases added to the eval set.

That's the loop actually closing: production just taught the evaluation set something its authors didn't know a month ago.

Month five, optimization: profiling shows the policy preamble dominates both cost and time-to-first-token, so it gets reordered and cached, and a separate proposal to also trim it by 5,000 tokens gets rejected outright, because the removed sections are regulatorily required and the quality bar from week one isn't something you renegotiate for a cost saving. And continuously, underneath all of it: dashboards tracking accuracy by claim type, escalation rate, cost per claim, cache-hit rate, and grader-versus-human agreement over time, with every surfaced failure becoming a candidate for the next version of the eval set.

The property worth naming

Nothing in that whole year depends on anyone's gut feeling about whether the system "feels" better. Every decision is gated by a number defined before the result was known, and every number can be traced back to a specific layer that produced it.
