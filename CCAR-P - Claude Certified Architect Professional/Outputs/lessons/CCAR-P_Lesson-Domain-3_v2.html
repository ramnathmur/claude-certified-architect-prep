Domains 1 and 2 were about the system you design. This one is about everything that system has to touch and you didn't design.

An identity provider somebody configured years ago. A document store on its own refresh schedule. A downstream service whose latency profile is not yours to change.

Read the eight objectives cold and they look like a grab bag: tool sprawl, auth gaps, latency trade-offs, observability, chunking, retrieval, protocols, discovery. They are eight versions of one question.

Every objective in this domain is an admission-control decision: what gets into the model's context, what the model is allowed to reach, what that costs, and what record survives the transaction.

Here is where each one sits on a single request.

Hold that thread. It is why the worked system closing this lesson runs all eight at once rather than one at a time.

Next: we start at the agent box, with the surface it carries. The cost of a tool turns out to be paid in two currencies, and only one of them shows up on a bill.

1. Tool sprawl and the two currencies

By the end of this section you will be able to explain why adding a twenty-first tool can break the twenty that were working, and why better wording is only half a fix.

Adding a tool feels free. Nobody has ever been stopped in review for adding one.

It is not free, and it bills you in two currencies that never appear on the same ledger.

The first is tokens. Every tool's name, description and input schema is serialized into the request whether or not that tool gets used. A large surface is a tax paid on every turn.

The second is discrimination, and this is the one that breaks production systems.

The model picks a tool by matching descriptions against the request. With five clearly distinct options that is an easy problem. With twenty it is not, because new arrivals tend to be near-neighbours of ones already there: search_documents beside find_files beside query_knowledge_base.

Selection error grows faster than tool count, because the density of confusable pairs grows faster than the count does.

The analogy

A tool surface is a classifier, and every tool you add is a class. You already know that a classifier's accuracy does not degrade with the number of classes. It degrades with how separable they are. Twenty tools where each new one lands next to an existing one is a classifier whose decision boundaries overlap, and no amount of extra training data fixes overlapping labels.

Where it breaks A trained classifier gives you a confusion matrix, so you can see which pairs collide before you ship. Tool selection is zero-shot from descriptions, so there is no confusion matrix until production traces build you one. You find out which pairs are confusable by watching them fail, which is why the fix in this section starts with a week of traces rather than a design review.

There is a third cost, and it only surfaces in an incident review. Every tool is a privilege. One the agent does not legitimately need is still one it can call when a prompt goes sideways.

Blast radius tracks the size of the tool surface, not the size of the intended workflow.

Putting numbers under it

An internal operations agent accumulated 22 tools over three quarters, one integration at a time. Nobody added twenty-two tools. Twenty-two people each added one.

Each definition runs about 180 tokens once its schema is counted. So 22 tools is roughly 4,000 tokens spent describing capabilities before a single word of the actual request arrives.

At 40,000 requests a day that is 160 million tokens daily, most of it irrelevant to whatever the request needed.

Then a week of traces showed the damage was not spread evenly. Misroutes clustered in three confusable pairs: get_customer/get_account, search_tickets/search_knowledge, send_notification/create_alert. Those ran an 11% error rate against under 2% everywhere else.

Notice what decomposition did that better wording could not. Tool surface per request drops from 22 to 3 or 4, saving about 3,300 tokens a call, and the confusable pairs end up in different agents entirely.

Tightening descriptions is still worth doing. It just comes second, on whatever pairs remain confusable inside a single agent.

One case runs the other way, and the exam does test it. A scoped agent with a genuinely high-frequency cross-role need should get the tool added, because routing every instance through a coordinator would be pure latency tax. Complex cases still go through the coordinator. Strict scoping taken past its useful point creates its own failure.

Checkpoint 1 · before you read on

A team merges get_customer and get_account into a single lookup_entity tool with an entity_type parameter. Tool count drops, tokens drop, and the confusable pair is gone.

What did they actually change, and why is this worse than it looks?

Answer first, then open
They moved the ambiguity, they did not remove it.

The model still has to decide between customer and account. That decision has just migrated from tool selection into parameter selection, where it is harder to catch: a wrong tool call is visible in a trace as the wrong tool name, while a wrong entity_type looks like a perfectly normal call to the right tool.

Contrast that with decomposition, which puts the two tools in surfaces that are never loaded together. That removes the decision rather than relocating it.

Four answers that sound responsible and aren't

Tightening every description is a genuine half-move. It improves discrimination and touches neither the token tax nor the privilege surface.

Adding a routing classifier in front of the agent sounds like proper architecture: a dedicated component with one job. It adds a component, a failure mode and a latency hop, to compensate for a configuration problem a smaller tool set already solves.

Keeping every tool "for flexibility" is the same mistake from the other direction. On a tool surface, flexibility is indistinguishable from ambiguity, and the cost lands on every request either way.

Merging confusable tools into one general one drops the count in a way that looks like progress. Checkpoint 1 covers where the lost precision actually goes.

2. Who is calling, and what may they do

By the end of this section you will spot the moment a user's identity gets dropped in an agentic system, and you will know the one reflex this domain rewards more than any other.

Two questions live in most people's mental model of security as one question. Who is calling, and what are they allowed to do.

Conventional architecture keeps them separate but travelling together. Identity is established at the edge and carried down through every layer, and each layer enforces what that identity may reach.

Agentic systems break this quietly, and the word quietly is doing real work. Nothing errors.

The agent runs as a service. When it calls a tool, the tool is invoked with the agent's credentials, not the user's. Every user collapses into one identity at exactly the point where data gets touched.

That is the confused-deputy problem: a privileged component acting for a less-privileged caller, with the caller's constraints stripped off somewhere in transit.

Three gaps, in increasing severity

An HR assistant serves 4,000 employees. Its document store has three tiers: general policy open to everyone, manager guidance for about 400 people managers, and compensation planning documents for 12 HR business partners.

The fast path to a working demo was one service account with read access across all three, plus a post-retrieval step dropping any chunk the requesting user is not entitled to see. It demos perfectly.

The shallow gap is a quality bug. If a compensation document is the strongest match for a manager's query, the filter drops it after ranking. The user gets whatever ranked fourth or fifth, with no indication why the answer feels thin.

The second gap is structural. The filter is application code sitting in one path. Any other path that reaches the index has no authorization at all: a debugging endpoint, a batch job, a feature somebody writes next quarter without knowing the filter exists.

The third is the one people miss entirely. Traces and logs capture retrieved context before filtering happens. The observability system now holds compensation data under access controls that were never designed for it.

All three come from the same decision, which is why the fix is one move rather than three.

Push authorization down into the query. The user's identity propagates from the edge to the retrieval layer, and the vector search runs with an entitlement filter as part of the query itself.

Where a store genuinely cannot filter at query time, the fallback is separate indexes per entitlement tier. That is more infrastructure, and it is the right trade against enforcement living in application code.

The reflex worth having cold

Least privilege means the capability doesn't exist, not that it's watched.

Logging a privileged action, requiring a confirmation step, restricting it to business hours. All three are real controls, and all three are the wrong answer to a scenario that says a capability is not needed.

They are what you deploy when a privilege is genuinely required and you are managing its risk. They are not what you deploy instead of removing something that should not be there. The tell sits in the scenario prose: if it says the agent does not need the capability, the answer removes it.

Why the compensating controls still tempt

A confirmation step is right for something needed but consequential. It is wrong for something not needed at all, where it taxes every legitimate use to guard against one that should not exist.

A business-hours restriction narrows a window, not a privilege, and produces the odd result that the thing you did not want is fine at 2pm.

A rule written into the system prompt is probabilistic by nature. A security control that fails 1% of the time across 40,000 daily requests fails 400 times a day, which is not a security control. When the scenario also names a regulated sector or an audit requirement, the answer that satisfies the auditor is the same one: enforcement provable at the point of access, not asserted in application logic.

Checkpoint 2 · before you read on

A review of a claims agent finds an update_claim_status tool that the agent's workflow never legitimately uses. Four proposals arrive: log every call to it, require human confirmation before it fires, restrict it to business hours, or remove it.

Pick one, and say what the other three have in common.

Answer first, then open
Remove it. The other three all keep the capability.

Logging tells you the boundary was crossed after it was crossed. Confirmation taxes legitimate use and fails the moment the confirming party is itself an automated pipeline. A time window narrows when the unwanted thing can happen, not whether it can.

All three are correct controls for a privilege you actually need. The scenario says this one is not needed, and that single clause is what selects the answer. Read for it: "the agent doesn't need X" is the exam telling you the answer deletes X.

3. Turning a trade-off into arithmetic

By the end of this section you will stop arguing about accuracy-versus-latency and start pricing it, and you will recognise the one move that funds an upgrade for free.

Nearly every mechanism that buys accuracy spends latency to do it. A bigger model, more retrieved chunks, a reranking pass, a self-critique step.

Everyone knows the trade-off exists. That is not what is being tested.

What is being tested is whether you can convert the argument into numbers. Compare these two sentences.

"We should use the faster model." That is an opinion, and the loudest person in the room wins it.

"Our p95 budget is 3,000ms, generation already spends 1,900 of it, and the reranking pass costs 300 for a 4-point recall gain, leaving 260 of slack." That is a decision you can defend to a stakeholder, and revisit when the SLA changes.

Two disciplines keep the arithmetic honest.

Budget against the tail your SLA actually names, p95 or p99. That is where users experience the system, and it is not the mean your dashboard shows by default.

Separate total latency from perceived latency. Streaming moves time-to-first-token dramatically for an interactive chat surface and does nothing at all for a downstream service that waits for the complete response before acting. The scenario prose tells you which consumer you have, and it is easy to read straight past.

A budget with real numbers

A document-triage assistant with a contractual p95 of 3,000ms:

Stage-level latency budget at p95
Stagep95 (ms)
Edge, auth, identity propagation120
Query embedding180
Vector search (top-20)240
Cross-encoder rerank (20 → 5)300
Generation1,900
Response assembly60
Total2,800

That leaves 200ms of slack, with quality at 91% against a business target of 95%. Then three proposals arrive.

Read the three off the chart. A self-critique pass costs about 1,400ms for a 3-point gain, landing at 4,200, which is 40% over. A higher-capability model pushes generation from 1,900 to 2,600, total 3,500, still over. Retrieving top-50 instead of top-20 and reranking harder costs 90ms in search and 210 in rerank, total 3,100, marginally over, for a 1.5-point gain.

The trap is treating this as "which accuracy gain is worth the overage." That question has no good answer, and being asked it is the signal that you are solving the wrong problem.

Look at the preamble instead. It runs 3,100 tokens, it is identical on every request, and it currently sits after the retrieved chunks rather than before them.

Reorder it to the front, turn on prompt caching, and both time-to-first-token and per-request cost fall. The budget that frees up is enough to fund the higher-capability model inside the original SLA, with the accuracy gain attached.

Whenever a scenario names latency and cost together alongside a large unchanging block of content, look for the reorder-and-cache move before anything more expensive.

The distractor shapes here

Optimizing the mean when the SLA names the tail can look like progress on a dashboard while the actual complaint sits untouched. Treating streaming as a fix for a consumer that isn't interactive changes nothing about total time. Buying more accuracy than the scenario asked for is unpriced cost dressed as thoroughness. Cutting retrieved context to hit a budget pulls out a working mechanism instead of tuning it, and usually costs more accuracy than the time it saves elsewhere. And caching the model's output is a different mechanism from caching a stable input prefix . An answer that conflates the two is wrong about how the saving is actually achieved.

Checkpoint 3 · before you read on

A batch reconciliation service calls your assistant and waits for the complete response before acting on it. p95 is 400ms over the contractual budget. A teammate proposes enabling streaming, pointing out that it dramatically improves time-to-first-token.

What happens to the SLA, and what should you have asked before this discussion started?

Answer first, then open
Nothing happens. The SLA is still 400ms over.

Streaming changes when the first token arrives. It changes neither total completion time nor cost. A downstream service that waits for the complete response experiences exactly the total, so there is no perceived-latency benefit to collect.

The question to ask first is who the consumer is. The scenario always names it, and it decides whether perceived latency is a currency you can spend at all. A human watching a cursor and a batch job waiting on a payload are different problems with different solution sets.

4. Watching a system that doesn't explain itself

By the end of this section you will know why the textbook sampling answer is the wrong one here, and be able to say what a trace has to contain to be worth storing.

In a deterministic service, a failure and its cause usually sit close together. A stack trace, a status code, a query plan.

Agentic systems do not offer that. The final output is the last thing in a chain of decisions, and it rarely explains itself.

A confidently wrong answer looks identical to a confidently right one, if the response is all you are looking at.

So the unit of observability here is the trace, not the log line. Which tools got called, with what arguments and results. What context was retrieved, down to chunk IDs and document versions. Where the model chose between branches, or a guardrail fired. All stitched together by one correlation ID from the original request.

What "at scale" changes

The objective's own wording carries three consequences.

Volume. Full-fidelity traces are large. At 200,000 requests a day and roughly 30KB per trace, that is about 6GB a day and 2.2TB a year, sitting in a store you actually intend to query.

Cardinality. A metric labelled with a user ID or session ID explodes the label space and makes the metrics backend slow and expensive. High-cardinality detail belongs in traces, queried on demand. Metrics stay on low-cardinality dimensions: tool name, model, tenant tier, outcome class.

Sensitivity. A trace holds prompts, retrieved documents and tool payloads. That is a second copy of your most sensitive data, usually sitting behind access controls designed for engineers debugging outages rather than for the data itself.

This is the same discipline Domain 4 applies to production logs used as eval samples. Here the trace store inherits the obligation, and section 2's third gap is exactly this failure arriving one layer earlier.

Why the answer is stratified, not uniform

Take a claims assistant at that same 200,000 requests a day. Full capture is the 6GB-a-day, keep-it-forever problem above, so something has to give.

The textbook answer is uniform sampling. Take 1% and storage drops to 60MB a day, which is entirely manageable.

Now count what you caught. The day contains about 2,000 escalations. A uniform 1% sample captures roughly 20 of them.

Twenty escalations is nowhere near enough to characterise what is failing, and this is the trap: uniform sampling is calibrated to the common case, and the common case is not what you are hunting.

The policy that produces those numbers looks like this.

Stratified capture policy
StratumSample rateRationale
Requests ending in error or exception100%Rare and maximally informative
Requests escalated to a human100%The system's own admission of difficulty
Requests below confidence threshold100%Leading indicator of quality drift
Requests touching regulated claim data100% metadata, redacted payloadAudit needs the fact of access, not the content
Successful routine requests2%Enough for baseline distributions

Underneath the traces, low-cardinality metrics run on 100% of traffic: latency percentiles, tool-call counts by tool name, retrieval hit rate, escalation rate, guardrail-trigger rate, cost per request.

Alerting sits on those metrics, never on the traces. And instrumenting per stage rather than end-to-end is what turns "the system got slow" into "the reranker got slow."

Two wrong turns

Logging inputs and final outputs at 100% feels complete, and most API gateways hand it to you free. It is the highest-volume, lowest-information capture available. It tells you what happened and nothing about why.

Uniform low-rate sampling is genuinely the right textbook answer for high-volume homogeneous traffic. That is exactly why it is tempting, and exactly why it is wrong here: this traffic is not homogeneous, and the events you need are the rare ones.

Checkpoint 4 · before you read on

A team wants to find out which tools are involved in escalations. They add user_id and session_id as labels on their metrics so they can group by them, and sample traces uniformly at 1% to keep storage down.

Name both mistakes, and say which one will surface first.

Answer first, then open
Cardinality on the metrics, and the wrong sampling axis on the traces.

Cardinality. A user or session ID as a metric label explodes the label space and makes the metrics backend slow and expensive. That detail belongs in traces, queried on demand. Metrics stay on tool name, model, tenant tier, outcome class.

Sampling. Escalations are the rare stratum. A uniform 1% sample catches about 20 of 2,000, which cannot characterise anything.

Which surfaces first: the cardinality problem, and it surfaces as a bill or a slow dashboard. The sampling problem surfaces as an investigation that quietly fails to find an answer, which is far easier to mistake for "we looked and there was nothing there."

5. What a chunk actually is

By the end of this section you will be able to look at a chunk and say whether it can ever be retrieved usefully, and to diagnose a RAG system that went confidently wrong overnight.

Model weights hold general knowledge. Your organization's specifics live somewhere else, change on their own schedule, and carry their own access rules.

RAG is the pipeline that pulls the right specifics into context at request time. It has five stages where things go wrong: ingestion, chunking, embedding, indexing, retrieval. Diagnosing a RAG failure means working out which of the five.

Start with a sentence. "This limit does not apply to renewals."

Lift it out of the middle of a long policy document, with no heading above it, and ask what it means. Which limit? Renewals of what?

It is unanswerable, and that is the failure chunking exists to prevent.

A chunk is the smallest span of a document that still makes sense read completely out of context.

That rules out fixed-size splitting as any kind of default. A flat 512-token window cuts wherever 512 tokens happens to land: mid-clause, mid-table, mid-function.

It points instead at document structure. Clause boundaries in a policy manual, endpoint boundaries in an API reference, ticket boundaries in a support archive. The structure a human author already imposed is a map of where the real seams are.

Two refinements make it work in practice.

A small overlap, 10 to 15%, is insurance against a key sentence straddling a boundary. It is not a strategy in its own right.

Contextualization matters more than it looks. Prepend the document title and heading path to the chunk text before it gets embedded.

If that feels like a familiar move, it is. Prepending the heading path is doing for a chunk what positional encoding does for a token: putting where this came from into the representation itself, so the thing downstream can actually use it.

Four content types, four different answers

An insurance operations knowledge base
ContentChunking approachWhy
Policy manuals (40–200pg, deep headings)Clause boundaries, 200–600 tokens, heading path + clause number prependedMetadata (policy ID, date, jurisdiction) lets a query filter to the version in force on the claim's date

Indexing is where the exam's own sample question lives, and it turns on one fact.

An index is one coupled unit made of three things: the chunking scheme, the embedding model, and the vector store.

Change any one without the others and the space becomes inconsistent. Vectors from a different embedding model land in a different geometry, so similarity scores between them are arithmetic without meaning.

And here is the part that makes it dangerous. The system does not error. It returns confident nonsense.

The analogy

An index is a tokenizer paired with a model. You already know what happens if you swap the tokenizer under a trained model and change nothing else: no exception, no warning, just output that is fluent and wrong, because the model is faithfully interpreting IDs that now mean something different. Chunking scheme, embedding model and vector store are coupled the same way, and re-embedding with a different model version is the same class of mistake.

Where it breaks A tokenizer mismatch usually degrades every single input immediately and obviously. Embedding drift degrades only retrieval quality, only on some queries, and leaves generation looking healthy. There is no crash and no error rate to alert on, which is why this one needs a deliberate validation gate rather than ordinary monitoring. The analogy tells you the mechanism and understates how hard it is to notice.
Worked case: the refresh incident

Six weeks after launch, a nightly reload of the policy manuals runs. The next morning the assistant is confidently citing clause numbers that don't match the text it quotes. A RAG system that starts returning confident, wrong answers immediately after a document refresh is a retrieval and indexing problem . Not the model, not the prompt, not the temperature. The timing is the whole clue.

The investigation runs in a fixed order. First, did the re-index complete? Compare chunk count against the expected count from source, where a 30% shortfall means a partial run. Second, did the chunking configuration change alongside the refresh. Third, did the embedding model version move, comparing what's recorded in the index against what's running at query time , the classic silent killer, because nothing errors when it happens. Fourth, did deleted or superseded documents actually leave the index, or are they still ranking as stale vectors. Only after all four does the prompt or the model get a look.

In this case the cause was the embedding version drifting because the ingestion job pulled a floating version tag. The fix pins the version to the index and re-embeds the corpus; the prevention is a validation gate after every re-index : a fixed set of golden queries with known-correct chunk IDs, blocking promotion if the hit rate drops.

Three tempting wrong answers

Lower the temperature. "Confidently wrong" sounds like a sampling problem, so this feels responsive. Temperature governs how the model picks tokens and has nothing to say about which documents were retrieved.

Swap in a more capable model. Same shape. A better model reading the wrong document produces a more articulate wrong answer.

Increase chunk size to give the model more context. This one is the closest to plausible, because the complaint really is about missing context. A larger chunk dilutes the embedding across more topics and lowers precision. Contextualization solves the context problem without paying that.

6. RAG is not a synonym for vector search

By the end of this section you will be able to look at a query and name the retrieval mechanism it needs, including the cases where the answer is not retrieval at all.

"RAG" and "vector database" have collapsed into one idea in casual usage. That collapse is the source of most retrieval mistakes on this exam.

Retrieval strategy is a choice on two independent axes.

What shape the data is: prose, structured records, code, tables, entities with relationships, time series.

What the query is asking for: look up an identifier, find something semantically similar, filter by attribute, aggregate across records, traverse a relationship.

The mechanisms line up against those axes unevenly.

Retrieval mechanisms by strength
MechanismStrong atWeak at
Dense / vectorParaphrase, conceptual similarityExact tokens: part numbers, error codes, rare terms
Lexical / BM25Exact terms, identifiers, rare vocabularyParaphrase, queries sharing no vocabulary with the answer
Hybrid (fused)Corpora and queries mixing both formsCost and complexity when only one form is present
Metadata filter + semanticScoping to jurisdiction, tenant, date, entitlementLittle; usually additive and underused
Structured query (SQL)Aggregation, counting, joins, exact numericsAnything needing semantic understanding of prose
Graph traversalMulti-hop relationship questionsEverything else; expensive to build and maintain

The weakness worth sitting with

The dense-retrieval failure is counterintuitive and heavily tested, so let me walk it slowly.

Embedding models compress meaning. A code like ERR_5521 has almost no distributional meaning to compress: it is rare, it appears in few contexts, and its vector ends up closer to other rare token sequences than to the document that explains it.

Meanwhile every article about upgrade errors clusters tightly on the same topic, because they genuinely are about the same thing.

Now ask a vector index: "why does ERR_5521 happen after upgrade?"

Hybrid retrieval earns its place exactly when a corpus mixes natural-language explanation with exact identifiers and users query in both forms.

That describes support, legal, medical and engineering content. It does not describe everything. Bolting hybrid onto a corpus of pure narrative prose queried in plain language buys a second index and a fusion step for nothing.

Two more moves in the same toolkit

Filter before ranking. Apply the metadata constraint as part of the query, so semantic ranking runs only across the eligible set. That is a precision gain, and where entitlement is involved it is also section 2's correctness requirement showing up again.

Retrieve wide, rerank narrow. Pull the top 20 to 50 candidates, then rerank down to 3 to 5. You get most of the precision of an expensive search at most of the speed of a cheap one, and you pay for it with a latency stage that has to fit the budget from section 3.

One router, six query shapes

A field-service assistant over three sources, troubleshooting articles in prose with codes inline, a 45,000-row parts catalog, an equipment hierarchy with supersession relationships, shows the router this implies:

Query shape → retrieval strategy
QueryShapeStrategy
"Compressor is short-cycling on a model 400"Prose, conceptualDense, filtered on model=400
"What does ERR_5521 mean"Exact identifierLexical

Count the rows. One strategy across all six would be wrong four times out of six.

Three wrong turns are worth naming. Assuming RAG means vector search fails outright on identifiers, aggregations and relationship queries. Building a knowledge graph for what is actually a single-hop foreign-key lookup buys years of maintenance for a join. And raising top-k until the right document appears floods the context and worsens lost-in-the-middle, when reranking is the targeted version of the same intent.

Checkpoint 6 · before you read on

A stakeholder asks you to justify building a second retrieval index. Your corpus is internal narrative policy prose, and users ask questions in plain language: "what is our parental leave entitlement?"

Do you build it, and what would change your answer?

Answer first, then open
No. Hybrid is not a default, it is a response to a specific corpus shape.

Narrative prose queried in plain language is precisely where dense retrieval is strong. A lexical index and a fusion step add cost, latency and a second thing to keep in sync, in exchange for nothing measurable.

What would change it: exact identifiers appearing in the corpus and in how people search. Policy clause numbers, form codes, system error codes, drug names, part numbers. The moment a user types "what does form P-45B require" you have the mixed corpus that hybrid is for.

Notice the shape of the justification either way: it is measured hit rate on the query types you actually receive, never "hybrid is best practice."

7. Who decides what happens next

By the end of this section you will have one question that sorts any integration into the right mechanism, and you will know which mechanism is chronically over-used.

Three mechanisms exist for connecting an agent to something outside it. One question tells them apart.

Who decides what happens next?

Your code decides: a direct API or CLI call. The sequence is known at design time, it runs whether or not a model is involved, and the result is deterministic. Cheapest, fastest, most testable, and the most under-used of the three, because "let the agent decide" is a seductive default even when nothing needs deciding.

The model decides: MCP, inside a surface your server exposes. Tools are actions the model can call. Resources are read-only content it can consult. Prompts are reusable templates. All discovered at connection time.

MCP's real value is standardization. Prefer an existing community server for standard systems like issue trackers or source control, and reserve custom builds for workflows genuinely unique to your organization.

Another agent decides: agent-to-agent. You are handing over a task rather than requesting data, and the other side brings its own context, tools and judgment, returning a result rather than a payload. Right when the work needs reasoning your agent should not be doing.

Cost climbs in exactly that order, and the reason is worth seeing rather than reading.

One distinction inside MCP is easy to blur. A resource is something the agent looks at without spending a tool call. A tool is something it does.

Exposing a content catalog as a resource gives the agent a map without burning a model turn on an exploratory query, which is exactly what the next section is about.

Five systems, three mechanisms

A claims-processing assistant earns all three on one build. Take the five systems one at a time, asking each time who decides.

The claims database. The claim ID is already known and nothing is left for the model to decide, so this is a direct call in pre-processing. One round-trip, deterministic, and it removes an entire category of "the agent forgot to look up the claim" failures.

The policy document store. Here the agent genuinely has to decide whether and what to search, so it becomes an MCP tool, paired with a resource exposing the catalog.

The fraud scoring service. Deterministic in and out, and required on every claim above a threshold. It stays a direct API call from the orchestration layer rather than a tool, because a tool is something the model can choose not to call.

The issue tracker. A standard system widely integrated elsewhere, so it uses an existing community MCP server, configured with per-user credential substitution. That is section 2's authorization logic showing up inside a protocol decision.

Medical necessity review. It needs clinical reasoning the claims agent has no business holding, and a determination attributable to the clinical function for audit. That goes agent-to-agent: hand over the case, get back a determination with a rationale.

Four wrong turns, all the same mistake

Every one of them blurs the decision boundary.

Exposing a deterministic, always-run step as a tool so the agent "can decide" introduces non-determinism where there was none, and risks a mandatory step being skipped.

Building a custom MCP server for a standard integration reimplements something already maintained, and inherits its upkeep forever.

Reaching for agent-to-agent when a tool call would do pays for a full inference loop to perform a function call.

Pasting a catalog into the system prompt instead of exposing it as a resource bloats every request with content that goes stale the moment the catalog changes.

Checkpoint 7 · before you read on

A fraud scoring service is deterministic in and out, and compliance requires it to run on every claim above a threshold. A designer proposes exposing it as an MCP tool "so the agent can call it when relevant."

What is wrong with this, and what is the correct mechanism?

Answer first, then open
A tool is something the model can choose not to call.

That is the entire objection. Exposing a mandatory control as a tool converts "always runs" into "usually runs," and the failure is silent: a claim that skipped fraud scoring looks exactly like one that passed it.

Correct mechanism: a direct API call from the orchestration layer. Nothing here needs deciding, so nothing should be delegated to a decision.

The general form, worth carrying into the exam: if a step must always happen, it must not be a tool. Read scenarios for the words "every", "always", "must", and "required" attached to a step.

8. Loading everything versus loading a map

By the end of this section you will be able to argue this objective in both directions, which is what the exam actually asks for.

Monolithic context loads the whole surface up front. Every tool definition, every schema, the full document catalog, all of it in the request.

Progressive discovery loads a compact map instead, and fetches detail on demand.

Three forces push toward the second as a surface grows.

Token cost is paid on every request regardless of use.

Discrimination degrades with surface size. That is section 1's argument, applied to the whole context rather than just the tool count.

Long context has an attention gradient. Content at the start and end of a long input is attended to more reliably than content buried in the middle. A monolithic surface therefore guarantees that most of itself sits in the penalized middle.

None of which makes progressive discovery free.

It adds a round-trip, which is real latency on every request that needs one. And it introduces a genuine failure mode of its own: the agent can fail to find a capability that exists, because the index entry did not make it obvious.

A monolithic surface at least guarantees visibility. That is why it stays correct in three cases: when the surface is small and stable, when the latency budget cannot absorb a round-trip and the surface fits anyway, and when the content is needed on literally every request.

That third case is section 3 arriving again. Content needed every time belongs in the request, and being identical every time, it should be ordered first and served from a cached prefix.

Where the two actually cross

The source numbers: a 60-tool, 8-namespace agent costs 12,000 tokens loaded monolithically (60 × 200 tokens each) versus roughly 2,700 progressively (8 namespace entries at 150 tokens, plus one expansion averaging 7.5 tools). But that's one snapshot. The relationship underneath it holds for any surface size and any namespace granularity , which is what the widget below actually computes, live, rather than asserting for a single example.

Both directions, and the half-moves

The exam runs this objective in both directions. The one people drill less is the rejection: a small, stable surface with a tight latency budget gets a discovery mechanism proposed anyway, and the correct answer turns it down, because below the crossover the round-trip costs more than the tokens it saves.

Watch for two disguises. Content identical on every request dressed up as a discovery problem is a caching answer. And a "list everything" discovery tool the agent has to remember to call first is a half-move: it provides the map but makes reaching it probabilistic, when readable content the agent can simply consult is the stronger form.

The better real-world answer is rarely either pure strategy. Trace analysis on that 60-tool agent showed six tools accounting for 61% of all calls. Promoting those six into the base surface brought the base to 2,400 tokens and meant 61% of requests needed no expansion at all.

That is cheaper in both tokens and latency than either pure version, and it was justified by a measured call distribution rather than picked in the abstract.

Checkpoint 8 · before you read on

An agent carries 9 tools that change roughly once a year, on a service with a hard 800ms p95 budget already running at 740ms. A proposal arrives to move it to progressive discovery, citing the token savings.

Accept or reject, and give the number that decides it.

Answer first, then open
Reject. The deciding number is the 60ms of headroom.

Nine tools at roughly 200 tokens each is about 1,800 tokens. Progressive discovery would trade that for a round-trip, and a round-trip does not fit inside 60ms. The surface is also small and stable, which is the exact condition under which monolithic remains correct.

Below the crossover, discovery costs more than it saves. Token savings are real and irrelevant when the budget that binds you is latency.

The reflex: this objective is not "progressive is more advanced." It is a crossover with a computable location, and the exam tests the side of it you are standing on.

9. One system, all eight objectives

By the end of this section you will have seen all eight objectives decided on one system, and seen why fixing only the objective a question names leaves it half-solved.

A regional insurer is building a claims assistant. 900 adjusters, 180,000 requests a day, a contractual p95 of 3,000ms, and a seven-year audit requirement on protected claim data.

Protocol choices set the shape first. The claim record comes in through a direct API call in pre-processing. The policy store is an MCP tool with a companion resource carrying its catalog. The fraud scorer is a direct API call from the orchestration layer, never a tool. Escalations go through an existing community MCP server for the issue tracker. Medical necessity review is agent-to-agent.

Then the tool surface. Version one of the adjuster agent carried all 19 available tools and ran an 8% misroute rate, concentrated in three near-duplicate pairs.

It gets split into three role-scoped agents of 4 to 6 tools each, with one deliberate exception. The claims agent keeps a read-only policy-status check, because it is needed on nearly every turn and the coordinator round-trip was the dominant latency cost.

Across those three agents the total surface is 34 tools, restructured as five namespaces, with the seven tools covering 64% of calls promoted into the base. That is about 2,600 tokens against 6,800 monolithic.

Identity propagates the whole way. The policy store's retrieval query carries an entitlement filter. The issue tracker uses per-user credential substitution. And a review turns up an unused update_claim_status tool, which gets removed outright rather than logged, confirmed, or time-boxed.

The knowledge layer follows the same discipline. Policy manuals are chunked on clause boundaries with the heading path prepended. The embedding model version is pinned to the index. Every re-index runs 40 golden queries before promotion.

The claims-history table is never embedded. It is queried directly.

Retrieval over the policy corpus runs hybrid, filtered by metadata before ranking, retrieved at the top 30 and reranked to the top 4. Claims-history questions route straight to SQL.

The latency budget lands at 2,750ms against the 3,000ms SLA. Those 250ms of slack exist because a 3,400-token static preamble was moved to the front of the request and cached, which is what funds the reranking stage that would not otherwise have fit.

Observability closes the loop. One correlation ID from the edge through every downstream call. Stratified capture at 100% for errors, escalations, low-confidence paths and clinical handoffs, 2% for routine successes.

Metrics on stage-level latency, retrieval hit rate and mean retrieval score run across all traffic. Note which two those last are: retrieval hit rate and mean retrieval score are exactly the pair that would have caught section 5's embedding-version drift within the hour, instead of the following morning.

The interlock is the point

None of those eight decisions sits in isolation. The caching decision funds the reranking stage. The entitlement filter lives inside the retrieval query, which constrains what the observability pipeline is even allowed to store. The tool split changes the exact surface the discovery layer has to cover.

A scenario built to test one objective almost always has a second one wired underneath it, and the answer that fixes only the first leaves the question half-solved.

Where these reflexes show up again

Three of this domain's habits reappear in other domains under different names, and the exam does not respect the boundaries.

The golden-query gate meets Domain 4's regression set. Forty queries with known-correct chunk IDs, blocking promotion if the hit rate drops, is a regression set applied to retrieval instead of to the whole system. Same reasoning: a measuring stick only works if it stays the same length.

Stratified capture meets Domain 4's stratified eval set. Section 4 over-samples errors and escalations because rare events carry the information. Domain 4 over-samples the rare document type for the identical reason. If you learned one, you already know the other.

Least privilege meets Domain 5's guardrail layers. Section 2's rule that a capability should not exist is the strongest of the four layers Domain 5 sets out, and it is strongest for the reason given here: it removes a failure class rather than mitigating it.

Common misconceptions

The mythLeast privilege means monitoring what the agent does with its permissions.
Why it's temptingLogging and confirmation are real, unambiguous security practices that show up in every checklist, so keeping the capability and instrumenting it feels responsible.
The realityLeast privilege means the permission doesn't exist. Logging, confirming, and time-boxing are controls for privileges you've decided to keep , never substitutes for removing one that was never needed.
The one testDoes the scenario say the agent doesn't need this capability? If yes, the answer removes it. Logging or confirming it is the designated wrong answer.
The mythRAG means searching a vector database.
Why it's temptingVector search is the default in most tooling and the first thing most tutorials show, so it's the mental model that sticks.
The realityVector search is one mechanism among several. Exact identifiers want lexical search, aggregation wants SQL, multi-hop relationships want graph traversal . Matching mechanism to query shape is the actual skill.
The one testDoes the query need an exact code, a count, or a relationship traversal? If so, a vector index was never going to answer it, however it's tuned.
The mythA RAG system giving confident wrong answers needs a better model or a lower temperature.
Why it's tempting"Confidently wrong" sounds like a sampling or capability problem, and both are one-line changes with no pipeline work required.
The realityTemperature governs token selection, not which documents were retrieved. When the degradation lines up with a document refresh or re-index, the fault is in retrieval and indexing . A better model just reads the same wrong passage more articulately.
The one testDid the failure start right after a refresh, re-index, or ingestion change? If the timing lines up, check retrieval against known-good passages before touching the model.
Four distractor shapes worth checking every option against

ARCHITECTED sounds most like proper engineering: a routing classifier, a validation layer, a second retrieval hop. It is wrong because it adds a component to compensate for something a narrower configuration already solves.

OVERSPEC delivers more than the scenario asked for, at a cost nobody priced in.

DISCARD removes a working mechanism instead of adjusting it. Cutting retrieved context to hit a latency budget, rather than finding the latency being wasted elsewhere.

HALF-MOVE looks like it addresses the problem, with better tool descriptions or a discovery tool the agent must remember to call, and leaves the actual decision space or privilege surface untouched.

Read every option in this domain against those four before asking whether it sounds correct.
