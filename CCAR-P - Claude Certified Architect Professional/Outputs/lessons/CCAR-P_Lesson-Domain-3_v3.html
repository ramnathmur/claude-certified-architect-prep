One thing before we get into the material, because it should shape how you spend your remaining study time. The exam runs 63 items in 120 minutes, scored on a 100-to-1000 scale against a 720 pass mark, and there's no per-domain floor — you pass or fail on total score alone. Two things about item structure are still genuinely unclear: whether items stand alone or arrive in shared-scenario blocks, and whether multiple-response items carry partial credit. Study as though they don't. That's the more expensive assumption to make, and it's the same habit that already cost you on CCAR-F: losing multiple-response items by being mostly right when the scoring was all-or-nothing.

Domain 1 and Domain 2 were about the system you design. This domain is about everything that system has to touch that you didn't design: an identity provider someone configured years ago, a document store on its own refresh schedule, a downstream service with a latency profile you don't control. The eight objectives — tool sprawl, auth gaps, latency trade-offs, observability, chunking, retrieval, protocols, discovery — look like a grab bag the first time you read through them. They're not. They're eight versions of one question.

Every objective in this domain is an admission-control decision: what gets into the model's context, what the model is allowed to reach, what that costs, and what record survives the transaction.

Hold onto that thread as you work through the rest of this lesson. It's why the harder items in this domain often test two objectives at once instead of one, and it's exactly the point of the worked system that closes this lesson out.

1. Tool sprawl and its two costs

Every tool you register costs you twice, and the two costs are usually tracked by different people. The first is tokens: a tool's name, description, and input schema get serialized into the request whether or not that tool ends up being used, so a large tool surface is overhead you pay on every single turn. The second cost is discrimination, and it's the one that actually breaks production systems. Think about how the model picks a tool: it matches descriptions against the request. With five clearly distinct options, that's an easy problem. With twenty, new tools tend to be near-neighbors of ones already there — search_documents sitting beside find_files sitting beside query_knowledge_base — and selection error grows faster than the tool count does, because the number of confusable pairs grows faster too. There's a third cost that only shows up in an incident review: every tool is a privilege, and one the agent doesn't legitimately need is still one it can call if a prompt goes sideways. Blast radius tracks the size of the tool surface, not the size of the workflow you actually intended.

Putting numbers under it

Here's what that looks like with real numbers. An internal operations agent accumulated 22 tools over three quarters, one integration at a time. Each definition runs about 180 tokens once its schema is counted, so 22 tools means roughly 4,000 tokens spent describing capabilities before a single word of the actual request arrives. At 40,000 requests a day, that's 160 million tokens daily, most of it irrelevant to whatever the request actually needed. A week of traces showed the damage wasn't spread evenly: misroutes clustered in three confusable pairs — get_customer/get_account, search_tickets/search_knowledge, send_notification/create_alert — at an 11% error rate, against under 2% everywhere else.

The fix isn't better wording on those six tools. It's decomposition: a customer-lookup agent with 4 tools, a knowledge agent with 3, a notification agent with 3, and each request gets routed to exactly one of them. Tool surface per request drops from 22 to 3 or 4, saving about 3,300 tokens a call, and the confusable pairs end up living in different agents entirely — so the discrimination problem disappears instead of getting patched over. Tightening descriptions is still worth doing. Just do it after the decomposition, on whatever pairs are still confusable inside a single agent.

There's one case where the exam actually wants a tool added rather than removed: a scoped agent with a genuinely high-frequency cross-role need, where routing every single instance through a coordinator would be pure latency tax. A narrow, scoped exception is the right call there, with complex cases still routed through the coordinator. Strict scoping pushed past its useful point becomes its own failure.

Four answers that sound responsible and aren't

Tightening every tool's description is a genuine half-move: it improves discrimination, but it doesn't touch the token cost or the privilege surface. Adding a routing classifier in front of the agent sounds like proper architecture — a dedicated component with one job — but really it just adds a component, a failure mode, and a latency hop to compensate for a configuration problem a smaller tool set would already solve. Keeping every tool "for flexibility" makes the same mistake from the other direction: on a tool surface, flexibility is indistinguishable from ambiguity, and the cost lands on every request regardless of whether that flexibility ever gets used. And merging confusable tools into one general one — get_customer and get_account collapsing into lookup_entity — drops the count in a way that looks like progress. It isn't: the lost precision doesn't disappear, it just moves into parameter selection, where it's harder to catch.

2. Who is calling, and what may they do

Most people's mental model of security collapses two separate questions into one: who is calling, and what are they allowed to do. In conventional architecture, those stay two distinct ideas that travel together: identity gets established at the edge, carried down through every layer, and each layer enforces what that identity is allowed to reach. Agentic systems break that quietly. The agent itself runs as a service, and when it calls a tool, that tool is usually invoked with the agent's own credentials, not the user's. Every individual user collapses into one identity at the point where the data actually gets touched. That's the confused-deputy problem: a privileged component acting on behalf of a less-privileged caller, and the caller's own constraints get lost somewhere along the way.

Three gaps, in increasing severity

Take an HR assistant serving 4,000 employees — this is what that gap looks like once it's actually live. The document store behind it has three tiers: general policy open to everyone, manager guidance for about 400 people managers, and compensation planning documents for 12 HR business partners. The fast path to a working demo was one service account with read access across all three, and a post-retrieval step that drops any chunk the requesting user isn't entitled to see.

The shallow gap is a quality bug. If a compensation document is the strongest match for a manager's query, the filter drops it after ranking, and the user just gets whatever ranked fourth or fifth instead — with no indication why the answer feels weak. The second gap is structural: the filter is application code sitting in one path, and any other path that reaches the index — a debugging endpoint, a batch job, a feature someone writes next quarter without knowing the filter exists — has no authorization at all. The third is the one people miss entirely: traces and logs capture retrieved context before filtering happens, so the observability system ends up holding compensation data under access controls that were never built for it.

The fix pushes authorization down to the query itself. The user's identity propagates from the edge all the way to the retrieval layer, and the vector search runs with an entitlement filter built into the query — so a document outside the caller's line of business is never a candidate, never ranked, never retrieved, and never written to a trace. Where the store genuinely can't filter at query time, the fallback is separate indexes per entitlement tier: more infrastructure, but the right trade against leaving enforcement sitting in application code.

The reflex worth having cold

Least privilege means the capability doesn't exist — not that someone's watching it. Logging a privileged action, requiring a confirmation step, restricting it to business hours: these are real controls, and all three are the wrong answer when a scenario tells you a capability isn't needed. They're what you deploy when a privilege is genuinely required and you're managing its risk — not what you deploy instead of removing something that shouldn't be there in the first place. Watch the scenario prose: if it says the agent doesn't need the capability, the answer removes it.

Why the compensating controls still tempt

A confirmation step makes sense for something needed but consequential; it's the wrong answer for something not needed at all, and it taxes every legitimate use to guard against a use that shouldn't exist. A business-hours restriction narrows a window, not a privilege — which produces the odd result that the thing you didn't want is perfectly fine at 2pm. And a rule written into the system prompt is probabilistic by nature: a security control that fails 1% of the time across 40,000 daily requests fails 400 times a day, and that isn't a security control at all. When the scenario also names a regulated sector or an audit requirement, the answer that satisfies the auditor is the same one: enforcement provable at the point of access, not just asserted in application logic.

3. Turning a trade-off into arithmetic

Nearly every mechanism that buys you accuracy spends latency to do it: a bigger model, more retrieved chunks, a reranking pass, a self-critique step. Each one has a real accuracy story and a measurable cost, and what's actually being tested isn't whether you know the trade-off exists — everyone knows that — it's whether you can turn the argument into numbers. "We should use the faster model" is an opinion. "Our p95 budget is 3,000 milliseconds, generation already spends 1,900 of it, and the reranking pass on the table costs 300 for a 4-point recall gain, leaving 260 of slack" is a decision you can defend to a stakeholder and revisit when the SLA changes.

Two disciplines keep that arithmetic honest. Budget against the tail your SLA actually names — p95 or p99 — because that's where your users experience the system, not the mean a dashboard shows you by default. And separate total latency from perceived latency: streaming moves time-to-first-token dramatically for an interactive chat surface, and does nothing at all for a downstream service that waits for the complete response before it acts. The exam tells you which consumer you have right there in the scenario prose, and it's easy to read straight past it.

A budget with real numbers

A document-triage assistant with a contractual p95 of 3,000ms:

Stagep95 (ms)

That leaves 200ms of slack, with quality sitting at 91% against a business target of 95%. Three proposals show up. A self-critique pass costs about 1,400ms for a 3-point gain, which pushes the total to 4,200 — 40% over budget. A higher-capability model pushes generation from 1,900 to 2,600, for a total of 3,500 — still over. Retrieving top-50 instead of top-20 and reranking harder costs 90ms in search and 210 in rerank, for a total of 3,100 — marginally over, for a 1.5-point gain. All three genuinely improve accuracy. All three blow the SLA. The trap is treating this as "which accuracy gain is worth the overage," when the real move is finding latency you're already wasting.

Here's the latency actually being wasted: the static system preamble runs 3,100 tokens, identical on every single request, and currently sits after the retrieved chunks instead of before them. Move it to the front and turn on prompt caching, and you cut both time-to-first-token and per-request cost — and the budget that frees up is exactly enough to fund the higher-capability model inside the original SLA, with a real accuracy gain attached. Whenever a scenario names latency and cost together alongside a large, unchanging block of content, look for that reorder-and-cache move before reaching for anything more expensive.

The distractor shapes here

Optimizing the mean when the SLA names the tail can look like progress on a dashboard while the actual complaint goes untouched. Treating streaming as a fix for a consumer that isn't interactive changes nothing about total time. Buying more accuracy than the scenario asked for looks thorough. It's actually a cost nobody priced in. Cutting retrieved context to hit a budget pulls out a working mechanism instead of tuning it, and usually costs you more accuracy than the time it saves elsewhere. And caching the model's output is a different mechanism from caching a stable input prefix — an answer that conflates the two has the wrong idea about how the saving actually happens.

4. Watching a system that doesn't explain itself

In a deterministic service, a failure and its cause usually sit close together: a stack trace, a status code, a query plan. In an agentic system, the final output is just the last thing in a whole chain of decisions, and it rarely explains itself. A confidently wrong answer looks identical to a confidently right one once all you're looking at is the response. That's why the unit of observability here is the trace, not the log line: which tools got called, with what arguments and what results, what context got retrieved down to the chunk IDs and document versions, where the model chose between branches or a guardrail fired — all tied together by one correlation ID from the original request.

The objective's own wording — "at scale" — changes the design in three concrete ways. Volume: full-fidelity traces are large, and at 200,000 requests a day and roughly 30KB per trace, that's about 6GB a day, or 2.2TB a year, sitting in a store you actually have to query. Cardinality: a metric labeled with a user ID or session ID explodes the label space and makes the metrics backend slow and expensive, so high-cardinality detail belongs in traces, queried on demand, while metrics stay on low-cardinality dimensions like tool name, model, tenant tier, outcome class. And sensitivity: a trace holds prompts, retrieved documents, and tool payloads — a second copy of your most sensitive data, usually sitting behind access controls that were designed for engineers debugging outages, not for the data itself. It's the same discipline Domain 4 applies to production logs of eval samples; here it's the trace store that inherits the obligation.

Why the answer is stratified, not uniform

Take a claims assistant running at that same 200,000 requests a day — it shows you why. Full capture gives you the 6GB-a-day, indefinite-retention problem above. Uniform sampling at 1% drops that to 60MB a day, but it only catches about 20 of the day's 2,000 escalations — nowhere near enough to characterize what's actually failing. Here's what the stratified version looks like instead:

Stratified capture policy
StratumSample rateRationale
Requests ending in error or exception100%Rare and maximally informative
Requests escalated to a human100%The system's own admission of difficulty
Requests below confidence threshold100%Leading indicator of quality drift
Requests touching regulated claim data100% metadata, redacted payloadAudit needs the fact of access, not the content
Successful routine requests2%Enough for baseline distributions

That lands you around 5 to 7% of requests fully traced, roughly 350MB a day, with every high-information event captured and retention set per stratum instead of one blanket policy. Underneath that, low-cardinality metrics run on 100% of traffic: latency percentiles, tool-call counts by tool name, retrieval hit rate, escalation rate, guardrail-trigger rate, cost per request. Alerting sits on those metrics, not on the traces, and instrumenting per stage rather than only end-to-end is what turns "the system got slow" into "the reranker got slow."

Two wrong turns keep recurring here. Logging inputs and final outputs at 100% feels complete, and it's what most API gateways hand you for free — but it's the highest-volume, lowest-information capture you can choose. It tells you what happened and nothing about why. Sampling uniformly at a low rate is genuinely the right textbook answer for high-volume, homogeneous traffic, which is exactly why it's tempting here, and exactly why it's wrong: it's calibrated to the common case, and the common case isn't what you're hunting for.

5. What a chunk actually is

Model weights hold general knowledge. Your organization's specifics live somewhere else entirely — they change on their own schedule and carry their own access rules. RAG is the pipeline that pulls those specifics into context at request time, and it has five stages where things can go wrong: ingestion, chunking, embedding, indexing, retrieval. Diagnosing a RAG failure really just means figuring out which of the five.

Take a sentence like "this limit does not apply to renewals," lifted out of the middle of a long policy document with no heading above it. On its own, it means nothing — and that's exactly the failure chunking is supposed to prevent. A chunk is the smallest span of a document that still makes sense read completely out of context. That rules out fixed-size splitting as any kind of default: a flat 512-token window just cuts wherever 512 tokens happens to land — mid-clause, mid-table, mid-function. What it points to instead is document structure: clause boundaries in a policy manual, endpoint boundaries in an API reference, ticket boundaries in a support archive. The structure a human author already imposed is a map of where the real seams are.

Two refinements make that work in practice. A small overlap — 10 to 15% — is insurance against a key sentence straddling a boundary, not a strategy in its own right. And contextualization, prepending the document title and heading path to the chunk text before it gets embedded, matters more than it looks: putting the heading path into the text itself, not just the metadata, is what would have saved that renewals sentence. It puts the context into the vector itself, where retrieval can actually use it. It's one of the highest-return, least glamorous changes you can make in a RAG pipeline.

Indexing is where the exam's own sample question lives. An index is one coupled unit made of three things: the chunking scheme, the embedding model, and the vector store. Change any one of them without the others, and the space becomes inconsistent — vectors from a different embedding model land in a different geometry, and similarity scores between them stop meaning anything, even though you can still compute them. The system doesn't error. It just returns confident nonsense.

Worked case — the refresh incident

Six weeks after launch, a nightly reload of the policy manuals runs. The next morning, the assistant is confidently citing clause numbers that don't match the text it quotes. A RAG system that starts returning confident, wrong answers immediately after a document refresh is a retrieval and indexing problem — not the model, not the prompt, not the temperature. The timing tells you everything you need to know.

Run the investigation in a fixed order. First: did the re-index actually complete? Compare chunk count against the expected count from source — a 30% shortfall means a partial run. Second: did the chunking configuration change alongside the refresh? Third: did the embedding model version move? Compare what's recorded in the index against what's actually running at query time — this is the classic silent killer, because nothing errors when it happens. Fourth: did deleted or superseded documents actually leave the index, or are they still ranking as stale vectors? Only after checking all four do you go look at the prompt or the model.

In this case, the cause was the embedding version drifting because the ingestion job pulled a floating version tag. The fix pins the version to the index and re-embeds the corpus. The prevention is a validation gate after every re-index: a fixed set of golden queries with known-correct chunk IDs, blocking promotion if the hit rate drops.

Two tempting wrong answers show up right here. Lowering the temperature to stop confidently-wrong answers sounds right, because "confidently wrong" sounds like a sampling problem — but temperature governs how the model picks tokens, and has nothing to say about which documents got retrieved. Swapping in a more capable model makes the same mistake: a better model reading the wrong document just produces a more articulate wrong answer. And increasing chunk size to give the model more context looks like it addresses the complaint directly, but a larger chunk dilutes the embedding across more topics and lowers precision. Contextualization solves the actual context problem without that dilution.

6. RAG is not a synonym for vector search

"RAG" and "vector database" have collapsed into the same idea in casual usage, and that's the source of most retrieval mistakes on this exam. Retrieval strategy is really a choice on two independent axes: what shape the data actually is — prose, structured records, code, tables, entities with relationships, time series — and what the query is actually asking the system to do — look up an identifier, find something semantically similar, filter by attribute, aggregate across records, traverse a relationship. The available mechanisms line up against those two axes unevenly:

Retrieval mechanisms by strength
MechanismStrong atWeak at
Dense / vectorParaphrase, conceptual similarityExact tokens: part numbers, error codes, rare terms
Lexical / BM25Exact terms, identifiers, rare vocabularyParaphrase, queries sharing no vocabulary with the answer
Hybrid (fused)Corpora and queries mixing both formsCost and complexity when only one form is present
Metadata filter + semanticScoping to jurisdiction, tenant, date, entitlementLittle; usually additive and underused
Structured query (SQL)Aggregation, counting, joins, exact numericsAnything needing semantic understanding of prose
Graph traversalMulti-hop relationship questionsEverything else; expensive to build and maintain

The dense-retrieval weakness is worth slowing down on, because it's counterintuitive and it's heavily tested. Embedding models compress meaning, and a code like ERR_5521 carries almost no distributional meaning: it's rare, it appears in very few contexts, and its vector sits closer to other rare token sequences than to the document that actually explains it — while every article about upgrade errors clusters tightly around the same topic. Ask "why does ERR_5521 happen after upgrade" against a vector index, and you get five thematically perfect articles back, none of which even mention ERR_5521. Lexical search returns the one that does. Hybrid retrieval earns its place exactly when a corpus mixes natural-language explanation with exact identifiers, and users query in both forms — common in support, legal, medical, and engineering content. It isn't universal, though: bolting hybrid onto a corpus of pure narrative prose, queried in plain language, buys you a second index and a fusion step for nothing.

Two more moves belong in the same toolkit. Filtering before ranking — applying a metadata constraint as part of the query itself, so semantic ranking only runs across the eligible set — is both a precision gain and, tying back to Objective 2, a correctness requirement wherever entitlement is involved. And retrieving wide before reranking narrow: pulling the top 20 to 50 candidates before reranking down to 3 to 5 buys you most of the precision of an expensive search at most of the speed of a cheap one, at the cost of a latency stage that has to fit inside whatever budget Objective 3 set.

One router, six query shapes

A field-service assistant over three sources, troubleshooting articles in prose with codes inline, a 45,000-row parts catalog, an equipment hierarchy with supersession relationships, shows the router this implies:

The measured payoff on that last row alone justifies the added complexity to a stakeholder in a way "hybrid is best practice" never will: dense-only retrieval hit that query type 34% of the time; hybrid fusion hit it 89%. The wrong turns worth naming here: assuming RAG means vector search, which fails outright on identifiers, aggregations, and relationship queries; building a knowledge graph for what's actually a single-hop foreign-key lookup; and raising top-k until the right document shows up, which floods context and makes the lost-in-the-middle problem worse — when reranking gets you the same intent in a targeted way.

7. Who decides what happens next

There are three mechanisms for connecting an agent to something outside it, and the question that tells them apart is who decides what happens next. With a direct API or CLI call, your code decides. The sequence is known at design time, it runs whether or not a model is even involved, and the result is deterministic — which makes it the cheapest, fastest, most testable option, and also the most under-used one, because "let the agent decide" is a seductive default even when nothing actually needs deciding. With MCP, the model decides, inside a surface your server exposes: tools, which are actions the model can call; resources, which are read-only content it can consult; and prompts, reusable templates — all discovered at connection time. Its real value is standardization: prefer an existing community server for standard systems like issue trackers or source control, and save custom builds for workflows genuinely unique to your organization. With agent-to-agent, another agent decides. You're handing over a task, not requesting data, and the other side brings back its own context, tools, and judgment as a result rather than a payload — the right call when the work needs reasoning your own agent shouldn't be doing itself.

The cost climbs in that same order. A direct call is one round-trip. An MCP tool call is a model's decision to make the call, plus the round-trip, plus a result the model then has to interpret. Agent-to-agent is all of that plus an entire second inference loop. Each step up buys you flexibility and spends determinism. One distinction inside MCP is easy to blur: a resource is something the agent looks at without spending a tool call; a tool is something it does. Exposing a content catalog as a resource gives the agent a map without burning a model turn on an exploratory query — which matters directly for the next objective.

Five systems, three mechanisms

A claims-processing assistant shows all three mechanisms earning their place on one build. The claims database, where the claim ID is already known and there's no decision left for the model to make, gets a direct call in pre-processing — one round-trip, deterministic, and it removes an entire category of "the agent forgot to look up the claim" failures. The policy document store, where the agent genuinely has to decide whether and what to search, becomes an MCP tool paired with a resource exposing the catalog. The fraud scoring service is deterministic in and out, and has to run on every claim above a threshold, so it stays a direct API call from the orchestration layer rather than a tool — exposing it as a tool would let the model choose not to call it, which is exactly wrong for a control that must always fire. The issue tracker, a standard system widely integrated elsewhere, uses an existing community MCP server configured with per-user credential substitution — Objective 2's authorization logic showing up again, this time inside a protocol decision. And medical necessity review, which needs clinical reasoning the claims agent has no business holding, plus a determination attributable to the clinical function for audit, goes agent-to-agent: hand over the case, get back a determination with a rationale.

The wrong turns here all cluster around blurring that decision boundary. Exposing a deterministic, always-run step as a tool so the agent "can decide" introduces non-determinism where there wasn't any, and risks a mandatory step getting skipped. Building a custom MCP server for a standard integration means reimplementing something already maintained, and inheriting its upkeep forever. Reaching for agent-to-agent when a tool call would do pays for a full inference loop to perform what's actually just a function call. And pasting a catalog into the system prompt instead of exposing it as a resource bloats every request with content that goes stale the moment the catalog changes.

8. Loading everything versus loading a map

Monolithic context loads the whole surface up front — every tool definition, every schema, the full document catalog, all of it in the request. Progressive discovery loads a compact map instead, and fetches detail on demand. Three forces push you toward the second option as a surface grows. Token cost gets paid on every request regardless of use. Discrimination degrades with surface size — Objective 1's argument, applied to the whole context instead of just tool count. And long context has an attention gradient: content at the start and end of a long input gets attended to more reliably than content buried in the middle, so a monolithic surface guarantees most of itself ends up sitting in that penalized middle.

None of that makes progressive discovery free. It adds a round-trip — real latency on the requests that need it — and it introduces a genuine discovery failure mode: the agent can fail to find a capability that actually exists, just because the index entry didn't make it obvious. A monolithic surface at least guarantees visibility, which is why it's still the right answer when the surface is small and stable, when the latency budget can't absorb a round-trip and the surface fits anyway, or when the content is needed on literally every request. In that last case it belongs in the request, and since it's identical every time, it should be ordered first and served from a cached prefix — which is exactly where this objective meets Objective 3.

Where the two actually cross

Here are the source numbers: a 60-tool, 8-namespace agent costs 12,000 tokens loaded monolithically (60 × 200 tokens each), versus roughly 2,700 progressively (8 namespace entries at 150 tokens, plus one expansion averaging 7.5 tools). But that's one snapshot. The relationship underneath it holds for any surface size and any namespace granularity — and that's what the widget below actually computes live, rather than just asserting it for a single example.

Try moving the granularity buttons and watch what happens to the crossover point, not just to the two costs. Tighter namespaces cross over sooner, because each expansion pulls in less waste. Broader namespaces need more tools before progressive pays for itself, because a single expansion drags in more tools the request never actually wanted. Namespace design is itself a lever you can pull — not just tool count.

The exam tests this objective in both directions, and the direction people drill less is the one where a small, stable surface with a tight latency budget gets a discovery mechanism proposed anyway — correctly rejected, because below the crossover the round-trip costs more than the tokens it would save. Watch also for content that's identical on every request being framed as a discovery problem when it's actually a caching answer, and for a "list everything" discovery tool the agent has to remember to call first — a half-move that provides the map but makes reaching it probabilistic, when content the agent can simply read is the stronger form.

The better real-world answer is rarely either pure strategy on its own. When trace analysis on the 60-tool agent showed six tools accounting for 61% of all calls, promoting those six into the base surface brought the base to 2,400 tokens, and meant 61% of requests needed no expansion at all — cheaper in both tokens and latency than either pure version, and justified by measured call distribution instead of picked in the abstract.

9. One system, all eight objectives

Let's put all eight objectives to work at once. A regional insurer is building a claims assistant for 900 adjusters, 180,000 requests a day, a contractual p95 of 3,000ms, and a seven-year audit requirement on protected claim data — and it shows why the eight objectives don't resolve independently.

Protocol choices set the shape first. The claim record comes in through a direct API call in pre-processing. The policy store is an MCP tool with a companion resource carrying its catalog. The fraud scorer is a direct API call from the orchestration layer — never a tool. Escalations go through an existing community MCP server for the issue tracker. Medical necessity review is agent-to-agent.

The first version of the adjuster agent carried all 19 available tools, and showed an 8% misroute rate concentrated in three near-duplicate pairs. So it gets split into three role-scoped agents of 4 to 6 tools each, with one deliberate exception: the claims agent keeps a read-only policy-status check, because it's needed on nearly every turn and the coordinator round-trip was the dominant latency cost. Across those three agents the total surface is 34 tools, restructured as five namespaces, with the seven tools covering 64% of calls promoted into the base — about 2,600 tokens against 6,800 monolithic. The adjuster's identity propagates all the way from the edge to the data layer: the policy store's retrieval query carries an entitlement filter, the issue tracker uses per-user credential substitution, and a review turns up an unused update_claim_status tool that gets removed outright, rather than logged, confirmed, or time-boxed.

The knowledge layer follows the same discipline. Policy manuals are chunked on clause boundaries with the heading path prepended, the embedding model version is pinned to the index, and every re-index runs 40 golden queries before promotion. The claims-history table is never embedded — it's queried directly. Retrieval over the policy corpus runs hybrid, filtered by metadata before ranking, retrieved at the top 30 and reranked to the top 4, while claims-history questions route straight to SQL. On the latency side, the stage budget lands at 2,750ms against the 3,000ms SLA, with the 250ms of slack there because a 3,400-token static preamble was moved to the front of the request and cached — funding the reranking stage that wouldn't otherwise have fit. Observability closes the loop: one correlation ID from the edge through every downstream call, stratified capture at 100% for errors, escalations, low-confidence paths, and clinical handoffs, 2% for routine successes, with metrics on stage-level latency, retrieval hit rate, and mean retrieval score running across all traffic. That's the same pair of metrics that would have caught Objective 5's embedding-version drift within the hour it happened, instead of the following morning.

The interlock is the point

None of those eight decisions sits in isolation. The caching decision funds the reranking stage. The entitlement filter is implemented inside the retrieval query, and it constrains what the observability pipeline is even allowed to store. The tool split changes the exact surface the discovery layer has to cover. A scenario built to test one objective almost always has a second one wired in underneath it, and an answer that only fixes the first one leaves the exam question half-solved.

Common misconceptions

The mythLeast privilege means monitoring what the agent does with its permissions.
Why it's temptingLogging and confirmation are real, unambiguous security practices that show up in every checklist, so keeping the capability and instrumenting it feels responsible.
The realityLeast privilege means the permission doesn't exist. Logging, confirming, and time-boxing are controls for privileges you've decided to keep — not substitutes for removing one that was never needed.
The one testDoes the scenario say the agent doesn't need this capability? If yes, the answer removes it — logging or confirming it is the designated wrong answer.
The mythRAG means searching a vector database.
Why it's temptingVector search is the default in most tooling and the first thing most tutorials show, so it's the mental model that sticks.
The realityVector search is one mechanism among several. Exact identifiers want lexical search, aggregation wants SQL, multi-hop relationships want graph traversal — matching mechanism to query shape is the actual skill.
The one testDoes the query need an exact code, a count, or a relationship traversal? If so, a vector index was never going to answer it, however it's tuned.
The mythA RAG system giving confident wrong answers needs a better model or a lower temperature.
Why it's tempting"Confidently wrong" sounds like a sampling or capability problem, and both are one-line changes with no pipeline work required.
The realityTemperature governs token selection, not which documents were retrieved. When the degradation lines up with a document refresh or re-index, the fault is in retrieval and indexing — a better model just reads the same wrong passage more articulately.
The one testDid the failure start right after a refresh, re-index, or ingestion change? If the timing lines up, check retrieval against known-good passages before touching the model.
Four distractor shapes worth checking every option against

ARCHITECTED is the option that sounds most like proper engineering — a routing classifier, a validation layer, a second retrieval hop — and it's wrong because it adds a component to compensate for something a narrower configuration would already solve. OVERSPEC delivers more than the scenario asked for, at a cost nobody priced in. DISCARD removes a working mechanism instead of adjusting it — cutting retrieved context to hit a latency budget, rather than finding the latency actually being wasted elsewhere. HALF-MOVE looks like it addresses the problem — better tool descriptions, a discovery tool the agent must remember to call — and leaves the real decision space or privilege surface untouched. Check every option in this domain against those four before you check whether it merely sounds correct.
