1. Configuring tools and environments

By the end of this section you will answer "where should this rule live?" with two questions, and you will know which mechanism survives a clone.

Start from what a language model actually is at the moment of a request. It is a function from a body of text to a body of text.

It has no memory of yesterday, no awareness of your repository's history, and no opinion about your team's conventions except the one you put in front of it.

Every constraint you want it to honour has to arrive as tokens in that request.

That single fact produces the whole configuration problem. Type the convention into the chat each morning and it is in the request for that session and gone by Tuesday. Put it in a file the tool loads automatically and it is in every request for as long as the file exists. Put it in a file on your own machine and it is in every request you make and none that your teammates make.

So configuration is the mechanism for turning a rule someone knows into a rule that is present whether or not anyone remembers it. Carry that definition into the exam, because it explains every answer in this objective.

When you are asked which mechanism to use, you are being asked: which mechanism puts this content in front of the model, at the right moment, for the right people, without depending on anyone's memory?

The layers

Claude Code discovers instruction files at several levels and concatenates them into context, loading from the root down to the working directory.

This is the point people get backwards, and it decides items. It is a concatenated load order, not an override precedence.

Alongside the instruction layers sit two invocation layers. Skills live at .claude/skills/<name>/SKILL.md and are invoked on demand rather than loaded into every session. Custom slash commands live at .claude/commands/ for the project or ~/.claude/commands/ for one person, with the text typed after the command arriving as $ARGUMENTS.

In current Claude Code the two are unified. .claude/commands/ is legacy but supported, and both produce a /name command.

Skill frontmatter

This is where the exam likes to live, because it is where a behaviour gets scoped.

KeyWhat it does

allowed-toolsScopes which tools the skill may use
A source caveat worth carrying, not smoothing over

allowed-tools has a documented double framing. The Foundations exam guide framed it as restricting tool access during skill execution. Current product documentation frames it as a list of tools the skill may use without prompting the user, which is a permission pre-grant where unlisted tools follow the normal permission flow rather than being hard-blocked.

Both framings agree on the judgement the exam tests: allowed-tools in frontmatter is where you scope what a skill may do. In production, scope it minimally, because the mechanism is a pre-grant.

Precedence between personal and project skills runs the other way from the instruction files. A personal skill overrides a project skill of the same name.

So an engineer who wants their own /commit behaviour creates ~/.claude/skills/commit/SKILL.md. Same name, personal override, team unaffected. Creating ~/.claude/skills/my-commit/ instead produces a second command with an unfamiliar name and leaves the shared one still firing.

One more mechanism keeps instruction files navigable. A CLAUDE.md can reference another file with @path, the @ immediately before the path with no space, relative and absolute both supported, and a relative path resolving against the file that contains the import rather than the working directory.

A number you must not answer on

The maximum @import nesting depth is contested between the Foundations study material and current product documentation. Treat it as unsafe and never build an answer on it. The syntax and the resolution rule are stable, and they are what a sensible question would test.

What belongs in committed project context

The recurring failure on real codebases is not repository size, language, or contributor count. It is the absence of committed context describing conventions and structure.

A model handed a 400,000-line monorepo with a good CLAUDE.md produces better work than one handed a 40,000-line service with none. The constraint that binds is not how much code exists but how much of the code's implicit knowledge is written down anywhere the tool can reach.

Belongs there. Architectural shape and where things live. Naming and module conventions a reader could not infer from any single file. The testing framework, fixture conventions, and what "done" means. Build and run commands that are not obvious. Constraints existing for reasons nobody documented: the library you must not use, the directory that is generated, the API surface that is public and versioned.

Does not. Anything the model can read from the code faster than you can describe it. Anything one engineer prefers and the team has not agreed. Secrets and customer data. And workflow procedures needed only occasionally, which become skills invoked on demand rather than tokens paid for in every session.

That last split is a real cost decision and the Professional-tier version of this question. Project instruction files load in every session, so a 500-line file is 500 lines of tokens on every request every engineer makes, all day.

The standard answer to a CLAUDE.md grown to 400 or 500 lines: keep universal standards in CLAUDE.md, move workflow-specific guidance into skills with trigger keywords, and move file-type-scoped conventions into .claude/rules/ where globs load them only when relevant.

Moving everything to skills is the wrong end of the same axis. Universal standards would then need explicit invocation every time, which is exactly the memory dependency configuration exists to remove.

Worked example: the fourth developer

A platform team of four has used Claude Code for six months. Three engineers consistently get generated code with comprehensive error handling. The fourth, who joined three weeks ago, consistently does not.

All four work in the same repository, on the same branch, with the same version of the tool. The new engineer's pull requests come back with the same review comment every time, and they have started manually adding error handling after generation, which is slower than writing it themselves.

Push it further, because the exam will. The architect's answer adds two more things beyond the fix and the cleanup.

Cost. Every convention added to the always-loaded file is paid for on every request by every engineer. Error handling is universal and earns its place. A twelve-step release checklist does not.

How you explain it to a delivery manager who asks why the new joiner is slower. Not "their configuration is wrong." Rather: the team's coding standards were living on individual laptops instead of in the repository, so a new joiner inherited none of them, and the fix moves the standards into the repository where onboarding already picks them up. That framing gets funded. The first one gets a shrug.

How the exam probes it

The distractors are almost never absurd. They are usually the right idea placed at the wrong layer, or the right layer addressed by the wrong mechanism.

"Why does this behaviour differ between engineers?" Nearly always a scope mismatch. User-level configuration is the usual culprit because it is invisible in code review.

"Where should this rule live?" Two questions in order. Who needs it, one person or the team, which picks user against project. When is it needed, always or on certain file types or on demand, which picks CLAUDE.md against .claude/rules/ against a skill.

"How do we make this available to everyone who clones the repo?" The word clones is doing the work. Anything in .claude/ inside the repository travels with a clone. Anything in ~/.claude/ does not.

Checkpoint 1 · before you read on

A team's CLAUDE.md has reached 480 lines. It mixes coding standards, a PR checklist, and a deploy runbook. An engineer proposes moving all of it into skills so nothing loads unless invoked.

What is right about that, what is wrong, and what is the actual split?

Answer first, then open
Right that it should be split. Wrong about which end of the axis.

What is right: 480 lines is 480 lines of tokens on every request by every engineer all day, and a deploy runbook does not earn that. Occasional procedures genuinely belong in skills.

What is wrong: moving everything means universal coding standards now need explicit invocation every time, which reintroduces exactly the memory dependency configuration exists to remove. You would be back to output quality depending on who remembered.

The split: universal standards stay in CLAUDE.md. Workflow-specific guidance becomes skills with trigger keywords. File-type-scoped conventions move to .claude/rules/ with globs, so they load only when relevant.

The axis is when it is needed, and the cost is tokens per session.

The wrong turns

Answering with a document. A wiki page is genuinely useful to humans and has no effect on generated output, because the model never reads it. Any option whose mechanism is "write it down somewhere people can find it" is answering a different question.

Answering with a training session. Same defect, wrapped in more effort. Half-life about a fortnight, and it does not reach anyone hired afterwards.

Answering with a recorded walkthrough. The version that catches careful people, because a recording feels durable. It is durable and frozen, and it teaches the old configuration confidently the day after the configuration changes.

Adding a subdirectory file to override a project one. This assumes an override precedence the concatenation model does not provide. Both load, and if they conflict you have given the model two contradictory instructions and a coin.

Reaching for the strongest available mechanism. Right when a rule must hold every time regardless of any prompt. Wrong for a style preference, where you have converted a suggestion into a hard failure and someone now has to merge a config change to format a file.

2. Improving developer workflows

By the end of this section you will know which of four refinement techniques a symptom calls for, and why measuring adoption is not measuring value.

The naive model of AI-assisted development is substitution. The engineer used to write the function, now the model writes it, and the saving is the time it took to write.

That model predicts a modest, bounded gain, and it is roughly what teams get when they adopt the tool without changing anything else.

The gains that justify the spend come from somewhere else. They come from changing where in the process work happens.

Requirements move earlier. In the interview pattern, instead of generating from an underspecified brief and iterating on wrong output, you have the model interview you first.

A caching layer prompts questions about invalidation strategy, tolerance for stale reads when the cache is unavailable, per-user against global scoping, and expected data volume. Those are exactly the questions whose answers you otherwise discover by shipping the wrong thing three times.

The value is not typing speed. It is that a requirements gap surfaces before code exists rather than after.

Verification moves earlier. Write the test suite first, then iterate by feeding failures back. Tests are a machine-checkable definition of done; prose acceptance criteria are not, and prose descriptions of an edge case get interpreted differently on each pass.

A migration script mishandling nulls is fixed fastest by supplying a sample input row containing nulls and the exact expected output, then iterating until it passes. Describing the bug more emphatically produces partial fixes and a longer meeting.

Review moves outward. A session that generated code is less effective at reviewing that code, because it carries its own reasoning context and is less likely to challenge decisions it just made. Run review in an independent instance.

Four refinement techniques

Hold them as a set, because exam scenarios usually describe a failure that one of them fixes and three of them do not.

The interview pattern, for underspecified tasks and unfamiliar domains. Diagnostic: each generated version misses a different requirement. That means the brief is incomplete rather than the model weak, and no amount of iterating on output completes a brief.

Test-driven iteration, for tasks with a checkable definition of correctness. Diagnostic: you can state what right looks like as an assertion.

Two or three concrete input/output examples, for transformations described in prose and interpreted inconsistently. Diagnostic: output shape varies run to run while the instruction stays the same. Lengthening the prose with more adjectives leaves it ambiguous, only longer.

Batching feedback correctly, which has two directions, and the exam tests the less obvious one.

When issues interact, put them in a single detailed message, because fixing them separately lets the second fix contradict the first. When issues are independent, iterate one at a time so each change stays easy to verify.

A review that found a locking bug, a retry bug whose behaviour depends on the locking design, and an unrelated typo should send locking and retry together. "Always report one issue per message so it can focus" is a reasonable-sounding generalisation that is wrong precisely where it matters.

Putting the tool in the pipeline

Interactive use helps individuals. Pipeline use is where a workflow change becomes a team property, because it happens whether or not anyone chooses it.

For non-interactive execution, claude -p "<prompt>" (equivalently --print) processes the prompt, prints to stdout, and exits. Without it the tool waits for interactive input and the pipeline hangs until it times out.

Three specific distractors do not exist or do not apply: a --batch flag, a CLAUDE_HEADLESS=true environment variable, and redirecting stdin from /dev/null, the last being a Unix workaround rather than the documented mechanism.

When output is consumed by another program rather than read by a person, ask for it structurally. --output-format json forces JSON and --json-schema enforces a schema so downstream parsing is safe.

Adding an "Output Format" section to the instruction file is not equivalent, and neither is asking for JSON in the prompt. Both produce output that is usually right, and usually right is a parse error in production.

Two pipeline behaviours are the difference between a review bot people trust and one they mute.

Re-runs must carry prior findings. Feed the previous run's findings into the prompt and instruct it to report only new or still-unaddressed issues. A blank-slate re-run re-litigates settled findings and floods the pull request with near-duplicate comments in slightly different wording every time the author pushes.

The blank-slate instinct is usually defended as objectivity. It produces noise, and noise gets the bot turned off.

Give the CI-invoked instance project context. The instruction file is the mechanism for handing it testing standards, fixture conventions and review criteria. For test generation specifically, putting the existing test files in context prevents it proposing scenarios the suite already covers.

Scheduling is a cost decision with a clear discriminator: is anyone waiting? Blocking pre-merge checks are synchronous. Overnight reports and weekly audits fit the Message Batches API, which halves cost against a window of up to 24 hours with no latency SLA, matching outputs to inputs via a custom_id per request.

One hard limitation decides several exam questions. Batch cannot execute a tool mid-request and return the result to the model. Any analysis needing to fetch related files partway through cannot use batch, regardless of how flexible its deadline is.

Measuring whether it was worth it

The wrong measurement is activity. Invocations per week, seats onboarded, hours in the tool, lines of generated code accepted. These all move when adoption moves, which makes them satisfying and makes them useless.

They tell you the tool is being used. Nobody asked whether the tool is being used. They asked whether the delivery outcomes improved.

So measure the outcome the tool was adopted to improve. Cycle time from first commit to merge. Defects found in production per release. Time from review requested to review completed. Time from a new engineer's start date to their first merged non-trivial change.

Three disciplines make those numbers survive a sceptical executive. Name the metric before adoption, because a metric selected after the fact is selected because it moved and everyone in the room knows it. Establish a baseline. And state the confound yourself, which is the difference between a credible measurement and a sales pitch.

There is one legitimate use for activity data: as a leading indicator during rollout, to tell you whether the thing you are about to measure is even being used yet. Low adoption explains a flat outcome metric. It does not substitute for one.

Worked example: the review bot nobody trusts

A 40-engineer organisation runs an automated first-pass review on every pull request. Six weeks in, the numbers look healthy: the job runs on every PR, posts a median of nine comments, and has never failed. Engineers have quietly agreed to ignore it.

Pull the complaints apart and there are three, each with a different mechanism.

It repeats itself. Every push produces a fresh batch including reworded ones from the previous run. Fix: feed prior findings into the re-run prompt.

It flags things that are conventions here. It objects to the repository pattern in the data layer, which is deliberate and documented nowhere the tool can see. Fix: put review criteria and architectural conventions in the project instruction file.

Its comments land as one wall of prose per PR. Fix: --output-format json with --json-schema, so each finding carries a file path, a line number and a severity the GitHub API can place inline.

None of those three is a prompt-quality problem, and the instinct to rewrite the prompt would have fixed none of them.

Checkpoint 2 · before you read on

A nightly job produces a tech-debt report. Someone proposes moving it to the Batches API for the 50% saving. The job works by reading a changed file, then following its imports to fetch related files, then analysing the set together.

Can it move? Say what decides it.

Answer first, then open
No, and the deadline is irrelevant to why.

The job fetches related files partway through, based on what the first read revealed. That is a tool call mid-request whose result has to return to the model, and batch cannot do it.

Why the tempting reasoning fails: every scheduling signal points to batch. Nightly, nobody blocked, no latency SLA, 50% cheaper. All true, and all irrelevant, because the limitation is a capability boundary rather than a timing preference.

What would make it eligible: resolving the full file set before the request, in the job's own code, and sending one complete prompt. That is a real redesign and it may well be worth doing, but it is a different job.

3. Debugging and operational resolution

By the end of this section you will stop bisecting and start identifying the layer, and you will check what is loaded before theorising about anything.

Conventional debugging rests on determinism. The same input produces the same output, so you bisect: halve the search space, observe, halve again. Ten steps and you have the line.

An agentic system breaks two assumptions in that method.

Output varies between runs on identical input, so a symptom that disappears is not evidence that a change fixed it.

And "the input" is not one thing. It is the assembled result of several layers, most of which nobody looked at: a system prompt, concatenated instruction files, possibly path-scoped rules, a tool schema, retrieved documents, prior turns, and the user's actual message.

When behaviour is wrong, the wrongness lives in exactly one of those layers, and the layer is rarely the one named in the bug report.

So the question is not "what line is wrong" but "which layer owns this symptom, and did the content I think is present actually arrive?"

The analogy

This is Domain 4's diagnosis order, applied to a developer tool. There the rule was data and retrieval first, then prompt and context, then model mismatch, because the fault sits in what feeds the model far more often than in the model itself. Same reflex here: check what reached the request before theorising about how it was interpreted.

Where it breaks In Domain 4 the layers are separate services you can query independently: you can hit the retriever, inspect the index, and read the passages it returned. Here several instruction layers concatenate into one opaque blob before the model sees it, so inspecting any single file tells you what that file says and not what the model received. That is why the ladder's first rung is a command rather than a hypothesis: /context shows what actually loaded, which no amount of reading the individual files will give you.

Two details on the middle rungs earn their own sentences.

On rung 3, /compact compresses context while preserving what it judges essential. That judgement is the risk: exact numeric values, dates and specific details are exactly the kind of detail a summary drops. Compacting mid-task, when the implementation phase still needs the discovery detail, is the classic wrong call. The right one is isolating verbose discovery in a subagent from the start so the main session never fills.

On rung 4, the guide's own sample material carries the governing principle. Least privilege means removing an unneeded capability, not logging its use or asking for confirmation. Logging tells you afterwards. Confirmation makes a human the rate limiter. Neither is least privilege.

Worked example: "it works on my machine"

An engineer reports that Claude Code applies the team's API error-envelope convention in some sessions and not others, on the same repository, within the same week. They have started prefixing prompts with the convention manually, in capitals, which works about four times in five.

Rung 1. Run /context in a session where the convention held and one where it did not, and compare.

Suppose the convention lives in a path-scoped rule with a glob for src/api/**/*.ts. Sessions started while working in the API directory load it. Sessions started at the repository root, or from a test file elsewhere, do not.

The behaviour is not intermittent. It is conditional, and the condition is the file path, exactly as configured.

That reframes the fix into a genuine design choice with no default answer. If the convention truly only applies to API handlers, the configuration is correct and the engineer's real problem is that they are editing API code from outside the directory. If it applies to any code constructing an error response anywhere, the glob is too narrow, or the rule belongs in the always-loaded project file.

Note what did not fix anything: capitalising the instruction. It worked four times in five, which is the worst possible outcome, because a workaround that mostly works suppresses the signal that would have led to the actual cause.

Checkpoint 3 · before you read on

A nightly test-generation job has run for two months. This week its output started duplicating scenarios the existing suite already covers, and one service's tests reference a fixture helper deleted in a refactor.

Name both faults. Then say what the Professional-tier answer adds beyond fixing them.

Answer first, then open
Two context faults, one layer apart. Neither is a model-quality regression.

The duplication. Test generation avoids re-proposing covered scenarios when the existing test files are in context. If the job's file-collection step changed, a path filter or a renamed directory or a glob that no longer matches, the model is generating against a suite it cannot see and will cheerfully re-invent it.

The stale fixture. Fixture conventions live in the project instruction file, which is how a CI-invoked instance gets project context. The refactor deleted the helper without updating that file, so the file now describes a codebase that no longer exists and is loaded with full authority every run.

What Professional tier adds: close the loop that let the instruction file drift for a week unnoticed, because the same drift recurs after the next refactor. Committed context is an asset that decays, and nothing warns you when it goes stale.

The temptation was to treat both as one quality regression and reach for a more capable model. It would have fixed neither.

4. The two documented gaps

Both of these returned 0% on the real Foundations paper. They are here because they are known-weak, not because they are hard. This section has two checkpoints for that reason.

The mechanism reflex

A behaviour governed by a configuration mechanism is corrected by adjusting that mechanism. Adding a prompt instruction beside it that asks for the same outcome is not a fix.

Why it is tempting. A prompt instruction is fast, reversible, requires no merge, and often appears to work on the first try. It reads as pragmatic, and every incentive in the moment points at it.

Why it fails. A prompt instruction is advisory input the model weighs against everything else in context. A configuration mechanism sets a condition.

When the two disagree, the mechanism is the thing that is actually true, and you have built a system whose behaviour depends on which of two contradictory inputs happens to dominate on a given run. You will then debug the model for a week.

The analogy

This is Domain 5's guardrail layering, in a developer tool. You already accept there that a rule in the system prompt is a strong default and a scoped permission is a boundary, and that anything which must never happen belongs in the second. CLAUDE.md prose is the default. allowed-tools and context: fork are the boundary. Same two layers, same rule about which one a "must" belongs in.

Where it breaks In Domain 5 the two layers are usually built by different people at different times, so a prompt instruction sitting where a permission belongs is visible as a design gap in review. Here both layers live in the same repository, often in adjacent files and sometimes in the same one, so a contradictory pair reads as a single coherent configuration. Nothing flags the conflict, which is why this failure needs a deliberate reflex rather than a code review.
Three shapes of the same error
SymptomThe prompt-instruction non-fixThe mechanism fix
A skill uses a tool it should not touchAdd "do not use the Bash tool" to the skill bodyScope allowed-tools in the skill's frontmatter
A skill's exploratory output crowds out the main taskAdd "be concise, summarise your findings"Set context: fork so it runs in an isolated context
A convention applies only to test files but bleeds elsewhereAdd "only apply this to tests" to the project fileMove it to .claude/rules/ with a glob for test paths

In every row the middle column asks the model to simulate a constraint the right column simply imposes. The middle column will work most of the time, which is what makes it dangerous.

The generalisation carries into every other domain. When one option adjusts the existing mechanism narrowly and another adds something beside it, prefer the narrow adjustment.

Selecting the mechanism

Two questions, asked in this order, resolve most of these items.

The rightmost cell on the second axis deserves care rather than a guess. The general property is what the exam tests: a mechanism running outside the model's discretion is what you reach for when a rule must hold unconditionally, and it is over-specification to reach for it when the rule is a preference.

Where a scenario names a specific enforcement mechanism, answer with the property, meaning unconditional enforcement with no model judgement involved, rather than from a half-remembered file schema.

Checkpoint 4 · the mechanism reflex

A skill that summarises a codebase keeps flooding the main conversation with exploratory output, and the original task drifts out of focus. A teammate adds "be concise and summarise only your findings" to the skill body. It helps, mostly.

What is the mechanism fix, and what does "it helps, mostly" actually tell you?

Answer first, then open
context: fork in the skill's frontmatter.

That runs the skill in an isolated subagent context so its output never enters the main conversation at all. The instruction asks the model to simulate not polluting the context. The frontmatter key makes pollution structurally impossible.

What "it helps, mostly" tells you is the important half. A fix that works most of the time on a non-deterministic system is not a partial fix, it is a suppressed signal. It removes the symptom often enough that nobody investigates, and the underlying condition is still there for the run where it matters.

This is the same shape as the engineer capitalising their prompt in section 3, which worked four times in five. Mostly-working workarounds are the most expensive kind, because they buy silence rather than correctness.

Plan mode versus direct execution

The discriminator is not task size and it is not difficulty. It is whether the approach is already determined.

If several valid approaches exist and choosing wrong means expensive rework, plan first. The tool explores, understands and designs, presenting a plan before executing, and it is confined to read-only operations while doing so.

If the scope is clear and the approach is defined, execute directly, because a planning round on a determined task is pure overhead.

One Professional-tier extension. Plan mode is not only a quality mechanism, it is a stakeholder mechanism.

A plan produced before execution is a reviewable artifact: something a tech lead can challenge, something a regulated-sector change process can attach to a ticket, something a non-engineer sponsor can be walked through. A large refactor arriving as a completed diff offers no such surface.

So if a scenario mentions review, approval or auditability alongside a multiple-approach task, plan mode is answering two requirements at once.

Checkpoint 5 · plan mode

Two tasks. (a) A 45-file library migration where the team has already agreed the target library, the mapping for every deprecated call, and the order of the phases. (b) A single-file change to add caching to one endpoint, where three caching approaches are viable and the choice affects two other services.

Which gets plan mode? Say what the sizes are doing to your instinct.

Answer first, then open
(b) gets plan mode. (a) executes directly.

(a) is large and the approach is fully determined: target library agreed, mapping agreed, phase order agreed. Nothing is left to decide, so a planning round produces a document restating decisions already made.

(b) is one file and three viable approaches, one of which affects two other services. That is the approach being the decision, and getting it wrong is expensive to unwind across service boundaries.

What the sizes are doing: pulling you toward "big task, plan it." That instinct is the misconception this objective is built on. Size correlates with undetermined approach often enough to feel like a rule and it is not the rule.

Note that (b) also mentions two other services, which hints at review and approval. When that appears alongside a multiple-approach task, plan mode is answering two requirements at once.

5. Enabling a team end to end

By the end of this section you will have a structure to reach for when a scenario asks you to roll a capability out to an organisation, and when a stakeholder asks what your plan is.

Establish the baseline before you change anything. Pick the delivery outcome the adoption is meant to improve and measure it now, while nobody has an interest in the number. Without this, every later claim is unfalsifiable, and unfalsifiable claims do not survive a budget review.

Write the codebase's implicit knowledge into committed context. Structure, conventions, testing and fixture standards, the constraints that exist for reasons nobody wrote down. This is the step that unblocks work on an existing codebase, and teams skip it because it looks like documentation rather than engineering.

Split configuration by scope and by strength. Universal standards in the project instruction file. File-scoped conventions in path-scoped rules with globs. Occasional procedures in skills, so they cost nothing when unused. Capability boundaries in tool scoping. Unconditional rules in deterministic enforcement. Version-control all of it, because the point is that it survives a clone and a personnel change.

Build an onboarding path a new engineer actually walks. Cloning the repository must be sufficient to inherit the team's configuration. That is the test. Whatever cannot be inherited by cloning has to be a step in a checklist someone owns, not a paragraph in a wiki someone wrote.

Change the process, not only the tooling. Requirements gathered by interview before generation. Tests written before implementation. Review run in an independent instance. Pipeline jobs that carry prior findings and emit schema-enforced structured output. These are the changes that produce a different number at the end.

Instrument for the debugging you will need. Somebody will report inconsistent behaviour in week three. The team needs to know to check what is loaded before theorising, and to reach for the mechanism rather than a louder prompt.

Re-measure the outcome, with the confounds named. Same metric, same baseline, honest account of what else changed. This is the artifact that gets the second year funded.

Own the decay. Committed context describes a codebase that keeps moving, and nothing in the system tells you when the description stopped being true. Whatever process updates the code has to have a step that updates the context.

Where this domain stops being about tooling

Enablement is not a project with an end date. It is a maintained asset, and an architect who hands over shared configuration without handing over the responsibility for keeping it true has handed over a liability with good initial conditions.

Where these reflexes show up again

The mechanism reflex meets Domains 3 and 5. "Remove the capability rather than instruct against it" is section 4's rule, Domain 3's authorization objective, and Domain 5's strongest guardrail layer. One reflex, three domains.

The diagnostic ladder meets Domain 4. Check what feeds the model before blaming the model. Same order, same economics, different tool.

Measuring outcomes meets Domain 6. Baseline before adoption, metric named before adoption, confound stated by you. That is Domain 6's discovery discipline arriving in a tooling context.

Common misconceptions

The mythA lower-level CLAUDE.md overrides the project-level one for that directory.
Why it's temptingOverride precedence is how almost every other configuration system works, from CSS to environment variables to gitignore.
The realityInstruction files concatenate from root to working directory. All discovered files contribute, and there is no documented override precedence between levels.
The one testIf two files disagree, does one win? No. The model sees both, so edit the files.
The mythIf the model does the wrong thing, tell it more firmly in the prompt.
Why it's temptingIt is fast, reversible, needs no merge, and it usually appears to work on the first try.
The realityA behaviour governed by a configuration mechanism is corrected at that mechanism. Prose beside it competes with it, and you will debug the model for a week.
The one testIs there a mechanism that already governs this? Then adjust it, do not argue with it.
The mythPlan mode is for big tasks, and you can switch to it if things get hard.
Why it's temptingSize correlates with undetermined approach often enough to feel like a rule, and starting fast feels pragmatic.
The realityPlan mode is for undetermined approaches. By the time it "gets hard," structural decisions are already sunk.
The one testIs the approach already decided? If yes, execute, however large. If no, plan, however small.
The mythAdoption is up and usage is high, so the investment is paying off.
Why it's temptingIt has numbers in it, the numbers are real, and they are the easiest numbers to collect.
The realityActivity metrics move with adoption, not with value. Measure the delivery outcome the tool was adopted to improve, against a baseline.
The one testIf usage doubled and delivery did not change, would this metric move? If yes, it is an activity metric.

Quick reference

Configuration scope. Project-level is version-controlled and reaches everyone who clones. User-level reaches one person, is invisible in review, and does not travel. Personal skills override project skills of the same name.

Configuration loading. Instruction files concatenate root to working directory and all contribute. .claude/rules/*.md load conditionally on glob match. Skills and commands load on invocation. @import uses @ immediately before the path, no space, relative paths resolving against the importing file. Import depth is contested between sources, so never answer on the number.

Skill frontmatter. description for the menu, argument-hint for expected arguments, context: fork for isolated execution, allowed-tools for scoping what it may do.

Mechanism selection. When is it needed: always, path-scoped, or on demand. How hard must it hold: guidance, tool scope, isolation, or deterministic enforcement. Does it need to survive a clone: then it lives in the repository. Does it need to be paid for every session: weigh always-loaded against on-demand.

Plan against direct. Undetermined approach with expensive rework means plan first, read-only exploration, plan presented before execution. Determined approach means direct. Never switch reactively once it gets hard. Plan output doubles as a reviewable artifact for approval and audit.

Refinement techniques. A different requirement missed each round means the interview pattern. Checkable correctness means tests first. An inconsistent transformation means two or three concrete input/output pairs. Interacting issues go in one message; independent issues go sequentially.

Pipeline. -p or --print for non-interactive. --output-format json plus --json-schema when a program parses the output. The project instruction file supplies CI context. Existing tests in context prevent duplicate test generation. Re-runs carry prior findings. Review runs in an instance separate from the one that generated the code.

Batch against synchronous. Someone waiting means synchronous. Overnight or nightly or weekly with nobody blocked means the Batches API: 50% cheaper, up to 24 hours, custom_id matches outputs to inputs, and no tool calls mid-request.

Debugging ladder. Loaded? Right layer? Context polluted or stale? Tooling wired and scoped? Retrieval? Only then prompt or model.

Measurement. Cycle time, defect escape, review latency, time to a new joiner's first merged change. Baseline before adoption, metric chosen before adoption, confounds stated. Invocations, seats and hours in the tool are rollout indicators, not evidence of value.

Exam posture. Roughly four or five items out of 63, and no per-domain floor, so study it once and thoroughly and put the marginal hour into Integration at 19%. Answer every multiple-response item as if a single missing selection zeroes it, and do not assume you know how the items are grouped.
