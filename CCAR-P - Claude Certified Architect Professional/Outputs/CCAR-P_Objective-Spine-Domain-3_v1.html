A claims assistant for 900 adjusters

A regional insurer is building it. 900 adjusters, 180,000 requests a day, a contractual p95 of 3,000ms, and a seven-year audit requirement on protected claim data. Eight objectives, and each decision constrains the next one.

3.1Split the surface before rewording it

Version one of the adjuster agent carried all 19 available tools and ran an 8% misroute rate, concentrated in three near-duplicate pairs. It gets split into three role-scoped agents of 4 to 6 tools each, with one deliberate exception: the claims agent keeps a read-only policy-status check, because it is needed on nearly every turn and the coordinator round-trip was the dominant latency cost.

A tool surface bills in two currencies: tokens on every request, and discrimination, which degrades faster than the tool count grows. Decomposition takes the confusable pair out of one decision. Tightening descriptions comes second.

The half-moveRewording six confusable tools leaves every definition in every request and leaves the pair in the same decision. Merging two into one relocates the ambiguity into a parameter, where a trace cannot show it.

3.2Carry the identity all the way down

The policy store's retrieval query carries an entitlement filter, so ineligible documents are never candidates, never ranked, never retrieved and never written to a trace. The issue tracker uses per-user credential substitution. And a review turns up an unused update_claim_status tool, which gets removed outright rather than logged, confirmed, or time-boxed.

Least privilege means the capability does not exist, not that it is watched. Push authorization into the retrieval query: a filter in application code ranks first and drops after, and every other path to the index has no authorization at all.

The tell in the proseIf the scenario says the agent does not need a capability, the answer removes it. Logging it, confirming it, and restricting it to business hours are the designated wrong answers, and all three keep it.

3.3Price the trade-off in stage-level numbers

The latency budget lands at 2,750ms against the 3,000ms SLA. Those 250ms of slack exist because a 3,400-token static preamble was moved to the front of the request and cached. That reorder is what funds the reranking stage, which would not otherwise have fit. Nothing was cut to make room for it.

Budget against the tail the SLA names, and convert the argument into stage-level numbers before comparing options. Every proposal that adds a stage crosses the line. The move that works touches a stage already being paid for.

Read the consumerStreaming moves time-to-first-token for an interactive surface and does nothing for a downstream service that waits for the complete response. The scenario names which one you have.

3.4Sample where the information is

One correlation ID runs from the edge through every downstream call. Stratified capture takes 100% for errors, escalations, low-confidence paths and clinical handoffs, and 2% for routine successes. Metrics on stage-level latency, retrieval hit rate and mean retrieval score run across all traffic. Those last two are the pair that would have caught the embedding-version drift within the hour instead of the following morning.

Stratified capture, not uniform sampling: the events worth having are the rare ones. High-cardinality detail belongs in traces queried on demand. Metrics stay on low-cardinality dimensions, and alerting sits on the metrics.

Why one percent failsA uniform 1% sample catches about 20 of a day's 2,000 escalations, which characterises nothing. Uniform sampling is calibrated to the common case, and the common case is not what you are hunting.

3.5Chunk on structure, pin the index

Policy manuals are chunked on clause boundaries with the heading path prepended before embedding. The embedding model version is pinned to the index. Every re-index runs 40 golden queries with known-correct chunk IDs before promotion. The claims-history table is never embedded: it is queried directly, because a row of it embeds as mostly noise.

A chunk is the smallest span that still makes sense read completely out of context, and an index is one coupled unit: chunking scheme, embedding model, vector store. Change one without the others and similarity scores become arithmetic without meaning.

The timing is the clueConfident wrong answers starting right after a refresh or re-index is a retrieval and indexing fault. Temperature governs token selection, not which document came back. A better model reads the same wrong passage more articulately.

3.6Match the mechanism to the query shape

Retrieval over the policy corpus runs hybrid, filtered by metadata before ranking, retrieved at the top 30 and reranked to the top 4. Hybrid earns its place because the corpus mixes narrative explanation with exact identifiers and users query in both forms. Claims-history questions route straight to SQL, because a count has no vector-space answer.

Vector search is one mechanism among several, so the query shape decides. Exact identifiers want lexical, aggregation wants SQL, multi-hop relationships want graph traversal. Filter before ranking; retrieve wide and rerank narrow.

Measured, not assertedOn identifier queries dense-only retrieval hit 34% and hybrid 89%. The dense results are excellent answers to a question nobody asked, which is why this failure survives review.

3.7Ask who decides what happens next

The claim record comes in through a direct API call in pre-processing. The policy store is an MCP tool with a companion resource carrying its catalog. The fraud scorer is a direct API call from the orchestration layer, never a tool. Escalations go through an existing community MCP server for the issue tracker. Medical necessity review is agent-to-agent.

One question sorts any integration: who decides what happens next. Your code decides, so it is a direct call. The model decides, so it is MCP. Another agent decides, so it is agent-to-agent. Cost climbs in that order.

The disqualifierA tool is something the model can choose not to call, so a step the scenario says must always happen cannot be a tool. Read for every, always, must, and required attached to a step.

3.8Find the crossover, then stand on the right side

Across the three scoped agents the total surface is 34 tools, restructured as five namespaces, with the seven tools covering 64% of calls promoted into the base. That is about 2,150 tokens against 6,800 monolithic. Neither pure strategy wins: promoting the measured high-frequency tools into the base is cheaper in tokens and in latency than either one.

This is a crossover with a computable location, not a maturity ladder. Monolithic stays correct when the surface is small and stable, when the latency budget cannot absorb a round-trip, and when the content is needed on every request.

Both directionsThe rejection is the under-drilled half: a small stable surface on a tight latency budget gets discovery proposed, and the correct answer turns it down. Below the crossover a round-trip costs more than the tokens it saves.

The interlock is the point. The caching decision in 3.3 funds the reranking stage in 3.6. The entitlement filter from 3.2 lives inside the retrieval query, which constrains what 3.4's observability pipeline is allowed to store. The tool split in 3.1 changes the exact surface 3.8's discovery layer has to cover. A scenario built to test one objective almost always has a second wired underneath it, and the answer that fixes only the first leaves the question half-solved.
